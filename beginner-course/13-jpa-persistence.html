Part 1 · What JPA actually is

1.1 Two worlds that do not speak the same language

Your Java program lives in a world of objects. An Account, a Customer, a List of orders. Each object has fields, and each field holds a value.

The database lives in a completely different world: tables, rows and columns. No objects, no fields, no methods — just rows of plain values.

Both worlds describe the same information. Neither one understands the other. Something has to translate.

🗣️
Analogy Picture two people who speak different languages, sitting at a table to do business. The person on the left speaks Java objects. The person on the right speaks database rows. They agree on everything — but neither can say a word the other understands. In the middle sits a translator, who listens to one and says it again in the other's language.

Before this unit, you were the translator. JDBC is the low-level way: you write every SQL string yourself, send it to the database, then copy each column out of the result into an object. It works, but it is repetitive, and every hand-typed column name is a chance to make a mistake.

JPA — the Jakarta Persistence API — is the translator. Its formal name for what it does is an object-relational mapper, usually shortened to ORM: software that maps objects to relational tables, and rows back to objects.

In plain words

You work with Java objects. The database works with rows. JPA is the translator in the middle, so you rarely have to speak SQL yourself.

1.2 What it looks like when you use it

You almost never see the SQL. You talk to the objects, and JPA writes the SQL behind your back:

  • You call em.persist(account) → JPA writes the INSERT.
  • You call em.find(Account.class, 42) → JPA runs the SELECT and hands you a ready Account object.

em is the EntityManager — the object you do all of this through. It gets its own section in Part 2; for now, read it as “the thing that talks to the database for me.”

the whole idea, in two lines
em.persist(account);                          // INSERT — save this object

Account a = em.find(Account.class, 42);      // SELECT … WHERE id = 42
💡
The one thing to notice Nowhere in that code is there an INSERT or a SELECT written by you. You called a method on an object and mentioned an object class. Turning that into SQL is the whole job of JPA.

One more word you will hear: a provider. JPA is only a specification — a written set of rules. Something concrete has to actually do the work. On WildFly that something is Hibernate.

⚠️
JPA is not a database JPA stores nothing on its own. There is always a real database underneath (PostgreSQL, MySQL, H2…) and a real connection to it. JPA just saves you from writing the SQL that travels over that connection.
↩︎
Where this sits An entity is a plain Java class carrying @Entity and an @Id, mapped to a database table (Session 4 introduced the shape). JDBC (Session 8) is the low-level alternative where you write every SQL string yourself. JPA sits on top of JDBC and hides almost all of it.

Part 2 · The three things every JPA application needs

Storing an object is a three-part deal. Miss any one part and nothing works. Here they are, in the order you set them up.

  1. An entity that tells JPA how to map it

    An entity is an ordinary Java class with a handful of annotations that say which table it belongs to and which field is its identity. It is not a special kind of class — it is a normal class wearing labels.

    Account.java — a properly mapped entity
    import jakarta.persistence.*;

@Entity
@Table(name = "accounts")
public class Account {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;                       // the database assigns it

    @Column(name = "account_holder", nullable = false)
    private String holder;

    private double balance;

    @Version                              // optimistic locking (Session 4)
    private int version;

    // getters / setters
}
    • @Entity — “this class is stored in the database.”
    • @Table(name = "accounts") — the table it maps to. Without it, the class name is used.
    • @Id — the field that uniquely identifies each row. Every entity must have one.
    • @GeneratedValue(IDENTITY) — the database fills the id in for you.
    • @Column(name = "account_holder", nullable = false) — the column name, and that it may not be empty.
    • @Version — a counter JPA uses for optimistic locking (Session 4): if two users edit the same row at once, one of them is told to retry.
    💡
    The one thing to notice The class name Account and the table name accounts are not the same — and that is the point of @Table. The Java side and the database side can use whatever names they like, because the annotations are the bridge between them.

  2. A persistence unit that tells JPA where the database is

    A persistence unit is a named bundle of settings: which data source to use, which transaction style, and any provider options. It lives in one small XML file inside your project.

    src/main/resources/META-INF/persistence.xml
    <persistence xmlns="https://jakarta.ee/xml/ns/persistence" version="3.0">
  <persistence-unit name="globalbankPU" transaction-type="JTA">
    <jta-data-source>java:/jdbc/GlobalBankDB</jta-data-source>
    <properties>
      <property name="jakarta.persistence.schema-generation.database.action"
                value="update"/>      <!-- create/update tables from entities -->
    </properties>
  </persistence-unit>
</persistence>

    It does three jobs: it names the unit (globalbankPU, the name you will refer to from Java), it points at a DataSource (the connection pool from Session 3, here java:/jdbc/GlobalBankDB), and it can optionally let JPA build the tables from your entities via schema-generation.database.action.

    🗄️
    Analogy Think of a filing cabinet full of labelled folders. Each entity is one labelled folder — “Accounts.” The persistence unit is the index card taped inside the cabinet door: it says where this cabinet stands, which key opens it, and whether new folders may be created automatically. The card holds no files itself; it tells you how to reach them.

  3. An EntityManager, injected into a bean

    The EntityManager is the object you actually talk to. You never create it with new — you declare a field and let the container inject it, exactly as you would a session bean.

    AccountService.java — one bean, three useful methods
    @Stateless
public class AccountService {

    @PersistenceContext(unitName = "globalbankPU")
    private EntityManager em;              // container injects & manages it

    public Account open(String holder) {
        Account a = new Account();
        a.setHolder(holder);
        em.persist(a);                     // INSERT (inside the method's transaction)
        return a;                          // a.getId() is now populated
    }

    public Account get(Long id) {
        return em.find(Account.class, id); // SELECT by primary key, or null
    }

    public void deposit(Long id, double amount) {
        Account a = em.find(Account.class, id);
        a.setBalance(a.getBalance() + amount);
        // no save() call needed: a managed entity is flushed at commit (Session 4)
    }
}
    • @PersistenceContext(unitName = "globalbankPU") — “inject the EntityManager for the persistence unit called globalbankPU.”
    • open() calls persist(), which runs the INSERT inside the method's transaction. Afterwards the id is filled in for you.
    • get() calls find(), which looks a row up by primary key and returns the object — or null if there is no such row.
    • deposit() loads an object, changes a field, and calls nothing else. Still the change is saved. That is the trick explained in Part 3.
    💡
    The one thing to notice There is no new EntityManager() anywhere. The container hands you one that is already wired to the right database and to the current transaction — just like @EJB hands you a bean.
⚠️
Forgetting @Id stops the whole application An entity with no @Id is rejected with No identifier specified for entity. JPA cannot map a row it cannot identify, so it refuses to start. Every entity needs exactly one @Id.

Part 3 · The four things you do with an object

Nearly everything in JPA is one of four verbs. Learn these four and you can already store and retrieve real data.

CallThe SQL it runs
em.persist(obj)INSERT
em.find(Class, id)SELECT … WHERE id = ?
mutate a managed entityUPDATE at commit
em.remove(obj)DELETE

Here are all four, side by side, in the order you would normally meet them:

the four verbs, in one place
@PersistenceContext(unitName = "globalbankPU")
private EntityManager em;

Account a = new Account();                      // 1. a brand-new object
a.setHolder("Ada");
em.persist(a);                                  // 1. INSERT — a row now exists

Account found = em.find(Account.class, 42L);    // 2. SELECT … WHERE id = 42

found.setBalance(found.getBalance() + 100.0);   // 3. UPDATE at commit — no save() needed

em.remove(found);                               // 4. DELETE at commit
💡
The one thing to notice Verb 3 is the strange one: you do not call anything. You simply change a field on an object you loaded with find(), and the change is saved when the transaction commits. There is no save() method in JPA.
✦
The “managed entity” trick An entity returned by find() or passed to persist() is managed: JPA is watching it. Change a field, and at transaction commit JPA writes the UPDATE automatically. No explicit save, ever.
🗂️
Analogy An EntityManager is like a personal assistant who remembers where every one of your papers went. You never say “please refile this.” You hand them a document, and it is now on their desk — being watched. If you later scribble a correction on a document the assistant is holding, they notice, and at the end of the day they update the filing cabinet to match. You only speak up for two things: “here is a brand-new document” (persist) and “throw this one away” (remove).
In plain words

Load an object with find(), change it, and it saves itself. There is no save() method. If you are looking for one, that is the whole reason why.

⚠️
find() does not throw — it returns null If no row matches the id, em.find() gives you back null. It does not raise an exception. Check for null before you use the result, or the very next line will throw a NullPointerException instead.
Checkpoint 3 · before you move on
  1. Which four SQL statements do the four operations run?
  2. You loaded an object and changed a field, and called nothing else. Why is it still saved?
  3. What does find() return when the row does not exist?
Show answers
  1. INSERT (persist), SELECT (find), UPDATE (mutate a managed entity), DELETE (remove).
  2. Because a loaded entity is managed. JPA watches it and flushes the UPDATE at commit. There is no save().
  3. null — not an exception.

Part 4 · JPQL — asking for objects, not rows

find() has one big limitation: it only looks up one row, by its primary key. It cannot answer “give me every account with a balance over 10,000.” For that you need a query language.

JPA's language is called JPQL — the Jakarta Persistence Query Language. It looks a lot like SQL, and that is deliberate — but it is not SQL.

In plain words

JPQL is a query language that asks for objects and their fields, not tables and columns. You write Account and a.balance — the names you use in Java — and JPA translates that into the real SQL for whichever database you are on.

📇
Analogy Imagine a records clerk surrounded by shelves of physical folders. You could give them exact shelf coordinates — “row 3, folder 12, line 4” — which is what SQL feels like. Or you could simply ask for “every account with a balance over ten thousand.” JPQL is the second style: you describe the records you want in the language of the records themselves, and the clerk works out which shelf to walk to.

4.1 A JPQL query

Here is the “rich accounts” query written in JPQL:

a JPQL query, run through the EntityManager
List<Account> rich = em.createQuery(
        "SELECT a FROM Account a WHERE a.balance > :min ORDER BY a.balance DESC",
        Account.class)
    .setParameter("min", 10_000.0)
    .getResultList();

Read it clause by clause — every piece names something from the Java side:

PartWhat it means
SELECT aReturn whole Account objects, given the alias a.
FROM Account aFrom the entity Account — the Java class — aliased as a.
WHERE a.balance > :minCompare the entity's field balance against a value.
ORDER BY a.balance DESCSort by that field, highest first.
:minA named parameter — a placeholder you fill in safely.
.setParameter("min", 10_000.0)Bind min to 10000.0. Safer than gluing strings together.
.getResultList()Run the query and return the matching objects as a List.
💡
The one thing to notice The query says FROM Account — the class — not FROM accounts, the table. And it says a.balance — the field — not the balance column. That single difference is the whole point of JPQL, and the exact thing beginners get wrong.
⚠️
JPQL is not SQL If you write SELECT * FROM accounts, or use a column name like account_holder, it fails. JPQL knows nothing about your table names or column names — only about your entities and their fields. Use Account and holder, never accounts and account_holder.
Checkpoint 4 · before you move on

  3. What is :min, and what fills it in?
Show answers
  1. find() only retrieves one row by primary key. JPQL can filter, sort and return many objects.
  2. The entity class Account — not the accounts table.
  3. A named parameter (a placeholder). .setParameter("min", …) binds a value to it.

Part 5 · Relationships — linking objects together

Real data is connected. A customer has accounts. An order has lines. In the database, two tables are joined by a foreign key: a column in one table that holds the id of a row in another.

In Java there are no foreign keys — only fields. So JPA lets you link objects the Java way: one field holds another entity, or a list of them. Annotations tell JPA how that link maps onto the foreign key.

Customer.java and Account.java — two entities, linked
@Entity
public class Customer {
    @Id @GeneratedValue private Long id;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL)
    private List<Account> accounts = new ArrayList<>();
}

@Entity
public class Account {
    @Id @GeneratedValue private Long id;

    @ManyToOne
    @JoinColumn(name = "customer_id")
    private Customer customer;
}
📒
Analogy Picture two binders on a shelf. The Customer binder has a page listing all their account slips. Each Account slip, for its part, has the customer's number written at the top. The two sides describe the same connection from opposite ends — and only one of them actually carries the number. That is exactly what mappedBy records.

5.1 The four annotations you need

AnnotationMeaning
@OneToMany / @ManyToOneOne customer has many accounts; each account has one customer.
@JoinColumnThe foreign-key column that stores the link — here customer_id.
cascade = ALLPersisting or removing the customer cascades to its accounts: they are saved or deleted along with it.
mappedBy“The other side owns the foreign key.” It stops JPA creating a second, duplicate column.
In plain words

Customer holds a List of accounts; Account holds one customer. Both describe the same link, but the foreign-key column lives on the Account side — the @JoinColumn side. The @OneToMany side just points at it with mappedBy.

💡
The one thing to notice Only one side carries the @JoinColumn — the “many” side. The “one” side says mappedBy = "customer", which means “that other field owns the column.” Put @JoinColumn on both and JPA creates two foreign-key columns for a single relationship.
⚠️
LazyInitializationException — the trap that catches everyone Load one Customer and JPA does not immediately load all of its accounts. Related lists are loaded lazily — only when you first touch them. If you touch them after the transaction has ended and the EntityManager has closed, JPA has no open connection to fetch them, and you get LazyInitializationException.

The fix is to use the related list while the transaction is still open — inside the bean method, before you return. Fetch what you need there, not later in the web page.

Checkpoint 5 · before you move on
  1. In the database, what links two related tables?
  2. On the Account side, which annotation holds the foreign-key column?
  3. What does mappedBy prevent, and what error happens if you load a lazy list too late?
Show answers
  1. A foreign key — a column holding the id of a row in the other table. @JoinColumn maps it.
  2. @ManyToOne together with @JoinColumn(name = "customer_id").
  3. mappedBy prevents JPA creating a duplicate foreign-key column. Loading a lazy list after the transaction closes throws LazyInitializationException.

📋 The full JPQL clause reference

JPQL supports more than the small query in Part 4. These are the clauses you will meet:

ClauseWhat it doesExample
SELECTWhich entity (or field) to return.SELECT a
FROMThe entity to query, with an alias.FROM Account a
WHEREFilter rows by a condition.WHERE a.balance > :min
ORDER BYSort the results.ORDER BY a.balance DESC
GROUP BYGroup rows before aggregating.GROUP BY a.holder
HAVINGFilter the grouped results.HAVING SUM(a.balance) > 5000
JOINFollow a relationship to another entity.JOIN a.customer c
UPDATE / DELETEBulk change or remove (used far less often).DELETE FROM Account a WHERE a.balance = 0

Named parameters (:min) are bound with setParameter("min", value). Positional parameters (?1) are bound with setParameter(1, value). Use getResultList() when you expect many objects, and getSingleResult() when you expect exactly one.

🔗 The full relationship-annotation table
AnnotationWhen to use it
@OneToOneOne row in each table is paired with exactly one in the other (a person and their passport).
@OneToManyOne row on this side owns many on the other (a customer and their accounts). Placed on the “one” side, on a Collection field.
@ManyToOneThe reverse — many rows point to one. Placed on the “many” side, on a single-entity field.
@ManyToManyMany on both sides (a student and their courses). Needs a @JoinTable to hold the links.
@JoinColumnNames the foreign-key column. Sits on the side that owns the link.
@JoinTableNames the intermediate table used by @ManyToMany.
mappedBy“The other side owns the foreign key” — set on the non-owning side to avoid a duplicate column.
cascade = CascadeType.ALLOperations on the parent propagate to the child (save together, delete together).
fetch = FetchType.LAZY / EAGERWhether the related object loads immediately or only when first used. Collections default to LAZY; single references often default to EAGER.
orphanRemoval = trueWhen a child is removed from the parent's collection, delete its row too.

🔄 The entity lifecycle, in one picture

An entity is always in one of four states. The four operations move it between them:

   new Account()          em.persist()        transaction commits
        │                       │                       │
        ▼                       ▼                       ▼
   ┌──────────┐          ┌──────────┐  em.close()  ┌──────────┐
   │TRANSIENT │─────────►│ MANAGED  │─────────────►│ DETACHED │
   │(unknown) │          │(watched) │              │(forgotten)│
   └──────────┘          └────┬─────┘              └──────────┘
                              │ em.remove()
                              ▼
                        ┌──────────┐
                        │ REMOVED  │   DELETE at commit
                        └──────────┘

Transient — a plain object JPA has never seen. Managed — JPA is watching it; changes flush at commit. Detached — it was managed, but the EntityManager that watched it closed. Removed — scheduled for deletion.

One-line summary of everything

JPAAn object-to-row mapper. It translates between Java objects and database rows, so you rarely write SQL.
ProviderThe software that does the actual mapping. On WildFly it is Hibernate.
EntityA normal class with @Entity and an @Id, mapped to a table. @Table, @Column and @Version refine the mapping.

EntityManagerInjected with @PersistenceContext. The object you do all database work through.
CRUDpersist / find / mutate-then-commit / remove.
Managed entityChanges flush automatically at commit — there is no save().
JPQLA query language over entities and fields, not tables and columns.

Common mistakes to avoid

❌ The mistake✅ The fix
Forgetting @Id on an entityEvery entity needs exactly one @Id. Without it JPA refuses to start the application.
Looking for em.save()There is no save method. Load with find(), change the field, and the UPDATE flushes at commit.
Writing SQL names in JPQLUse the entity Account and the field balance — never the table accounts or column account_holder.
Creating the EntityManager with newInject it with @PersistenceContext(unitName = "…"). The container gives you one bound to the open transaction.
Touching a lazy list after the transaction closesUse (or fetch) the related collection inside the open transaction, before you return from the bean method.
Putting @JoinColumn on both sides of a relationshipOnly the owning (“many”) side carries it. The other side uses mappedBy.
Expecting find() to throw when the row is missingIt returns null. Check for it before using the result.
