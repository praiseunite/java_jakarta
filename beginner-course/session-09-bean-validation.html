Session 9 · Bean Validation — Write the Rule Once, Check It Everywhere

Every program has to check its data before it trusts it: a name is not blank, an age is a real number, an account number is really ten digits. For years programmers wrote each of those checks three times over — once in the browser, once in the business code, once in the database — and the three copies quietly drifted apart. Jakarta Bean Validation ends that. You write each rule once, as a short label on the field it guards, and every layer of the application obeys it automatically. If you have never heard of a “constraint” or a “validator”, this page is written for exactly you.

🎯

  4. By the end you can do it yourself. Read the rules, write your own from scratch, and run the check by hand from plain Java.

Part 1 · One rule on the field, honoured by every layer

1.1 The same check, written three times

Checking data before you trust it is called validation. A name is not blank. An age is a number, not the word “banana”. An account number is exactly ten digits.

For years, programmers wrote each check in three separate places:

  • in the browser, as JavaScript, so the user gets an instant “that's wrong”;
  • in the business code (the EJB layer), as hand-written if checks, in case the browser check was skipped;
  • in the database, as table rules, as a last line of defence.

Three copies of one rule. The danger shows the moment the rule changes: someone updates the browser to allow twelve digits, forgets the database, and now the two disagree. The copies drift apart, and the bugs that follow are miserable to find.

In plain words

The rule “an account number is ten digits” lived in three notebooks at once. Change one notebook and the others are quietly wrong — and nobody can tell which notebook is the real one.

1.2 The fix: write the rule once, on the field itself

Jakarta Bean Validation is the Jakarta EE feature that ends the duplication. You attach the rule straight to the field it guards, as a short label called a constraint, and you write it once.

In plain words

A constraint is a label on a field that states a rule the value must obey — “not blank”, “between 2 and 50 characters”, “looks like an email”. You stick the label on; you do not write the checking code.

The checking code already exists. It lives in an engine called a validation provider; the one almost everyone uses is Hibernate Validator. It reads your labels and does the work.

✦
The one-sentence definition Jakarta Bean Validation lets you declare a data rule once, as a constraint on a field, getter or class of an ordinary Java object — and every layer of the application then enforces that same rule for you, automatically.
🛂
Analogy — one rulebook, every gate Picture an airport with a single official list of what you may carry on board. It is written once and pinned up where individual staff cannot edit it. Security, the check-in desk and the boarding gate all read that same list and turn away the same forbidden items. Nobody keeps a private version, so no two gates can disagree. Bean Validation is that one pinned-up rulebook; the gates are your web, business and database layers.

1.3 “Enforce everywhere” — the three layers that obey the label

Here is the part that feels like magic the first time. Once the constraint is on the field, you never call it. Three different layers notice it and enforce it on their own:

  • the web tier — your JSF screens from Session 5;
  • the business tier — your EJB and CDI beans;
  • the persistence tier — JPA, the part that saves objects to the database.

Each one checks the rule at the right moment and reacts in its own sensible way. The table spells out exactly when, and what happens when a value is rejected.

LayerHow it enforces the constraintWhat happens when a value fails
Presentation tier (JSF Facelets) JSF reads the model's constraints automatically during Phase 3 — the validation step of the JSF lifecycle from Session 5. Stops the request and shows localized error messages (phrased in the user's own language and locale) in the <h:messages> tag — without ever reaching the EJB.
Business tier (EJB / CDI) The container intercepts method calls (method validation; tuned with @ValidateOnExecution) and checks any parameter marked @Valid. Throws ConstraintViolationException before the method body runs.
Persistence tier (JPA) JPA runs the validator automatically before executing any SQL INSERT or UPDATE. Aborts the transaction (the unit of database work) before invalid SQL reaches the database.
In plain words

You pin the rule to the field. The screen refuses bad input before it is sent. The business bean refuses it before it runs. The database layer refuses it before it writes. One label, three guards, no wiring from you.

💡
The one thing to notice You never register these checks with JSF, EJB or JPA. Putting the constraint on the field is the whole of the work — the three tiers find it and honour it by themselves. That is what declarative means: you state the rule, you do not run it.

Part 2 · The ready-made rules you can just drop on

You almost never have to invent a rule. Jakarta ships a whole shelf of them in one package, jakarta.validation.constraints. You pick the label you want and put it above the field. That is the entire job.

📏
Analogy — a drawer of ready-made gauges A workshop keeps a drawer of measuring tools: a ruler, a set of go/no-go gauges, a pair of scales, a date stamp. You do not file your own ruler from scratch to measure a plank — you open the drawer and grab the right one. The built-in constraints are that drawer. Each annotation is a finished gauge; you just clip it onto the field you want measured.

2.1 The rules you will use most

They sort naturally by the question they answer. Every name below comes from jakarta.validation.constraints.

“Is a value even there?”

  • @NotNull — the value must not be null. (An empty string "" still passes — it is not null.)
  • @NotEmpty — not null and not empty: a string, collection, map or array must have at least one element.
  • @NotBlank — for text only: not null, not empty, and not just whitespace. At least one visible character.

“How big, how long, how much?”

  • @Size(min = X, max = Y) — a string's length, or a collection's size, must fall between the two bounds.
  • @Min(val) / @Max(val) — a number must be at least, or at most, the given value (works on int, long, BigDecimal and friends).
  • @Positive / @PositiveOrZero — a number must be strictly greater than zero, or zero and above.

“What shape is the text?”

  • @Email — the string must look like a real email address.
  • @Pattern(regexp = "…") — the string must match a regular expression (a compact pattern language for text). "^\\d{10}$" means “exactly ten digits”.

“Is the date on the right side of today?”

  • @Past — the date must be before now (a date of birth).
  • @Future — the date must be after now (a card's expiry).

2.2 The trap: @NotNull is usually not what you want

The three “not” rules look alike and are the single most common mix-up on this topic. On a text field, the difference is exactly this:

RuleRejects null?Rejects "" (empty)?Rejects " " (only spaces)?
@NotNullYesNoNo
@NotEmptyYesYesNo
@NotBlankYesYesYes
⚠️
The one everyone gets wrong Putting @NotNull on a name field to mean “the user must type something” does not work: "" and " " both slip past it. When you mean “must actually contain text”, the rule is @NotBlank.

2.3 Putting them on a real class

Here is a registration form's data as a plain Java class — a domain class, meaning it just holds application data. Watch how the rules stack up, one or more per field, each with its own message for when it is broken.

CustomerRegistration.java — a domain class with constraints
package com.globalbank.model;

import jakarta.validation.constraints.*;
import java.io.Serializable;
import java.time.LocalDate;

public class CustomerRegistration implements Serializable {

    @NotBlank(message = "First name is mandatory")
    @Size(min = 2, max = 50, message = "Name must be between 2 and 50 characters")
    private String fullName;

    @NotBlank(message = "Email is required")
    @Email(message = "Invalid email format")
    private String email;

    @Pattern(regexp = "^\\d{10}$", message = "Account number must be exactly 10 digits")
    private String accountNumber;

    @NotNull(message = "Date of birth required")
    @Past(message = "Date of birth must be in the past")
    private LocalDate dateOfBirth;

    @Positive(message = "Opening deposit must be greater than zero")
    private double initialDeposit;

    // Getters and setters — an IDE generates these in one keystroke
    // (IntelliJ: Alt+Insert → Getter and Setters; Eclipse: Source → Generate Getters and Setters).
    // The setters used by the demos on this page are written out in full:

    public void setFullName(String fullName) { this.fullName = fullName; }
    public void setEmail(String email) { this.email = email; }
    public void setAccountNumber(String accountNumber) { this.accountNumber = accountNumber; }
    public void setDateOfBirth(LocalDate dateOfBirth) { this.dateOfBirth = dateOfBirth; }
    public void setInitialDeposit(double initialDeposit) { this.initialDeposit = initialDeposit; }
}
💡
The one thing to notice The labels are the only validation code here — there is not a single if statement. Several constraints can stack on one field: fullName is both @NotBlank and @Size, and each carries its own message that the user will see.

2.4 Where a rule is allowed to sit

In the class above every constraint sits on a field. That is the usual place, but not the only one. The same label works in three spots:

  • On a field — @NotBlank private String fullName; — the everyday choice.
  • On a getter (a “property”) — @NotBlank public String getFullName() — handy when the value is computed rather than stored.
  • On the whole class — a class-level constraint, for a rule that needs to see several fields at once (for example, “end date must be after start date”).
In plain words

A rule about one value goes on that field (or its getter). A rule that compares two values goes on the class, because only the class can see both. Field and getter are the everyday choices; class-level is for cross-field rules.

Part 3 · Writing your own rule when none fits

The drawer of ready-made gauges is deep, but it cannot cover rules that are specific to your business. Two common examples:

  • a bank account number with a check digit — the digits must add up a certain way, or the number is a typo;
  • password complexity — at least one capital, one digit, one symbol.

No off-the-shelf annotation knows your check-digit maths, so you build your own custom constraint. It is always the same two pieces, and they split the job cleanly.

🕵️
Analogy — a badge and the inspector who wears it Imagine adding a new quality check to a factory. First you print a badge that names the role: “Account-Number Inspector”. Then you hire the inspector who actually knows how to do the checking, and give them the badge. The badge alone inspects nothing; the inspector without a badge is never called to the line. You need both, and they are made separately. The annotation is the badge; the ConstraintValidator is the inspector.

So the build is two steps: Step 1 defines the badge (an annotation), Step 2 writes the inspector (a class). Here they are.

  1. Step 1 — Define the annotation (the badge)

    A new annotation is declared with @interface. Four lines on top of it do the setup, and the body lists three attributes every constraint must have.

    ValidAccountNumber.java — the custom constraint annotation
    package com.globalbank.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = AccountNumberValidator.class) // Links to validator class
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
public @interface ValidAccountNumber {

    // Mandatory standard Bean Validation attributes:
    String message() default "Invalid bank account number check-digit";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}

    Reading the four setup lines:

    • @Documented — include this constraint in generated documentation. Cosmetic.
    • @Constraint(validatedBy = AccountNumberValidator.class) — the wire: it names the class that holds the checking code (Step 2).
    • @Target({ElementType.FIELD, ElementType.PARAMETER}) — where the label may be used: on fields and on method parameters.
    • @Retention(RetentionPolicy.RUNTIME) — keep the label around while the program runs, so the engine can read it. Without this the rule would vanish at compile time.

    The three attributes — message, groups and payload — are mandatory on every constraint. message is the text shown when the rule fails; groups and payload are advanced extras you can leave empty for now (both are explained in the Reference).

    🔑
    The one thing to notice @Constraint(validatedBy = AccountNumberValidator.class) is the only line that links the badge to the inspector. Miss it, and your annotation compiles, sits on the field, and silently checks nothing.

  2. Step 2 — Implement the ConstraintValidator (the inspector)

    The checking code goes in a class that implements ConstraintValidator. It takes two type parameters in angle brackets: the annotation it serves and the type of value it inspects — here ConstraintValidator<ValidAccountNumber, String>.

    AccountNumberValidator.java — the validator logic
    package com.globalbank.validation;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

public class AccountNumberValidator implements ConstraintValidator<ValidAccountNumber, String> {

    @Override
    public void initialize(ValidAccountNumber constraintAnnotation) {
        // Initialization if annotation has configurable attributes
    }

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null || value.length() != 10) {
            return false; // Null or incorrect length fails
        }

        // Simple check-digit sum: the ten digits must add up to a multiple of 10.
        // (This is a plain digit sum, not the full Luhn algorithm — Luhn doubles every
        //  second digit, which a real bank rule would need.)
        int sum = 0;
        for (int i = 0; i < value.length(); i++) {
            char c = value.charAt(i);
            if (!Character.isDigit(c)) return false;
            sum += Character.getNumericValue(c);
        }
        return (sum % 10 == 0); // Check-digit rule: total must be divisible by 10
    }
}

    Two methods matter. initialize(...) runs once and can read settings off the annotation (this one needs none). isValid(...) is where the decision is made: it returns true if the value passes and false if it fails.

    🔑
    The one thing to notice isValid returns a plain boolean. It never throws an exception to signal bad data, and it never fixes the value — it just answers yes or no. On false, the engine raises the constraint's message for you.
⚠️
The trap: doing too much inside isValid Beginners sometimes throw an exception, print an error, or try to correct the value inside isValid. Do none of that: decide true or false and return it — reporting the failure is the engine's job, using the message from Step 1. Deciding how to treat null is yours, though. This validator rejects it; many built-ins instead let null pass and leave that to a separate @NotNull.

  1. What are the two pieces of a custom constraint, and what does each one do?
  2. Which single line connects the annotation to the class that checks it?
  3. What does isValid return, and what should it not do?
Show answers
  1. An annotation (the badge: declares the rule and its message) and a ConstraintValidator class (the inspector: holds the checking logic).
  2. @Constraint(validatedBy = AccountNumberValidator.class) on the annotation.
  3. It returns a boolean — true passes, false fails. It must not throw, print, or fix the value; the engine reports the failure using the constraint's message.

Part 4 · Running the check yourself, from code

So far the rules fire on their own, inside a running server — a JSF form, an EJB call, a JPA save. But sometimes there is no server doing it for you: a nightly batch job importing a file, a small command-line tool, or a unit test. In those places you run the validation engine yourself, in three short lines.

⚖️
Analogy — your own weighing scale At the airport your bag is weighed for you at the check-in desk. But you can also buy a small luggage scale and weigh the bag at home, whenever you like, before you ever leave. The Validator API is that handheld scale: the same measurement, run on demand, in your own code, without waiting for a checkpoint to do it.

4.1 The three moves

The pattern never changes:

  1. Build a ValidatorFactory — the engine, created once.
  2. Ask it for a Validator — the thing that does the checking.
  3. Call validate(bean) — it hands back a Set of ConstraintViolation objects, one per broken rule. An empty set means everything passed.
ProgrammaticValidationDemo.java — running the Validator by hand
package com.globalbank.validation;

import com.globalbank.model.CustomerRegistration;
import jakarta.validation.Validation;
import jakarta.validation.Validator;
import jakarta.validation.ValidatorFactory;
import jakarta.validation.ConstraintViolation;
import java.util.Set;

public class ProgrammaticValidationDemo {

    public static void main(String[] args) {
        // 1. Build the default ValidatorFactory and retrieve Validator instance
        try (ValidatorFactory factory = Validation.buildDefaultValidatorFactory()) {
            Validator validator = factory.getValidator();

            // 2. Instantiate bean with deliberate constraint violations
            CustomerRegistration customer = new CustomerRegistration();
            customer.setEmail("invalid-email-address"); // Fails @Email
            customer.setInitialDeposit(-50.0);          // Fails @Positive

            // 3. Validate bean and inspect violation set
            Set<ConstraintViolation<CustomerRegistration>> violations = validator.validate(customer);

            if (violations.isEmpty()) {
                System.out.println("Customer data is valid!");
            } else {
                System.err.println("Validation failed with " + violations.size() + " error(s):");
                for (ConstraintViolation<CustomerRegistration> v : violations) {
                    System.err.println(" • Field '" + v.getPropertyPath() + "': " + v.getMessage());
                }
            }
        }
    }
}
⚠️
Before this code will run, add a provider

Validation.buildDefaultValidatorFactory() is not part of the JDK. With no provider on the classpath it throws NoProviderFoundException. Inside WildFly the provider is already present, but a plain project must name it in pom.xml — the engine plus the Expression Language library it uses to build messages:

<dependency>
    <groupId>org.hibernate.validator</groupId>
    <artifactId>hibernate-validator</artifactId>
    <version>8.0.1.Final</version>
</dependency>
<dependency>
    <groupId>org.glassfish.expressly</groupId>
    <artifactId>expressly</artifactId>
    <version>5.0.0</version>
</dependency>

Then run the class the usual way — right-click it in your IDE and choose Run, or from the command line with the Maven exec plugin:

mvn -q compile exec:java -Dexec.mainClass="com.globalbank.validation.ProgrammaticValidationDemo"
🔬
The one thing to notice validate() does not throw when data is bad — it returns the problems as a set. Empty set, all good; otherwise you loop through it. Each ConstraintViolation tells you two things: getPropertyPath() (which field failed) and getMessage() (the message you wrote on the constraint).

    🧩 The ConstraintValidator interface, and the three members every constraint needs
    
The interface your validator implements has two type parameters and two methods:

    
public interface ConstraintValidator<A extends Annotation, T> {
    default void initialize(A constraintAnnotation) { }
    boolean isValid(T value, ConstraintValidatorContext context);
}

    
A is the annotation (the badge), T is the type of value being checked, and
      isValid returns the yes/no decision.

    
Every constraint annotation — built-in or custom — must declare these three members:

    

      
MemberPurpose

      
        
message()The text reported when the rule fails. Has a default and may contain placeholders.

        
groups()Which validation groups this constraint belongs to (see below). Defaults to none.

        
payload()Extra typed metadata carried to whoever reads the violation (e.g. a severity). Defaults to none.

      
    

  


  

    🏷️ What groups and payload are for
    
Both appear in every constraint, and both can be left empty until you need them.

    
    
      
  • groups lets you sort constraints into named sets and run only some
        of them at a time. A classic use is a draft versus a final save: a half-filled
        form passes the Draft group, while the Final group demands every field.
        Without groups, all constraints are in the one default group and always run together.
    • 
      
  • payload lets you attach extra typed information to a constraint —
        most often a severity such as “error” or “warning” — which the code reading the
        violations can act on. It changes nothing about whether the value is valid; it is a label for the
        caller.
