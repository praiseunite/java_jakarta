concept

Part 1 · How the five CDI features work as one pipeline

CDI is not five separate topics you memorise and forget. In a real application the five features stack on top of one request, each doing exactly one job. Here they are together, and — this is the part worth reading twice — what each one is for.

1.1 The five features, and the job each one does

CDI FeatureRole in the integrated architectureBenefit
Contextual Scopes @RequestScoped for an incoming transaction; @ApplicationScoped for a rate cache. The container creates an instance when it is needed and releases it when the scope ends — no manual lifetime code.
Type-Safe Qualifiers @Domestic and @International choose the payment route at compile time. Eliminates fragile string-based lookups and guarantees type-safety.
Producer & Disposer @Produces Connection and @Disposes Connection. Brings a non-CDI, third-party resource cleanly into container injection — and closes it again.
Interceptors @Audited around-invoke logging and timing. Applies auditing and latency timers without altering a single line of the business method.
Events & Observers event.fire(new PaymentCompletedEvent(...)) Decouples notification services and receipt printers from the payment core.
In plain words

Think of one customer clicking “Pay”. The scope decides how long the objects live. The qualifier decides which gateway handles it. The interceptor times the call without the method knowing. The event tells everyone else what happened without the payment code knowing who is listening. The producer is the extra piece you add when CDI cannot build something by itself.

Five features, one click, and the business method at the centre mentions none of them.

🏦
Analogy A bank counter. The scope is how long you keep your own clerk. The qualifier is saying “foreign desk, please” instead of “desk”. The interceptor is the CCTV camera recording everyone, unasked. The event is the bell at the back that tells compliance “a large transfer just happened” — the teller rings it without knowing who runs to answer.

1.2 Trace it yourself — predict before you check

Do this now, before you see a line of the code. Guessing first is how the picture sticks.

  1. Which gateway does an overseas payment reach?

    A request arrives with isOverseas = true. Two beans implement PaymentGateway. Which one runs, and what made the decision?

    You should have written: the @International gateway. The decision was made by the qualifier, at the injection point — the compiler checked it, not a string at runtime.

  2. Where does the timing code live?

    The server log shows how long routePayment() took. Is that line inside routePayment(), or somewhere else?

    You should have written: somewhere else — inside a separate interceptor class. The business method contains no timing code at all; the container wraps the call for you.

  3. Who does the dispatcher tell about the payment?

    After the gateway finishes, a compliance service checks the transfer. Does PaymentDispatcher name that service anywhere?

    You should have written: no. The dispatcher only fires an event. The compliance service has a method marked @Observes and reacts on its own. That is what decoupling means: the sender never names the receiver.

Checkpoint 1 · before you move on

Answer out loud, in your own words. Then open the answers.

  1. In one sentence, what does an interceptor buy you that pasting logging code into every method does not?
  2. You have two beans implementing the same interface and you @Inject it bare. What does CDI do, and what is the fix?
  3. Why is a @RequestScoped bean tied to “one request”, and what happens if you use it where there is no request at all?
Show answers
  1. The concern is written once and applied to every tagged method by the container, so the business method stays clean and you change logging in one place.
  2. CDI refuses to deploy with an ambiguous dependency. Add a @Qualifier to each bean and the matching qualifier at the injection point.
  3. A request scope lives for one web request; the container creates the instance when the request starts and destroys it when it ends. With no active request — say a raw new Thread() — the scope is not active, so you get ContextNotActiveException.

Part 2 · Build the payment pipeline, step by step

Now you assemble a small but complete CDI application: a dispatcher that routes a payment to one of two gateways chosen by a qualifier, times the call with an interceptor, and announces the result with an event. Create the files in the project you have been building since Session 11 — a Maven WAR project (<packaging>war</packaging>) with an empty src/main/webapp/WEB-INF/beans.xml and the Jakarta EE web + CDI APIs on its classpath, so it can be deployed to WildFly. Step 8 adds a servlet, so the project must be a WAR, not a JAR. Nothing here is a toy — this shape is exactly how real pluggable services are wired.

In plain words — what you are about to build

One method (routePayment) decides nothing by hand: a qualifier hands it the right gateway, an interceptor times the call behind its back, and an event tells a compliance service what happened. The method itself stays almost empty.

Do the steps in order. Each one is small, and each one tells you exactly what you should see before you continue.

  1. Step 1 — the two qualifiers

    Create two tiny annotations. Each one is marked @Qualifier, which is the single line that tells CDI “this is a label I can match on”.

    src/main/java/com/globalbank/qualifiers/Domestic.java
    package com.globalbank.qualifiers;

import jakarta.inject.Qualifier;
import java.lang.annotation.*;

@Qualifier                                     // the one line that makes it a CDI qualifier
@Retention(RetentionPolicy.RUNTIME)            // keep the label around while the app runs
@Target({ElementType.TYPE, ElementType.FIELD, ElementType.PARAMETER, ElementType.METHOD})
public @interface Domestic {}

    Then create International.java in the same package, identical except the name:

    @Qualifier
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.FIELD, ElementType.PARAMETER, ElementType.METHOD})
public @interface International {}

    You should see two small files. Neither does anything on its own yet — they are just names CDI will match later. What to notice: a qualifier is a real type, so a typo in it is a compiler error, not a runtime surprise.

  2. Step 2 — the gateway interface and its two implementations

    One interface, two beans. Both implement it; the only thing that tells them apart is the qualifier on each class.

    PaymentGateway.java — the interface
    package com.globalbank.payments;

public interface PaymentGateway {
    void process(double amount);
}
    The two implementations
    package com.globalbank.payments;

import jakarta.enterprise.context.ApplicationScoped;
import com.globalbank.qualifiers.Domestic;

@Domestic                                       // this bean IS the domestic one
@ApplicationScoped
public class DomesticPaymentGateway implements PaymentGateway {
    @Override
    public void process(double amount) {
        System.out.println("Clearing $" + amount + " through the local ACH network.");
    }
}
    package com.globalbank.payments;

import jakarta.enterprise.context.ApplicationScoped;
import com.globalbank.qualifiers.International;

@International                                  // this bean IS the international one
@ApplicationScoped
public class InternationalPaymentGateway implements PaymentGateway {
    @Override
    public void process(double amount) {
        System.out.println("Processing SWIFT foreign exchange wire transfer: $" + amount + " USD.");
    }
}

    You should see two classes that both say implements PaymentGateway. What to notice: the qualifier does not change what they are — it only gives each one a name the dispatcher can ask for.

  3. Step 3 — the dispatcher, which uses both qualifiers

    This is the heart of the lab. Two fields, same type, distinguished only by the qualifier next to @Inject.

    PaymentDispatcher.java
    package com.globalbank.payments;

import jakarta.inject.Inject;
import jakarta.enterprise.context.RequestScoped;
import com.globalbank.qualifiers.Domestic;
import com.globalbank.qualifiers.International;
import com.globalbank.interceptors.Audited;

@RequestScoped
public class PaymentDispatcher {

    // CDI supplies the exact matching implementation without ambiguity
    @Inject @Domestic
    private PaymentGateway domesticGateway;

    @Inject @International
    private PaymentGateway internationalGateway;

    @Audited // Automatically intercepted for timing and security logging!
    public void routePayment(double amount, boolean isOverseas) {
        if (isOverseas) {
            internationalGateway.process(amount);
        } else {
            domesticGateway.process(amount);
        }
    }
}

    What to notice — read the code aloud and you can name the decision:

    • @RequestScoped — one dispatcher per web request; the scope ends with the request.
    • @Inject @Domestic — “inject the domestic PaymentGateway.”
    • @Inject @International — the same type, a different bean, chosen by the label.
    • @Audited — a marker you will write in Step 4, which wraps this method with timing and logging.

    You should be able to say which line decides the route. If you cannot yet, do not move on — the next three steps all build on this one.

  4. Step 4 — the @Audited interceptor

    An interceptor needs two files: a binding (the marker) and the interceptor itself. The binding does nothing alone; it is the name the dispatcher and the interceptor agree on.

    src/main/java/com/globalbank/interceptors/Audited.java — the binding
    package com.globalbank.interceptors;

import jakarta.interceptor.InterceptorBinding;
import java.lang.annotation.*;

@InterceptorBinding                            // declares an interceptor "contract"
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface Audited {}
    src/main/java/com/globalbank/interceptors/AuditedInterceptor.java
    package com.globalbank.interceptors;

import jakarta.annotation.Priority;
import jakarta.interceptor.AroundInvoke;
import jakarta.interceptor.Interceptor;
import jakarta.interceptor.InvocationContext;

@Interceptor
@Audited                                       // links this class to the @Audited marker
@Priority(Interceptor.Priority.APPLICATION)    // switches the interceptor on, application-wide
public class AuditedInterceptor {

    @AroundInvoke
    public Object audit(InvocationContext context) throws Exception {
        long start = System.currentTimeMillis();
        System.out.println("[AUDIT] calling " + context.getMethod().getName());

        try {
            return context.proceed();          // <- the real method runs HERE
        } finally {
            long ms = System.currentTimeMillis() - start;
            System.out.println("[AUDIT] finished in " + ms + "ms");
        }
      }
}

    What to notice: context.proceed() is the exact point where routePayment() runs. Everything above it happens before; the finally block happens after. Forget proceed() and the real method never runs — the single most common interceptor mistake.

    You should be able to say: routePayment() contains no timing code, yet the timing line will appear. That is the interceptor doing its job.

  5. Step 5 — an event, and an observer that reacts

    The event is just a small record carrying the facts. The observer is any bean with a method whose parameter is marked @Observes.

    PaymentCompletedEvent.java — the payload
    package com.globalbank.events;

public record PaymentCompletedEvent(double amount, boolean overseas) {}
    CurrencyComplianceService.java — the observer
    package com.globalbank.events;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.event.Observes;

@ApplicationScoped
public class CurrencyComplianceService {

    // Runs automatically whenever a PaymentCompletedEvent is fired
    public void onPayment(@Observes PaymentCompletedEvent event) {
        System.out.println("[COMPLIANCE] Verified AML status for $" + event.amount()
                + " (overseas=" + event.overseas() + ")");
    }
}

    Now fire the event from the dispatcher. Add two imports at the top of PaymentDispatcher.java, plus the injected publisher field, and the fire() call at the end of routePayment():

    // new imports at the top of PaymentDispatcher.java
import jakarta.enterprise.event.Event;
import com.globalbank.events.PaymentCompletedEvent;

// new field in PaymentDispatcher
@Inject
private Event<PaymentCompletedEvent> events;

// new last line inside routePayment(), after the gateway call
events.fire(new PaymentCompletedEvent(amount, isOverseas));

    You should be able to say: PaymentDispatcher still never mentions CurrencyComplianceService. Add a second observer tomorrow — a receipt printer, an audit log — and routePayment() does not change by a single character.

  8. 
      
    Step 8 — call it, then prove the qualifier is doing the work
    
      
    Expose the dispatcher through a tiny servlet so you can trigger it from a browser. A request
        reaches a servlet, and the servlet asks CDI for the dispatcher with @Inject:
    
      
    src/main/java/com/globalbank/web/PayServlet.java — the window onto the pipeline
    
      
    package com.globalbank.web;

import com.globalbank.payments.PaymentDispatcher;
import jakarta.inject.Inject;
import jakarta.servlet.ServletException;
import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

@WebServlet("/pay")
public class PayServlet extends HttpServlet {

    @Inject                                   // CDI injects the @RequestScoped dispatcher
    private PaymentDispatcher dispatcher;

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        double amount = Double.parseDouble(request.getParameter("amount"));
        boolean overseas = Boolean.parseBoolean(request.getParameter("overseas"));

        dispatcher.routePayment(amount, overseas);
        response.getWriter().println("Payment routed. Check the server log.");
    }
}
    
      
    Rebuild, redeploy, then open this URL:
    
      
    http://localhost:8080/cdi-payments/pay?amount=4200&overseas=true
    
      
    You should see this in the server console, in order:
    
      
    [AUDIT] calling routePayment
Processing SWIFT foreign exchange wire transfer: $4200.0 USD.
[COMPLIANCE] Verified AML status for $4200.0 (overseas=true)
[AUDIT] finished in 12ms
    
      
    Now change the URL to overseas=false and repeat (a fresh request, because the
        dispatcher is @RequestScoped):
    
      
    http://localhost:8080/cdi-payments/pay?amount=200&overseas=false
    
      
    You should see the local message —
        Clearing $200.0 through the local ACH network. — and the compliance line now read
        overseas=false. Same servlet, same method, different gateway. That contrast
        is the whole point: the qualifier, not an if on a string, chose the bean.

    Step 9 — break it on purpose, right now
    
      
    Before you read Part 3, produce the first error yourself so it stops being scary. Ambiguity needs
        two beans that both fit one injection point, so you must clear
        the labels on both sides — the beans and the injection points. Make these four edits:
    
      
      
        
    • In DomesticPaymentGateway.java, delete the @Domestic line.
      • 
        
    • In InternationalPaymentGateway.java, delete the @International line.
      • 
        
    • In PaymentDispatcher.java, change @Inject @Domestic to a bare
          @Inject.
      • 
        
    • In the same file, change @Inject @International to a bare @Inject.
      • 
      
    
      
    Now both gateways carry only the implicit @Default qualifier, and both fields ask
        for a bare @Default PaymentGateway. Rebuild and redeploy:
    
      
    mvn clean package
copy target\cdi-payments.war  C:\wildfly\standalone\deployments\
    
      
    You should see the deployment fail with
        AmbiguousResolutionException:
        Ambiguous dependencies for type PaymentGateway with qualifiers [@Default] — two
        @Default beans match one bare @Inject PaymentGateway, and nothing says
        which you meant.
    
      
    Why removing only the bean's label is not enough: if you delete
        @International from the gateway but leave @Inject @International on the
        field, the field asks for a qualifier that no bean has — that is
        UnsatisfiedResolutionException, a different fault. Ambiguity needs a point that
        several beans satisfy, so you clear the labels on both sides.
    
      
    Put all four lines back, rebuild, redeploy — it deploys cleanly again. You have just reproduced
        the most common CDI error, on purpose, and cured it. Part 3 explains exactly why.

Part 3 · The three errors you will actually hit


  
Wiring CDI always produces errors while you learn — that is normal, not failure. If you can name
    these three on sight and know where to look, CDI stops being intimidating. First, learn the one skill
    that solves all of them.


  
🔎
    
How to read a CDI error, in three moves
      
    
        
  1. Read the exception class name. Ambiguous means “more than one
          bean fits”; Unsatisfied means “no bean fits”; ContextNotActive means
          “the scope you asked for is not alive here”.
    2. 
        
  2. Read the type after the words for type. That tells you
          which injection point is unhappy — the interface or class CDI could not resolve.
    3. 
        
  3. Check two things, in this order: does the bean have a qualifier that matches
          the injection point, and does the bean have a scope (or does beans.xml exist under
          bean-discovery-mode="annotated")? Those two questions cover almost every CDI
          deployment failure.
    4. 
      

    

  


  
3.1 The three faults, side by side

  
Read the symptom, then the cause, then the fix. These are the three you will meet in real work.


  
In plain words — where each fault lives
    
The first two — ambiguous and unsatisfied — stop the application
      at deployment. Nothing runs; the server tells you the wiring is wrong before any
      user is affected. The third, context not active, waits until the application is running
      and then fails on one bad line — usually a scoped bean touched from the wrong
      thread. Deployment faults are safe: you cannot ship them by accident. Runtime faults are the ones
      to think about.

  


  
1️⃣
    
Fault 1: jakarta.enterprise.inject.AmbiguousResolutionException
      
Symptom: the application fails to deploy:
        Ambiguous dependencies for type PaymentGateway with qualifiers [@Default].

      
Root Cause: two or more beans implement
        PaymentGateway, and neither has a distinguishing @Qualifier annotation.

      
Fix: create custom qualifier annotations (e.g.
        @Domestic and @International) and apply them to both the bean classes
        and the @Inject fields.

    

  


  
2️⃣
    
Fault 2: jakarta.enterprise.inject.UnsatisfiedResolutionException
      
Symptom: deployment aborted:
        Unsatisfied dependencies for type AccountService.

      
Root Cause: CDI could not find any bean implementing that
        interface — either the module is missing beans.xml, or the bean class is missing a
        scope annotation under bean-discovery-mode="annotated".

      
Fix: verify WEB-INF/beans.xml exists and
        ensure the target bean carries a valid CDI scope (e.g. @ApplicationScoped).

    

  


  
3️⃣
    
Fault 3: jakarta.enterprise.context.ContextNotActiveException
      
Symptom: invoking a @RequestScoped bean from
        a raw background thread (e.g. new Thread(...)) crashes at runtime.

      
Root Cause: a raw, unmanaged Java thread has no active
        HTTP request context, so the @RequestScoped scope is not alive on that thread.

      
Fix: use the Jakarta EE Concurrency
        ManagedExecutorService, which carries the context across, or inject an
        @ApplicationScoped singleton for background work.

    

  


  
3.2 Reproduce each one, then fix it

  
You already reproduced Fault 1 in Step 9 by stripping the qualifiers from both the beans and the
    injection points. Here is the full set, so you have caused all three yourself before the exam.


  
    
    
  1. 
      
    Ambiguous — you did this in Step 9
    
      
    Delete @Domestic and @International from the two gateway classes,
        and the matching qualifiers from the two @Inject fields in
        PaymentDispatcher, so both beans are @Default and both fields are bare.
        Rebuild and redeploy. You should see the deployment stop with
        Ambiguous dependencies for type PaymentGateway with qualifiers [@Default] — two
        @Default beans, one bare injection point. Restore all four qualifiers and it deploys
        again.
    
    
    2. 
    
  2. 
      
    Unsatisfied — remove the scope annotation
    
      
    Delete @ApplicationScoped from DomesticPaymentGateway so it is a plain
        class with only a qualifier. Rebuild and redeploy. You should see
        Unsatisfied dependencies for type PaymentGateway with qualifiers [@Domestic] — the
        injection point still wants a @Domestic bean, but with no scope the class is not a
        bean at all.
    
      
    The fix: give it a scope. Any valid CDI scope works; the point is that
        being discovered requires a scope under annotated discovery. Restore it, rebuild,
        redeploy.
    
    
    3. 
    
  3. 
      
    Context not active — call the request-scoped dispatcher from a raw thread
    
      
    In the servlet, wrap the call in a plain thread instead of calling it directly:
    
      
    new Thread(() -> dispatcher.routePayment(amount, overseas)).start();
    
      
    Rebuild, redeploy, and hit the URL again. You should see a
        ContextNotActiveException in the server log: the raw thread has no HTTP request, so
        the @RequestScoped dispatcher has no scope to live in.
    
      
    The fix: either call the dispatcher on the request thread (as it did before),
        or — if the work genuinely must go to the background — let the container manage the thread with
        ManagedExecutorService, which reproduces the request context for you. Restore the
        direct call.
    
    
    4. 
  


  
3.3 Troubleshooting: the three errors beginners actually see

  
When deployment or a request goes wrong, find your symptom in this table before doing anything
    else.


  

    
What you seeWhat it meansWhat to do

    
      

        AmbiguousResolutionException
        More than one bean matches an injection point, and nothing says which you meant
        Add a @Qualifier to each candidate and the matching qualifier on the @Inject field. Do not guess — make the choice explicit.
      

      

        UnsatisfiedResolutionException
        No bean matches the injection point
        Check that WEB-INF/beans.xml exists and that the target class carries a CDI scope annotation (e.g. @ApplicationScoped). A class with no scope is not a bean.
      

      

        ContextNotActiveException
        You asked for a scoped bean outside the scope it belongs to — usually @RequestScoped on a raw thread
        Do the work on the request thread, or use ManagedExecutorService (or an @ApplicationScoped singleton) for background work so the context is preserved.
      

    
  


  
💡
    
The rule that saves the most time
      CDI errors are almost always about wiring, not about your business logic. Before
      you touch a single method body, ask the two wiring questions: is there exactly one matching
      bean for this injection point, and does that bean have a scope that is alive on this thread?
      The three exceptions above are just those two questions failing.

    🧩 The full interceptor wiring, in order
    
Four pieces, each with its own annotation. Miss one and the interceptor silently never runs.

    

      
PieceAnnotationWhat it does

      
        
Binding@InterceptorBindingThe marker you invent (e.g. @Audited) that links interceptor to target.

        
Interceptor class@Interceptor + the bindingHolds the wrapping logic. One method is marked @AroundInvoke.

        
The around method@AroundInvokeTakes an InvocationContext, returns Object, and calls context.proceed() to run the real method.

        
Enabling@Priority (or beans.xml)@Priority(Interceptor.Priority.APPLICATION) turns it on everywhere. Without enabling, nothing happens.

        
Applyingthe binding, on a bean or methodTagging a method with the binding is what gets it wrapped.

      
    

    
InvocationContext also lets the interceptor read and change the call: getMethod(),
      getParameters(), setParameters(...) and getTarget().

  


  

    🏭 Producer and disposer rules — what you can and cannot produce
    
    
      
  • A producer can be a method (@Produces on a method) or a
        field (@Produces on a field).
    • 
      
  • The produced object gets its own scope (e.g. @RequestScoped) and
        its own qualifiers — put a qualifier on the producer and inject with the same
        qualifier.
    • 
      
  • A producer method may take injected parameters; CDI supplies them before
        calling it.
    • 
      
  • A disposer matches a producer when its @Disposes parameter has the
        same type and qualifiers as the producer's return. One disposer per producer.
    • 
      
  • Only produced objects can be disposed — a disposer never fires for a bean CDI
        constructed normally.
    • 
    

  


  

    📡 Event fine print — qualifiers, async and transaction phases
    
    
      
  • Qualified events. Observers can be narrowed with a qualifier:
        @Observes @Domestic PaymentCompletedEvent only reacts to domestic payments. Add the
        qualifier when firing with eventPublisher.select(...).fire(...).
    • 
      
  • Async. fireAsync() runs @ObservesAsync observers on a
        background thread; fire() runs @Observes observers on the caller's
        thread and makes the caller wait.
    • 
      
  • Transaction-phase observers.
        @Observes(during = TransactionPhase.AFTER_SUCCESS) delays the reaction until the
        surrounding transaction commits — handy so you only notify a customer if the save actually
        succeeded.
    • 
    

  


  

    🏷️ The qualifiers you already have: @Default, @Any, @Named
    
Qualifiers are not new — CDI has been using them invisibly all along.

    

      
QualifierWhat it means

      
        
@DefaultEvery bean with no explicit qualifier silently has this one. It is why a single unqualified bean injects fine — and why two unqualified beans clash: both are @Default.

        
@AnyA wildcard every bean also carries. Injecting @Any Instance<PaymentGateway> gives you all implementations to loop over.

        
@NamedA built-in, string-based qualifier used mainly to reach beans from Jakarta Faces (EL) pages. Avoid it for type-safe code — use your own qualifier instead.

      
    

  


  

    🗂️ Bean scopes you will meet, and how long each lives
    

      
ScopeHow long the instance lives

      
        
@ApplicationScopedOne instance for the whole application. Shared by every user — guard mutable state.

        
@RequestScopedOne instance per web request; created when the request starts, destroyed when it ends. No request, no scope.

        
@SessionScopedOne instance per HTTP session — survives several requests from the same browser.

        
@DependentNo scope of its own: it lives exactly as long as the bean it was injected into.

      
    

    
The @RequestScoped row is the one behind
      ContextNotActiveException: use it where no request is alive and there is nothing for
      the scope to attach to.

Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      

        Two beans implement one interface and you @Inject it bare
        Add a qualifier to each bean and the same qualifier at the injection point.
      

      

        Telling beans apart with @Named("x") strings
        Use a type-safe @Qualifier annotation, checked by the compiler.
      

      

        A bean class with no scope annotation under annotated discovery
        Add a scope such as @ApplicationScoped, or CDI will not see it as a bean and you get UnsatisfiedResolutionException.
      

      

        A producer that opens a resource but has no disposer
        Write the matching @Disposes method so CDI closes it when the scope ends.
      

      

        Pasting timing or logging code into every business method
        Move it into one @AroundInvoke interceptor and tag methods with your binding.
      

      

        Writing an interceptor but never enabling it
        Give it @Priority (or list it in beans.xml), or it silently never runs.
      

      

        Forgetting context.proceed() in an interceptor
        Call it — otherwise the real method never executes at all.
      

      

        Invoking a @RequestScoped bean from a raw new Thread()
        Keep the work on the request thread, or use ManagedExecutorService so the context is carried across.
      

      

        A publisher calling each reaction directly
        Fire a CDI event and let @Observes methods react, so new reactions need no change to the publisher.
