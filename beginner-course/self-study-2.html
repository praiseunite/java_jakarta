1.1 Jakarta Bean Validation (Session 9)

Bean Validation lets you write the rules of your data as annotations on the fields themselves. A program called the validation engine reads those annotations and reports every rule that a value breaks — you never write an if statement for it.

In plain words

A constraint is a rule written as an annotation, such as @NotNull or @Size(min = 3, max = 50). A violation is one broken rule. A ConstraintValidator is the class that does the actual checking for a custom constraint. The constraints are declarations; the engine does the enforcing.

These are the standard constraints the revision material singles out. Read the last column slowly — plenty of beginners assume the first three behave the same, and they do not:

ConstraintWorks onThe rule, in plain words
@NotNullAny objectThe value must be present. Careful: an empty string "" is still present, so @NotNull lets it through.
@NotEmptyText, collections, mapsMust be present and must have something in it: length or size greater than zero.
@NotBlankText onlyMust be present and contain at least one character that is not a space. This is the one you usually want for names.
@Size(min, max)Text, collections, arraysThe length or size must fall between min and max, inclusive.
@Min(n) / @Max(n)NumbersThe value must be at least n / at most n.
@EmailTextMust look like a valid email address.
@Past / @FutureDates and timestampsThe moment must fall strictly before / after the current clock.
@Pattern(regexp)TextMust match the regular expression you supply.

The architecture of a custom constraint

A custom constraint is always two artifacts working as a pair. If you can name the two pieces, you can answer any exam question about them:

  1. The annotation definition. An interface annotated with @Constraint(validatedBy = MyValidator.class), plus @Target to say where it may be placed, and @Retention(RUNTIME) so the engine can still read it while the program runs.
  2. The validator class. A class implementing ConstraintValidator<MyAnnotation, TargetType>, whose isValid method returns true or false for one value.
🧩
Analogy The annotation is the label on a parcel — "fragile". The validator is the worker in the depot who actually shakes the box and decides whether the label is telling the truth. A label with no worker checks nothing; a worker with no label never gets called.

You will build exactly this pair, end to end, in Lab Project 1 (Part 3) and in Assignment 9 (Part 2).

1.2 EJB transactions: BMT versus CMT (Session 10)

A transaction is a unit of work that is all-or-nothing: either every change inside it is written, or none of it is. The only real question is who controls the boundaries — the container, or you. That is the whole difference between CMT and BMT.

In plain words

CMT (Container-Managed Transaction). You add one annotation (@TransactionAttribute) and the container opens, commits and — if something goes wrong — rolls back the transaction for you. This is the default and it is right for about 95% of business code.

BMT (Bean-Managed Transaction). You take the controls yourself with a UserTransaction object. You call begin(), commit() and rollback() by hand. It is more work, but it lets you publish work in chunks instead of one giant all-or-nothing block.

CriterionContainer-Managed (CMT)Bean-Managed (BMT)
Who demarcates it (decides where it starts and ends)The container, driven by @TransactionAttributeYou, through the UserTransaction API
Methods availableNone to call — it is handled declarativelyutx.begin(), utx.commit(), utx.rollback()
How it is obtainedThe container manages the lifecycle automatically@Resource private UserTransaction utx;
How it is switched onThe default, or @TransactionManagement(CONTAINER)@TransactionManagement(TransactionManagementType.BEAN)
Which beans may use it@Stateless, @Stateful, @Singleton, @MessageDriven@Stateless, @Stateful, @MessageDriven — not @Singleton
Best used forStandard create, read, update and delete work, and ordinary business workflowsMulti-phase batch processing, manual checkpoints, non-standard rollback rules
⚠️
The crucial rule for BMT In a BMT bean you cannot leave a transaction uncommitted across method invocations in a @Stateless bean. The transaction must begin and end within the same method call. Stateless beans may be reused freely between calls, so there is no safe place to park an open transaction — if you forget to commit or roll back, it will sit on the thread holding locks until it times out.
🏦
Analogy CMT is a restaurant where the waiter handles the bill for you — you just eat. BMT is a self-checkout till: you scan each item, and you press "pay". If you walk away mid-scan, the basket stays open and blocks the till.

1.3 CDI scopes and lifecycles (Sessions 11 and 12)

CDI (Contexts and Dependency Injection) is the part of Jakarta EE that creates objects for you and decides how long each one lives. That lifespan is called a scope. Choosing the right scope is the whole skill of this section: a shopping cart must survive from page to page, but a search-query bean should be thrown away the moment the response is sent.

In plain words

A scope is a bean's lifetime. When you annotate a class with a scope, you are telling the container how long to keep that object and who shares it. CDI 4.0 defines five standard scopes:

CDI scopeAnnotationHow long it livesTypical use
Dependent (the default) @Dependent Exactly as long as the bean it was injected into. Utility classes, loggers, stateless helpers.
Request @RequestScoped One single HTTP request and its response. Form backing beans, search query parameters.
Session @SessionScoped Across many requests from the same browser session. The class must be Serializable. Logged-in user state, shopping cart.
Application @ApplicationScoped As long as the deployed application is running. Shared by every user. Configuration caches, global counters.
Conversation @ConversationScoped Across several requests, but you decide the start and end by hand with conversation.begin() and conversation.end(). Multi-step registration wizards.
🏨
Analogy Think of a hotel. A request scope is a room key handed out for one night. A session scope is your whole stay — the key keeps working until you check out. An application scope is the building itself, the same for every guest. A conversation is a conference booking: it lasts exactly as long as the organiser says, and can span several rooms and days.

1.4 CDI qualifiers, producers, interceptors and events (Sessions 12 and 13)

Four small mechanisms turn a pile of classes into a decoupled architecture. Each one gets a one-sentence meaning and the exact shape of the code.

Qualifiers — how to say "this particular one"

A qualifier is a custom annotation that disambiguates between several implementations of the same interface. When two classes both implement PaymentGateway, the container cannot guess which one you meant; the qualifier names it, and it does so in a type-safe way rather than with a brittle string lookup.

@Inject @CreditCard PaymentGateway gateway;

Read it as: "inject the credit-card implementation of the payment gateway".

Producer methods — how to make a foreign class injectable

A producer method is a method that CDI calls to create an injectable object. It is how you bring a third-party class, a factory output, or a value that must be computed at startup into the world of injection.

@Produces @ApplicationScoped public Connection createDBConnection() { ... }

Read it as: "whenever something asks for a Connection, call this method and give them what it returns".

Interceptors — how to add cross-cutting behaviour

An interceptor runs code around a business method — before it, after it, or both — without the business class knowing. Logging, timing, and security auditing are the classic examples: concerns that are not the business's job but must happen on every call anyway.

@AroundInvoke public Object audit(InvocationContext ctx) throws Exception { ... return ctx.proceed(); }

ctx.proceed() is the line that actually runs your business method. Everything you write before it happens on the way in; everything after it happens on the way out.

CDI events — how to decouple without a queue

A CDI event is an in-memory announcement: one bean says "this happened", and any number of other beans may react, without the sender knowing who is listening. It is fired with an injected Event<T> object and received by an observer method.

// fire it
event.fire(new OrderPlacedEvent(order));            // synchronous: listeners run now
event.fireAsync(new OrderPlacedEvent(order));       // asynchronous: listeners run on their own thread

// receive it
void onOrder(@ObservesAsync OrderPlacedEvent event) { ... }
In plain words — synchronous vs asynchronous

fire() announces the event and waits while every listener finishes; the sender and the listeners share the same thread. fireAsync() announces it and returns immediately; the listeners run later on separate threads, so a slow listener cannot hold up the caller.

1.5 Packaging architectures (Session 14)

Finally, a server will not accept a folder of loose source files. It wants one archive, built to a shape it recognises. There are four shapes worth knowing, and the last one is the modern default.

PackageWhat it holdsIn plain words
EJB JAR
(ejb-jar.xml)		 Compiled business interfaces and session beans. A box of pure business logic. Its descriptor is now optional in modern Jakarta EE.
Web Archive (WAR) Web resources: WEB-INF/web.xml, JSF views, servlets, and CDI beans under WEB-INF/classes. The web-facing box — the pages and endpoints a user reaches.
Enterprise Archive (EAR) Several WARs and EJB JARs, plus a shared lib/, declared in META-INF/application.xml. One delivery van carrying several boxes — a whole multi-module suite in one file.
Skinny WAR EJBs, JPA entities, CDI beans and web views all inside a single .war, with the server's own API libraries left out. The modern recommended shape: one box, no EAR required. "Skinny" because it does not carry a duplicate copy of the Jakarta EE API — the server already has that.
💡
Why "skinny" matters If you bundle the Jakarta EE API inside your WAR instead of marking it <scope>provided</scope> in Maven, you ship two copies of the same classes — yours and the server's. That causes confusing, intermittent errors such as ClassCastException or "loaded by a different classloader". A WAR that carries only your code, and lets the server supply the API, is skinny — and correct.

1.6 Exam-style questions you must be able to answer

These three come straight from the revision material. Answer each out loud before you open it.

Q1 · What is the difference between @SessionScoped in CDI and @Stateful in EJB?

@SessionScoped CDI beans are bound to the HTTP session and manage web-tier user state. @Stateful EJBs are transactional business beans with container-managed clustering, failover, and passivation (@PrePassivate / @PostActivate). Modern applications frequently inject a @Stateful EJB into a @SessionScoped CDI backing bean — the session bean remembers the web conversation, and the stateful bean does the transactional work.

Q2 · What is the difference between CDI Events and JMS Messaging?

CDI Events are lightweight, in-memory events dispatched within the same JVM, with no network serialisation overhead. Jakarta JMS is an external messaging subsystem supporting distributed queues and topics, persistent message storage on disk, and message delivery across distinct servers. Choose CDI events to decouple beans inside one application; choose JMS to survive a restart or to talk to another machine.

Q3 · Why is beans.xml required in WEB-INF/ or META-INF/?

beans.xml tells the CDI container how to discover beans inside the archive. Setting bean-discovery-mode="annotated" scans only classes that carry CDI scope annotations — the fastest startup, and the modern default. Setting bean-discovery-mode="all" scans every class in the JAR or WAR, which is slower but catches beans you forgot to annotate.

Lab Project 1 · Validated hospital patient triage service

The scenario

A hospital admission intake system must enforce strict medical data constraints:

  1. A patient's National Health ID must follow the format NHID-XXXX-YYYY, enforced by a custom constraint @ValidHealthId.
  2. Blood pressure readings must validate that the systolic reading is strictly greater than the diastolic reading — a rule that compares two fields, so it needs a class-level validator, @ValidBloodPressure.
  3. The admission is executed with Bean-Managed Transactions (BMT). If either the bed assignment or the insurance verification fails, the whole admission is rolled back with utx.rollback().
In plain words

A class-level validator is a constraint placed on the class itself rather than on one field. It exists for rules that need to see two or more fields at once — "systolic must be greater than diastolic" cannot be checked by looking at either number alone.

Step 1 — the custom constraint and its validator

com/aptech/hospital/validation/ValidHealthId.java
package com.aptech.hospital.validation;

import jakarta.validation.Constraint;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = ValidHealthId.HealthIdValidator.class)
@Documented
public @interface ValidHealthId {
    String message() default "Invalid National Health ID format. Must match 'NHID-XXXX-YYYY'";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};

    class HealthIdValidator implements ConstraintValidator<ValidHealthId, String> {
        private static final String PATTERN = "^NHID-\\d{4}-[A-Z]{4}$";

        @Override
        public boolean isValid(String value, ConstraintValidatorContext context) {
            if (value == null) return false;
            return value.matches(PATTERN);
        }
    }
}

Read the two halves as the label and the worker from Part 1.1: the annotation names the validator with validatedBy, and the nested HealthIdValidator does the actual matching. The pattern says: the letters NHID, a hyphen, four digits, a hyphen, then exactly four capital letters.

What you should see: a file with no red underlines once Maven has downloaded the Jakarta Validation API.

Step 2 — the validated admission model

com/aptech/hospital/model/PatientAdmissionDTO.java
package com.aptech.hospital.model;

import com.aptech.hospital.validation.ValidHealthId;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;

public class PatientAdmissionDTO {

    @NotBlank(message = "Patient name is required")
    private String fullName;

    @ValidHealthId
    private String healthId;

    @NotNull
    @Min(value = 60, message = "Systolic BP below safe human threshold")
    @Max(value = 250, message = "Systolic BP above measurable threshold")
    private Integer systolicBP;

    @NotNull
    @Min(value = 40, message = "Diastolic BP below safe human threshold")
    @Max(value = 150, message = "Diastolic BP above measurable threshold")
    private Integer diastolicBP;

    public PatientAdmissionDTO(String fullName, String healthId, Integer systolicBP, Integer diastolicBP) {
        this.fullName = fullName;
        this.healthId = healthId;
        this.systolicBP = systolicBP;
        this.diastolicBP = diastolicBP;
    }

    // Getters and setters
    public String getFullName() { return fullName; }
    public String getHealthId() { return healthId; }
    public Integer getSystolicBP() { return systolicBP; }
    public Integer getDiastolicBP() { return diastolicBP; }
}

What you should see: a compile-clean class. Note that the field rules give you the systolic and diastolic ranges; the relationship between the two readings is the class-level rule the scenario asks for, which you would add as a class-level @ValidBloodPressure constraint on this same class.

Step 3 — the BMT transactional admission service

com/aptech/hospital/service/PatientAdmissionServiceBean.java
package com.aptech.hospital.service;

import com.aptech.hospital.model.PatientAdmissionDTO;
import jakarta.annotation.Resource;
import jakarta.ejb.Stateless;
import jakarta.ejb.TransactionManagement;
import jakarta.ejb.TransactionManagementType;
import jakarta.transaction.UserTransaction;
import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validation;
import jakarta.validation.Validator;
import java.util.Set;

@Stateless
@TransactionManagement(TransactionManagementType.BEAN)
public class PatientAdmissionServiceBean {

    @Resource
    private UserTransaction utx;

    public boolean processAdmission(PatientAdmissionDTO dto) {
        // Step 1: Validate payload using Bean Validation API
        Validator validator = Validation.buildDefaultValidatorFactory().getValidator();
        Set<ConstraintViolation<PatientAdmissionDTO>> violations = validator.validate(dto);

        if (!violations.isEmpty()) {
            System.err.println("[AdmissionService] Validation failed for: " + dto.getFullName());
            for (ConstraintViolation<PatientAdmissionDTO> v : violations) {
                System.err.println(" -> " + v.getPropertyPath() + ": " + v.getMessage());
            }
            return false;
        }

        // Step 2: Execute programmatic BMT transaction
        try {
            utx.begin();
            System.out.println("[AdmissionService] Started UserTransaction for: " + dto.getHealthId());

            allocateBed(dto);
            verifyInsurance(dto);

            utx.commit();
            System.out.println("[AdmissionService] Admission committed successfully.");
            return true;
        } catch (Exception ex) {
            System.err.println("[AdmissionService] Error occurred: " + ex.getMessage() + ". Rolling back.");
            try {
                utx.rollback();
            } catch (Exception rbEx) {
                System.err.println("Rollback error: " + rbEx.getMessage());
            }
            return false;
        }
    }

    private void allocateBed(PatientAdmissionDTO dto) {
        System.out.println(" -> Allocated bed in Ward 3 for " + dto.getFullName());
    }

    private void verifyInsurance(PatientAdmissionDTO dto) {
        if (dto.getHealthId().endsWith("FAIL")) {
            throw new IllegalStateException("Insurance authorization rejected by payer network");
        }
        System.out.println(" -> Insurance pre-authorization approved.");
    }
}
💡
The detail that makes the failure path reachable The health ID must match NHID-XXXX-YYYY — four characters, any of the letters A to Z. So an ID such as NHID-4421-FAIL is a perfectly valid ID, and yet it ends in FAIL, which trips the insurance rule and rolls the admission back. That is the whole point of the lab: valid shape is not the same as an approved decision.

Step 4 — run it and read the result

Send one good admission (for example health ID NHID-4421-WXYZ) and one that ends in FAIL. The first prints the committed path; the second prints the rollback path. Because the insurance check happens after the bed is allocated, a rollback means the bed allocation is discarded too — nothing is half-done.

What you should see for a successful admission:

[AdmissionService] Started UserTransaction for: NHID-4421-WXYZ
 -> Allocated bed in Ward 3 for Johnathan Vance
 -> Insurance pre-authorization approved.
[AdmissionService] Admission committed successfully.

What you should see when the insurance check fails: the same first two lines, then an [AdmissionService] Error occurred: Insurance authorization rejected by payer network. Rolling back. line instead of the commit line.

Lab Project 2 · Pluggable multi-gateway payment system

The architecture

A checkout controller calls a payment gateway, an interceptor times the call, and the gateway announces success as an asynchronous event that a receipt observer picks up. Read the picture from top to bottom: the call flows down, and the reaction flows sideways.

How the call flows
              ┌───────────────────────────┐
              │    CheckoutController     │
              └─────────────┬─────────────┘
                            │ @Inject @Stripe
                            ▼
     ┌──────────────────────────────────────────────┐
     │  @Logged (AuditInterceptor intercepts call)  │
     │  StripePaymentGateway.processPayment()       │
     └──────────────────────┬───────────────────────┘
                            │ event.fireAsync(PaymentSuccessEvent)
                            ▼
         ┌──────────────────────────────────────┐
         │ @ObservesAsync onPaymentSuccess(...) │
         │ (Generates invoice & sends receipt)  │
         └──────────────────────────────────────┘

Step 1 — the custom qualifier and the interceptor binding

com/aptech/payment/cdi/Stripe.java and Logged.java
package com.aptech.payment.cdi;

import jakarta.inject.Qualifier;
import jakarta.interceptor.InterceptorBinding;
import java.lang.annotation.*;

@Qualifier
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.FIELD, ElementType.METHOD, ElementType.PARAMETER})
public @interface Stripe {}

@InterceptorBinding
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface Logged {}

Two annotations, two jobs. @Stripe is a qualifier: it lets an injection point say "the Stripe gateway, please" when several gateways exist. @Logged is an interceptor binding: it is the marker you put on a method to say "run the logging interceptor around this".

Step 2 — the logging and performance interceptor

com/aptech/payment/cdi/LoggingInterceptor.java
package com.aptech.payment.cdi;

import jakarta.annotation.Priority;
import jakarta.interceptor.AroundInvoke;
import jakarta.interceptor.Interceptor;
import jakarta.interceptor.InvocationContext;

@Logged
@Interceptor
@Priority(Interceptor.Priority.APPLICATION)
public class LoggingInterceptor {

    @AroundInvoke
    public Object profileMethod(InvocationContext ctx) throws Exception {
        long start = System.currentTimeMillis();
        String methodName = ctx.getMethod().getName();
        System.out.println("[Interceptor] ENTER: " + methodName);
        try {
            return ctx.proceed();
        } finally {
            long duration = System.currentTimeMillis() - start;
            System.out.println("[Interceptor] EXIT: " + methodName + " executed in " + duration + "ms");
        }
    }
}

The @Logged annotation on the class means "this is the interceptor for anything marked @Logged". ctx.proceed() runs the real business method; the finally block measures the time even if the method throws.

Step 3 — the gateway, with asynchronous event dispatch

com/aptech/payment/service/StripePaymentGateway.java
package com.aptech.payment.service;

import com.aptech.payment.cdi.Logged;
import com.aptech.payment.cdi.Stripe;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.event.Event;
import jakarta.inject.Inject;
import java.math.BigDecimal;

@Stripe
@ApplicationScoped
public class StripePaymentGateway {

    @Inject
    private Event<PaymentReceiptEvent> receiptEvent;

    @Logged
    public boolean processPayment(String orderId, BigDecimal amount) {
        System.out.println("[StripeGateway] Processing charge of $" + amount + " for order " + orderId);

        // Fire asynchronous decoupled receipt event
        receiptEvent.fireAsync(new PaymentReceiptEvent(orderId, amount, "STRIPE-TX-" + System.currentTimeMillis()));
        return true;
    }
}

The @Logged on processPayment is what triggers the interceptor from step 2. The fireAsync call announces the payment and returns straight away — the receipt is produced on another thread.

Step 4 — the decoupled asynchronous receipt observer

com/aptech/payment/service/ReceiptNotificationObserver.java
package com.aptech.payment.service;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.event.ObservesAsync;

@ApplicationScoped
public class ReceiptNotificationObserver {

    public void onPaymentCompleted(@ObservesAsync PaymentReceiptEvent event) {
        System.out.println("[AsyncObserver] Dispatched PDF receipt for order: " + event.getOrderId()
                + " (Transaction ID: " + event.getTransactionRef() + ")");
    }
}

The observer knows nothing about the gateway, and the gateway knows nothing about the observer. That is the decoupling: either can be replaced without touching the other.

What you should see when the controller pays for an order: the interceptor's ENTER line, the gateway's charge line, the interceptor's EXIT line with a millisecond count, and then — possibly a moment later, because it runs asynchronously — the observer's receipt line.

Step 2 — the role-secured medical record bean

com/aptech/healthcare/security/MedicalRecordServiceBean.java
package com.aptech.healthcare.security;

import jakarta.annotation.security.DeclareRoles;
import jakarta.annotation.security.RolesAllowed;
import jakarta.ejb.Stateless;
import jakarta.inject.Inject;
import jakarta.security.enterprise.SecurityContext;

@Stateless
@DeclareRoles({"DOCTOR", "ADMIN", "NURSE"})
public class MedicalRecordServiceBean {

    @Inject
    private SecurityContext securityContext;

    @RolesAllowed({"DOCTOR", "ADMIN"})
    public String accessConfidentialDossier(String patientId) {
        String caller = securityContext.getCallerPrincipal().getName();
        System.out.println("[SecurityService] Authorized caller '" + caller + "' accessed records for " + patientId);
        return "DOSSIER-PATIENT-" + patientId + ": Diagnosis: Acute Hypertension.";
    }

    @RolesAllowed({"NURSE", "DOCTOR", "ADMIN"})
    public void recordVitals(String patientId, String vitals) {
        System.out.println("[SecurityService] Vitals recorded for " + patientId + " by " + securityContext.getCallerPrincipal().getName());
    }
}

Reading the security in plain words. @DeclareRoles lists the roles the application knows about. @RolesAllowed on a method says who may call it. So a nurse can record vitals but cannot open a confidential dossier; a doctor can do both. Attempting the forbidden call returns HTTP 403 and the method body never runs. SecurityContext is how your own code asks "who is calling?" — getCallerPrincipal().getName().

Three questions, one per lab. Answer without scrolling back.

One-line summary

Bean ValidationDeclarative constraints (@NotNull, @NotBlank, @Size, @Pattern) checked before any work begins.
Custom constraintsTwo files: the annotation (@Constraint(validatedBy = …)) and the validator (ConstraintValidator). Inside a class-level rule, two fields can be compared.
CMT vs BMTCMT: the container opens and commits. BMT: you call begin(), commit() and rollback() — and must never forget the rollback.
CDI scopes@Dependent, @RequestScoped, @SessionScoped, @ApplicationScoped, @ConversationScoped — choose by how long the state must live and who must share it.
CDI decouplingQualifiers pick an implementation; producers create injectable objects; interceptors wrap methods; events let beans announce without knowing who listens.
Security@DeclareRoles names the roles; @RolesAllowed and @PermitAll decide who may call what; SecurityContext tells your code who is calling.
PackagingEJB JAR (logic), WAR (web), EAR (everything, one delivery), Skinny WAR (everything in one .war, API left to the server).
Order mattersValidation runs before the transaction, so a badly shaped request never costs a connection or a lock.

Common mistakes to avoid

❌ The mistake✅ The fix
Using @NotNull where you meant "must have content" An empty string passes @NotNull. Use @NotBlank for text fields that must actually contain something.
Writing if (value == null) throw … by hand Declare it as a constraint: @NotNull(message = "…"). The engine enforces it and the message comes back for free.
Trying to compare two fields with a field-level constraint A rule such as "systolic greater than diastolic" needs a class-level validator, because it must see both values at once.
In BMT, catching an error and returning without utx.rollback() Always roll back in the catch. An open transaction stays on the thread holding locks and a connection until it times out.
Leaving a BMT transaction open across method calls in a @Stateless bean The transaction must begin and end within the same method call — stateless beans are reusable, so there is no safe place to park it.
Forgetting @Any on an Instance<T> field Without @Any the container only considers beans matching the field's own qualifiers, so you will not see every implementation.
Assuming fireAsync() has finished when it returns It returns immediately and observers run on other threads. If you must wait, use the returned CompletionStage.
Bundling the Jakarta EE API inside a WAR Mark it <scope>provided</scope>. The server supplies its own copy; shipping yours causes duplicate-class clashes and "loaded by a different classloader" errors.
Getting a 403 and blaming your code Check the role strings first. @RolesAllowed is case-sensitive: "admin" and "ADMIN" are different roles.
Dropping shared JARs into the root of an EAR Put them in the lib/ folder named by <library-directory> in application.xml. Root-level JARs are not on the modules' classpaths.
Deploying a new version before undeploying the old one Undeploy first, or you get DuplicateResourceException on the context root.
Guessing why a deployment failed Open the .failed marker file — it holds the stack trace. Read the deepest Caused by: line, the last in the chain.
