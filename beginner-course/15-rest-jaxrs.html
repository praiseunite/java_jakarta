concept

Part 1 · REST in plain English

REST is a way of designing the conversation between a client and a server. That is genuinely all it is — a set of habits for naming things and asking for them. There are three habits, and you can learn them in the next few minutes.

1.1 A resource is just a thing, with its own web address

In REST you model your system as resources. A resource is simply a thing your system knows about: an account, an order, a customer, a book.

Every resource gets its own URL — its own web address. The account numbered 123 lives at /accounts/123. The collection of all accounts lives at /accounts. The 123 part is the resource's own identity.

In plain words

A resource is a thing, and every thing gets its own address. You do not send the server a list of instructions like “go into the database and…” — you point at a thing and say what you want done to it.

1.2 The verb is the action you want

If the URL says which thing, the HTTP verb says what to do to it. There are four you will use every day:

VerbMeansExample
GETreadGET /accounts/123
POSTcreatePOST /accounts
PUTreplace / updatePUT /accounts/123
DELETEremoveDELETE /accounts/123

Notice the pattern. The GET and DELETE examples point at one account (/accounts/123). The POST example points at the collection (/accounts), because the new thing does not exist yet and has no number.

🍽️
Analogy Think of a restaurant menu. Each dish on the menu is a thing with a name — that is your URL. The verb is what you want done: look at it (GET), order a new one (POST), send it back to be remade (PUT), cancel it (DELETE). You never say “rearrange the kitchen” — you point at the dish and say what you want.
⚠️
Never change data with a GET A GET means “read this and change nothing.” Browsers, proxies and search engines all assume that, and they may repeat a GET on their own. If a link can delete an account, you have used the wrong verb — that action belongs on DELETE or POST.

1.3 The status code is the answer

Every HTTP response carries a status code: a three-digit number saying whether the request worked, and if not, what went wrong. The source material lists the six you will meet constantly: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 404 Not Found, 500 Server Error. Each one gets a full explanation in the Reference section at the end.

In plain words

The status code is the server answering one question in a single number: did it work? Numbers starting with 2 mean yes; 4 means you (the client) asked for something wrong; 5 means the server itself broke while trying.

🧾
Analogy A shop counter stamps your receipt before handing it back. “Done” (200). “We made you a new one” (201). “Done, nothing to give you” (204). “Your form makes no sense” (400). “We have no such item” (404). “Our till has crashed” (500). One stamp, and you know exactly where you stand.

1.4 Putting it together

That is the whole of REST. Every request is three decisions:

  1. Which resource? → the URL, such as /accounts/123
  2. Which verb? → GET, POST, PUT or DELETE
  3. What came back? → the status code, plus a body (usually JSON — plain text describing an object, such as {"balance":42})

Everything else on this page is about how Java answers steps 2 and 3.

Part 2 · Turning it on

REST is a set of rules; JAX-RS is the part of Jakarta EE that lets your Java methods follow those rules. JAX-RS stands for Jakarta RESTful Web Services — the modern name you will also see is simply Jakarta REST.

Switching it on takes one tiny class. It contains no logic at all.

RestConfig.java — switch JAX-RS on
import jakarta.ws.rs.ApplicationPath;
import jakarta.ws.rs.core.Application;

@ApplicationPath("/api")          // all endpoints live under /api
public class RestConfig extends Application { }

Three things are happening, and only three:

  • extends Application — you are telling the server “this class is my REST configuration.” That is the signal that makes the server start looking for endpoints.
  • @ApplicationPath("/api") — you are choosing the shared prefix every endpoint will begin with. An endpoint written as /accounts is really served at /api/accounts.
  • The class body is empty — { }. It holds no code because it has no job other than to exist and carry that one label.
In plain words

This class is a signpost, not a worker. It does nothing by itself. It tells the server two facts: “turn REST on for this application,” and “put everything under /api.”

🚪
Analogy An office building with one front door. @ApplicationPath("/api") is that door — every visitor comes in through it. Inside, each @Path is a different office. Nobody needs to know the room numbers from the street; everyone starts at the same entrance.
💡
The one thing to notice The class is empty. All of the meaning sits in the two lines above it. That is the pattern for this whole unit: you rarely write logic to get enterprise features — you declare what you want with a label, and the container does the work.
⚠️
Changing the prefix changes every URL Rename @ApplicationPath("/api") to "/bank" and every client that called /api/accounts now gets a 404. Choose the prefix once and treat it as part of your public address. And do not forget extends Application — without it, JAX-RS is simply never switched on and every endpoint disappears.

Part 3 · Turning a Java method into a URL

Now the payoff. A resource class is an ordinary Java class that the server maps to URLs. Each method on it answers one combination of a URL and a verb. You mark the class and its methods with annotations, and JAX-RS does the wiring for you.

3.1 The annotations you will always use

These six labels do almost all of the work. Do not memorise them now — recognise them, and come back after you have seen the code.

AnnotationJob
@PathURL this class / method answers on
@GET @POST @PUT @DELETEWhich HTTP verb triggers the method
@PathParamPull a value out of the URL (/{id})
@QueryParamPull a value from ?name=…
@Produces / @ConsumesResponse / request body format (usually JSON)

3.2 The resource class, line by line

Here is a complete resource for accounts. Read the comments on the right first; the explanation follows underneath.

AccountResource.java — one URL per method
import jakarta.ws.rs.*;
import jakarta.ws.rs.core.MediaType;
import jakarta.ws.rs.core.Response;
import jakarta.inject.Inject;

@Path("/accounts")                                   // base path
@Produces(MediaType.APPLICATION_JSON)                // methods return JSON
@Consumes(MediaType.APPLICATION_JSON)                // methods accept JSON
public class AccountResource {

    @Inject AccountService accounts;                 // your EJB / CDI bean (see the CDI sessions)

    @GET
    public List<Account> list() {
        return accounts.findAll();
    }

    @GET @Path("/{id}")
    public Response getOne(@PathParam("id") Long id) {
        Account a = accounts.get(id);
        return (a != null)
            ? Response.ok(a).build()
            : Response.status(Response.Status.NOT_FOUND).build();
    }

    @POST
    public Response create(Account incoming) {       // JSON body -> Account, automatically
        Account saved = accounts.open(incoming.getHolder());
        return Response.status(Response.Status.CREATED).entity(saved).build();
    }

    @DELETE @Path("/{id}")
    public void delete(@PathParam("id") Long id) {
        accounts.remove(id);
    }
}

Four methods, four endpoints. Under the @ApplicationPath("/api") from Part 2, they are:

  • @GET list() → answers GET /api/accounts. It returns the whole collection as JSON.
  • @GET @Path("/{id}") getOne(...) → answers GET /api/accounts/123. The {id} is a placeholder in the URL; @PathParam("id") hands that segment to the method as a Long. Found → Response.ok(a) is a 200; missing → Response.Status.NOT_FOUND is a 404.
  • @POST create(...) → answers POST /api/accounts. The JSON body arrives as the Account incoming parameter; the method saves it and returns 201 Created with the saved account in the body.
  • @DELETE delete(...) → answers DELETE /api/accounts/123. It removes the account. Returning void is enough — the server sends a 204.
💡
The one thing to notice Look at what each method does not do. It never opens a database connection, never checks a user's role, never starts a transaction. It collects a value from the URL, calls accounts, and shapes the answer. The real work is in the injected AccountService bean.

3.3 JSON comes and goes by itself

Clients usually send and receive JSON — plain text describing an object, such as {"holder":"Ada Lovelace","balance":0.0}. You never parse or build that text by hand.

The conversion is automatic through JSON-B: a public field or a getter becomes a JSON property, and an incoming JSON body is bound straight to your method parameter. @Produces declares the response format and @Consumes declares the request format — and MediaType.APPLICATION_JSON is the name for JSON.

In plain words

You write a method that takes an Account and returns a List<Account>. JSON-B looks at those types, sees JSON on the wire, and converts in both directions for you. You never touch the text.

🛎️
Analogy The resource class is a hotel front desk. The receptionist does not fix the plumbing or cook the meals. They take your request, hand it to the right department (the injected bean), and hand you back the answer. That is why a resource is called a thin layer.

🔬
    
Where JAX-RS sits
      A JAX-RS resource is a thin edge. It parses the request, calls your session bean
      / CDI service for the real work (transactions, security and persistence all still apply there),
      and shapes the response. Keep business logic out of the resource class.

  


  
⚠️
    
Do not let the resource grow
      It is tempting to put the database code and the rules straight into the resource method “just
      this once.” Do not. The moment logic lives there, you lose @TransactionAttribute,
      declarative security and clean testing. The resource asks accounts to do things — it
      does not do them itself.

Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Using GET to create or change dataUse POST to create, PUT to update, DELETE to remove. GET only ever reads.

      
Putting business logic in the resource methodKeep the resource thin; call an injected session bean / CDI service where @TransactionAttribute, security and JPA apply.

      
Parsing the JSON body by handDeclare @Consumes(MediaType.APPLICATION_JSON) and let JSON-B bind the body to your parameter.

      
Returning an object but forgetting @ProducesAdd @Produces(MediaType.APPLICATION_JSON) so the response is declared as JSON.

      
Hard-coding the base path into every @PathSet one shared prefix with @ApplicationPath, and let each @Path be relative to it.

      
Confusing @Path with @PathParam@Path defines the URL template; @PathParam pulls a value out of that template into a parameter.
