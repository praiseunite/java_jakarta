Session 8 · Connecting to Outside Systems — JCA and JDBC, Explained Slowly

Your application almost never stands alone. It has to reach the big back-office systems a company already runs — an SAP finance platform, an IBM mainframe, a message broker, a plain database — and most of those were built long before your code existed. This page is about how Jakarta EE lets your code talk to all of them through one standard plug (Jakarta Connectors, or JCA), and how it talks to relational databases in particular (JDBC). You do not need to have met any of these words before — each one is explained the moment it appears.

🎯

  3. You can watch it happen. Press Run on the simulation and see a two-phase commit replay, line by line.

Part 1 · Why joining systems together explodes — and how a standard adapter fixes it

1.1 Your code is the new kid in a very old building

Picture a bank. Long before anyone wrote your application, that bank already ran:

  • an SAP ERP system for finance and payroll (ERP stands for enterprise resource planning),
  • an IBM CICS mainframe that has processed transactions since the 1980s,
  • a Siebel CRM holding every customer record (CRM stands for customer relationship management),
  • a message broker and a relational database or two.

Your new app has to talk to all of them. None of them is going away to suit you, and you are not allowed to rewrite them. You just have to connect.

1.2 What an EIS actually is

Those systems have a collective name.

✦
The term An Enterprise Information System (EIS) is any core corporate data engine — an SAP ERP platform, an IBM CICS mainframe, a Siebel CRM, or a legacy transaction manager — that a business runs its operations on.
In plain words

An EIS is just a big, established back-office system the company already depends on. Your job is not to replace it. Your job is to plug into it.

1.3 The explosion: M servers times N systems

Here is the trouble. Imagine the bank runs three application servers (one for the web site, one for the mobile app, one for internal tools), and they each need to reach four back-end systems (SAP, the mainframe, the CRM, the database).

Without a shared standard, every server needs its own hand-written connector to every system. That is not three plus four. It is three times four:

In plain words

M application servers, each needing a custom connector to N systems, means M×N separate connectors to write, test and maintain. Three servers times four systems is twelve brittle connectors. Add one more back-end and you are suddenly at fifteen. The cost grows by multiplication, not addition.

Every one of those connectors is custom, vendor-locked, point-to-point code. Each is a place to leak a connection, mishandle a password, or break when the mainframe team upgrades. This is the M×N integration problem.

1.4 The fix: agree on one shape of plug

The way out is the same trick that transformed world trade.

📦
Analogy — the shipping container Before the standard shipping container, every load of cargo was packed, lifted and stowed its own way: every combination of ship, crane, truck and dock needed custom handling. Then the world agreed on one box. Now any crane lifts it, any ship stows it, any truck carries it. One agreed shape collapsed a tangle of special cases into a single standard. JCA is that agreement, for software.

Jakarta Connectors Architecture (JCA) is the standard. Instead of every server writing its own connector to SAP, the SAP vendor writes one connector that follows the JCA standard. That connector is called a resource adapter, and it is packaged as a single file with the extension .rar — a Resource Adapter Archive.

🔌
Analogy — the universal travel adapter You travel with one laptop charger and one little adapter that fits every country's wall socket. You do not buy a different laptop for every country. A .rar resource adapter is that one adapter: the EIS vendor builds it once, and it plugs into the standard “socket” that every certified Jakarta EE server provides.
In plain words

M×N custom connectors become M + N: each server just has its standard socket, and each system ships one standard plug (its .rar). Write once, plug in anywhere.

1.5 Before and after, side by side

This is the whole argument for JCA in one table. Read the left column as “the pain”, the right as “what the standard buys you”.

Without a standard — the M×N tangleWith JCA — one pluggable adapter
Every application server needs its own custom, proprietary drivers to talk to SAP, CICS or Tuxedo. The EIS vendor creates one standardized resource adapter (packaged as a .rar file).
There is no unified connection pooling; each vendor driver invents its own threading and pooling. The application server container manages connection pooling uniformly across every adapter.
Transactions that span several back-ends at once are impossible, or painfully hand-coded. Standard two-phase commit (XA) coordinates transactions seamlessly across databases and mainframes.

Do not worry about “connection pooling”, “two-phase commit” or “XA” yet — those are exactly what Part 2 explains. For now, notice only the shape: one standard plug replaces a pile of custom wiring.

Part 2 · The contracts the server and the adapter sign — and which way the data flows

2.1 What a “system-level contract” means

When a resource adapter plugs into a server, the two of them have to agree on who handles what. That agreement is written down in the JCA standard as a set of system-level contracts. A contract here is not legal paperwork — it is simply a fixed list of jobs the server promises to do for the adapter, so the adapter never has to do them itself.

🏠
Analogy — the tenancy agreement When you rent a flat, the agreement spells out that the landlord handles the plumbing, the heating and the building's security, while you just live and work there. You do not fix the boiler. The JCA contracts are that agreement: the server handles connections, transactions, security and threads, and the adapter just gets on with talking to the EIS.

2.2 The four things the server quietly handles

There are four contracts. You will not write code for any of them — that is the point — but you should be able to say what each one buys you.

1. Connection Management — borrow a connection, never build one

The server keeps a ready pool of open connections to the EIS and lends them out. Your beans borrow a connection, use it, and hand it back — with zero manual socket handling.

🪜
Analogy — the equipment-hire depot You need a ladder for an hour. You do not buy one, store it and maintain it — you hire one from the depot, use it, and return it. The depot keeps a stock ready and looks after them. A connection pool is that depot: a stock of warm connections, borrowed and returned in milliseconds.

2. Transaction Management — all of it, or none of it

Sometimes one action has to change two systems at once — say, debit a PostgreSQL database and record the same movement in SAP. Either both changes stick, or neither does; a half-done money transfer is a disaster. The server's transaction manager — its JTA (Jakarta Transaction API) — enlists the EIS into the same transaction as the database, using a protocol called XA. XA runs a two-phase commit: first it asks every system “are you ready to commit?”, and only if all of them say yes does it tell them all to commit for real.

🧳
Analogy — booking a trip, flight and hotel together A good travel agent will not book your flight until she knows the hotel is free, and will not confirm the hotel until the flight is held. She checks both (“ready? … ready?”), then confirms both together. If the hotel is full, she quietly releases the flight hold too — so you are never left with half a holiday. That “ask everyone first, then commit everyone together” is exactly two-phase commit.

3. Security Management — your identity travels with the request

When your bean calls the mainframe, the mainframe wants to know who is really asking. The security contract propagates the caller's identity and credentials through to the EIS, so the backend can refuse unauthorized access instead of trusting anything that knocks.

🪪
Analogy — the conference lanyard At a big conference your badge is scanned at every room, and each scanner already knows who you are — you do not re-register at every door. The security contract carries your identity along with the request, so the mainframe recognises you without a fresh login at every step.

4. Work Management — the adapter borrows workers, it does not hire its own

An adapter sometimes needs to run background tasks. If it spawned its own threads, a buggy adapter could spawn thousands and starve the whole server of CPU. Instead, the work contract lets the adapter run tasks on the server's own managed thread pool, so the server stays in control.

👥
Analogy — the shared staffing pool A department that hires its own staff off the books can blow the whole company's budget. One that requests workers from the company's central staffing pool can only ever use what the company allows. Work Management keeps every adapter's background tasks inside the server's shared, bounded pool.
In plain words

Four promises, one sentence each: pool my connections (Connection Management), make my changes all-or-nothing across systems (Transaction Management), carry my identity to the backend (Security Management), and run my background work on your threads, not mine (Work Management). The full, formal table is in the Reference at the end if you want the exact wording.

2.3 Which way does the data flow?

A resource adapter can carry traffic in either direction. The difference is simply who starts the exchange — who knocks on whose door.

🚪
Analogy — who knocks on the door Outbound is your app knocking on the EIS's door to ask for something. Inbound is the EIS knocking on your app's door to announce that something happened. Bidirectional means both can knock, any time.
ModelData flowWho starts it
Outbound App server → backend EIS Your application EJB invokes a method on the resource adapter to send data out.
Inbound Backend EIS → app server An external event inside the EIS triggers a message-driven bean (MDB) or message endpoint in the server.
Bidirectional Both directions Supports interactive requests and asynchronous notifications at the same time.
In plain words

“Inbound” is the one beginners forget. It means the outside system can wake up your code — the same message-driven bean idea from Session 1, where the container calls onMessage() for you when something arrives.

⚠️
A common mix-up “Outbound” does not mean “output” and “inbound” does not mean “input”. They describe who initiates the call, not which way a single value travels. An outbound call can still return data; what makes it outbound is that your application started it.

Part 3 · Talking to the database safely — JDBC and its three statement types

3.1 JDBC in one line, and how it relates to JCA

JCA connects your server to any kind of EIS. But the system almost every application talks to is an ordinary relational database, and that has its own dedicated Java standard: JDBC (Java Database Connectivity). JDBC is the standard way to run SQL against PostgreSQL, Oracle, MySQL or SQL Server.

In plain words

JCA is the general-purpose plug for any back-end system. JDBC is the specialised plug for relational databases. You will meet two more three-letter names in passing — CCI (the generic client interface for talking to an EIS through an adapter) and SPI (the contract side the adapter implements for the server). A tidy comparison of CCI, SPI and JDBC is in the Reference; for now, just know JDBC is the database-only one.

3.2 How one database call flows

Every JDBC operation follows the same six-step shape. You do not need to memorise it — read it once to see the pattern, then watch it in the code below.

  1. Load the driver. In modern JDBC (4.0+) this is automatic — the driver on the classpath registers itself. No more Class.forName(...).
  2. Get a connection. Ask a pooled DataSource (looked up by JNDI name) — the hire depot from Part 2 — not the raw DriverManager, the older call that opens a brand-new connection by hand every time. That is the Connection Management contract from Part 2 at work.
  3. Make a statement. Almost always a PreparedStatement (Section 3.3 explains why).
  4. Run it. executeQuery() for a SELECT; executeUpdate() for INSERT, UPDATE or DELETE.
  5. Read the results. A ResultSet is a forward-only cursor; you step through it one row at a time with rs.next().
  6. Clean up. Close everything — handled for you by try-with-resources (Section 3.5).

The full pipeline, with the best practice for each stage, is in the Reference.

3.3 The three kinds of statement

JDBC gives you three ways to send SQL. Choosing the right one is mostly about safety.

  • Statement — for fixed SQL with no outside values in it, such as a one-off CREATE TABLE. You build it with conn.createStatement(). Never feed it user-provided values.
  • PreparedStatement — the standard choice for anything with a value in it. You write the SQL with a ? where each value goes, then fill the blanks separately. It pre-compiles the SQL and blocks injection attacks (next section).
  • CallableStatement — for calling a stored procedure, a named routine that lives inside the database engine itself. You build it with conn.prepareCall("{call calculate_interest(?)}").

The side-by-side comparison table lives in the Reference. The one you will reach for ninety per cent of the time is PreparedStatement — and here is why that matters so much.

3.4 The trap: SQL injection

Suppose you build a query by gluing the user's input straight into the SQL text:

DANGER — never build SQL by string concatenation
// accountId came from the web form as text
String sql = "SELECT balance FROM accounts WHERE account_id = " + accountId;
Statement st = conn.createStatement();
ResultSet rs = st.executeQuery(sql);     // whatever the user typed is now part of the command
🔬
The one thing to notice The user's text became part of the command, not just the data. If someone types 0 OR 1=1 as the account id, the query returns every row. Nastier input can read other tables, or delete them. The database did nothing wrong — it just ran the sentence you handed it.
⚠️
This is SQL injection, the classic beginner catastrophe Any time user input is concatenated into SQL, the user can smuggle in their own commands. The fix is never “filter bad words”. The fix is to stop mixing data and commands in the first place: use a PreparedStatement with a ? placeholder, and bind the value separately with setInt, setString and friends.
📝
Analogy — the form with fixed boxes String concatenation is like handing a clerk a blank sheet and asking them to act on whatever is written — including any extra orders someone scribbles at the bottom. A PreparedStatement is a printed form with a box labelled “Account ID:”. Whatever goes in that box is read as a value, full stop. There is no room to write a second instruction, because the form has no blank line for one.

3.5 The safe, complete version

Now the same read done properly: a pooled connection, a PreparedStatement with a bound parameter, a forward-only ResultSet, and automatic cleanup. This is the pattern to copy.

AccountDAO.java — one safe database read, start to finish
package com.globalbank.dao;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

public class AccountDAO {

    private final DataSource dataSource;

    public AccountDAO(DataSource ds) { this.dataSource = ds; }

    public double fetchBalance(int accountId) throws SQLException {
        String sql = "SELECT balance FROM accounts WHERE account_id = ?";

        // Try-with-resources: automatically closes ResultSet, Statement, and Connection in reverse order!
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {

            ps.setInt(1, accountId); // Safe parameter binding

            try (ResultSet rs = ps.executeQuery()) {
                if (rs.next()) {
                    return rs.getDouble("balance");
                }
            }
        }
        return 0.0; // Not found
    }
}
🔬
The one thing to notice Two habits do all the work. The ? plus ps.setInt(1, accountId) means the account id is always treated as a value — SQL injection simply cannot happen here. And the try (…) header opens the connection and statement and closes them automatically in reverse order, even if an exception is thrown. There is no finally block and no leaked connection.
In plain words — what try-with-resources is

Anything you open inside the try (…) brackets is closed for you the instant the block ends, whether it finished normally or blew up. For a pooled connection, “closed” means returned to the pool, ready for the next request — exactly the Connection Management contract from Part 2.

🚪
Analogy — the self-closing gate A spring-loaded gate shuts behind you on its own — you never leave it swinging open, even if you walk through in a hurry. Try-with-resources is that spring: you cannot forget to close the connection, because closing is automatic the moment you leave.

3.6 Everything at once: one transaction across two systems

Here is the capstone that ties Part 2 and Part 3 together. A single money transfer updates a PostgreSQL database and an SAP ERP system, reached through its JCA resource adapter. The Transaction Management contract puts both inside one XA two-phase commit, so they either both succeed or both roll back. Press Run and read the trace.

interactive simulation JCA Resource Adapter & JDBC XA Coordination 
// Distributed Transaction T1: updates PostgreSQL and SAP ERP via JCA
UserTransaction tx = getUserTransaction();
tx.begin();
accountDAO.debit(1001, 5000.00);      // Resource 1: PostgreSQL JDBC DataSource
sapAdapter.recordLedger("SAP-99", 5000); // Resource 2: JCA Resource Adapter (.rar)
tx.commit(); // 2-Phase Commit coordinates both resources
Traces two-phase commit across relational DB and SAP mainframe adapter.

    🧩 CCI vs SPI vs JDBC — three interfaces, not one
    
Three acronyms that are easy to confuse. The short version: JDBC is for databases, CCI is for
      everything else, and SPI is the part the adapter vendor writes.

    

      
InterfaceWhat it isWho writes against it

      
        

          CCI — Common Client Interface
          A generic, EIS-agnostic client API your code uses to send and receive data through any resource adapter.
          Application developers (like JDBC, but for non-database EIS such as SAP or CICS).
        

        

          SPI — Service Provider Interface
          The system-contract side the resource adapter implements so the server can manage its connections, transactions, security and work.
          The EIS / adapter vendor — not you.
        

        

          JDBC
          The specialised Java standard for relational databases only.
          Application developers, for everyday SQL.
