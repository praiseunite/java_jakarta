Practical 1 · Build the Core

You have read about enterprise beans, containers and transactions. Now you build one. GlobalBank is a small banking application that you will grow across three practicals — this one is the core: a bank account stored in a database, a service bean that moves money, a counter that hands out account numbers, and a web address you can drive from your browser. Nothing here is simulated. You will build a real .war file, deploy it to a real WildFly, and watch a real transaction refuse to move money that is not there.

✓
Four promises before we start
  1. It is already written. Every file exists in the project folder. You are not typing a hundred lines from a textbook — you are building, running and then reading code that works.
  2. There is nothing to install first. No PostgreSQL. No driver. No database setup. WildFly ships an in-memory database, and this project is configured to use it.
  3. Every step is checkable. Each step gives the exact command and then what you should see. If what you see is different, there is a troubleshooting table.
  4. By the end you will have watched a transaction save you. You will make a transfer fail on purpose, and see that nothing was lost — which is the single most important idea in the whole course.

concept

Part 1 · What you are building

GlobalBank is a deliberately tiny bank. It has accounts, each with a holder's name and a balance, and it can do four things: open an account, deposit, withdraw, and transfer between two accounts. That is the whole business. Everything else in this practical is about how those four things are written — and the "how" is the entire point of Jakarta EE.

1.1 The project on disk

Open the folder beginner-course/lab/practical-1-core/. It looks like this:

practical-1-core/
├── README.md                                     run guide, troubleshooting, challenges
├── pom.xml                                       how to build the project
└── src/main/
    ├── java/com/globalbank/
    │   ├── entity/Account.java                   the bank account, a JPA entity
    │   ├── ejb/AccountService.java               open / deposit / withdraw / transfer
    │   ├── ejb/AccountNumberGenerator.java       one counter, @Singleton @Lock(WRITE)
    │   ├── ejb/InsufficientFundsException.java   a refusal that undoes the transaction
    │   ├── ejb/LedgerInitializer.java            seeds demo data at startup
    │   └── web/AccountServlet.java               a browser front door for the beans
    ├── resources/META-INF/persistence.xml        which database, which entities
    └── webapp/WEB-INF/beans.xml                  CDI marker (used properly in Practical 2)

Six Java files and two configuration files. That is a complete enterprise application.

1.2 The five classes, and the job each one does

Read this table slowly. Every row is one idea from Sessions 1–4, and you will meet each of these classes again later in this page.

ClassIts one jobSession it comes from
Account Be the shape of a bank account — id, holder, balance — and let the framework store it in a table without you writing SQL. Session 3 + JPA bonus
AccountService Be the bank's business logic. It knows how to open, deposit, withdraw and transfer, and nothing else in the application is allowed to know that. Sessions 1–2
AccountNumberGenerator Hand out the next account number — exactly once each, even if a hundred people open accounts in the same second. Session 4
InsufficientFundsException Be the bank's official refusal, carrying the rule that a refusal must undo the whole operation. Session 10
LedgerInitializer Put three demo accounts in the database the moment the application is deployed, so you have something to play with. Session 4 (lifecycle)
AccountServlet Be the front door: turn a web address into a call on AccountService and print the answer. Sessions 1–2
In plain words

A JPA entity is a Java class that a framework has been told to remember. You write @Entity on it and mark one field @Id; from then on, changing an object in memory is enough — the framework works out the SQL.

A stateless session bean is a class the server creates and reuses. You never call new on it. You ask for one, and the server hands you a ready instance with a database connection and a transaction already attached.

A singleton is the opposite: the server creates exactly one of it, shared by everybody. That is perfect for a counter and dangerous for almost everything else.

🍽️
Analogy — the restaurant AccountServlet is the waiter: it takes your order and carries it to the kitchen. It cannot cook. AccountService is the kitchen: it does the work and never talks to customers. Account is the ingredients list. AccountNumberGenerator is the single ticket dispenser by the door — one machine, one roll of numbers, so two customers can never get ticket 47. And LedgerInitializer is the staff who unlock the restaurant and set the tables before the first customer arrives.

1.3 The one dependency you will not find

Open pom.xml and look at the dependencies section. There is exactly one entry, and it has provided scope. There is no database driver, no connection pool, no Hibernate version to choose.

In plain words

<scope>provided</scope> means "do not ship this inside my application — the server already has it". WildFly is a Jakarta EE server: the API and an implementation of every specification are already there. Your .war stays small, and it does not fight the server's copies.

The database comes from the same place. persistence.xml names java:jboss/datasources/ExampleDS — an in-memory database WildFly creates for you at startup. It is empty again every time you stop the server, which is ideal while learning.

⚠️
In-memory means temporary Everything you create in this practical disappears when you shut WildFly down. That is not a bug and nothing is broken. Restart the server, redeploy, and you are back to the three seeded accounts.

Part 2 · Build it and put it on a server

Four steps: start the server, build the project, look at what you built, hand it to the server. Nothing here is hard, but it is all new, so each step tells you what success looks like.

  1. Start WildFly

    Open a terminal in WildFly's bin folder and run:

    standalone.bat          REM  Windows
./standalone.sh         #    macOS / Linux

    Leave this window open for the whole practical — it is the server's log, and it will tell you things the browser never will. Wait until you see a line like:

    WildFly Full 30.0.1.Final started in 3512ms

    You should see that started in …ms line. If it never appears, jump to the troubleshooting table further down this part — do not guess.

  2. Build the project

    Open a second terminal and move into the project — the folder that contains pom.xml:

    cd beginner-course/lab/practical-1-core
mvn clean package

    You should see BUILD SUCCESS, and a few lines above it:

    [INFO] Building war: target/globalbank-core.war

    Confirm the file is really there:

    dir target              REM  Windows
ls target               #    macOS / Linux

    You should see globalbank-core.war in the list. That single file contains your six classes, persistence.xml and beans.xml. Everything else in target/ is scaffolding.

  3. Deploy it

    Hand the war to the server by copying it into the folder WildFly watches:

    copy target\globalbank-core.war  c:\wildfly\standalone\deployments\      REM  Windows
cp target/globalbank-core.war    ~/wildfly/standalone/deployments/       #    macOS / Linux

    Now watch the server window — the first terminal. Within a few seconds it prints several lines, and you should find these among them:

    Deployed "globalbank-core.war"
WFLYUT0021: Registered web context: '/globalbank-core'
[Ledger] seeded 3 accounts: 1001, 1002, 1003

    That third line is the one worth staring at. You never ran it. Nobody clicked anything, and no request has arrived yet. LedgerInitializer is marked @Startup, so the server created it and called its @PostConstruct method the instant your application went live — and that method wrote three rows into the database.

    You can also do the same job through the management CLI, which is how deployments are done on real servers. Connect and ask WildFly about your application:

    jboss-cli.bat --connect                  REM  Windows
./jboss-cli.sh --connect                 #    macOS / Linux

deploy target/globalbank-core.war
deployment-info --name=globalbank-core.war

    You should see a row whose RUNTIME-STATUS reads OK:

    NAME                     RUNTIME-NAME             PERSISTENT RUNTIME-STATUS
globalbank-core.war      globalbank-core.war      true       OK

    That OK is the server's own answer that your application is live. It is worth more than any amount of confidence.

  4. Practise the commands safely first

    If you would rather try the commands before touching your real machine, the terminal below is a simulation. It runs nothing — but it answers exactly as a real one would, so you can see what BUILD SUCCESS and a successful deploy look like before you go looking for them.

    Try help, then mvn clean package, then dir c:\wildfly\standalone\deployments — and notice the .deployed marker file next to your war. That file is the server's status light.

  5. Watch the whole startup play out

    Press Run below to replay what the server actually logged while you were copying that file. Read it as a sequence: the war is opened, the persistence unit starts and generates the tables, the beans are registered, the startup bean seeds the ledger, the web context is mounted, and the deployment marker flips to green.

Part 3 · Drive the bank from the address bar


  
The application has no web page yet — that arrives in Practical 2. For now,
    AccountServlet answers on a web address and prints plain text, which is all you need to
    see the beans working. Every address looks the same:


  
http://localhost:8080/globalbank-core/account?action=<what-to-do>&…


  
The ? begins the parameters, & separates them, and action
    says what you want. Leave action off entirely and it lists everything.


  
    

    
  1. 
      
    Look at the ledger
    
      
    http://localhost:8080/globalbank-core/account?action=all
    
      
    You should see exactly this (spacing aside):
    
      
    3 account(s) in the ledger:
  Account 1001 | Ada Lovelace | balance 1500.00 | @Version 0
  Account 1002 | Grace Hopper | balance 250.00 | @Version 0
  Account 1003 | Alan Turing | balance 0.00 | @Version 0
    
      
    Notice what is missing from this output. There is no connection string, no
        SELECT, no ResultSet, no while (rs.next()). The servlet
        asked a bean for a list of accounts and got objects back. Remember the last number on each line;
        it is about to change.
    
    
    2. 

    
  2. 
      
    Deposit money, and watch a number nobody asked about
    
      
    http://localhost:8080/globalbank-core/account?action=deposit&id=1001&amount=250.00
    
      
    You should see:
    
      
    Deposited. Now: Account 1001 | Ada Lovelace | balance 1750.00 | @Version 1
    
      
    The balance went from 1500.00 to 1750.00, which you expected. But
        @Version went from 0 to 1, and you never wrote a line of
        code that touches it.
    

      
    In plain words
        
    @Version is an optimistic lock — a counter the framework keeps
          beside every row. Every time the row changes, the counter goes up. When it writes an
          UPDATE, it adds "…and only if the version is still the one I read" to the
          WHERE clause.
    
        
    Why bother? Imagine two clerks open Ada's account at the same time and both deposit £100.
          Without the counter, the second UPDATE would overwrite the first and £100 would
          vanish. With it, the second one fails loudly instead — a refused request is far better than
          silently losing money.
    
      
    
    
    3. 

    
  3. 
      
    Try to take out money that is not there
    
      
    Alan Turing's account holds 0.00. Ask for £100 anyway:
    
      
    http://localhost:8080/globalbank-core/account?action=withdraw&id=1003&amount=100.00
    
      
    You should see a refusal, and your browser may also show a
        400 status — that is deliberate:
    
      
    FAILED: InsufficientFundsException: Account 1003 holds 0.00, so 100.00 cannot be withdrawn
    
      
    Read that message carefully and you will learn three things at once. It names the exception
        class, it says why in the bank's own words, and it includes the numbers involved. Your
        future self, debugging at midnight, will thank you for writing messages like this.
    
      
    Now check the ledger again with ?action=all. Ada still holds
        1750.00. Nothing was half-applied.
    
    
    4. 

    
  4. 
      
    Move money between two accounts — the real test
    
      
    A transfer is the operation that needs a transaction, because it changes two rows. If
        the debit happened and the credit did not, money would simply disappear.
    
      
    http://localhost:8080/globalbank-core/account?action=transfer&id=1001&to=1002&amount=100.00
    
      
    You should see:
    
      
    Transferred 100.00 from 1001 (Ada Lovelace) to 1002 (Grace Hopper)

Now: Account 1001 | Ada Lovelace | balance 1650.00 | @Version 2
Now: Account 1002 | Grace Hopper | balance 350.00 | @Version 1
    
      
    Both balances changed, and both version numbers went up. One HTTP request, one
        transaction, two rows. You wrote no begin(), no commit() and no
        rollback() anywhere — that is what "container-managed" means.
    
      
    Now make it fail. Grace has 350.00; ask her to send £9,000:
    
      
    http://localhost:8080/globalbank-core/account?action=transfer&id=1002&to=1001&amount=9000.00
    
      
    You should see FAILED: InsufficientFundsException: … — and now the
        important part. Call ?action=all and check both accounts. They are exactly
        as they were: Ada 1650.00, Grace 350.00. Not a penny moved in either
        direction.
    
    
    5. 

    
  5. 
      
    Open a brand-new account
    
      
    http://localhost:8080/globalbank-core/account?action=open&holder=Your%20Name&balance=500.00
    
      
    You should see:
    
      
    Opened: Account 2001 | Your Name | balance 500.00 | @Version 0
    
      
    Where did 2001 come from? Nowhere in the servlet — the servlet has no idea what an
        account number is. It came from AccountNumberGenerator, the single
        @Singleton counter. Open a second one and you will get 2002.
    
      
    Note the %20 in the address. A URL cannot contain a space, so a space is written
        %20. Type a plain space and the browser may cope; other tools will not.
    
    
    6. 
  


  
💡
    
Read the server window while you click
      persistence.xml sets hibernate.show_sql=true, so WildFly prints the SQL it
      generated. Do a transfer and look: you will see two update accounts … statements
      appear after your Java method has already returned its answer. That is the commit
      happening — the moment your in-memory changes became permanent.

Part 4 · Break it on purpose, and learn why the rule exists


  
In Part 3 a refusal left the ledger untouched. It is tempting to think that is automatic — that a
    thrown exception stops everything. It is not, and this part proves it. You are going to remove one
    word from one file, and watch the difference.


  
    

    
  1. 
      
    Look at the refusal first
    
      
    Open src/main/java/com/globalbank/ejb/InsufficientFundsException.java. The class
        itself is almost empty; the important line is above it:
    
      
    @ApplicationException(rollback = true)
public class InsufficientFundsException extends Exception {
    

      
    In plain words
        
    The container has a rule about exceptions, and it is the opposite of what beginners expect:
    
        
      
          
    • An unchecked exception (a RuntimeException) means "something
            went wrong that nobody planned for" — the container rolls the transaction back
            automatically.
      • 
          
    • A checked exception means "this was anticipated; the caller will handle
            it" — and the container leaves the transaction alone.
      • 
        
    
        
    InsufficientFundsException extends Exception, so it is checked. The
          container would therefore assume the transfer should still be saved. rollback = true
          overrides that: "no — treat this refusal as a failure and undo everything."
    
      
    
    
    2. 

    
  2. 
      
    Remove the rule
    
      
    Delete (rollback = true) so the line becomes just:
    
      
    @ApplicationException
public class InsufficientFundsException extends Exception {
    
      
    Rebuild and redeploy — copy the new war over the old one and WildFly will redeploy it by
        itself:
    
      
    mvn clean package
copy target\globalbank-core.war  c:\wildfly\standalone\deployments\      REM  Windows
cp target/globalbank-core.war    ~/wildfly/standalone/deployments/       #    macOS / Linux
    
      
    Wait for Deployed "globalbank-core.war" in the server window. Then check what the
        ledger holds — remember that ExampleDS is in memory, so you are back to the three
        seeded accounts:
    
      
    http://localhost:8080/globalbank-core/account?action=all
    
    
    3. 

    
  3. 
      
    Now try the transfer that has to fail — with extra steps
    
      
    This is the interesting part. AccountService.transfer() checks the balance
        before changing anything, so a plain refusal still leaves nothing to undo. To see the
        difference, you have to make the failure happen after a change.
    
      
    Open AccountService.java and find the transfer method. Move the balance
        check so it happens after the debit:
    
      
    from.setBalance(from.getBalance().subtract(amount));   // debit FIRST
to.setBalance(to.getBalance().add(amount));            // credit

if (from.getBalance().compareTo(BigDecimal.ZERO) < 0) {
    throw new InsufficientFundsException(
            "Account " + fromId + " would be overdrawn by " + from.getBalance().abs().toPlainString());
}
    
      
    Yes, this is bad code. That is the point — you are building the accident on purpose, in a safe
        place, so you recognise it later. Rebuild, redeploy, then transfer more than Grace has:
    
      
    http://localhost:8080/globalbank-core/account?action=transfer&id=1002&to=1001&amount=9000.00
    
      
    You should see the refusal — and now check the ledger:
    
      
    http://localhost:8080/globalbank-core/account?action=all
    
      
    You should see Grace's balance has gone negative and Ada's has gone up by
        £9,000. The bank created money out of nothing. That is exactly what a missing
        rollback = true costs you.
    
    
    4. 

    
  4. 
      
    Put it back
    
      
    Restore the annotation to @ApplicationException(rollback = true) and move the check
        back above the two setBalance calls, so the method matches the original. Rebuild,
        redeploy, and repeat the failed transfer. This time the ledger is untouched.
    
      
    Do this now — do not leave the broken version in place, or Practical 2 will start from a bug.
    
    
    5. 
  


  
🔑
    
The lesson, in one sentence
      A transaction is not "undone because an exception was thrown" — it is undone because
      somebody told the container to undo it. For unchecked exceptions the container
      decides by default; for checked ones you decide, with @ApplicationException(rollback = true).
      Knowing which of the two you have is the difference between a bank and a money printer.

    📄 The code, in full — click any file to read it

    
entity/Account.java — the shape of an account.

    
@Entity
@Table(name = "accounts")
public class Account implements Serializable {

    @Id
    private int id;

    @Column(name = "holder", nullable = false, length = 60)
    private String holder;

    @Column(name = "balance", nullable = false, precision = 12, scale = 2)
    private BigDecimal balance;

    @Version
    private int version;

    protected Account() { }   // JPA needs a no-arg constructor

    public Account(int id, String holder, BigDecimal openingBalance) { … }

    public void setBalance(BigDecimal balance) { this.balance = balance; }
}

    
Notice there is a setter for the balance but not for the id or the holder. An account number never
      changes; a balance does. The class's methods describe what is allowed to happen to it. And the
      balance is a BigDecimal, never a double — a double cannot
      store 0.10 exactly, and those tiny errors add up across millions of transactions.


    
ejb/AccountNumberGenerator.java — the one counter.

    
@Singleton
@Lock(LockType.WRITE)
public class AccountNumberGenerator {

    private int next = 2000;

    public int nextAccountNumber() {
        return ++next;
    }
}

    
++next is not one operation — it is "read, add one, write back". Two requests doing
      that at the same instant could both read 2000 and both write 2001, handing two customers the same
      account number. @Lock(LockType.WRITE) lets one caller in at a time. A plain
      int is used on purpose, so the lock is visibly the only thing keeping it safe.


    
ejb/LedgerInitializer.java — the setup that runs once.

    
@Singleton
@Startup
public class LedgerInitializer {

    @PersistenceContext
    private EntityManager em;

    @PostConstruct
    public void seed() {
        Long existing = em.createQuery("SELECT COUNT(a) FROM Account a", Long.class)
                          .getSingleResult();
        if (existing > 0) {
            System.out.println("[Ledger] " + existing + " account(s) already present - not seeding");
            return;
        }
        em.persist(new Account(1001, "Ada Lovelace", new BigDecimal("1500.00")));
        em.persist(new Account(1002, "Grace Hopper", new BigDecimal("250.00")));
        em.persist(new Account(1003, "Alan Turing", new BigDecimal("0.00")));
    }
}

    
There is no commit() anywhere. The container commits when the method returns. And the
      count check at the top makes it idempotent — safe to run again without creating duplicates,
      which matters the day this points at a real database instead of an in-memory one.


    
ejb/AccountService.java — the bank's rules.

    
@Stateless
public class AccountService {

    @PersistenceContext
    private EntityManager em;

    @EJB
    private AccountNumberGenerator numbers;

    public Account find(int id) {
        Account account = em.find(Account.class, id);
        if (account == null) throw new IllegalArgumentException("No account with id " + id);
        return account;
    }

    public List<Account> findAll() {
        return em.createQuery("SELECT a FROM Account a ORDER BY a.id", Account.class)
                 .getResultList();
    }

    @TransactionAttribute(TransactionAttributeType.REQUIRED)
    public Account deposit(int id, BigDecimal amount) {
        requirePositive(amount);
        Account account = find(id);
        account.setBalance(account.getBalance().add(amount));   // no update() — just change it
        return account;
    }
}

    
That string in findAll is JPQL — SQL written against your Java
      classes. Account is the class, a.id is the field; JPA translates it into
      the table and column names you mapped. And in deposit there is no update()
      call: the EntityManager is already tracking the object, so at commit time it compares the object
      with what it loaded and writes the UPDATE itself.

  


  

    🗄️ Why there is no database to install
    
Three files decide where your data lives, and all three are already written:

    

      
FileWhat it says

      
        
pom.xmlOne dependency, provided scope. No driver, no pool — the server supplies both.

        
persistence.xml<jta-data-source>java:jboss/datasources/ExampleDS</jta-data-source> — WildFly's built-in in-memory database.

        
beans.xmlbean-discovery-mode="all" — tells CDI to look at every class. Not strictly needed yet; Practical 2 relies on it.

      
    

    
Schema generation is switched on with
      jakarta.persistence.schema-generation.database.action=drop-and-create, which is why the
      accounts table appears without you writing a single CREATE TABLE. On a real
      project you would never use drop-and-create — it destroys your data on every deploy.
      Here it means you always start clean.

    
When you are ready for a real database, the change is one line in persistence.xml: the
      JNDI name of a datasource you have configured, exactly as
      Session 3 describes.

  


  

    🧰 Debugging: reading a WildFly failure without panicking
    
    
      
  1. Find the marker file. WildFly writes a small file next to your archive in
        deployments/: .deployed means live, .failed means it
        stopped. The .failed file is the error report.
    2. 
      
  2. Read the deepest Caused by:. A stack trace is a chain of
        consequences. The first lines are what broke last; the last Caused by: in
        the chain is the root cause. Start there, not at the top.
    3. 
      
  3. Search your own code first. If the deepest line mentions a class of yours —
        AccountService, Account — the problem is yours. If it mentions
        Hibernate or Weld, it is usually configuration.
    4. 
      
  4. Then search your configuration. persistence.xml in the wrong
        folder and a mistyped JNDI name cause most of the failures beginners see.
    5. 
      
  5. Change one thing at a time. Rebuild, redeploy, check. Two changes at once and
        you learn nothing about either.
    6.

One-Line Summary

  

    
What you builtGlobalBank core — a JPA entity, a stateless service bean, a locked singleton counter, a startup seeder and a servlet front door, packaged as globalbank-core.war.

    
Where the data livesWildFly's built-in ExampleDS in-memory database. Nothing to install; everything resets when the server stops.

    
Who creates the beansThe container. There is no new AccountService() anywhere in the project.

    
Who writes the SQLJPA. You change the object; the UPDATE is written at commit time.

    
What @Version is forOptimistic locking — it refuses a write based on a stale read instead of silently overwriting somebody else's change.

    
What rollback = true is forChecked exceptions do not roll back by default. This annotation says "undo the transaction" — the difference between a bank and a money printer.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      

        Writing new AccountService() in the servlet
        Inject it with @EJB (or @Inject). A bean you construct yourself gets no transaction, no pooling and no injected EntityManager — it will fail with a NullPointerException on em.
      

      

        Using double or float for money
        Use BigDecimal, and build it from a String: new BigDecimal("1500.00"). The BigDecimal(double) constructor faithfully stores the double's error.
      

      

        Putting persistence.xml beside the Java files
        It belongs at src/main/resources/META-INF/persistence.xml, so it ends up in WEB-INF/classes/META-INF/ inside the war.
      

      

        Throwing a checked exception and expecting a rollback
        Checked exceptions commit by default. Add @ApplicationException(rollback = true).
      

      

        Guessing why the deployment failed
        Open the .failed marker file and read the deepest Caused by: — the last one in the chain. That is the root cause.
      

      

        Bundling the Jakarta EE API into the war
        Keep <scope>provided</scope>. The server already has it, and shipping a second copy causes classloading conflicts.
      

      

        Adding business logic to the servlet because it is "easier"
        Keep the servlet a doorway. The moment a rule lives in two places, the two copies drift apart.
