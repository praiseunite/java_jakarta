Part 1 · Where the web page actually comes from

1.1 A bean with no screen

Your GreeterBean can greet somebody. But a user cannot see a bean. A user needs something on a screen to look at, and something to type into.

So what is that thing on the screen? A web page is text that a program called a browser has been taught how to draw. The text is called HTML. Some pages also contain a form — a set of boxes and a button. When the user presses the button, the browser collects what they typed and sends it back to the server.

That is the whole shape of the web: a server sends text, the browser draws it, the user submits something, the server responds. The only real question is: who builds that text?

There are two answers, and they are the whole reason this session exists:

  • You build it by hand. Your code glues strings of HTML together and prints them. Simple at first, a nightmare once the page has fifty boxes.
  • The server builds it for you. You tell the server “there is a text box here” and “there is a button there”, and the server draws the HTML, reads the values back, and knows what each box means. This is the approach we learn today.

1.2 The idea: the server remembers the boxes

Here is the surprising part, and it is the key to everything on this page.

When you use this approach, the server does not just send some text and forget about it. It also keeps, on its own memory, a live model of every box, button and table on the page. Each of those is a real Java object. Those objects nest inside one another, so the server is holding a small tree of objects that mirrors the page.

When the user presses the button, the server compares what came back with its model and updates the objects. Because the server knows what each box was, it can also check the value, convert it, and hand it to your Java bean.

In plain words

Ordinary HTML is like a photograph of a form: once it is printed, it is only paper.

With the approach we are learning, the server keeps the original form — a live set of objects — and can therefore read it, check it, and change it. You write the boxes once; the server keeps them alive on every round trip.

1.3 So what is Jakarta Server Faces?

Now we can define the first big word.

✦
Jakarta Server Faces Jakarta Server Faces (JSF) is a standardised, server-side user interface framework, built on the component-tree model. Instead of writing raw HTML strings or JSP scriptlets, a JSF application assembles pages out of reusable, stateful UI components — inputs, buttons, tables — each backed by a Java object.

That sentence is dense, so here it is pulled apart word by word:

WordWhat it actually means
FrameworkA ready-made structure and set of pieces that you build inside, rather than starting from an empty file.
Server-sideThe work happens on the company's machine, not in the user's browser. The browser only draws what it is sent.
ComponentOne piece of the page with a life of its own — a text box, a label, a button, a table. Each has its own value and behaviour.
Component treeAll those components, nested inside one another, held in memory as objects. A form containing a label and a box is already a tiny tree.
JSP scriptletThe old way: small blobs of Java code written straight inside the page text. Messy, and now retired.
In plain words

JSF turns a web page from a wall of text into a set of objects the server understands. You say “text box” and “button”, not “print these angle brackets”.

Because the server understands the objects, it can also do the boring parts for you — reading the typed values, converting them to numbers, checking them, and putting them into your Java bean.

1.4 And what is Facelets?

Now the second big word — and it is easier, because it answers a different question.

If JSF is the machinery in the server that understands components, then Facelets is the language you write those pages in.

✦
Facelets Facelets is the default view declaration language for modern JSF. It replaces the older, legacy JSP files with clean, well-formed XHTML templates.
WordWhat it actually means
ViewOne page, as the server sees it. “The view” is the page currently being built or shown.
View declaration languageThe way you declare what a view looks like. English, just in a very strict grammar.
XHTMLHTML written to strict rules: every tag must be properly closed, and tags must nest neatly. Extra typing, far fewer bugs.
JSPJavaServer Pages — the older page language Facelets replaced. You will still meet it in old books.
🎭
Analogy Picture a puppet show. In plain HTML you are the puppeteer and the stagehand: you thread every string, paint every puppet, and move every joint yourself. With Facelets, the server keeps a live cast of actors (the components). You say “this actor has a text box”, press a button, and the server moves the actor, checks its state, runs your bean's method, and re-draws the stage.

1.5 A page is objects that nest

Look at any real page and you will see the same shape repeated: a page contains a form; the form contains a label, a text box and a button; the button contains a piece of text. Every one of those is an object, and every object knows its parent and its children.

That is all a “component tree” means — the same nesting you would draw on paper, but held in the server's memory.

🪆
Analogy Russian nesting dolls. Open the big one and there is a smaller one inside; open that and there is another. The page is the biggest doll, the form is inside it, and the button is inside the form. The server holds the whole set, and can open any doll to look at what is inside.
💡
The one thing to notice Because the server holds the objects and not just text, it can do things to them: set their values, convert them, validate them, and ask your bean for data to display.

1.6 The five features that make this worth using

This table is the honest list of why a company chooses this over hand-written HTML. Read the left column now; the right column is what you would otherwise have to build yourself.

FeatureAdvantage in enterprise applications
Component-centricUI elements manage their own rendering, state saving, and event handling.
Template reuse<ui:composition> and <ui:decorate> eliminate duplicate headers, footers and sidebars.
Expression Language (EL)#{bean.property} seamlessly binds view inputs to Java getter and setter methods.
Built-in validationAutomatic conversion and validation before any business method runs.
No scriptletsStrict XML syntax prevents developers from cluttering the presentation with raw Java code.

1.7 Expression Language — the glue between page and bean

Two of those features need a new word straight away: Expression Language.

Somewhere in the page you want to show the greeting your bean produced. Facelets lets you write a tiny instruction for that, wrapped in #{ }. Here is the whole idea in one line of a view:

<p><h:outputText value="#{helloWorld.message}"/></p>

The #{helloWorld.message} part is Expression Language (EL) — a small expression the server evaluates. It says: “find the object called helloWorld, and ask it for its message.” The server does that by calling a Java method, getMessage(), and writes the result into the page.

Put the same kind of expression on an input box instead of an output, and it works in both directions: the server reads the bean's value to fill the box, and — when the user submits — it writes the typed value back into the bean. That two-way behaviour is called binding, and it is the single most useful thing on this page.

In plain words

#{bean.property} is a message from the page to the server: “put the bean's value here,” or “take what the user typed and put it there.”

It is short because the server does the work — you never write the code that fetches or stores the value yourself.

⚠️
The trap: #{ } is not JavaScript Nothing inside #{ } reaches the browser. The server replaces it with a plain value before the page is sent. So a browser viewing the page above never sees #{helloWorld.message} — it sees the greeting text. Forget this and you will hunt for a bug in the wrong program.

1.8 Your page is built from ready-made tags

You do not invent these tags. Facelets gives you a shelf of them, grouped into small libraries. Each library is switched on in the page with an xmlns: line at the top. The templating library is called ui:

<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:ui="jakarta.faces.facelets">

Five tags from the ui library do most of the work in a real application:

TagPurposeDescription
<ui:composition>Page template wrapperDefines a page composition, ignoring any surrounding content outside this tag.
<ui:define>Named content blockFills a specific placeholder defined in a master template.
<ui:insert>Template placeholderDesignates an insertion point in the master template (e.g. body, header).
<ui:include>Modular page fragmentEncapsulates and pulls in another XHTML file (like a navigation menu).
<ui:repeat>Iterative loopLoops over a collection or list of objects to render repeated UI elements.
💡
The one thing to notice <ui:insert> and <ui:define> are a pair. The master template inserts a placeholder (“put the header here”); each individual page defines what goes into it. One header, written once, used by every page of the site.

Part 2 · What happens between the click and the new page

2.1 One click starts six jobs

When a user presses a button on a Facelets page, a lot has to happen before the next page appears. The server does not do it in one lump. It does it as a strict sequence of six steps, and every single step has to finish — or be deliberately skipped — before the next one begins.

This sequence has a formal name: the request processing lifecycle. Examiners love it. The good news is that the idea behind it is completely ordinary.

🏃
Analogy A relay race with six legs. The baton is the user's request. One runner cannot start until the previous one has handed the baton over. Six runners later, the response crosses the finish line and goes back to the browser.
And like a real relay, there is one rule that can cut the race short: if a runner finds a problem, the baton goes straight to the last runner and the middle legs are skipped.

2.2 The two kinds of request

One word has to be introduced before the six legs make sense: postback.

  • The first visit. The user opens the page for the first time. There are no values to read back — the server must build the component tree from scratch.
  • A postback. The user is returning to the same page, usually by pressing a button or submitting a form. This time the server already has the page's objects from before, and it has also stored their values in a hidden place — the view state. It restores them, then reads what the user just typed.
In plain words

“Postback” simply means the user sent something back to the page they were already on. The server remembers what the page looked like last time, so it does not have to guess.

2.3 The six legs, one at a time

Here they are in order. Each has a formal name (the one an exam will use) and a plain-English description of what actually happens.

Leg 1 — Find the page's memory — “Restore View”

The container locates or constructs the component tree for the requested page, and holds it inside the FacesContext — the object that represents “this request, right now”. On a first visit the tree is built fresh; on a postback, the saved view state is restored.

Leg 2 — Read what the user typed — “Apply Request Values”

Each component decodes the HTTP request parameters sent back by the browser and stores the raw value locally on itself. Nothing is converted or checked yet — it is parked exactly as typed, as text.

Leg 3 — Check it makes sense — “Process Validation”

Now the raw text is turned into the right type (a string becomes a number, a date, a boolean), and the validation rules are run. If validation fails, processing jumps directly to Leg 6 — the response is re-rendered so the user can see the error messages and try again.

Leg 4 — Save it into your bean — “Update Model Values”

The validated values are copied out of the components and into the properties of your server-side backing bean — by calling its setters. This is where the page's data finally becomes your Java object's data.

Leg 5 — Run your business method — “Invoke Application”

The action method runs — the one named in the button, such as action="#{bean.transferFunds}". It does the real work and returns a navigation outcome that decides which page is shown next.

Leg 6 — Draw the answer — “Render Response”

The component tree renders itself into ordinary HTML and that response is sent back to the browser. Legs 1 to 5 handled the incoming input; Leg 6 produces the outgoing page.

In plain words

Run the six legs together as one sentence: get the page back → read the typing → check it → hand it to the bean → run the method → draw the new page.

Steps 1 to 5 are about believing nothing until it has been checked. Step 6 is the only one the user ever sees.

🔍 How to read that diagram, ring by ring

A lifecycle diagram like this is a loop, not a line. Read it as: the six boxes are the six legs, and each one either passes the baton on or bounces the request out to the finish.

In the diagramWhat it is telling you
The six named boxesThe six legs of the race, in order. Every request walks the same path.
The arrow that jumps from “Process Validation” to the endThe short-circuit. A failed check does not try to save bad data — it goes straight to rendering so the user can correct it.
The arrow back to “Restore View”The next request begins the whole race again. The lifecycle does not remember between requests except through what it saved.
The final boxRender Response. Its output leaves the server as plain HTML — by then no component objects have left the building.

2.4 The short-circuit rule

One rule from Leg 3 matters more than all the others, because it is the one that confuses beginners. When validation fails, the server does not carry on and hope for the best. It abandons the middle legs and jumps straight to rendering the response.

🩺
Analogy A form at a doctor's office. Before you see the doctor, the receptionist checks your paperwork. If a field is missing, you are sent straight back to the waiting room — you never reach the doctor's room, and the doctor's notes are never filled in from a broken form. Only a complete form gets past the desk.
⚠️
The trap: bad input never reaches your bean If a user types letters into a field that must be a number, your business method is never called and your bean's field is never updated. Conversion and validation happen in Leg 3, before Legs 4 and 5. Beginners often add a null check inside their action method to “catch” bad input — it will never run, because bad input was stopped two legs earlier.

Part 3 · Building a complete (small) Facelets application


  
You now know what the pieces are and how a request travels through them. Time to put a whole,
    working application together. It needs exactly four things:

  
    
    
  1. A configuration descriptor — a small file that tells the server to send web
      requests to the Faces machinery.
    2. 
    
  2. A CDI marker file — an empty beans.xml, the file every Jakarta EE
      project carries. We will come back to exactly what it does in Section 3.2.
    3. 
    
  3. A backing bean — an ordinary Java object that holds the page's data and the
      buttons' actions.
    4. 
    
  4. A view — the XHTML page the user actually sees.
    5. 
  


  
🏢
    
Analogy
      A small office with a front desk. The configuration file is the door sign that
      says “all visitors go to the front desk”. The CDI marker file is the note on the
      staffroom door telling the agency which staff are on duty. The backing bean is the
      clerk, holding the clipboard with the details on it and knowing what to do when you press a button. The
      view is the printed form on the counter — the only part the visitor ever sees.

  


  
3.1 File one: web.xml — the front door

  
You have met a servlet before: a Java class that answers a URL. Facelets is
    driven by one special servlet, the FacesServlet. It must be registered as the
    front controller — the single entry point that every page request goes through
    first.


  
In plain words
    
A front controller is exactly like a hotel receptionist. You never walk
      straight to a room; everyone reports to the desk first, and the desk decides where you go. The
      web.xml file is where you write down that the desk exists and which addresses it
      handles.

  


  
WEB-INF/web.xml — Faces front controller registration

  
<?xml version="1.0" encoding="UTF-8"?>
<web-app xmlns="https://jakarta.ee/xml/ns/jakartaee" version="6.0">

    <servlet>
        <servlet-name>Faces Servlet</servlet-name>
        <servlet-class>jakarta.faces.webapp.FacesServlet</servlet-class>
        <load-on-startup>1</load-on-startup>
    </servlet>

    <servlet-mapping>
        <servlet-name>Faces Servlet</servlet-name>
        <url-pattern>*.xhtml</url-pattern>
    </servlet-mapping>

</web-app>


  
💡
    
The one thing to notice
      The <url-pattern>*.xhtml</url-pattern> line is the whole point.
      Every URL ending in .xhtml is handed to the Faces servlet. Without a
      mapping like this, the server would serve your page as plain text and none of the components
      would ever come alive.

  


  
3.2 File two: beans.xml — the file that is nearly always there

  
The backing bean in the next section is not created by new. It is created and
    managed by CDI — the part of Jakarta EE that wires objects together. In almost every
    Jakarta EE project you will find a file called beans.xml next to web.xml,
    and this is the file people say “turns CDI on”.


  
📌
    
What is actually true today
      
Put an empty beans.xml file inside src/main/webapp/WEB-INF/. That is
        what the projects in this course do, and it always works.

      
But know the precise rule, because you will meet people who believe the older version of it.
        Since CDI 1.1 the file is optional. An archive that contains classes with
        bean-defining annotations (@Named, @SessionScoped, and so on) is an
        implicit bean archive — CDI discovers it with no beans.xml at all.
        The file is only required when you want to change something: switch the discovery mode,
        or declare alternatives, interceptors or decorators (Session 12).

      
So an empty beans.xml is not a switch, strictly speaking. It is a habit that is
        harmless, universal, and the thing every tutorial and every colleague expects to see. Keep it.

    

  


  
⚠️
    
The trap: the empty file everyone deletes
      beans.xml often contains nothing at all, which makes beginners delete it “to tidy up”
      and then wonder why something stopped working. An empty file costs nothing — leave it alone. And be
      careful which way round you learn the rule: an empty beans.xml does not prove
      that CDI needs it, because the annotations alone are usually enough.

  


  
3.3 File three: the CDI backing bean

  
A backing bean is the Java object that stands behind the page. It holds the
    page's data and it holds the methods the buttons call. Two annotations turn an ordinary class into
    one.


  
HelloWorldBean.java — CDI backing bean

  
package com.globalbank.web;

import java.io.Serializable;
import jakarta.enterprise.context.SessionScoped;
import jakarta.inject.Named;

@Named("helloWorld")          // Accessible in Facelet pages as #{helloWorld}
@SessionScoped                // Retains state throughout client session
public class HelloWorldBean implements Serializable {

    private String message = "Welcome to Jakarta Server Faces 4.0!";

    public String getMessage() { return message; }
    public void setMessage(String message) { this.message = message; }
}


  
Three details carry all the meaning, so take them one at a time:

  

    
In the codeWhat it gives you

    
      
@Named("helloWorld")Gives the bean a name in the view. That name is how the page reaches it: #{helloWorld.message}. Named, or the view cannot find it.

      
@SessionScopedGives the bean a lifetime: one instance per user, alive for their whole browsing session. The bean's fields survive from one request to the next.

      
implements SerializableAllows the server to store the bean safely between requests. A session-scoped bean must be serializable, so make it so.

      
getMessage() / setMessage()The getter and setter that #{helloWorld.message} uses. The view never touches the field directly — it always goes through these.

    
  


  
In plain words
    
@Named answers “what do I call this bean from the page?”
      @SessionScoped answers “how long does it live?”

    
Together with the getter and setter, they are the bridge that lets a line of XHTML talk to a
      Java object. Nothing else connects them — no new, no lookup, just the name.

  


  
3.4 File four — the view itself

  
Finally, the page the user sees. Notice how little there is: no loop building strings, no
    println. Just components, and one expression.


  
helloWorld.xhtml — Facelets view

  
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html">
<h:head>
    <title>Jakarta Faces Demo</title>
</h:head>
<h:body>
    <h1>Facelet Application Response</h1>
    <!-- Evaluates to helloWorld.getMessage() -->
    <p><h:outputText value="#{helloWorld.message}"/></p>
</h:body>
</html>


  
Two things in it are new. h:head and h:body are the JSF versions of the
    ordinary head and body — the server puts its own scripts and styles into them. And
    h:outputText is a component whose only job is to print its value.


  
🔑
    
The one thing to notice
      The comment in the file says “Evaluates to helloWorld.getMessage()”, and that is
      literally true. #{helloWorld.message} is not a property lookup in the browser — it
      is the server calling a Java method for you. That is the whole of Expression
      Language in one line.

Part 4 · Making your own tags, and loading your own files


  
One small page is easy. A real application has fifty pages, and they all want the same login box,
    the same address form, the same footer. Copying and pasting that around is how projects become
    unmaintainable.


  
4.1 The problem: the same screen, written eight times

  
Facelets offers two answers, and they solve different halves of the problem:

  
    
    
  • Composite components package a repeated piece of screen into your own
      custom tag, so you write it once and reuse it everywhere.
    • 
    
  • Web resources let a page load its CSS, JavaScript and images from a
      standard place, without hard-coded file paths.
    • 
  


  
🍪
    
Analogy
      A cookie cutter. You carve the shape once, and then press out as many identical cookies as you
      like — with no skill required each time, and no two cookies that look slightly different. The
      composite component is the cutter; every page just presses it.

  


  
4.2 What a composite component is

  
A composite component is a reusable custom tag you build yourself. It packages a
    complex UI pattern — a login box, credit-card entry fields, an address form — into a single tag,
    without writing a single Java renderer class. You write only XHTML.

  
The file has two halves, and the names are honest about their jobs:

  
    
    
  • composite:interface — the contract: what you must hand
      the component, and what is optional.
    • 
    
  • composite:implementation — the layout: what the
      component actually draws.
    • 
  


  
📋
    
Analogy
      A hiring form. The interface is the list of boxes at the top — “name (required),
      date of birth (optional)”. The implementation is the rest of the form, laid out
      to be filled in. Everyone who uses the form must accept the same contract; only the filling-in
      changes.

  


  
resources/components/loginBox.xhtml — composite component definition

  
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html"
      xmlns:composite="jakarta.faces.composite">

    <!-- 1. Declare the component's public attribute contract -->
    <composite:interface>
        <composite:attribute name="usernamePrompt" default="Username:"/>
        <composite:attribute name="buttonLabel" required="true"/>
    </composite:interface>

    <!-- 2. Provide the implementation layout -->
    <composite:implementation>
        <div class="login-panel">
            <h:outputLabel value="#{cc.attrs.usernamePrompt}" />
            <h:inputText id="usr" />
            <h:commandButton value="#{cc.attrs.buttonLabel}" />
        </div>
    </composite:implementation>
</html>


  
🔑
    
The one thing to notice
      The two #{cc.attrs.…} expressions. cc means “this component itself”, and
      attrs means “the values the caller passed in”. So
      #{cc.attrs.buttonLabel} reads like an ordinary sentence: the value the user gave
      for my button's label. That is how a component becomes reusable — it refers to whatever it
      was handed, never to a hard-coded name.

  


  
4.3 Web resources — where CSS, JavaScript and images live

  
The second half of reuse is the files around the page. Jakarta Faces gives you a standard folder,
    /resources/, and three components for pulling files out of it. Each component takes a
    library (the sub-folder) and a name (the file).


  

    
Asset typeDisk locationFacelets tag in XHTML

    
      

        CSS stylesheet
        /resources/css/style.css
        <h:outputStylesheet library="css" name="style.css"/>
      

      

        JavaScript
        /resources/js/app.js
        <h:outputScript library="js" name="app.js"/>
      

      

        Image asset
        /resources/images/logo.png
        <h:graphicImage library="images" name="logo.png"/>
      

    
  


  
In plain words
    
Instead of writing a file path like /my-app/css/style.css, you name the
      library the file lives in and the file itself. The server works
      out the real URL for you.

    
That matters because the real URL changes when the application is deployed under a different
      name or a different folder. You write it once; the server gets it right everywhere.

  


  
⚠️
    
The trap: hard-coding <link> and
      <img> paths
      It is tempting to write an ordinary HTML <link href="css/style.css"> or
      <img src="images/logo.png">. Use the Faces tags instead. The
      library and name form is what lets the server resolve the correct path
      and version for the file, wherever the application is deployed — a hand-written path is the
      classic “works on my machine, 404 in the browser” bug.

    📋 The Facelets tag library, in full
    
The templating tags from the ui library — the formal descriptions, word for word.

    

      
TagPurposeDescription

<ui:define>Named content blockFills a specific placeholder defined in a master template.

      in a template, and <ui:composition> is the usual outer tag of every page.

  


  

    🔄 All six lifecycle phases — the formal wording
    
This is the table an exam question will be marked against. The plain-English versions in Part 2
      say the same thing.

    

      
Phase #Phase nameWhat happens in this phase

      
        
Phase 1Restore ViewThe container locates or constructs the component tree for the requested page inside FacesContext. For a postback, view state is restored.

        
Phase 2Apply Request ValuesEach component decodes its submitted HTTP request parameters and stores the raw value locally.

        
Phase 3Process ValidationComponents convert strings to types (e.g. string to double) and check validation rules. If validation fails, processing jumps directly to Phase 6.

        
Phase 4Update Model ValuesThe validated local values are copied into the properties of the server-side backing bean.

        
Phase 5Invoke ApplicationThe action method (e.g. action="#{bean.transferFunds}") executes business logic and returns a navigation outcome.

        
Phase 6Render ResponseThe component tree renders itself into standard HTML and sends the HTTP response back to the browser.

      
    

  


  

    🏷️ The namespace lines you will type
    
Each line switches on one library of tags for the page. The prefix (h,
      ui, composite) is the short name you then use in every tag.

    

      
DeclarationWhat it switches on

      
        
xmlns="http://www.w3.org/1999/xhtml"Plain HTML elements such as <div> and <p>.

        
xmlns:h="jakarta.faces.html"The HTML components — h:form, h:inputText, h:commandButton.

        
xmlns:ui="jakarta.faces.facelets"The templating tags — ui:composition, ui:insert, ui:define.

        
xmlns:composite="jakarta.faces.composite"The composite-component tags — composite:interface, composite:implementation.

        
xmlns:f="jakarta.faces.core"The core tags — validators, converters and Ajax. Covered in later sessions.

      
    

    
Facelets pages declare tag libraries using modern Jakarta EE namespaces, such as
      xmlns:ui="jakarta.faces.facelets".

  recap
  
One-line summary of everything

  

    
Jakarta Server Faces (JSF)A standardised server-side UI framework built on the component-tree model.

    
FaceletsThe default view declaration language for modern JSF — clean, well-formed XHTML instead of legacy JSP.

    
Component treeThe server's live model of every box, button and table on the page, held as nested Java objects.

    
Expression Language#{bean.property} — evaluated on the server; calls the getter or setter for you.

    
Backing beanThe CDI bean behind the page: @Named gives it a name, @SessionScoped gives it a lifetime.

    
web.xmlRegisters the FacesServlet as the front controller for *.xhtml.

    
beans.xmlThe CDI marker file. Since CDI 1.1 it is optional — bean-defining annotations alone are enough — but every project keeps one because it is the conventional place to declare alternatives, interceptors and decorators.

    
The 6 phasesRestore View → Apply Request Values → Process Validation → Update Model Values → Invoke Application → Render Response.

    
Validation short-circuitA failure in Phase 3 skips Phases 4 and 5 and jumps straight to Phase 6.

    
Composite componentA reusable custom tag written in XHTML — composite:interface is the contract, composite:implementation the layout.

    
Web resourcesCSS, JS and images live in /resources/ and load via <h:outputStylesheet>, <h:outputScript> and <h:graphicImage>.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Deleting beans.xml because it is emptyLeave it alone — it costs nothing and every project expects it. But do not mis-learn the reason: since CDI 1.1 it is not what makes CDI find your beans. The bean-defining annotations do that.

      
Writing CSS or image paths by hand, such as <link href="css/style.css">Use <h:outputStylesheet library="css" name="style.css"/> so the server resolves the correct path.

      
Checking for null or bad input inside your action methodIt will never run — validation failed in Phase 3, so the action is skipped entirely.

      
Thinking #{bean.value} runs in the browserIt is evaluated on the server, before the page is sent. The browser only ever sees the finished value.

      
Writing a Java renderer class for a composite componentYou do not need one. A composite component is pure XHTML: an interface plus an implementation.

      
Using the wrong attribute name in #{cc.attrs.…}It must match the name declared in composite:interface, or the value arrives empty.

      
Mapping the FacesServlet to something other than *.xhtmlMap it to *.xhtml; otherwise the page is served as plain text and no components are processed.
