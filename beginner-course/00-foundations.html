concept

1. What is a program?

A program is a list of exact instructions a computer follows, one after another, top to bottom.

Here is the part that surprises beginners: a computer never guesses and never fills in a gap. If you did not say it, it does not happen. Ten steps that are almost right produce an almost-right result — or none at all.

🍳
Analogy A recipe. “Heat the pan. Add the oil. Wait 30 seconds. Add the egg.” The cook is the computer: they follow the recipe exactly, in order, and never improvise. Swap two steps, or leave one out, and breakfast is ruined. Code is a recipe with zero tolerance for vague steps.
In plain words

A program is a recipe. The computer is a cook with no imagination — it does exactly what the recipe says, and nothing you forgot to write.

concept

2. What is Java? What is the JVM?

Java is a programming language — a fixed vocabulary and grammar for writing those instructions. You write Java as plain text in files ending in .java.

The computer cannot run that text directly. Two steps turn it into something that runs:

  1. Compile. A tool called javac (the Java compiler) reads your .java file and produces a .class file full of bytecode — a compact instruction format halfway between your text and the machine.
  2. Run. A program called the JVM (Java Virtual Machine), launched with the java command, reads that bytecode and actually does the work.

So there are three things, and beginners mix them up constantly: Java is the language, javac is the translator that compiles it, and the JVM is the machine that runs the result.

🔌
Analogy A travel power adapter. Bytecode is a plug with one standard shape. Every country (Windows, macOS, Linux) has a different socket, but every one of them ships its own adapter — the JVM. Write the plug once, and it fits any socket. That is why Java was adopted by banks decades ago and is still used today.
⚠️
Two traps worth naming now .java files do not run. They are text, and the computer does not read them. Only the compiled .class file runs. And “virtual machine” does not mean a fake or slow computer — it means a real program that behaves identically on every operating system.

Here are the two commands, and what each one does:

javac Demo.java      // the compiler reads your text and writes Demo.class
java  Demo           // the JVM reads Demo.class and runs it
💡
The one thing to notice You compile once, but the same .class file runs anywhere a JVM exists. The JVM is what makes “write once, run anywhere” true.
try it

3. Your first “it works” moment

A complete Java program is short. Here is the smallest one that does something, and the three commands that turn the text into a working program. Follow along — the order matters.

  1. Write the file

    Save this as Demo.java. The file name must match the class name exactly — Demo, capital D.

    public class Demo {
    public static void main(String[] args) {   // the JVM always starts here
        System.out.println("Hello from the JVM");
    }
}

    Every Java program you run starts at main. Do not worry about the rest of the words yet; they all get explained later on this page.

  2. Compile it

    The compiler reads your text and writes the bytecode file next to it.

    javac Demo.java      // creates Demo.class

    If it prints nothing, it worked — silence is success. If it prints an error, the error names the file and the line number. Start at that line, not at the bottom of the message.

  3. Run it

    The java command starts the JVM, which reads the bytecode and runs it.

    java Demo            // prints: Hello from the JVM

    That line of text on your screen is the program working. You have now compiled and run Java.

  4. Try it right here, without installing anything

    Below is a program like the one you just wrote. Press Run and watch the output, then change the numbers and run it again — the panel recomputes, so you are the one driving.

4. The building blocks, smallest to largest

  
Java is built from a handful of pieces. Learn these and the rest of the course reads like English.
    We go from the smallest piece to the largest.


  
Variable — a labelled box

  
A variable is a named box that holds one value. int score = 5; makes
    a box called score holding the number 5. Later, score = 6; replaces what
    is in the box.


  
Type — the shape of the box

  
A type says what kind of value a box may hold. Common ones: int
    (whole number), double (decimal number), boolean
    (true/false), and String (text, always in double quotes:
    "hello"). Java checks types before it runs, so int x = "hello";
    will not even compile.


  
📦
    
Analogy
      A variable is a labelled box; the type is the shape of its opening. A round hole takes round
      pegs. Try to push a piece of text into a box built for whole numbers, and Java stops you at the
      lid.

  


  
Method — a named, reusable block of steps

  
A method is a named block of steps, often taking some input and giving back a
    result. You call it by name: add(2, 3) produces 5.


  
// name: add   inputs: two ints   gives back: an int
int add(int a, int b) {
    return a + b;      // "return" hands the answer back to whoever called add(...)
}


  
🥤
    
Analogy
      A vending machine. You press a button (call the method), feed it a coin (pass an input), and a
      drink comes out (a result is returned). You do not need to know the wiring inside — only the
      button and what comes out.

  


  
💡
    
The one thing to notice
      return is how a method gives its answer back. Without it, a method can still do work
      — but it hands nothing to whoever asked.

  


  
Class — a blueprint

  
A class is a blueprint that groups related data and methods under one name. A
    BankAccount class might hold a balance and offer deposit(...)
    and withdraw(...) methods.


  
Object — a real item built from the blueprint

  
An object (also called an instance) is an actual thing built
    from a class, created with the new keyword. Each object has its own copy of the data.


  
BankAccount acc = new BankAccount();   // one real object, built from the class blueprint


  
🍪
    
Analogy
      A class is a cookie cutter; an object is a cookie. One cutter, many cookies — and each cookie is
      its own thing, even though they all share the same shape.

  


  
In plain words
    
Class = the plan. Object = a real item made from the plan with
      new. Almost everything in Java is an object created from some class.

  


  
Interface — a promise about method names

  
An interface lists what methods exist, with no code for how they work. It is a
    contract: any class that claims to implement it must supply those methods.


  
interface Greeter {
    String greet(String name);   // any Greeter MUST provide this method
}


  
A class then implements the interface and supplies the real code:
    class FriendlyGreeter implements Greeter { ... }. Other code can then ask for “any
    Greeter” without caring which one it gets. This is exactly how Jakarta EE lets your
    code talk to a bean without knowing the bean's real class.


  
📋
    
Analogy
      A job description. It lists the duties (“must be able to greet customers”) but not how any one
      person does them. Anyone who can do those duties fits the role — and you can hire a replacement
      without rewriting the advert.

  


  
Inheritance — taking after a parent

  
class Cat extends Animal means Cat gets everything Animal
    has, plus its own extras. You will meet this mostly as extends HttpServlet — “my class
    is a kind of servlet”.


  
class Cat extends Animal { ... }   // Cat inherits Animal's members, then adds its own


  
👪
    
Analogy
      Family resemblance. A child inherits traits from a parent, then develops their own on top. The
      child does not have to be taught the family's traits again — they come included.

5. Packages & imports

  
Real projects have thousands of classes. They are filed into packages — folders
    for classes, written with dots, such as com.globalbank.accounts. The first line of a
    file declares which package it lives in.


  
🗄️
    
Analogy
      A filing cabinet. Each drawer is a package, and each class is a file inside a drawer. To use a
      file from another drawer, you have to say which drawer it came from — that is what an
      import does.

  


  
To use a class from another package, you import it, so the compiler knows where to
    look:


  
package com.globalbank.web;

import jakarta.ejb.Stateless;   // "let me use the Stateless class from jakarta.ejb"


  
💡
    
The one thing to notice
      The package line comes first and says where this file lives. The
      import lines come after and say which other drawers you are borrowing from.
      They are opposite directions.

  


  
⚠️
    
You will meet jakarta.* and javax.* together
      Years ago these packages were named javax.*. Most were renamed to
      jakarta.*, but a few deliberately kept the old name — javax.sql and
      javax.naming. So import javax.naming.InitialContext; is
      correct, while import jakarta.naming.InitialContext; does not exist.
      Session 3 covers this trap properly. For now, just know both spellings are the same technology.

  


  
In plain words
    
A package is a folder for classes. An import is a note at the top of your file saying “I will be
      using a class from that folder.” Without it, the compiler cannot find the class.

  


  


  

  concept
  
6. Annotations — the @ things

  
An annotation is a label you stick on a class or a method that some tool reads
    later to change how the code is treated. It is not a step that “runs” by itself; it is a sticky note
    with meaning.


  
📝
    
Analogy
      A sticky note on a box. The box still holds whatever it holds, but the note tells whoever opens
      it how to treat the contents: “fragile”, “this way up”, “staff only”. The note changes nothing
      inside the box — it changes how the box is handled.

  


  
Here is an annotation telling the server how to treat a whole class, and another telling the
    compiler something about a method:


  
@Stateless                 // sticky note: "server, treat this as a stateless bean"
public class CalculatorBean implements CalculatorRemote {
    @Override               // sticky note to the compiler: "this replaces an interface method"
    public int add(int a, int b) { return a + b; }
}


  
💡
    
The one thing to notice
      The annotation changes how the class is treated, not what the class does. Every
      annotation in Jakarta EE works the same way: you write an ordinary class, add a few
      @ labels, and the server does the heavy lifting the labels describe — transactions,
      security, pooling. That is the whole course in one sentence.

  


  
In plain words
    
An annotation is a sticky note that only tools read. @Stateless means nothing at all
      to a plain Java program — but it means everything to the server, which reads it and says “I will
      manage this class for you.”

7. Collections & generics

  
You rarely have exactly one of something. A collection holds many values at once.
    Two of them appear constantly in this course:

  
    
    
  • List<String> — an ordered sequence of text values. list.add("a")
      adds one; list.get(0) fetches the first.
    • 
    
  • Map<String, Integer> — a lookup by key. map.get("apples") gives
      you back the count stored under "apples".
    • 
  


  
🧰
    
Analogy
      A toolbox with labelled compartments. A List is a shelf where things sit in the order
      you placed them; a Map is a set of labelled drawers you open by name. The
      < > part is the label on the toolbox telling you what belongs inside.

  


  
The < > part is called generics: it tells Java what is inside,
    so List<String> accepts only text, and you never have to guess the type coming
    back out.


  
List<String> names = new ArrayList<>();
names.add("Ada");
names.add("Grace");

Map<String, Integer> stock = new HashMap<>();
stock.put("apples", 12);
int apples = stock.get("apples");   // look up by key — returns 12


  
💡
    
The one thing to notice
      List<String> and Map<String, Integer> put the type in
      once, and Java then keeps the promise for you everywhere. stock.get("apples")
      comes back as an int with no casting and no guessing.

  


  
In plain words
    
A collection is a container for many values. Generics is the label on the container that says
      what kind of values go in — so Java can stop you putting the wrong thing in, and tell you exactly
      what comes out.

8. Exceptions & stack traces

  
When something goes wrong while a program runs, Java throws an exception: it stops
    the current work and hands you an error object. Two you will see early are
    NullPointerException (you used something that was empty) and
    ArithmeticException (like dividing by zero).

  
You can catch that error instead of letting it crash the program:


  
try {
    int result = 10 / 0;                       // this blows up at run time
} catch (ArithmeticException e) {
    System.out.println("Not allowed: " + e.getMessage());
}


  
If you do not catch it, Java prints a stack trace: the chain of method calls that
    led to the failure, most recent first. Reading a stack trace is a skill you will use forever, and
    it comes down to two places in the printout:


  
java.lang.ArithmeticException: / by zero
    at com.example.CalculatorBean.divide(CalculatorBean.java:42)   <-- the real culprit line
    at com.example.Main.main(Main.java:11)
Caused by: ...                                                     <-- look here for the ROOT cause


  
📦
    
Analogy
      A delivery tracking log. A parcel changed hands several times; the log lists every handoff, most
      recent first, all the way back to where it started. The stack trace is that log for a failure —
      and the bottom line is where the trouble really began.

  


  
💡
    
The one thing to notice
      Do not read a stack trace top to bottom like a paragraph. Scroll to the first line that
      mentions your own code, and read any “Caused by:” at the bottom. Those
      two spots hold almost all the answer.

  


  
⚠️
    
Do not fix the last line
      Beginners panic at the length of the trace and start editing the bottom of it. The last line is
      usually a symptom. The cause sits in your own code — the first line in the trace that names a file
      you wrote.

  


  
In plain words
    
An exception is Java refusing to carry on with something impossible. A stack trace is the
      receipt: it lists the calls that led to the crash. Read the first line that mentions your code,
      and any “Caused by” at the bottom.

9. Libraries, JARs & “an API”

  
A library is someone else's prewritten code that you reuse instead of writing
    your own. Java libraries ship as JAR files — a .jar is simply a zip
    full of compiled .class files.

  
An API (Application Programming Interface) is the set of classes and methods a
    library offers you to call — its “control panel”. “The JMS API” means “the classes you use to do
    messaging”. You will hear the word API constantly; it just means the callable surface
    of some component.


  
🪑
    
Analogy
      A flat-pack furniture kit. The JAR is the box of parts — everything you need,
      packed up. The API is the instruction sheet and the labelled handles: the
      specific places you are meant to grip and turn. You do not need to know how the factory cut the
      wood; you only need the handles it gives you.

  


  
// a library arrives as a .jar: a zip of .class files you add to your project
import jakarta.persistence.Entity;   // one class an API hands you to use


  
💡
    
The one thing to notice
      A JAR is the file; an API is the set of ways you use it. When someone says “the
      Jakarta Mail API”, they mean the classes and methods you call — not a file you download.

10. Build tools & pom.xml

  
Typing javac by hand for hundreds of files and downloading every JAR yourself is not
    how real projects work. A build tool does it for you. This course uses
    Maven.

  
You describe the project once, in a file called pom.xml, and then the tool takes over.
    Here is the whole idea as four steps.


  
    

    
  1. 
      
    Describe the project
    
      
    The pom.xml names your project and says what to build. The most important tags are
        groupId, artifactId, version and
        packaging. The full anatomy is in the reference section.
    
      
    <groupId>com.globalbank</groupId>
<artifactId>accounts-ejb</artifactId>
<version>1.0.0</version>
<packaging>war</packaging>      <!-- build me a web app -->
    
    
    2. 

    
  2. 
      
    Declare the libraries you need
    
      
    Instead of hunting down JAR files, you list them. Maven finds and downloads them.
    
      
    <dependency>
  <groupId>jakarta.platform</groupId>
  <artifactId>jakarta.jakartaee-api</artifactId>
  <version>10.0.0</version>
  <scope>provided</scope>      <!-- the server already has it — do not bundle a copy -->
</dependency>
    
      
    scope provided means “I need this to compile, but the server already ships its
        own copy — do not include mine.” Getting that wrong causes confusing version clashes.
    
    
    3. 

    
  3. 
      
    Build it with one command
    
      
    Maven compiles everything and packages it into a target/ folder.
    
      
    mvn clean package      // → BUILD SUCCESS → target/accounts-ejb.war
    
      
    That .war file is what you hand to the server later. A build tool turns a folder
        of source files into one deployable file.
    
    
    4. 

    
  4. 
      
    Try it in the pretend terminal
    
      
    Below is a simulated command line. It is safe — nothing touches your computer. Type
        help to see what is available.
    
      
    
        
    
        
    
        
    
      
    
      
    Try: help, then
        java -version, cat pom.xml, mvn clean package. Use ↑ to
        repeat a command.
    
    
    5. 
  


  
🏗️
    
Analogy
      A general contractor. You hand over a job spec (the pom.xml) and walk away. The
      contractor orders the materials (dependencies), assembles the building (compile), and leaves one
      finished package on the site (target/). You never fetch a single brick yourself.

  


  
💡
    
The one thing to notice
      You describe the project once; the tool does the same work every time, on every
      machine. That repeatability is the whole reason build tools exist — not speed, but the fact that
      everyone gets the identical result.

  


  
In plain words
    
A build tool is a robot assistant for turning many source files into one ready-to-ship file. The
      pom.xml is the brief you give it: what the project is called, what it should become,
      and which libraries it needs.

11. Servers, clients, HTTP

  
A server is a program that stays running and waits for requests. A
    client is whatever sends a request — a browser, a phone app, or another program.

  
HTTP is the request-and-response language of the web. A client sends a
    request (“GET me the data at /accounts/123”); the server sends back a
    response (the data, plus a status code like 200 OK or
    404 Not Found).


  
📮
    
Analogy
      A post office. The server is the sorting office, open all day, waiting for mail.
      The client is you posting a letter. HTTP is the standard envelope
      format and the addressing rules both sides agreed on. The status code on the
      reply is the stamp: delivered, or address unknown.

  


  
A request and its response look like this:


  
GET /accounts/123 HTTP/1.1
Host: localhost:8080

HTTP/1.1 200 OK
Content-Type: application/json

{ "account_id": 123, "balance": 500 }


  
An address starting http://localhost:8080 means “a server on this same machine,
    listening on port 8080” — which is exactly where WildFly runs in this course.


  
💡
    
The one thing to notice
      The status code on the first line of the response tells you instantly whether it worked.
      200 means success; 404 means the server answered but had nothing at that
      address. You will meet the full list in the reference section.

  


  
⚠️
    
localhost is not the internet
      localhost always means this same machine. A server at
      localhost:8080 is only reachable from your own computer — nobody else can open it.
      That is deliberate: it is your private practice server.

  


  
In plain words
    
A server waits; a client asks; HTTP is the language they use; a status code is the one-word
      reply that says whether the asking worked. A port is which counter at the post office you
      walk up to.

12. Databases & SQL

  
A database stores data that must survive after the program stops — accounts,
    orders, users. A relational database (PostgreSQL, MySQL, H2…) stores that data in
    tables: rows and named columns, like a spreadsheet with rules.

  
SQL is the language for talking to it. Three commands cover most of what you will
    do — read, add, and change:


  
SELECT balance FROM accounts WHERE account_id = 123;            -- read one value
INSERT INTO accounts (account_id, balance) VALUES (124, 0);     -- add a row
UPDATE accounts SET balance = 500 WHERE account_id = 124;       -- change a row


  
Your Java code sends SQL to the database and gets rows back. Later units show two ways to do that:
    raw JDBC, and JPA, which hides most of the SQL behind ordinary Java objects.


  
📚
    
Analogy
      A library. The shelves are the tables; each book is a row; the
      call number on the spine is the primary key that identifies it uniquely. SQL is
      the request slip you fill in at the desk — and the librarian fetches exactly the books you asked
      for.

  


  
💡
    
The one thing to notice
      The data is not inside your program. Your program asks the database a question in SQL and gets
      rows back. That is why the data survives when the program stops — it was never the program's to
      begin with.

  


  
In plain words
    
A database is a permanent store of data, kept in tables. SQL is how your program asks it
      questions — “read this”, “add that”, “change that”. The data outlives the program that wrote it.

    🔢 Java's primitive types and their wrapper classes
    
A primitive is a raw value — fast, but not an object. A wrapper
      is the object version of the same value, needed whenever Java wants an object (for example, inside
      a collection: you write List<Integer>, never List<int>).

    

      
PrimitiveWrapper classWhat it holds

      
        
intIntegerA whole number, e.g. 42.

        
longLongA whole number, for very large values.

        
doubleDoubleA decimal number, e.g. 3.14.

        
booleanBooleantrue or false.

        
charCharacterA single character, e.g. 'A'.

      
    

    
Java converts between them automatically in most cases, so you rarely see the wrapper name
      written — except in generics, where only the wrapper is allowed.

Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Expecting a .java file to run on its ownCompile it first with javac, then run the .class with java.

      
Thinking the JVM is the Java languageThey are three things: Java the language, javac the compiler, JVM the runner.

      
Confusing a class with an objectA class is the blueprint; an object is one real item made with new.

      
Writing import jakarta.naming.InitialContext;JNDI kept its old name: import javax.naming.InitialContext;.

      
Using List<int>Generics need the wrapper: List<Integer>.

      
Reading a stack trace bottom-line-firstRead the first line that names your code, and any “Caused by:” at the bottom.

      
Treating a JAR and an API as the same thingA JAR is the file; an API is the set of classes and methods you call from it.

      
Believing localhost:8080 is a public addressIt is your own machine only. Nobody else can reach it.
