Session 12 · CDI Part 2 — The Four Advanced Powers, Explained Slowly

In Session 11 you learned how CDI quietly hands your objects to one another with @Inject. This page goes four steps further. You will learn how to tell CDI which object you meant when two would fit, how to teach it to build things it could not build on its own, how to wrap a method in extra behaviour without touching the method, and how to let one part of your app announce news that other parts quietly react to. You need nothing beyond Session 11, and every new word is explained the moment it appears.

🎯

Part 1 · Telling two identical beans apart

1.1 The problem: two beans fit one empty field

In Session 11 this worked perfectly:

@Inject
private PaymentProcessor processor;   // CDI finds the one PaymentProcessor and injects it

It worked because exactly one class implemented PaymentProcessor. CDI looked around, found one match, and filled the field.

Now your shop grows. You add a second way to pay. Suddenly two classes implement the same interface:

  • CreditCardProcessor — charges a card
  • PayPalProcessor — charges a PayPal account

You write @Inject PaymentProcessor processor; and the application refuses to start. CDI cannot read your mind. Two beans fit the empty field, nothing says which one you meant, and CDI will not guess. The deployment fails with an ambiguous dependency error.

In plain words

"Ambiguous" just means "could mean more than one thing." When two beans match one injection point, CDI stops and asks you to be more specific. It would rather fail at start-up than silently pick the wrong payment method.

☕
Analogy — "a coffee, please" You walk up to the counter and ask for "a coffee." But there are two pots: regular and decaf. The barista cannot pour until you say which. "A coffee" is ambiguous; "a decaf coffee" is not. A qualifier is you saying "decaf."

1.2 What a qualifier is

A qualifier is a tiny annotation that you invent. Its only job is to be a label CDI can match on. You put the label on a bean, and you put the same label at the injection point. CDI matches them like a key to a lock.

You turn an ordinary annotation into a qualifier with one line: @Qualifier.

⚠️
The tempting shortcut that goes wrong You can tell beans apart with string names — @Named("creditCard"). Don't. A string is not checked by anyone. Misspell it as "creditCrad" and the code compiles happily, then fails at runtime in production. A qualifier is a real type, so a typo is a compiler error you see immediately. That safety is the whole point.

1.3 Wiring a qualifier — three steps

  1. Define the qualifier annotations

    Two new annotations, each marked @Qualifier. The three lines underneath are boilerplate: keep the label at runtime, and allow it on a type, a field or a parameter.

    Qualifier annotations
    package com.globalbank.qualifiers;

import jakarta.inject.Qualifier;
import java.lang.annotation.*;

@Qualifier                                     // ① this one line makes it a CDI qualifier
@Retention(RetentionPolicy.RUNTIME)            // keep the label around while the app runs
@Target({ElementType.TYPE, ElementType.FIELD, ElementType.PARAMETER})
public @interface CreditCard {}

@Qualifier
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.FIELD, ElementType.PARAMETER})
public @interface PayPal {}
    💡
    The one thing to notice @Qualifier is the single line that matters. Without it, @CreditCard would be just a decoration CDI ignores. With it, CDI treats it as a label to match on.

  2. Tag each implementation

    Put the label on the class it describes. Now the credit-card bean is the @CreditCard one, and the PayPal bean is the @PayPal one.

    The two implementations
    @CreditCard                                    // this bean IS the credit-card one
public class CreditCardProcessor implements PaymentProcessor {
    public void pay(double amt) { System.out.println("Paid via Credit Card: $" + amt); }
}

@PayPal                                        // this bean IS the PayPal one
public class PayPalProcessor implements PaymentProcessor {
    public void pay(double amt) { System.out.println("Paid via PayPal: $" + amt); }
}
    💡
    The one thing to notice Both classes still implements PaymentProcessor. The qualifier does not change what they are — it only gives each one a name CDI can ask for.

  3. Ask for the one you want

    At the injection point, put the label next to @Inject. Read it aloud: "inject the credit-card PaymentProcessor."

    Injecting with type safety
    public class CheckoutService {

    @Inject @CreditCard                        // "inject the credit-card PaymentProcessor"
    private PaymentProcessor cardService;

    @Inject @PayPal                            // "inject the PayPal one"
    private PaymentProcessor payPalService;
}
    💡
    The one thing to notice Both fields are the same type, PaymentProcessor, yet they receive different beans. The qualifier beside @Inject is the only thing that tells them apart — and the compiler checks it for you.

Part 2 · Teaching the container to build (and bin) things

2.1 The problem: CDI cannot build everything

CDI makes a bean by calling its constructor. That is fine for your own classes. But some things cannot be made that way:

  • a java.sql.Connection — it has no plain constructor; you obtain it by asking a driver, and you must give it a URL;
  • an object from a third-party library with no no-argument constructor;
  • a value that is only known while the program is running — a setting read from the environment.

If you write @Inject Connection conn;, CDI shrugs: it has no idea how to construct one.

In plain words

CDI knows how to build the beans you wrote. It does not know how to build things that come from somewhere else or need a recipe. For those, you hand CDI the recipe.

2.2 The fix: a producer method

A producer method is a method you write, marked @Produces, that returns the object. From then on, whenever anything @Injects that type, CDI calls your producer method instead of trying to construct the object itself.

🏭
Analogy — the factory and the bin A producer is a little factory on call: when someone needs a widget, it makes one to order and hands it over. A disposer is the bin beside it: when the widget is finished with, it goes in the bin, which disposes of it properly — unscrewing it, draining it, whatever "properly" means for that item. You never do either job by hand.

2.3 Cleaning up: the disposer

Some objects must be closed, or they leak — a database connection is the classic case. A disposer method has one parameter marked @Disposes of the produced type. CDI calls it automatically when the produced object's scope ends.

Two scopes from Session 11 appear here. @ApplicationScoped means one instance for the whole application — a single factory. @RequestScoped means a fresh instance per web request. So below, there is one producer, but each request gets its own connection, closed again as soon as that request finishes.

DatabaseConnectionProducer.java — factory & cleanup lifecycle
package com.globalbank.producers;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.context.RequestScoped;
import jakarta.enterprise.inject.Disposes;
import jakarta.enterprise.inject.Produces;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;

@ApplicationScoped
public class DatabaseConnectionProducer {

    // ① @Produces turns this method into a factory for @RequestScoped Connections
    @Produces
    @RequestScoped
    public Connection createConnection() throws SQLException {
        String url = System.getProperty("db.url", "jdbc:postgresql://localhost:5432/bank");
        System.out.println("CDI Producer: Opening physical connection for request...");
        return DriverManager.getConnection(url, "user", "secret");
    }

    // ② @Disposes automatically executes when the RequestScope ends, closing the connection!
    public void closeConnection(@Disposes Connection connection) {
        System.out.println("CDI Disposer: Deterministically closing connection on request exit.");
        try {
            if (connection != null && !connection.isClosed()) {
                connection.close();
            }
        } catch (SQLException e) {
            e.printStackTrace();
        }
    }
}
💡
The one thing to notice Nobody ever calls closeConnection(). The @Disposes parameter is a signal to CDI: "this is the cleanup method for a Connection — run it yourself when the connection's scope is over." You wrote the recipe for building and for binning; the container runs both at the right moments.
⚠️
The leak everyone creates once A producer that opens something but has no matching @Disposes method leaks. Every request opens a new connection that is never closed, until the database runs out. If your producer opens, acquires or locks anything, write the disposer in the same breath.

Part 3 · Wrapping a method without touching it

3.1 The problem: the same chore in every method

You want to measure how long each important method takes, and write a line to an audit log every time one runs. The naive way is to paste the timing and logging code into every method:

public void approveLoan(int customerId, double amount) {
    long start = System.currentTimeMillis();        // chore
    // ... the actual loan rule ...
    log("approveLoan took " + (System.currentTimeMillis() - start));   // chore
}

Now imagine that in a hundred methods. The real rule is buried in plumbing, and the day you change how logging works you must edit all hundred. This kind of job — the same across many methods, and nothing to do with the business rule — is called a cross-cutting concern.

In plain words

A "cross-cutting concern" is a chore that cuts across lots of methods: logging, timing, auditing, security checks. It is not what the method is about, but it has to happen anyway. Pasting it everywhere is exactly the mess we want to avoid.

3.2 The fix: an interceptor

An interceptor is a separate class whose code runs around a target method — before it, after it, or both. The target method stays clean; the chore lives in one place.

🛫
Analogy — airport security Every passenger, whatever their destination, passes through the same security check before boarding. The check does not know or care where you are flying — it wraps everyone identically, does its one job, and then lets you proceed to your gate. An interceptor is that checkpoint, wrapped around your methods.

3.3 Wiring an interceptor — three steps

  1. Invent a binding annotation

    A binding is a marker you create — here @PerformanceLogged — that will later link the interceptor to the methods it should wrap. On its own it does nothing; it is just a name both sides agree on. @InterceptorBinding is the line that makes it a binding.

    The interceptor binding annotation
    package com.globalbank.interceptors;

import jakarta.interceptor.InterceptorBinding;
import java.lang.annotation.*;

@InterceptorBinding                            // declares an interceptor "contract"
@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
public @interface PerformanceLogged {}
    💡
    The one thing to notice This looks just like the qualifier from Part 1 — a hand-made annotation — but the magic word is different: @InterceptorBinding, not @Qualifier. The word decides what CDI does with it.

  2. Write the interceptor

    The interceptor class carries @Interceptor and the binding @PerformanceLogged, and @Priority switches it on. Inside, one method marked @AroundInvoke does the wrapping. It receives an InvocationContext — a handle to the call that is about to happen — and the key line is context.proceed(), which runs the real method.

    The interceptor implementation
    package com.globalbank.interceptors;

import jakarta.annotation.Priority;
import jakarta.interceptor.AroundInvoke;
import jakarta.interceptor.Interceptor;
import jakarta.interceptor.InvocationContext;

@Interceptor
@PerformanceLogged                             // links this interceptor to the @PerformanceLogged mark
@Priority(Interceptor.Priority.APPLICATION)    // turns the interceptor on, application-wide
public class PerformanceInterceptor {

    @AroundInvoke
    public Object profile(InvocationContext context) throws Exception {
        long start = System.currentTimeMillis();
        String methodName = context.getMethod().getName();

        try {
            // Proceed to execute the actual target business method
            return context.proceed();
        } finally {
            long duration = System.currentTimeMillis() - start;
            System.out.println("[AUDIT PROFILE] Method '" + methodName + "' executed in " + duration + "ms.");
        }
    }
}
    💡
    The one thing to notice context.proceed() is the exact point where the real method runs. Everything above it is the "before" part; everything in the finally block is the "after" part. Forget to call proceed() and the real method never runs at all.

  3. Tag any method you want wrapped

    Put the binding on a bean or a single method. That is all. The method's body stays pure business logic — not one line of timing code.

    Applying the interceptor
    @Stateless
public class LoanService {

    @PerformanceLogged                         // transparently profiled — no logging code in here
    public void approveLoan(int customerId, double amount) {
        // Pure business logic — zero logging boilerplate here!
    }
}
    💡
    The one thing to notice approveLoan has no idea it is being timed. Add the same @PerformanceLogged tag to twenty more methods and every one is profiled, with the logic written exactly once. That is the win.

3.4 The close cousin: decorators

A decorator also wraps a bean, but it is business-aware. Where an interceptor is generic and knows nothing about your domain, a decorator implements the same business interface as the bean it wraps, and enhances that specific logic. It gets a reference to the real bean through a field marked @Delegate, passes calls through, and adds its own behaviour on the way.

📱
Analogy — a phone case A phone case is a decorator. It is moulded to the shape of your exact phone (it "implements the same interface"), every button press passes straight through to the real phone underneath, and it adds grip and protection on the way. It cannot wrap just any object — it is built for that specific phone. Airport security, by contrast, wraps every traveller the same way and knows nothing about them.
AuditedPaymentProcessor.java — a decorator
@Decorator                                     // marks this class as a decorator
public class AuditedPaymentProcessor implements PaymentProcessor {

    @Inject
    @Delegate                                  // CDI injects the REAL PaymentProcessor here
    private PaymentProcessor delegate;

    @Override
    public void pay(double amt) {
        delegate.pay(amt);                     // 1) let the real bean do the work
        System.out.println("Audit: recorded a payment of $" + amt);   // 2) add our own behaviour
    }
}
💡
The one thing to notice @Delegate is the heart of a decorator: it is the real bean, handed to you so you can call it and then add to it. Like an interceptor, a decorator only runs once it is enabled — with @Priority, or a <decorators> entry in beans.xml. Section 3.5 shows both, and this is the step people forget.
In plain words

Use an interceptor for technical chores that look the same everywhere — logging, timing, security. Use a decorator when you want to add to the actual business behaviour of one specific interface. Interceptor = generic guard; decorator = business-aware wrapper.

3.5 Two ways to switch either one on

This catches nearly everybody, so it is worth its own section. An interceptor or a decorator that you have written correctly still does nothing until it is enabled. Writing the class is step one; switching it on is step two, and there are exactly two ways to do it.

How you enable itWhat you getWhen to choose it
@Priority(...) on the class Enabled for the whole application. No XML file involved at all. The normal choice. Nothing to forget, and the annotation and the switch cannot drift apart.
A beans.xml entry Enabled for that one bean archive only. When you want to be able to switch it off per deployment without recompiling.

Here is the XML form, so you recognise it when you meet it in somebody else's project. It goes in beans.xml — the file from Session 11, which is required for this particular job, because this is exactly the kind of thing Session 11 said it was for:

WEB-INF/beans.xml — enabling an interceptor and a decorator without @Priority
<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="https://jakarta.ee/xml/ns/jakartaee"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee
                           https://jakarta.ee/xml/ns/jakartaee/beans_4_0.xsd"
       version="4.0"
       bean-discovery-mode="annotated">

    <interceptors>
        <class>com.globalbank.interceptors.PerformanceInterceptor</class>
    </interceptors>

    <decorators>
        <class>com.globalbank.payment.AuditedPaymentProcessor</class>
    </decorators>

</beans>
💡
Which one wins if you do both? @Priority is the stronger of the two. An interceptor or decorator that carries it is enabled at application scope, and the beans.xml entry has nothing left to add. So there is no harm in leaving the XML out — which is why the projects in this course use @Priority throughout and never touch this file.
⚠️
The classic silent failure You write a perfect interceptor, put @InterceptorBinding on five methods, deploy — and nothing is logged. Nothing is broken and there is no error message; the interceptor simply was never enabled. If an interceptor or decorator seems to be ignored, check for @Priority first, then check beans.xml. One of the two must be there.

Part 4 · Announcing news other parts can react to

4.1 The problem: everyone has to know everyone

When a customer registers, several things should happen: send a welcome email, write an audit record, bump a "new customers today" counter. The obvious way is to call each one directly:

public void register(String email) {
    // ... create the customer ...
    welcomeEmailNotifier.send(email);     // register() must know about this...
    auditService.record(email);           // ...and this...
    statsCounter.increment();             // ...and this.
}

Now register() depends on three other classes, and every time the business wants a new reaction you must open register() and edit it. The parts are tightly coupled — bolted together so they cannot move independently.

In plain words

"Coupled" means two parts know about each other and cannot change without disturbing the other. We want the opposite: a registration step that just says "a customer was created" and does not care who, if anyone, is listening.

4.2 The fix: fire an event

CDI has a built-in publish-subscribe mechanism — one part publishes news, other parts subscribe to it — that works entirely inside one running program, with no heavyweight message broker (that is Session 7's JMS, for when the parts live on different machines). The registration code announces the news; any number of observer methods react.

📣
Analogy — the town crier A town crier stands in the square and shouts the news. He does not know who is listening, and he does not care. The baker might down tools; the children might ignore it; a newcomer might not even understand. Whoever cares reacts in their own way. The crier's job ends the moment he has announced it. Firing a CDI event is shouting in the square.

4.3 The three pieces

  • The payload — a plain object carrying the facts, e.g. a record holding the new customer's id and email.
  • The publisher — injects Event<T> and calls .fire(...) to announce.
  • The observer — any method with a parameter marked @Observes of that payload type. CDI runs it whenever the event fires.
In plain words

Event<CustomerCreatedEvent> is "the loudspeaker for customer-created news." @Observes CustomerCreatedEvent is a person in the square saying "I care about that kind of news — tap me when it happens."

Firing and observing an event
import jakarta.ejb.Stateless;
import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.event.Event;
import jakarta.enterprise.event.Observes;
import jakarta.inject.Inject;

// 1. The event payload — a plain record carrying the facts
public record CustomerCreatedEvent(int customerId, String email) {}

// 2. The publisher fires the event
@Stateless
public class CustomerRegistrationService {

    @Inject
    private Event<CustomerCreatedEvent> eventPublisher;

    public void register(String email) {
        int id = generateId();
        // Fire synchronously now (or fireAsync() to hand it to a background thread)
        eventPublisher.fire(new CustomerCreatedEvent(id, email));
        System.out.println("Registration complete.");
    }

    /**
     * A stand-in for a real id source. Note it holds no state of its own —
     * a @Stateless bean must not keep data in a field between calls (Session 1).
     * In a real application this would be the id your database assigned.
     */
    private int generateId() {
        return Math.abs(java.util.UUID.randomUUID().hashCode());
    }
}

// 3. An independent observer reacts — the publisher never names it
@ApplicationScoped
public class WelcomeEmailNotifier {

    // Runs automatically whenever a CustomerCreatedEvent is fired
    public void onNewCustomer(@Observes CustomerCreatedEvent event) {
        System.out.println("Sending welcome package email to: " + event.email());
    }
}
💡
The one thing to notice CustomerRegistrationService never mentions WelcomeEmailNotifier. Add a tenth observer tomorrow — an audit log, a stats counter — and register() does not change by a single character. That is what "decoupled" buys you.

4.4 Synchronous or asynchronous?

fire() runs the observers right now, on the same thread, before register() continues. If an observer is slow, the caller waits; if an observer throws, the caller sees the error. fireAsync() instead hands the event to a background thread; the caller returns immediately, and observers that want to run in the background opt in with @ObservesAsync.

📣
Analogy — the crier, two ways Synchronous (fire): the crier shouts, then waits in the square until everyone has finished reacting before he moves on. Asynchronous (fireAsync): the crier shouts and walks straight to the next street, leaving people to react in their own time.
Firing on a background thread
// Hand the event to a background thread instead — register() returns at once:
eventPublisher.fireAsync(new CustomerCreatedEvent(id, email));

// An observer that should run on that background thread opts in with @ObservesAsync:
public void onNewCustomer(@ObservesAsync CustomerCreatedEvent event) {
    sendSlowWelcomeEmail(event.email());
}
💡
The one thing to notice fire() pairs with @Observes; fireAsync() pairs with @ObservesAsync. Reach for the async pair when the reaction is slow and the user should not have to wait for it — like sending an email.

    📡 Event fine print — qualifiers, async and transaction phases
    
    
      
  • Qualified events. Observers can be narrowed with a qualifier: @Observes @CreditCard PaymentCompletedEvent only reacts to card payments. Add the qualifier when firing with eventPublisher.select(...).fire(...).
    • 
      
  • Async. fireAsync() runs @ObservesAsync observers on a background thread; fire() runs @Observes observers on the caller's thread.
    • 
      
  • Transaction-phase observers. @Observes(during = TransactionPhase.AFTER_SUCCESS) delays the reaction until the surrounding transaction commits — handy so you only email the customer if the registration actually saved.
    • 
    

  


  

    🏷️ The qualifiers you already have: @Default, @Any, @Named
    
Qualifiers are not new to Part 1 — CDI has been using them invisibly all along.

    

      
QualifierWhat it means

      
        
@DefaultEvery bean with no explicit qualifier silently has this one. It is why a single unqualified bean injects fine — and why two unqualified beans clash: both are @Default.

        
@AnyA wildcard every bean also carries. Injecting @Any Instance<PaymentProcessor> gives you all implementations to loop over.

        
@NamedA built-in, string-based qualifier used mainly to reach beans from Jakarta Faces (EL) pages. Avoid it for type-safe code — use your own qualifier instead.

      
    

  


  


  

  recap
  
One-line summary of everything

  

    
QualifierA label annotation you invent (marked @Qualifier) so CDI can tell two matching beans apart. Safer than a @Named string because the compiler checks it.

    
@Produces / @DisposesA factory method that builds something CDI could not construct, and a cleanup method CDI runs automatically when that object's scope ends.

    
Interceptor@InterceptorBinding + an @AroundInvoke method wrap a target with generic cross-cutting code; context.proceed() runs the real method.

    
DecoratorImplements the business interface and enhances it, calling the real bean through an @Delegate field. Business-aware, where an interceptor is generic.

    
CDI EventInject Event<T> and fire() (or fireAsync()); any @Observes (or @ObservesAsync) method reacts, with no link between publisher and observer.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Two beans implement one interface and you @Inject it bareAdd a qualifier to the beans and the same qualifier at the injection point.

      
Telling beans apart with @Named("x") stringsUse a type-safe @Qualifier annotation, checked by the compiler.

      
Trying to @Inject a type CDI cannot construct (a Connection)Write a @Produces method that builds and returns it.

      
A producer opens a resource but there is no disposerAdd a @Disposes method so CDI closes it when the scope ends.

      
Pasting timing or logging code into every business methodMove it into one @AroundInvoke interceptor and tag methods with your binding.

      
Writing an interceptor or decorator but never enabling itGive it @Priority (or list it in beans.xml) or it never runs.

      
Forgetting context.proceed() in an interceptorCall it — otherwise the real method never executes.

      
A publisher calling each reaction directlyFire a CDI event; let @Observes methods react, so new reactions need no change to the publisher.

      
Expecting fire() not to block the callerfire() runs observers on your thread; use fireAsync() + @ObservesAsync for slow background work.
