concept

Part 1 · What this lab proves, in plain words

Every serious application has two guards standing between a stranger and its data:

  1. A bouncer who checks your paperwork before you get in. That is Bean Validation. If the form is not filled in correctly, you never reach the vault.
  2. A vault that only opens all-or-nothing. That is a transaction. Either every change inside is written, or none of it is.
In plain words

Bean Validation answers one question: “is this data worth acting on?” It checks shapes and rules — is the account number exactly ten digits, is the amount greater than zero.

A transaction answers a different question: “if the work starts, can I be sure it finishes completely?” If the second half fails, the first half is undone.

Two different jobs. Validation protects the entrance. The transaction protects the journey.

🏦
Analogy A bank teller with two rules. Rule one: no transfer without a properly filled-in slip — she checks the slip before she touches the cash drawer. Rule two: the cash drawer ends up exactly as it started unless the whole transfer completes — if the computer dies halfway, the cash she already took out goes straight back in.
🎯
Your four objectives (from the Presenter's Manual, TL12)
  1. Construct an integrated enterprise flow combining Bean Validation constraints with transactional EJB execution
  2. Compare how validation failures halt execution before transactions open vs. how business exceptions trigger rollbacks
  3. Implement programmatic chunked commits using UserTransaction in Bean-Managed Transactions (BMT)
  4. Diagnose and handle ConstraintViolationException, TransactionRolledbackException, and rollback leaks

1.1 The four stages a transfer passes through

Here is the whole journey, in order. Read the last column slowly, because that is the part beginners get wrong: a failed validation stops the request before a transaction ever opens, which is exactly what makes it cheap.

StageLayerIntegrity checkWhat happens if it fails
1. View submission JSF Facelets form Validates field constraints (@NotBlank, @Positive) Fails in Phase 3; the view is redisplayed with errors; no EJB call and no database call is made at all.
2. Service entry Stateless EJB method Method parameter validation (@Valid TransferRequest req) Throws ConstraintViolationException; execution stops before the transaction opens.
3. Execution Container-managed transaction ACID transaction boundary (REQUIRED) A system exception or a setRollbackOnly() call triggers a complete ROLLBACK.
4. Persistence JPA / JDBC layer Entity-level constraints and database foreign keys JPA validates before the SQL flush; it aborts on an invalid state.
💡
If you remember only one thing from Part 1 Validating before the transaction is not a style preference — it is why a bad request costs a few microseconds instead of holding a database connection and a set of row locks while it fails.
Checkpoint 1 · before you move on

Answer out loud first, then open the answers. Do not skip this — the whole lab is built on it.

  1. Which guard runs first on a bad request — validation, or the transaction? Why does that order matter?
  2. An account number arrives as "123". Which stage in the table above catches it, and does any database connection get opened?
  3. A transfer debits account A correctly, then fails. What should account A's balance be when the dust settles?
Show answers
  1. Validation runs first. It is cheaper: a rejected request never opens a transaction, so it acquires no connection and takes no locks.
  2. Stage 2, service entry. The @Valid parameter check throws ConstraintViolationException before the transaction opens — so no, no connection is acquired.
  3. Unchanged. The transaction rolls back, so the debit is undone. All-or-nothing is the promise a transaction makes.

  3. Write the validated request object

    This is the object the caller must fill in. The three annotations are the rules: they are not comments describing a check, they are the check. The container enforces them; you never write the if statement.

    src/main/java/com/globalbank/dto/TransferRequest.java
    package com.globalbank.dto;

import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Positive;
import java.io.Serializable;

public class TransferRequest implements Serializable {

    @NotNull(message = "Source account required")
    @Pattern(regexp = "^\\d{10}$", message = "Source account must be 10 digits")
    private String fromAccount;

    @NotNull(message = "Destination account required")
    @Pattern(regexp = "^\\d{10}$", message = "Destination account must be 10 digits")
    private String toAccount;

    @Positive(message = "Transfer amount must be greater than zero")
    private double amount;

    public TransferRequest(String from, String to, double amount) {
        this.fromAccount = from;
        this.toAccount = to;
        this.amount = amount;
    }

    // Getters and setters...
    public String getFromAccount() { return fromAccount; }
    public String getToAccount() { return toAccount; }
    public double getAmount() { return amount; }
}

    Read the annotations as sentences:

    • @NotNull — the value may not be missing.
    • @Pattern(regexp = "^\\d{10}$") — exactly ten digits, nothing else.
    • @Positive — strictly greater than zero. A transfer of -1 is rejected.

    What you should see: a file with no red underlines once Maven has downloaded the API (see Part 3 if it has not).

  4. Write the bean that sets up the ledger

    The lab needs two bank accounts to exist before anyone transfers anything. A @Singleton @Startup bean runs once, automatically, when the application starts — you never call it.

    src/main/java/com/globalbank/ejb/LedgerInitializer.java
    package com.globalbank.ejb;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.Resource;
import jakarta.ejb.Singleton;
import jakarta.ejb.Startup;
import javax.sql.DataSource;
import java.sql.Connection;

@Singleton
@Startup                       // the container creates this when the app deploys
public class LedgerInitializer {

    @Resource(lookup = "java:jboss/datasources/ExampleDS")
    private DataSource dataSource;

    @PostConstruct
    public void setUp() {
        try (Connection c = dataSource.getConnection()) {
            c.createStatement().execute(
                "CREATE TABLE IF NOT EXISTS account (" +
                "  account_no VARCHAR(10) PRIMARY KEY," +
                "  balance    DECIMAL(12,2) NOT NULL)");

            // MERGE = "insert, or update if the key is already there"
            c.createStatement().execute(
                "MERGE INTO account (account_no, balance) KEY(account_no)" +
                " VALUES ('1002948192', 5000.00)");
            c.createStatement().execute(
                "MERGE INTO account (account_no, balance) KEY(account_no)" +
                " VALUES ('5551234567', 1000.00)");

            System.out.println("[Ledger] table ready, accounts seeded");
        } catch (Exception e) {
            throw new RuntimeException("Could not set up the ledger", e);
        }
    }
}

    This bean is also a safety net for you: every time you redeploy, the balances are reset to a known starting point, so the numbers in this lab are always reproducible.

    What you should see: nothing yet — but when the app deploys you will see [Ledger] table ready, accounts seeded in the server window.

  5. Write the transactional service bean

    This is the heart of Sessions 9 and 10 in about forty lines. Two annotations do all the work: @Valid on the parameter (validation) and @TransactionAttribute(REQUIRED) on the method (the transaction).

    src/main/java/com/globalbank/ejb/TransferManagerBean.java
    package com.globalbank.ejb;

import com.globalbank.dto.TransferRequest;
import jakarta.annotation.Resource;
import jakarta.ejb.SessionContext;
import jakarta.ejb.Stateless;
import jakarta.ejb.TransactionAttribute;
import jakarta.ejb.TransactionAttributeType;
import jakarta.validation.Valid;
import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;

@Stateless
public class TransferManagerBean {

    @Resource
    private SessionContext ctx;

    @Resource(lookup = "java:jboss/datasources/ExampleDS")
    private DataSource dataSource;

    // @Valid triggers automatic Bean Validation on the parameter BEFORE the method runs!
    @TransactionAttribute(TransactionAttributeType.REQUIRED)
    public void executeTransfer(@Valid TransferRequest request) {

        try (Connection conn = dataSource.getConnection()) {
            // 1. Debit from source
            debit(conn, request.getFromAccount(), request.getAmount());

            // 2. Simulated business check: block suspicious overseas routing
            if ("0000000000".equals(request.getToAccount())) {
                // Programmatic rollback in CMT
                System.err.println("Suspicious target account! Rolling back.");
                ctx.setRollbackOnly();
                return;
            }

            // 3. Credit to destination
            credit(conn, request.getToAccount(), request.getAmount());

        } catch (SQLException e) {
            // System exception automatically triggers container rollback
            throw new RuntimeException("Database error during transfer", e);
        }
    }

    private void debit(Connection c, String acc, double amt) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement(
                "UPDATE account SET balance = balance - ? WHERE account_no = ?")) {
            ps.setDouble(1, amt);
            ps.setString(2, acc);
            ps.executeUpdate();
        }
    }

    private void credit(Connection c, String acc, double amt) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement(
                "UPDATE account SET balance = balance + ? WHERE account_no = ?")) {
            ps.setDouble(1, amt);
            ps.setString(2, acc);
            ps.executeUpdate();
        }
    }
}
    In plain words

    @Valid tells the container: “before you let this method run, check every constraint on this object.” If anything fails, the method body never executes — no connection, no transaction, nothing.

    REQUIRED tells the container: “wrap this method in a transaction, or join one that already exists.” The container opens it, commits it, and rolls it back. You write none of that.

    ctx.setRollbackOnly() is the one decision only you can make: “the business rule says stop — undo everything I have done so far.”

    What you should see: a class with no compile errors, and — in a moment — a rollback you can prove.

  6. Write two small web endpoints

    A bean has no screen. To drive it from a browser we add two tiny servlets. A servlet is simply a Java class that answers a URL.

    src/main/java/com/globalbank/web/TransferServlet.java
    package com.globalbank.web;

import com.globalbank.dto.TransferRequest;
import com.globalbank.ejb.TransferManagerBean;
import jakarta.ejb.EJB;
import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.validation.ConstraintViolationException;
import java.io.IOException;

@WebServlet("/transfer")
public class TransferServlet extends HttpServlet {

    @EJB                                          // the container fills this in for us
    private TransferManagerBean manager;

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws IOException {

        response.setContentType("text/plain");

        String from = request.getParameter("from");
        String to   = request.getParameter("to");
        String text = request.getParameter("amount");

        try {
            double amount = Double.parseDouble(text == null ? "0" : text);
            TransferRequest req = new TransferRequest(from, to, amount);

            manager.executeTransfer(req);     // <- validation + transaction, all inside

            response.getWriter().println("TRANSFER ACCEPTED: " + from + " -> " + to + " $" + amount);

        } catch (ConstraintViolationException e) {
            // validation refused the request before the transaction ever opened
            response.getWriter().println("REJECTED BY VALIDATION:");
            for (var v : e.getConstraintViolations()) {
                response.getWriter().println("  - " + v.getMessage());
            }
        } catch (Exception e) {
            response.getWriter().println("FAILED: " + e.getClass().getSimpleName());
            for (Throwable t = e.getCause(); t != null; t = t.getCause()) {
                response.getWriter().println("  caused by " + t.getClass().getSimpleName()
                                             + ": " + t.getMessage());
            }
        }
    }
}

    Drive a transaction yourself — BMT with chunked commits
    
      
    So far the container has managed every transaction for you. In a
        Bean-Managed Transaction (BMT) you take that job over with
        UserTransaction. The reason you would: a batch of ten thousand transfers cannot be
        one transaction, because a failure at the end would undo all of it. So you commit in
        chunks.
    
      
    src/main/java/com/globalbank/ejb/BatchTransferBean.java
    
      
    package com.globalbank.ejb;

import com.globalbank.dto.TransferRequest;
import jakarta.annotation.Resource;
import jakarta.ejb.Stateless;
import jakarta.ejb.TransactionManagement;
import jakarta.ejb.TransactionManagementType;
import jakarta.transaction.UserTransaction;
import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.util.List;

@Stateless
@TransactionManagement(TransactionManagementType.BEAN)   // <- YOU manage the transaction now
public class BatchTransferBean {

    private static final int CHUNK = 3;      // publish a chunk every 3 transfers

    @Resource
    private UserTransaction utx;

    @Resource(lookup = "java:jboss/datasources/ExampleDS")
    private DataSource dataSource;

    public String runBatch(List<TransferRequest> transfers) {
        int done = 0;
        int chunks = 0;

        try {
            utx.begin();                     // 1. YOU open the transaction

            for (TransferRequest t : transfers) {
                if (t.getAmount() <= 0) {     // a bad entry part-way through
                    throw new IllegalArgumentException("amount must be positive");
                }
                move(t);
                done++;

                if (done % CHUNK == 0) {
                    utx.commit();            // 2. this chunk is now permanent
                    chunks++;
                    utx.begin();             // 3. open a fresh chunk
                }
            }

            utx.commit();                    // 4. commit whatever is left over
            chunks++;
            return "BATCH OK: " + done + " transfers in " + chunks + " chunks";

        } catch (Exception e) {
            try {
                utx.rollback();              // 5. YOU must undo the open chunk, nobody else will
            } catch (Exception ignored) {
            }
            return "BATCH ROLLED BACK on transfer " + (done + 1) + ": " + e.getMessage()
                 + "  (" + chunks + " earlier chunks stay committed)";
        }
    }

    private void move(TransferRequest t) throws Exception {
        try (Connection c = dataSource.getConnection()) {
            try (PreparedStatement debit = c.prepareStatement(
                    "UPDATE account SET balance = balance - ? WHERE account_no = ?")) {
                debit.setDouble(1, t.getAmount());
                debit.setString(2, t.getFromAccount());
                debit.executeUpdate();
            }
            try (PreparedStatement credit = c.prepareStatement(
                    "UPDATE account SET balance = balance + ? WHERE account_no = ?")) {
                credit.setDouble(1, t.getAmount());
                credit.setString(2, t.getToAccount());
                credit.executeUpdate();
            }
        }
    }
}

    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws IOException {

        response.setContentType("text/plain");

        List<TransferRequest> list = new ArrayList<>();
        for (int i = 0; i < 7; i++) {                        // 7 good transfers, $10 each
            list.add(new TransferRequest("1002948192", "5551234567", 10.0));
        }
        list.add(new TransferRequest("1002948192", "5551234567", -1.0));   // the 8th is broken on purpose

        response.getWriter().println(batch.runBatch(list));
    }
}

    mvn clean package
copy target\globalbank.war  C:\wildfly\standalone\deployments\
    
      
    http://localhost:8080/globalbank/batch
    
      
    What you should see:
    
      
    BATCH ROLLED BACK on transfer 8: amount must be positive  (2 earlier chunks stay committed)
    
      
    In plain words
        
    Seven transfers were good, but the eighth broke. Transfers 1–6 were in two finished
          chunks, so they are already committed and cannot be undone. Transfer 7 was still sitting in an
          open, uncommitted chunk when the error hit, so the utx.rollback() you wrote threw
          it away.
    
        
    That is the whole trade of BMT: you get to decide how much is at risk. Small chunks
          publish early; an open chunk is all-or-nothing.
    
      
    
      
    Prove it with the balance page. Compared with the numbers you wrote down before calling
        /batch, the first account should have dropped by $60 — six
        transfers, not seven. The seventh was rolled back with the broken chunk.
    
      
    Notice what you got and what you paid for. You got control over chunk
        boundaries. You paid for it with responsibility: if you had ever forgotten
        utx.rollback() in that catch block, the open chunk would have stayed
        alive on the thread, holding locks, until the transaction timed out. That is Trap 2 in Part 3.

  troubleshooting
  
Part 3 · The three traps — and the errors you will actually hit

  
These three traps are the ones the manual singles out, and they are the three that bite in this
    exact lab.


  
1️⃣
    
Trap 1: Expecting a checked exception to roll back automatically
      
Symptom: a custom
        InsufficientBalanceException extends Exception is thrown, but the earlier database
        writes are committed to disk anyway!

      
Fix: by default in EJB, checked application
        exceptions commit. You must annotate the exception class with
        @ApplicationException(rollback = true), or call ctx.setRollbackOnly()
        before it is thrown.

    

  


  
2️⃣
    
Trap 2: Swallowing an exception in BMT without calling utx.rollback()
      
Symptom: an error occurs inside your BMT bean; you catch
        it, log it, and return normally. The transaction stays open on the thread until it times out.

      
Fix: in BMT you are the transaction manager. If
        anything goes wrong between utx.begin() and utx.commit(), you
        must call utx.rollback() inside the catch block. This
        is exactly what step 13's bean does — look at line 5 in its catch.

    

  


  
3️⃣
    
Trap 3: Forgetting @Valid on a nested object or parameter
      
Symptom: constraints inside a child object (say
        Address.postalCode) are silently ignored during validation.

      
Fix: Bean Validation does not cascade into nested
        objects on its own. Put @Valid on the nested field or the method parameter to tell
        the engine to check the constraints inside it too. The lab's
        executeTransfer(@Valid TransferRequest request) is the parameter half of this rule;
        a field inside TransferRequest would need its own @Valid.

TransferManagerBean.java — as printed in the manual

    
package com.globalbank.ejb;

import com.globalbank.dto.TransferRequest;
import jakarta.annotation.Resource;
import jakarta.ejb.SessionContext;
import jakarta.ejb.Stateless;
import jakarta.ejb.TransactionAttribute;
import jakarta.ejb.TransactionAttributeType;
import jakarta.validation.Valid;
import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;

@Stateless
public class TransferManagerBean {

    @Resource
    private SessionContext ctx;

    @Resource(lookup = "java:/jdbc/GlobalBankDB")
    private DataSource dataSource;

    // @Valid triggers automatic Bean Validation on the parameter before method runs!
    @TransactionAttribute(TransactionAttributeType.REQUIRED)
    public void executeTransfer(@Valid TransferRequest request) {

        try (Connection conn = dataSource.getConnection()) {
            // 1. Debit from source
            debit(conn, request.getFromAccount(), request.getAmount());

            // 2. Simulated business check: block suspicious overseas routing
            if ("0000000000".equals(request.getToAccount())) {
                // Programmatic rollback in CMT
                System.err.println("Suspicious target account! Rolling back.");
                ctx.setRollbackOnly();
                return;
            }

            // 3. Credit to destination
            credit(conn, request.getToAccount(), request.getAmount());

        } catch (SQLException e) {
            // System exception automatically triggers container rollback
            throw new RuntimeException("Database error during transfer", e);
        }
    }

    private void debit(Connection c, String acc, double amt) throws SQLException { /* SQL UPDATE */ }
    private void credit(Connection c, String acc, double amt) throws SQLException { /* SQL UPDATE */ }
}

  


  

    🔒 CMT vs BMT at a glance
    

      
QuestionContainer-Managed (CMT)Bean-Managed (BMT)

      
        
Who opens the transaction?The container, because of @TransactionAttributeYou, with utx.begin()

        
Who commits or rolls back?The container, when the method exitsYou, with utx.commit() / utx.rollback()

        
How is it turned on?@TransactionAttribute(TransactionAttributeType.REQUIRED)@TransactionManagement(TransactionManagementType.BEAN) plus a UserTransaction field

        
How does it roll back?A system exception, or ctx.setRollbackOnly()You call utx.rollback() yourself, every time

        
What it is good forOrdinary business methods — the default in this courseBatches where you want to publish work in chunks

        
What it costs youNothing; you write one annotationYou must never forget commit(), rollback(), or the matching begin()

Your own checked exception extends ExceptionCommits@ApplicationException(rollback = true) on the exception class, or ctx.setRollbackOnly() before throwing

        
EJBExceptionRolls back automaticallyAlready does

  recap
  
One-Line Summary

  

    
Bean ValidationDeclarative constraints (@NotNull, @Size, @Positive) validated before opening transactions.

    
BMT DemarcationProgrammatic control via UserTransaction; always call rollback() on errors.

    
Rollback RulesSystem exceptions rollback automatically; Application exceptions commit unless flagged with rollback=true.

    
setRollbackOnly()Programmatic signal to container that current CMT transaction must be rolled back.

    
Recursive ValidationUse @Valid on parameters and nested objects to cascade constraint verification.

    
Chunked commitsIn BMT, committing every N items bounds how much a late failure can undo and releases locks early.

    
Order mattersValidation runs at the boundary, before the transaction — so a bad request never costs a connection or a lock.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Writing if (value == null) throw … instead of a constraint annotationDeclare it: @NotNull(message = "…"). The container enforces it before the method runs, and the message comes back for free.

      
Expecting a checked exception to roll back on its ownChecked exceptions commit by default. Add @ApplicationException(rollback = true) or call ctx.setRollbackOnly().

      
Catching an exception in a BMT method and returning without utx.rollback()Always roll back in the catch. Uncommitted work plus an open transaction means locks held until timeout.

      
Forgetting @Valid on a nested field or a method parameterValidation does not cascade by itself. Put @Valid on the parameter and on every nested object you want checked.

      
Assuming the method returning normally means the data was committedA method can return with the transaction marked rollback-only. Verify with a read — that is why this lab has a /balance page.

      
Making one enormous transaction for a whole batchIn BMT commit in chunks, so a late failure only discards the open chunk.

      
Bundling a Bean Validation implementation into the warKeep the API at scope provided. WildFly already ships the engine; bundling your own causes version clashes at deploy time.
