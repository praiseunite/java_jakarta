Part 1 · How the six pieces fit together

In enterprise engineering, beans and services never exist in isolation. They form a layered pipeline, and each layer has one job. Look at the picture first, then read the table under it — a diagram like this only helps once someone tells you how to read it.

1.1 One request, six stops

Follow a single click — “Transfer $350” — through the whole system. Six things happen, in this order:

StopLayer / ComponentEJB Technology UsedRole in the system
1 Web Tier Servlet / JSF Controller Handles the incoming HTTP request; looks up the Stateful bean via JNDI
2 Client State @Stateful Session Bean Remembers user session state (logged-in username, shopping cart) across requests
3 Business Tier @Stateless Session Bean Executes high-throughput business logic; pooled by the container
4 Security Gate @RolesAllowed("CUSTOMER") The container intercepts the call; verifies the client's identity before the method runs
5 Transaction Boundary @TransactionAttribute(REQUIRED) The container starts an ACID transaction; ensures all-or-nothing execution
6 Data Access @Resource DataSource The container injects a pre-warmed connection from the WildFly pool; the bean executes SQL
In plain words

Stops 4 and 5 have no code of their own. They are gates the container installs around your method because you put a label on it. The security gate checks who is calling; the transaction gate wraps everything that follows in an all-or-nothing envelope.

That is the whole trick of Jakarta EE: stops 4 and 5 happen between the lines you wrote. You cannot see them in the bean, but the container runs them every single time.

1.2 Which tier remembers what

Beginners lose marks by mixing these up. Learn this one table and half the exam questions disappear:

TierDoes it remember?How long for?
Web TierNoNothing — it passes each request straight through
Stateful BeanYesFor one client's conversation, until @Remove or a timeout
Stateless BeanNoNothing survives a call — the instance goes back to the pool
DataSourceThe connection, not your dataOnly until the connection returns to the pool
DatabaseYesForever — this is the only place data truly lives
🏦
Analogy A bank branch. The teller window (web tier) just passes you on. Your own account officer (stateful bean) remembers your file for the length of your visit. The cashier (stateless bean) serves whoever is next and forgets you instantly. The vault key cabinet (DataSource) hands out a key and takes it back. Only the ledger in the vault (database) keeps your money for good.

1.3 Trace it yourself — before you read Part 3

Do this now, even though you have not seen the code yet. Predicting is how the picture sticks.

  1. Name the six stops out loud

    Start at “browser sends the request” and finish at “row is updated in the database”. Say each stop and its one job.

    You should be able to say: Web Tier → Stateful Bean (who is this?) → Stateless Bean (do the work) → Security Gate (are they allowed?) → Transaction Boundary (all or nothing) → DataSource (borrow a connection) — six stops — and then the row is updated in the Database.

  2. Answer before you check: which stop knows the username?

    Cover the table in 1.2 with your hand. Which component remembers that the person clicking is “Alice”? Write your answer down.

    You should have written: the Stateful bean at stop 2. Nothing else in the pipeline remembers who the client is — the browser only sent a request, and the stateless bean and the pool forget immediately.

  3. Answer before you check: which stop can refuse the request outright?

    Which stop is allowed to stop the whole thing before a single line of your business logic runs?

    You should have written: the Security Gate at stop 4. It checks the caller's role before the method is entered — which is exactly why a rejected caller sees EJBAccessException and not a half-finished payment. Stop 5 can also abort work, but only after it has started.

Checkpoint 1 · before you move on

Answer out loud, in your own words. Then open the answers.

  1. Why is the Stateful bean a separate stop from the Stateless bean, rather than one bean doing both jobs?
  2. What does the container do at the security gate, and where is that decision written down?
  3. The user's shoppingCart field is held by a @Stateful bean. What happens to it when the user's session times out?
Show answers
  1. Because state is expensive and personal — one instance per user — while business logic must be shared and pooled to serve thousands of users. Mixing them means either paying for state you do not need or losing state you do.
  2. It checks whether the caller holds a role named in @RolesAllowed, and refuses the call before the method body runs. The decision is written on the method as an annotation, not in hand-written if statements.
  3. It is discarded, and the bean instance is destroyed. Conversational state is not permanent — only the database survives.

Part 2 · The three errors you will actually hit

Wiring components across tiers always produces integration errors; that is normal, not failure. If you can name these three on sight, you will look like the person who has done this before. First, learn the one skill that solves all of them.

🔎
How to read a WildFly stack trace, in three moves
  1. Read the top line. It names the exception that reached your code — that is the symptom, not always the cause.
  2. Scroll down to the first Caused by: line. That is the real problem. There can be several; the deepest one is the root.
  3. Fix that line, not the symptom. Then rebuild and redeploy. Most of the time the top-line message changes or disappears.

2.1 The three faults, side by side

Read the symptom, then the cause, then the fix. These are the three you will meet in real work.

1️⃣
Fault 1: javax.naming.NameNotFoundException

Symptom: NameNotFoundException: hello-ejb/PaymentProcessorBean -- service jboss.naming.context...

Root Cause: The client requested a JNDI string that does not match what WildFly registered at deployment time — usually a typo, a missing interface suffix, or the wrong namespace.

Fix: Check the WildFly boot log during deployment. WildFly prints lines starting with java:global/.... Copy the exact string into your lookup().

2️⃣
Fault 2: jakarta.ejb.EJBTransactionRolledbackException

Symptom: EJBTransactionRolledbackException: Transaction rolled back

Root Cause: An unhandled runtime exception occurred inside a transactional EJB method, so the container aborted and rolled the transaction back automatically.

Fix: The rollback is a consequence, not the cause! Scroll down the server console stack trace to find the Caused by: ... line (e.g. NullPointerException or SQLException: duplicate key). Fix that underlying bug.

3️⃣
Fault 3: jakarta.ejb.EJBAccessException

Symptom: EJBAccessException: Invocation on method is not allowed

Root Cause: The caller does not possess the role required by @RolesAllowed, or the user has not authenticated at all.

Fix: Verify the user's credentials and role mappings in WildFly's security realm, and make sure the Web Tier forces login before invoking the protected EJB.

2.2 Diagnose each one on a real server

These steps use the same WildFly you met in Session 3. They break the application you build in Part 3 on purpose, so Part 3 comes first: build and deploy it there, then return here to produce each fault deliberately. If WildFly is not running, start it first: open a terminal in WildFly's bin folder and run standalone.bat (Windows) or ./standalone.sh (macOS/Linux), then wait for the line that ends started in …ms, and leave that window open.

  1. Read the JNDI names WildFly printed at deployment

    In the server console (the first terminal), scroll up to where your application was deployed. WildFly lists every name it bound:

    java:global/hello-ejb/PaymentProcessorBean!com.globalbank.ejb.PaymentProcessor
java:app/hello-ejb/PaymentProcessorBean!com.globalbank.ejb.PaymentProcessor
java:module/PaymentProcessorBean!com.globalbank.ejb.PaymentProcessor

    You should see one line per view of each bean, each ending with the fully-qualified interface name after a !. That string is the exact text your lookup() must use. Copy it — never retype it.

    🔬
    Why the interface suffix must be there PaymentProcessorBean exposes exactly one business view — the @Local interface PaymentProcessor. A bean reached through an interface is not reachable by its short class name, so the !com.globalbank.ejb.PaymentProcessor part is mandatory, not decoration.

  2. Reproduce Fault 1 on purpose, then fix it

    The client is BankClientServlet — the small web-tier servlet you add to the hello-ejb project in Part 3 (its complete code is in Part 3, step 4). It performs the lookup and calls the bean. In that servlet's lookup string, deliberately introduce a typo — change PaymentProcessorBean to PaymentBean — then rebuild and redeploy the project:

    mvn clean package
copy target\hello-ejb.war  <WILDFLY_HOME>\standalone\deployments\   REM  Windows
cp   target/hello-ejb.war  <WILDFLY_HOME>/standalone/deployments/    #    macOS / Linux

    Replace <WILDFLY_HOME> with the folder you unzipped WildFly into. Then open http://localhost:8080/hello-ejb/bank. You should see a NameNotFoundException in the server console, and the servlet print “NameNotFoundException — check the lookup string”. Fix it by pasting the exact java:global/…!… line you copied in step 1 back into the servlet, rebuild, redeploy, and the call succeeds. You have now produced the most common integration error and cured it.

  3. Reproduce Fault 2 and find the real cause

    Inside processPayment(), just before the SQL runs, add an unhandled exception on purpose — for example, call a method on a variable that is null. Rebuild, redeploy, and call it.

    You should see two things, in this order, in the console:

    ERROR [Transaction] EJBTransactionRolledbackException: Transaction rolled back
    at com.globalbank.ejb.PaymentProcessorBean.processPayment(PaymentProcessorBean.java:24)
Caused by: java.lang.NullPointerException: Cannot invoke "java.sql.Connection.prepareStatement(String)" because "conn" is null

    The top line is the symptom. The Caused by: line underneath is the bug you must fix. Remove your deliberate fault, rebuild, redeploy — the rollback goes away.

  4. Check who is really logged in (Fault 3)

    Before blaming the server, confirm which roles the user actually holds in WildFly's realm. Run the CLI from WildFly's bin folder:

    jboss-cli.bat --connect      REM  Windows
./jboss-cli.sh --connect     #    macOS / Linux

    Then, at the [standalone@localhost:9990 /] prompt, list the users in the realm, then find the file that holds the user-to-role mapping:

    # 1. Which users exist in the realm?
/core-service=management/security-realm=ApplicationRealm:read-children-names(child-type=user)

# 2. Where is the role mapping stored?
/core-service=management/security-realm=ApplicationRealm/authorization=properties:read-attribute(name=path)

    You should see the users registered in the realm, then the path of the groups file — by default <WILDFLY_HOME>/standalone/configuration/application-roles.properties. Roles are not exposed as a management attribute, so open that file to see the mapping: each line maps one user to a role, for example alice=CUSTOMER. If the caller is missing, or has no CUSTOMER or TELLER line, the @RolesAllowed gate will keep throwing EJBAccessException no matter how many times you redeploy. Type quit to leave the CLI.

2.3 Troubleshooting: the three errors beginners actually see

When it goes wrong, find your symptom in this table before doing anything else.

What you seeWhat it meansWhat to do
NameNotFoundException Your lookup string does not match any name on the server Copy the exact java:global/…!… line WildFly printed at deployment into your lookup(). Check for a missing interface suffix after the !.
EJBTransactionRolledbackException An unchecked exception blew up inside a transactional method, so the container undid the work Do not fix the rollback line. Scroll down to the first Caused by: line and fix that bug, then rebuild and redeploy.
EJBAccessException The caller's role does not match what @RolesAllowed demands, or nobody is logged in Check the user's role in the security realm (step 4 above), and make the web tier force a login before it calls the protected bean.
💡
The rule that saves the most time The exception you see is almost never the exception you fix. A rollback, an access denial and a lookup failure are all attempts by the container to protect your data. The real bug is further down the trace, or in the realm settings. Read two lines further than your instinct tells you to.

Part 3 · Build the whole pipeline, line by line

Now you assemble the whole pipeline that makes Part 1 real, inside the project you already built in Session 1: lab/session-01-hello-ejb/. Its pom.xml sets finalName to hello-ejb, so every build produces target/hello-ejb.war and the application answers under http://localhost:8080/hello-ejb/. Add each file below to that project, in the package shown in its heading. One bean remembers the login; the other is guarded, transactional, and talks to the database. Notice how little code there is — the container does the rest.

  1. File 1 — the stateful bean that remembers the login

    Create UserSessionBean.java in lab/session-01-hello-ejb/src/main/java/com/globalbank/ejb/ and type it in:

    UserSessionBean.java — Stateful client session
    package com.globalbank.ejb;

import jakarta.ejb.Stateful;

@Stateful
public class UserSessionBean {
    private String username;
    private int loginAttempts = 0;

    public void login(String user) {
        this.username = user;
        this.loginAttempts++;
    }

    public String getUsername() { return this.username; }
    public int getAttempts() { return this.loginAttempts; }
}

    What to notice: the fields username and loginAttempts are the entire reason this bean is @Stateful. Between two calls from the same client, those values survive — this is stop 2 of the pipeline, and it is the only stop that remembers who is calling.

    You should be able to point at the word @Stateful and say: “the container keeps one of these per client, and fills it in before my code runs.”

  2. File 2 — the interface and the bean that is guarded and transactional

    A bean reached through a business interface is not addressable by its short class name — that is why the JNDI name in Part 2 ended in !com.globalbank.ejb.PaymentProcessor. So first create the interface, PaymentProcessor.java, in the same package:

    PaymentProcessor.java — the @Local business interface
    package com.globalbank.ejb;

import jakarta.ejb.Local;

@Local
public interface PaymentProcessor {
    void processPayment(int accountId, double amount);
}

    What to notice: the interface holds only the method signature. The security, transaction and resource annotations belong on the implementation below, not here. @Local means this view is only ever called from inside the same JVM — exactly what the servlet in step 4 does.

    Now create PaymentProcessorBean.java, implementing that interface and using WildFly's built-in ExampleDS — an in-memory H2 database, so there is no PostgreSQL to install:

    PaymentProcessorBean.java — secure, transactional business logic
    package com.globalbank.ejb;

import jakarta.annotation.Resource;
import jakarta.annotation.security.RolesAllowed;
import jakarta.ejb.Stateless;
import jakarta.ejb.TransactionAttribute;
import jakarta.ejb.TransactionAttributeType;
import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;

@Stateless
@RolesAllowed({"CUSTOMER", "TELLER"})
public class PaymentProcessorBean implements PaymentProcessor {

    @Resource(lookup = "java:jboss/datasources/ExampleDS")
    private DataSource dataSource;

    @Override
    @TransactionAttribute(TransactionAttributeType.REQUIRED)
    public void processPayment(int accountId, double amount) {
        String debitSql = "UPDATE accounts SET balance = balance - ? WHERE id = ?";

        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(debitSql)) {

            ps.setDouble(1, amount);
            ps.setInt(2, accountId);
            int rows = ps.executeUpdate();

            if (rows == 0) {
                throw new IllegalArgumentException("Account " + accountId + " does not exist!");
            }
            System.out.println("Debited $" + amount + " from account " + accountId);

        } catch (SQLException e) {
            throw new RuntimeException("Database error executing payment", e);
        }
    }
}

    What to notice — this one class contains three of the four pillars. Find each line:

    • @Stateless — the bean is pooled; nothing is remembered between calls.
    • @RolesAllowed({"CUSTOMER", "TELLER"}) — stop 4, the security gate. No if statement anywhere; the container refuses the call before the method body runs.
    • @TransactionAttribute(REQUIRED) — stop 5, the transaction boundary. Either the whole update happens or none of it does.
    • @Resource(lookup = "java:jboss/datasources/ExampleDS") — stop 6, the DataSource. WildFly's built-in H2 database; the container injects a pooled connection and you never open one yourself.
    • The throw new IllegalArgumentException(...) inside the try — an unchecked exception, so the container will roll the transaction back. This is the deliberate trigger for Fault 2 you will use in step 7.

    You should be able to say which line carries each of the three container services. If you cannot, re-read the bullets — this is the exam question.

  3. File 3 — the startup bean that creates the H2 table

    ExampleDS is an in-memory H2 database: it starts empty every time WildFly boots, and it is private to the server's JVM, so an outside SQL tool would only ever see a different, empty database. The application therefore has to create its own table. Add this small bean and it runs automatically at deploy time:

    SchemaBootstrapBean.java — creates and seeds the accounts table
    package com.globalbank.ejb;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.Resource;
import jakarta.ejb.Singleton;
import jakarta.ejb.Startup;
import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.Statement;

@Startup
@Singleton
public class SchemaBootstrapBean {

    @Resource(lookup = "java:jboss/datasources/ExampleDS")
    private DataSource dataSource;

    @PostConstruct
    public void createTable() {
        try (Connection conn = dataSource.getConnection();
             Statement st = conn.createStatement()) {

            // The actual DDL: this is the table processPayment() updates.
            st.executeUpdate(
                "CREATE TABLE IF NOT EXISTS accounts (id INT PRIMARY KEY, balance DECIMAL(10,2))");

            // Seed one row to debit. MERGE keeps this idempotent on every redeploy.
            st.executeUpdate(
                "MERGE INTO accounts (id, balance) KEY(id) VALUES (1001, 1000.00)");

            System.out.println("Table 'accounts' ready: id 1001, balance 1000.00");
        } catch (Exception e) {
            throw new RuntimeException("Could not create the accounts table", e);
        }
    }
}

    What to notice: @Startup makes the container build this bean the instant the application deploys, and @Singleton guarantees exactly one instance. This is the only place the accounts table is ever created.

  4. File 4 — the client that drives the pipeline

    Finally, the program that calls the pipeline. This is a servlet, and that choice is deliberate: it runs inside the same JVM, so it needs no extra classpath and no second Maven project — it looks the bean up by JNDI and calls it. Add BankClientServlet.java to the same package:

    BankClientServlet.java — the web-tier client
    package com.globalbank.ejb;

import jakarta.annotation.Resource;
import jakarta.servlet.ServletException;
import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;

import javax.naming.InitialContext;
import javax.naming.NamingException;
import javax.sql.DataSource;
import java.io.IOException;
import java.io.PrintWriter;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;

@WebServlet("/bank")
public class BankClientServlet extends HttpServlet {

    @Resource(lookup = "java:jboss/datasources/ExampleDS")
    private DataSource dataSource;

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        response.setContentType("text/plain");
        PrintWriter out = response.getWriter();

        String action = request.getParameter("action");
        if (action == null) action = "pay";

        try {
            if ("balance".equals(action)) {
                showBalance(out, 1001);
                return;
            }

            // ---- the login step: comment this block out for Fault 3 (step 8) ----
            if (request.getUserPrincipal() == null) {
                request.getSession(true);
                request.login("alice", "alice123");
            }

            // ---- the JNDI lookup string: put the typo here for Fault 1 ----
            InitialContext ctx = new InitialContext();
            PaymentProcessor processor = (PaymentProcessor) ctx.lookup(
                "java:global/hello-ejb/PaymentProcessorBean!com.globalbank.ejb.PaymentProcessor");

            processor.processPayment(1001, 350.00);
            out.println("Payment processed. Open ?action=balance to see the new balance.");

        } catch (NamingException e) {
            out.println("NameNotFoundException - check the lookup string: " + e.getMessage());
        } catch (Exception e) {
            out.println("Call failed: " + e);
        }
    }

    /** Reads the row through the same DataSource, so you can prove a rollback worked. */
    private void showBalance(PrintWriter out, int id) throws Exception {
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(
                 "SELECT id, balance FROM accounts WHERE id = ?")) {
            ps.setInt(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                if (rs.next()) {
                    out.println("Account " + rs.getInt("id") + " balance = " + rs.getBigDecimal("balance"));
                } else {
                    out.println("No row for account " + id);
                }
            }
        }
    }
}

    What to notice — three things the exam asks about:

    • The lookup string is the exact java:global/…!… name WildFly printed at deploy (Part 2, step 1). A typo here throws NameNotFoundException — Fault 1.
    • request.login("alice", "alice123") authenticates the caller before the bean is called, which is what gives the request the role the security gate checks.
    • The servlet casts the looked-up Object to the PaymentProcessor interface — it never sees the bean class itself.

        statement the container undid is exactly this SQL, which the bean ran inside the transaction:
    
      
    UPDATE accounts SET balance = balance - 350.00 WHERE id = 1001;
    
      
    Because ExampleDS is in-memory and private to the server, the reliable way to
        check the row is the client you already built: ?action=balance issues the matching
        SELECT id, balance FROM accounts WHERE id = 1001; through the servlet's own
        DataSource. The balance is still 1000.00 — the update was undone. That
        is REQUIRED doing exactly what it promised in Part 1: all-or-nothing. Remove the
        deliberate fault, rebuild, redeploy — the payment succeeds and the balance moves.
    
    
    8. 

    
  8. 
      
    Prove the security gate — call it as the wrong person
    
      
    In BankClientServlet, comment out the login step — the
        if (request.getUserPrincipal() == null) { … } block — so the request stays
        anonymous. Rebuild, redeploy, and open /hello-ejb/bank again.
    
      
    You should see EJBAccessException: Invocation on method is not
        allowed. Notice what you should not see: no SQL, no connection leased, no
        transaction opened. The container refused the call at stop 4, before a single
        line of your business logic ran. Put the login block back, rebuild, redeploy, and it works.
    
      
    That contrast is the lesson. Security fires before the work;
        transactions wrap the work. Two gates, two different moments, both declared with one line
        each.

    📋 The three faults at a glance
    

      
ExceptionSymptom textRoot causeFix

      
        

          javax.naming.NameNotFoundException
          NameNotFoundException: hello-ejb/PaymentProcessorBean -- service jboss.naming.context...
          The lookup string does not match any name WildFly registered — a typo, a missing interface suffix, or the wrong namespace.
          Copy the exact java:global/…!… line from the boot log into your lookup().
        

        

          jakarta.ejb.EJBTransactionRolledbackException
          EJBTransactionRolledbackException: Transaction rolled back
          An unhandled runtime exception occurred inside a transactional method; the container aborted the transaction automatically.
          Read the first Caused by: line in the stack trace — that is the real bug (e.g. NullPointerException, SQLException: duplicate key). Fix it.
        

        

          jakarta.ejb.EJBAccessException
          EJBAccessException: Invocation on method is not allowed
          The caller lacks the role named in @RolesAllowed, or is not authenticated at all.
          Verify credentials and role mappings in WildFly's security realm, and force login in the web tier before calling the protected bean.

    🧩 Why the names are spelled two ways: javax and jakarta
    
When the platform was renamed, most package names changed from javax.* to
      jakarta.*. A few deliberately kept the old spelling. Both are the same technology,
      and getting the pair wrong is a common cause of “cannot find symbol” build errors:

    

      
Still spelled javaxNow spelled jakarta

      
        
javax.naming (JNDI, InitialContext)jakarta.ejb (Session Beans)

        
javax.sql (DataSource)jakarta.annotation (@Resource, @RolesAllowed)

        
javax.transaction (JTA)jakarta.persistence (JPA)

      
    

    
So import javax.sql.DataSource; is correct — it is not a mistake for being
      old spelling.

PackageExtensionWhat is inside

Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      

        Retyping a JNDI string from memory
        Copy the exact java:global/…!… line WildFly printed at deployment. This is the fix for Fault 1.
      

      

        Trying to fix the EJBTransactionRolledbackException line itself
        Scroll to the first Caused by: line — that is the real bug. The rollback is a consequence, not the cause.
      

      

        Blaming the code for an EJBAccessException
        Check the user's roles in the security realm and ensure login happens before the call. The code may be perfectly correct.
      

      

        Using a @Stateful bean for work that needs no memory
        Use @Stateless. State costs one instance per client; only pay for it when the conversation needs it.
      

      

        Opening a database connection yourself inside an EJB
        Inject the pooled @Resource DataSource and let try-with-resources return the connection to the pool.
      

      

        Writing if (user.hasRole(...)) inside a business method
        Declare @RolesAllowed on the method and let the container enforce it at stop 4, before your code runs.
