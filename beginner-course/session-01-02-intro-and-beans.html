Part 1 · Why any of this exists

1.1 A shop that got too busy

Imagine you open a small shop. You are the only employee.

You greet customers. You take payments. You check the shelves. You call suppliers. You do the tax paperwork. You lock up at night.

With ten customers a day, this is fine. You are busy, but you cope.

Now the shop becomes famous. You get ten thousand customers a day.

Everything collapses — and not because the work got harder. It collapses because one person cannot do all of those jobs at once. You cannot personally check every payment and hold fifty conversations and count the shelves. You would need to hire specialists: a cashier, a security guard, an accountant, a stockroom clerk.

Each specialist does one job well. You stop doing everything yourself.

1.2 The same thing happens to computer programs

A simple Java program starts out like that shop: one class doing everything.

Then the application grows, and that one program now has to:

  • check whether the user is allowed to do this
  • make sure the database changes either all happen or none do
  • stop two users from corrupting the same data at the same time
  • manage connections to the database
  • …and do the actual work the business cares about

All five jobs tangled together in one class. It works — until it grows. Then it becomes impossible to change one thing without breaking another, and impossible to test.

🏪
Analogy A one-person shop is not a bad shop. It is a shop that cannot grow. The same is true of a Java program that does everything in one class.

1.3 The fix: keep the business rule, hand off the chores

Here is the whole idea, and it is genuinely this simple:

  1. You write only the part that is specific to your business — the rule, the calculation, the decision.
  2. You tell a big piece of software called an application server what chores you need, using labels on your code.
  3. The server does the chores for you, automatically, every time.
In plain words

You are the head chef. You decide what dish to cook. You do not personally install the ovens, hire the waiting staff or pay the electricity bill — the restaurant does that.

Jakarta EE is the restaurant. Your job is the cooking.

1.4 So what is Jakarta EE?

Jakarta EE is a set of rules and ready-made pieces for building large Java applications. It is not a program you install and click. It is a standard — a written agreement about how these pieces behave.

Because it is a standard, your code runs on any server that follows it. That is why you can learn it once and use it at any company.

Name you may hearWhat it means
J2EEThe old name (late 1990s). Retired.
Java EEThe middle name. You will still see it in older books.
Jakarta EEThe current name. This is what we use.
⚠️
Why you will see javax and jakarta in the same book When the technology was renamed, most package names changed with it: javax.ejb became jakarta.ejb. A few deliberately kept the old name — javax.naming and javax.sql. So import javax.naming.InitialContext; is correct, while import jakarta.naming.InitialContext; does not exist. Session 3 covers this trap properly. For now, just know both spellings are the same technology.

1.5 And what is an enterprise bean?

Now we can define it. Read the definition once, then read the translation underneath.

✦
The official definition An enterprise bean is a server-side software component that contains the business logic of an enterprise application. It runs inside an EJB container (EJB is short for Enterprise JavaBeans, the older name for enterprise beans) on an application server, which automatically provides it with services such as security, transaction management and concurrency control.
In plain words

An enterprise bean is an ordinary Java class with a few labels on it.

The labels tell the application server: “look after this object for me.” In exchange, the server handles the boring, error-prone chores — security, database safety, and sorting out what happens when many users arrive at once.

You write the interesting part. The server does the rest.

1.6 Every new word, translated

Six words appear in that definition. Here they all are, in one place. You will meet each one again later, so do not try to memorise them now — just recognise them.

WordWhat it actually meansEveryday comparison
Server-side The code runs on the company's machine, not on the user's phone or laptop. The cashier's till, not the customer's pocket.
Business logic The rules that make your company different. “A transfer over 10,000 needs a manager's approval.” “Students may take at most 5 courses.” The recipe. Not the oven.
Application server A large program that stays running and already contains all the Jakarta EE machinery. Our choice is WildFly. The restaurant building — kitchen, staff, electricity, all in place.
Container The part of the server that looks after your objects: it creates them, hands them out, fills in their dependencies, wraps them with security and transactions, and destroys them when done. The restaurant manager. You never hire your own waiter — you ask the manager.
Bean Simply “a class the container manages for you.” An enterprise bean is one carrying an EJB label such as @Stateless. A member of staff on the manager's payroll.
Deploy Hand your finished, packaged application to the server so it starts running it. Opening the restaurant for business.

1.8 The four chores the container takes off your desk

This is the single best argument for using enterprise beans. Here is what you would otherwise have to write yourself — correctly, every single time.

ChoreWithout a container you must…With a container you…
Transactions Write code to undo half-finished work when something fails midway. Write one label: @TransactionAttribute. The container rolls back for you.
Security Check the logged-in user's role at the top of every method. Write one label: @RolesAllowed("MANAGER"). The container refuses the call.
Concurrency Work out which threads — the workers running your code — may safely run at the same time. Nothing. The container decides who may enter, and when.
Connection pooling Open, reuse, and close database connections without leaking them. Nothing. You ask for a pool by name.
💡
If you remember only one thing from Part 1 The container is not a convenience. It is the difference between code that is correct and code that is usually correct. Security, transactions and concurrency are exactly where hand-written code quietly goes wrong.

Part 2 · Seeing the difference

Definitions are easy to forget. Seeing the same job written two ways is not. Here is one job — moving money between two bank accounts — written both ways.

2.1 The hard way: everything by hand

Read the comments on the right of each line. That is where the pain lives.

BankService.java — plain Java, no container
public class BankService {

    public void transferFunds(int from, int to, double amount) {

        Connection conn = getConnection();          // open a database connection yourself
        conn.setAutoCommit(false);                  // start the transaction yourself

        if (!currentUser.hasRole("TELLER")) {       // check the user's role yourself
            throw new SecurityException("Access denied");
        }

        synchronized (this) {                       // stop other threads yourself
            try {
                debit(from, amount, conn);          // do the work
                credit(to, amount, conn);           // do the work
                conn.commit();                      // commit yourself
            } catch (Exception e) {
                conn.rollback();                    // undo the half-done work yourself
            }
        }
    }
}

Count the responsibilities in that one method: connection handling, transaction handling, security, and thread safety — plus, somewhere in the middle, the actual business rule (move the money).

Every method in the application repeats this pattern. Miss one rollback() and you have quietly corrupted somebody's account.

2.2 The same job as a bean

Now the same method. Look at how much code disappeared — and where it went.

BankService.java — as an enterprise bean
@Stateless                                  // "container: manage this class for me"
@RolesAllowed("TELLER")                     // security: the container enforces it
public class BankService {

    @TransactionAttribute(TransactionAttributeType.REQUIRED)   // transaction: the container starts and commits it
    public void transferFunds(int from, int to, double amount) {

        debit(from, amount);                // ← the business rule. That is all that is left.
        credit(to, amount);

        // If an exception is thrown here, the container rolls back automatically.
        // If two users call at once, the container sorts it out.
        // If the user lacks the TELLER role, the container never lets them in.
    }
}

Same business rule. Every chore became a label — and labels are far harder to get wrong than hand-written plumbing.

In plain words

In the first version, the interesting line (move the money) is buried under four layers of plumbing.

In the second, the interesting line is the only line. Everything else is declared, not written.

That trade — write plain code, declare what you need — is Jakarta EE in one sentence.

🧾
Analogy A label like @RolesAllowed("TELLER") is a sign on a door that says “staff only.” You do not post a guard at the door and check badges yourself. You put up the sign, and the building's security system does the checking.

2.3 The one rule beginners get wrong: never write new

Everything else on this page follows from this one rule, so it gets its own section.

⚠️
Never do this BankService service = new BankService();
You would get an ordinary object with none of the container's services. No security. No transactions. No pooling. Just a plain Java object wearing a bean's name.

So how do you get a bean? You ask the container, in one of two ways:

WayLooks likeUse it when
Injection (the easy one) @EJB private BankService service; Both classes live in the same application. This is what you will use 95% of the time — and it is exactly what Part 4's lab does.
JNDI lookup ctx.lookup("java:global/…") The caller is outside the application — a separate program on another machine. Session 3 and Session 6 cover this properly.
In plain words

With @EJB you write the field and leave it empty. Before your code runs, the container fills it in with a ready-to-use bean. You never call new, and you never know or care which instance you were given — the container decides.

This is called injection: the container injects the object into your field.

Part 3 · The four kinds of enterprise bean

  
You now know what a bean is. The next question is which kind — and there are four:

  

    
KindOne-line job

    
      
Session bean (3 flavours: stateless, stateful, singleton)Does work on behalf of a user. This is the one you will use most.

      
Entity bean (today: a JPA entity)Represents data that lives in a database.

      
Message-driven beanWaits quietly in the background and reacts when a message arrives.

    
  


  
3.1 The one question that picks the right bean

  
Forget the jargon. Every choice comes down to one question:


  
❓
    
Between two calls from the same user, does this object need to
      remember anything?
      
    
        
  • No — every call stands alone → use @Stateless
    • 
        
  • Yes — but only for that one user's conversation → use @Stateful
    • 
        
  • One thing, shared by the whole application → use @Singleton
    • 
      

    

  


  
3.2 What "session" means

  
A session bean is a bean that does work on behalf of a client. The word
    "session" simply means a period of interaction with one user.

  
Think of a phone call:

  
    
    
  • You dial → the session begins
    • 
    
  • The person helps you → they are doing the work
    • 
    
  • You hang up → the session ends
    • 
  

  
Session beans do not store data permanently. They do things. Storing data is the job of
    an entity (Section 3.8).


  
3.3 Stateless — the everyday default

  
A stateless bean has no memory between method calls. The container keeps a
    pool of ready instances; when a request arrives it lends one out, the bean does
    the work, and the instance goes back into the pool for the next person.


  
🍔
    
Analogy
      A fast-food cashier. You order, they ring it up, done. The next customer steps up and the same
      cashier serves them — with no memory of you at all. Each order stands alone.

  


  
GreeterBean.java — a stateless bean

  
package com.example;

import jakarta.ejb.Stateless;

@Stateless                                     // the container will manage this class
public class GreeterBean {

    public String greet(String name) {          // no fields, so nothing to remember
        if (name == null || name.isBlank()) {
            name = "stranger";
        }
        return "Hello, " + name + "!";
    }
}


  
This is not a made-up example — it is the exact bean you will build and run in
    Part 4.


  
⚠️
    
The trap that catches everyone
      You can write a field in a stateless bean — but its value is only trustworthy
      during a single method call. The next call may land on a different instance from
      the pool, with a freshly initialised field. Never rely on a stateless bean remembering
      anything.

  


  
Reach for stateless when: calculations, lookups, reading and writing the
    database, sending an email — anything where each request is independent. This is your default.
    Use it unless you have a specific reason not to.


  
3.4 Stateful — for a conversation

  
A stateful bean is dedicated to one client and remembers its fields
    from one call to the next, for as long as that conversation lasts.


  
🎂
    
Analogy
      Ordering a custom birthday cake. You call on Monday to choose the design. You call on Wednesday
      to change the message. You call on Friday to confirm pickup. The baker remembers your order
      across every one of those calls — until you collect the cake and the order is closed.

  


  
That "remembering across the whole exchange" is called conversational state.
    It is exactly what a shopping cart, a checkout wizard or a multi-page form needs.


  
RunningTotalBean.java — a stateful bean

  
package com.example;

import jakarta.ejb.Stateful;
import jakarta.ejb.Remove;

@Stateful
public class RunningTotalBean {

    private int total = 0;        // THIS field survives between calls — for this one client only

    public int add(int amount) {
        total += amount;          // pick up where this client left off
        return total;
    }

    @Remove                       // the client calls this when the conversation is over
    public void finish() {
        // the container destroys this instance immediately afterwards
    }
}


  
Watch it remember. Run the panel:


  

    
try itreplay — real server output

    
// one client, one bean instance, four calls in the same session
cart.add(5);      // -> ?
cart.add(10);     // -> ?
cart.add(3);      // -> ?
cart.add(100);    // -> ?
cart.finish();    // ends the session

    

      
      Watch the total build up — that is the bean remembering you.
    

    
    

  


  
💡
    
Why not use stateful for everything?
      Because it costs memory. One instance is held per user and cannot be shared. A stateless pool
      might serve ten thousand users with twenty instances; stateful needs one instance per live
      conversation. Use it only when the conversation genuinely spans several calls.

  


  
3.5 Singleton — exactly one, shared by everyone

  
Exactly one instance exists for the entire application, and every user shares it
    at the same time. Good for a cache, a counter, application-wide settings, or work that must run
    when the application starts.


  
🏦
    
Analogy
      The branch manager. There is exactly one in the branch. Every teller and every customer deals
      with that same person. All decisions pass through them.

  


  
Because many users hit the same object at once, you must say who is allowed in at the same time.
    That is what @Lock does.


  
AuditLogger.java — a singleton

  
package com.example;

import jakarta.ejb.Singleton;
import jakarta.ejb.Startup;
import jakarta.ejb.Lock;
import jakarta.ejb.LockType;

@Singleton
@Startup                               // create this when the app starts, before any user arrives
public class AuditLogger {

    private int totalTransactions = 0;  // ONE counter, shared by the whole application

    @Lock(LockType.WRITE)               // only one thread at a time — because this changes data
    public void logTransaction(String description) {
        totalTransactions++;
        System.out.println("Transaction #" + totalTransactions + ": " + description);
    }

    @Lock(LockType.READ)                // many threads at once — safe, because this only reads
    public int getTotalTransactions() {
        return totalTransactions;
    }
}


  
In plain words
    
@Lock(WRITE) means “one at a time, please — I am changing something.”

    
@Lock(READ) means “come in together — I am only reading, so you cannot
      break anything.”

    
Get this wrong and two users incrementing a counter at the same instant can lose a count.
      That is a real bug that only shows up under load — which is why the container would rather you
      declare it.

  


  

    
try itreplay — real server output

    
// three users reach the site "at the same moment"
userA -> logTransaction()
userB -> logTransaction()
userC -> logTransaction()
anyone -> getTotalTransactions()

    

      
      @Lock(WRITE) queues the three increments, so none is lost.

3.7 Message-driven beans — the background worker

  
A message-driven bean (MDB) sits in the background and listens. When a message lands on a
    queue, the container wakes the bean and hands it the message. The sender did not wait around for
    the answer — that is what asynchronous means.


  
📧
    
Analogy
      A support inbox with an auto-responder. You send your email and get on with your day. The
      auto-responder is always listening and deals with it whenever it arrives — on its own schedule,
      not yours.

  


  
Why anybody bothers: ten thousand transfers at once

  
Ten thousand people click “Transfer money” at the same moment.

  
    
    
  • Synchronously — all ten thousand wait for their transfer to finish before
      their page responds. The system crawls, then falls over.
    • 
    
  • Asynchronously, with an MDB — each request is dropped onto a
      queue (a waiting line). The user instantly sees “Transfer submitted.” MDB
      instances chew through the queue in the background. The site stays fast.
    • 
  


  
FundTransferProcessor.java — a message-driven bean

  
package com.example;

import jakarta.ejb.MessageDriven;
import jakarta.jms.Message;
import jakarta.jms.MessageListener;
import jakarta.jms.TextMessage;

@MessageDriven(mappedName = "jms/FundTransferQueue")   // which queue to listen to
public class FundTransferProcessor implements MessageListener {

    @Override
    public void onMessage(Message message) {            // the container calls this, once per message
        try {
            TextMessage text = (TextMessage) message;
            String details = text.getText();

            System.out.println("Processing transfer: " + details);
            // ... update the database, then send a confirmation email

        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}


  
🔑
    
The one thing to notice
      Nobody ever calls onMessage() in your code. The container calls it,
      once for every message that arrives. An MDB has no client interface at all — clients never talk
      to it directly; they talk to the queue.

  


  

    
try itreplay — real server output

    
// the web page drops three transfers on the queue and returns immediately
queue.send("TRANSFER ACC-1 -> ACC-2  $150");
queue.send("TRANSFER ACC-7 -> ACC-3  $40");
queue.send("TRANSFER ACC-9 -> ACC-1  $999");
// the user has already seen "submitted". The MDB works in the background:

    

      
      The sends return instantly; onMessage() fires much later, once per message.

    the work.

3.8 Entity beans — the odd one out

  
Everything so far does something. An entity is something: it represents data
    that lives in a database and survives after the program stops.


  
🗂️
    
Analogy
      A library catalogue card. It has a unique number (the primary key), some fields (title,
      author, year), it stays in the drawer even when nobody is reading it (persistence), and
      several people can look up the same card (shared).

  


  
📌
    
Important: "entity bean" today means "JPA entity"
      The old EJB 2.x entity bean was heavy and is long gone. Modern Jakarta EE does persistence with
      JPA (Jakarta Persistence). An entity is just a plain class with
      @Entity and an @Id. If an exam question says "entity bean", it means
      this.

  


  
Account.java — an entity

  
package com.example;

import jakarta.persistence.Entity;
import jakarta.persistence.Id;

@Entity                                 // "map this class to a database table"
public class Account {

    @Id                                 // this field uniquely identifies each row
    private Long accountId;

    private String accountHolder;
    private double balance;

    // getters and setters ...
}


  
Here is how that class lines up with the database table it becomes:

  

    
In your Java codeIn the database

    
      
class Accounttable Account

      
Long accountId marked @Idaccount_id BIGINT PRIMARY KEY

      
String accountHolderaccount_holder VARCHAR

      
double balancebalance NUMERIC

    
  


  
In plain words
    
A session bean forgets; an entity is remembered.

    
Session beans do work. Entities hold data. Almost every real application uses both: a stateless
      bean receives a request, does the work, and saves the result into an entity.

    2. 

    
  2. 
      
    Open a second terminal in the lab folder
    
      
    A second window, so the server keeps running. Move into the folder that contains
        pom.xml:
    
      
    cd beginner-course/lab/session-01-hello-ejb
    
      
    Type dir (Windows) or ls (macOS/Linux) and confirm you can see
        pom.xml and src.
    
    
    3. 

    
  3. 
      
    Look at the build file before you build
    
      
    Open pom.xml. Only two lines in it really matter — the rest is bookkeeping:
    
      
    <packaging>war</packaging>

<dependency>
  <groupId>jakarta.platform</groupId>
  <artifactId>jakarta.jakartaee-api</artifactId>
  <version>10.0.0</version>
  <scope>provided</scope>      <!-- the server already has this — do not ship a copy -->
</dependency>
    
      
    packaging says “build me a .war”, a zip the server understands.
        scope provided says “I need the Jakarta EE API to compile, but the server already
        has its own copy — don't bundle mine.” Getting that wrong causes confusing version clashes.
    
    
    4. 

    
  4. 
      
    Look at the bean — the whole point of the lab
    
      
    src/main/java/com/example/GreeterBean.java
    
      
    package com.example;

import jakarta.ejb.Stateless;

@Stateless
public class GreeterBean {

    public String greet(String name) {
        if (name == null || name.isBlank()) {
            name = "stranger";
        }
        return "Hello, " + name + "! (said by a container-managed bean)";
    }
}
    
      
    That is the entire bean. There is no new, no threads, no security check, no
        database. Just one annotation and one business rule. The
        @Stateless label is what turns this ordinary class into something the container
        looks after.
    
    
    5. 

    
  5. 
      
    Look at the window we use to see it
    
      
    A bean has no screen. To watch it work we need something that can answer a web request — so
        the lab includes a tiny servlet. A servlet is simply a Java class that
        responds to a URL.
    
      
    src/main/java/com/example/GreeterServlet.java
    
      
    @WebServlet("/greet")
public class GreeterServlet extends HttpServlet {

    @EJB                                          // ← the container fills this in for us
    private GreeterBean greeter;

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {

        String name = request.getParameter("name");   // the ?name=... part of the URL

        response.setContentType("text/plain");
        response.getWriter().println(greeter.greet(name));
    }
}
    
      
    Two lines carry all the meaning. @WebServlet("/greet") gives the class a URL.
        @EJB asks the container for a bean — and we never write new.

    copy target\hello-ejb.war  C:\wildfly\standalone\deployments\      REM  Windows

    8. 

    
  8. 
      
    Use it
    
      
    Open your browser at:
    
      
    http://localhost:8080/hello-ejb/greet?name=Ada
    
      
    You should see exactly:
    
      
    Hello, Ada! (said by a container-managed bean)
    
      
    Stop for a second and appreciate this. A request arrived over HTTP, the
        container found a pooled GreeterBean instance, injected it into the servlet, the
        servlet called greet("Ada"), and the answer came back. You wrote the business rule
        and the labels. The container wrote the rest.
    
    
    9. 

    
  9. 
      
    Prove the bean is really doing the work
    
      
    Change the name in the URL:
    
      
    http://localhost:8080/hello-ejb/greet?name=YOURNAME
    
      
    Now leave the name off completely:
    
      
    http://localhost:8080/hello-ejb/greet
    
      
    → Hello, stranger! (said by a container-managed bean)
    
      
    That is your if (name == null…) rule in GreeterBean handling the
        missing value. The servlet did no work at all — it just passed the value on. The
        bean made the decision. That division is the entire lesson of Session 1.
    
    
    10. 

    
  10. 
      
    Break it on purpose, then fix it
    
      
    The fastest way to understand a rule is to break it. In GreeterBean.java,
        delete the @Stateless line, then rebuild and redeploy:
    
      
    mvn clean package
copy target\hello-ejb.war  C:\wildfly\standalone\deployments\
    
      
    Reload the page. It fails — because @EJB asks the container for a bean, and a
        class with no EJB annotation is not a bean. Nothing is managing it, so there is nothing to
        inject.
    
      
    Put @Stateless back, rebuild, redeploy, and it works again. You have just proved
        that the annotation, not the class, is what makes a bean a bean.

    📋 The six essential characteristics of an enterprise bean
    
The textbook lists these. They are the formal description of everything Part 1 explained.

    

      
CharacteristicWhat it means in plain words

      
        
Business logicIt holds the rules — transferFunds(), processLoanApplication(). It does not do UI, and it does not manage connections.

        
Container managementYou never create it with new. The container creates, pools and destroys it.

        
Customisable at deploymentYou can configure the same code differently for Dev, Test and Production without touching the source.

        
Declarative servicesTransactions and security are declared with annotations — @TransactionAttribute, @RolesAllowed — not written as code.

        
PortabilityStandard EJB code runs on any compliant server: WildFly, Payara, GlassFish, Open Liberty.

        
IntegrationBeans can be assembled into larger applications without recompiling.

PackageExtensionWhat is inside

      
        
JAR (standalone).jarJust your EJB classes.

        
WAR (embedded).warA web archive, with the beans inside WEB-INF/classes/. This is what our lab builds.

    🔄 What happens to a stateful bean when the server gets busy
    
A stateful bean is held in memory for its client. If that client goes quiet for a while, the
      container may write the bean to disk to free memory, then bring it back when the client returns.
      Those two moves have names:

    
                 ┌──────────────────┐
                 │  DOES NOT EXIST  │
                 └────────┬─────────┘
                          │ container creates the instance
                          │ @PostConstruct runs
                          ▼
                 ┌──────────────────┐
                 │      READY       │◄───────────────┐
                 │   (in memory)    │                │
                 └────────┬─────────┘                │
                          │ client silent for a while│ @Activate
                          ▼                         │ (brought back)
                 ┌──────────────────┐                │
                 │   PASSIVATED     │────────────────┘
                 │   (written to    │
                 │      disk)       │
                 └────────┬─────────┘
                          │ @Remove called, or the session times out
                          ▼
                 ┌──────────────────┐
                 │    DESTROYED     │
                 │  @PreDestroy     │
                 └──────────────────┘

    
Passivated means “parked on disk to save memory.”
      Activated means “brought back when the client needs it.” Stateless and singleton
      beans are never passivated.

  


  

    ⚙️ Controlled delivery — pausing a message-driven bean
    
Delivery Active

    
Controls whether an MDB is currently processing messages:

    
    
      
  • deliveryActive = true → the bean is listening and working.
    • 
      
  • deliveryActive = false → the bean is paused. Messages pile up on
        the queue but are not processed until you switch it back on.
    • 
    

    
📬
      
Analogy
        A mailroom over lunch. Parcels keep arriving and stack up. The workers return and clear the
        pile. The mailroom simply paused its "delivery active" status.

    


    
Delivery Groups

    
A delivery group is a named set of MDBs that share one on/off switch. Pausing
      the group pauses every bean inside it.

    
Delivery Group: "banking-processors"
  ├── FundTransferProcessor      (MDB 1)
  ├── LoanApplicationProcessor   (MDB 2)
  └── AuditEventProcessor        (MDB 3)
          │
          ▼
  Pause the group  →  all three pause together
  Resume the group →  all three resume together

    
🏥
      
Analogy
        A hospital with separate departments — Emergency, Surgery, Pharmacy. During an upgrade, IT can
        pause just "Pharmacy" while leaving "Emergency" running.

    

  


  

    📚 The old-style entity bean, for exam questions
    
Modern entity beans are JPA entities — a class with @Entity and @Id.
      But the textbook also describes the older EJB 2.x shape, which had four parts. If a question
      uses those terms, here is what they meant:

    

      
ComponentWhat it wasIn plain words

      
        
Remote componentAn interface listing the business methods"What can clients call on this entity?"

        
Home interfaceA factory for creating and finding entities"How do I create, find or delete one?"

        
Primary key classThe object that made an entity unique"What makes this row different from the others?"

        
Bean classThe real class with the logic"The actual object with the code in it."

      
    

    
In modern Jakarta EE you only need the bean class — one annotated Java class.
      The other three disappeared with EJB 3.0.

  


  


  

  recap
  
One-line summary of everything

  

    
Jakarta EEA standard for building large Java applications, where the server handles the infrastructure for you.

    
Enterprise beanAn ordinary Java class with a label on it, which the container creates, manages and destroys for you.

    
The containerThe part of the server that looks after your objects and supplies security, transactions, concurrency and pooling.

    
Why botherYou write only the business rule; the container does the error-prone chores that hand-written code gets wrong.

    
@StatelessNo memory between calls. Served from a shared pool. Your default choice.

    
@StatefulRemembers its fields for one client across a conversation. Ended with @Remove.

    
@SingletonOne instance for the whole application, shared by everyone. Guard state with @Lock.

    
Entity (JPA)Data with an identity, stored in a database. @Entity + @Id.

    
Message-driven beanA background worker. The container calls onMessage() when a message arrives. Clients never call it.

    
Delivery active / groupsSwitches that pause and resume MDBs — one bean, or a named group of them.

    
The golden ruleNever new a bean. Let the container inject it with @EJB, or look it up by JNDI.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Using @Stateful for a plain calculationIf the method needs no memory of past calls, use @Stateless.

      
Creating a bean with newLet the container give you one: @EJB, @Inject, or a JNDI lookup.

      
Expecting a stateless bean's field to survive between callsIt will not. Use a stateful bean, the database, or pass the value in each call.

      
A @Singleton without @LockAdd @Lock(WRITE) to anything that changes state, and @Lock(READ) to read-only methods.

      
Forgetting @Remove on a stateful beanWithout it the instance lingers until it times out, wasting memory.

      
Giving an MDB more than one interfaceAn MDB implements only MessageListener, from the JMS API.

      
Assuming the textbook's new DemoExampleBean() client code is realIt is not. It was pseudocode to keep the focus on the method call. Real clients use @EJB or JNDI — see Session 3.
