Session 7 · Messaging, Explained Slowly

This page teaches you what messaging is, why one program leaves a message instead of calling another and waiting, and how to send and receive one in Jakarta EE. You do not need to have heard of a queue, a topic, a broker or JMS before — every new word is explained the moment it appears. When a customer places an order, they should not have to sit and wait while invoices print, stock is reserved and confirmation emails go out. By the end you will know exactly how Jakarta Messaging (JMS) lets a program hand that work off and answer the customer in milliseconds.

Part 1 · Why programs send messages instead of waiting

1.1 The problem: a call makes you wait

Picture a checkout page. The customer clicks Pay. Behind that one click, your program has to charge the card, reserve the stock, generate an invoice and send a confirmation email.

The obvious way is to do them one after another: call the card service and wait for it to answer, then call the stock service and wait, then the invoice service, then the email service. Only when the last one finishes does the customer's page finally respond.

This is a synchronous call. The word just means “at the same time”: the caller and the thing it called are both busy with the same job at the same moment, and the caller does nothing else until the answer comes back.

Two things go wrong:

  • If any step is slow, the customer stares at a spinner for all of them added together.
  • If any step is down, the whole click fails — even the parts that would have worked.
☎️
Analogy A synchronous call is a phone call. You both have to be free at the same moment, you cannot do anything else while you hold the line, and if the other person does not pick up, you got nothing at all.
In plain words

Synchronous means “wait right here for the answer.” It is simple, but it ties the caller's speed — and its success — to everything it calls.

1.2 The fix: leave a message and move on

Here is the whole idea of messaging, and it is this simple:

  1. Instead of calling the card, stock, invoice and email services directly, your program writes down what it wants — “charge $450 to account 8812” — as a message.
  2. It drops that message into a safe holding place and immediately goes back to the customer with “Order submitted.”
  3. Something else picks the message up later and does the work, on its own schedule.

That “later, on its own schedule” is the key word: asynchronous — “not at the same time.” The sender does not wait for the work to finish.

In plain words

Asynchronous means “drop it off and carry on.” The sender is free the instant the message is handed over, no matter how long the actual work takes afterwards.

1.3 The thing in the middle: a broker

So who holds the message between “the sender drops it off” and “a worker picks it up”? A piece of software called a message broker. It receives messages, keeps them safe, sorts them, and hands each one on when a worker is ready.

The general name for middle software like this is Message-Oriented Middleware, almost always shortened to MOM. “Middleware” just means software that sits in the middle, between the programs that talk to each other.

You do not have to install one. In Jakarta EE, the application server already contains a broker. WildFly bundles one called Apache ActiveMQ Artemis (usually just “Artemis”). It is running the moment the server starts.

🏤
Analogy A broker is a post office. You drop your letter in the box and walk away — you do not stand on the recipient's doorstep waiting. The post office holds the letter, sorts it, and delivers it when it can. The recipient need not be home when you send it, and you need not know the route it takes.
In plain words

A broker is the trusted go-between that stores and delivers messages. MOM is just the category of software it belongs to. Because the broker holds the message, the sender and the receiver never have to be busy at the same instant.

Two words you will see on every diagram from here on:

  • A producer is any code that sends a message. (The checkout page, above.)
  • A consumer is any code that receives one. (The background worker that charges the card.)

In Jakarta EE the consumer is very often a message-driven bean — a background bean the container wakes up each time a message arrives. You met message-driven beans in Sessions 1 & 2; here you see where their messages come from.

1.4 So what is Jakarta Messaging (JMS)?

Jakarta Messaging is the standard Java way to talk to a broker. It is a set of interfaces — JMSContext, Queue, Message and a few more — that every compliant broker understands. You write to the standard; the broker does the real work underneath.

Because it is a standard, the same code works whether the broker is Artemis, ActiveMQ or something else — exactly the “learn it once, use it anywhere” idea from Session 1.

⚠️
Two names, one thing: “JMS” and “Jakarta Messaging” The technology was born as the Java Message Service (JMS), and almost everyone still says “JMS” out loud. Its current official name is Jakarta Messaging, and the classes now live in the jakarta.jms package (they used to be javax.jms). Same technology, newer label — just like javax → jakarta in Session 1.

1.5 A direct call versus messaging, side by side

The left column of the table below lists the usual ways one program calls another directly and waits: RMI (one Java program invoking a method on another across the network), RPC (the same idea in general) and REST (calling a web API over HTTP). Three more words appear too — here they are first, in one line each:

  • Blocking — the caller is frozen, doing nothing, until the answer arrives.
  • Coupling — how much one program must know about the other to work.
  • Temporal coupling — “temporal” means to do with time: whether both sides must be running at the same moment.

Now the comparison:

CriteriaSynchronous Calls (RMI / REST / RPC)Asynchronous Messaging (MOM / JMS)
Thread Blocking Blocking: Caller thread hangs until the receiver responds Non-blocking: Producer drops message and returns immediately
Coupling Tight: Caller must know exact host, port, and endpoint URL Loose: Producers and Consumers only know the destination — the named place a message is sent to — and nothing else about each other
Temporal Coupling Both client and server must be online at the exact same millisecond Time-independent: Consumer can be offline; broker buffers messages safely
Traffic Spikes Sudden spikes overwhelm the receiving server and cause HTTP 503 errors Queues absorb spikes seamlessly; consumers drain backlog at a steady rate
In plain words

A direct call is fast and simple when everything is up and quick. Messaging keeps working when a part is slow, overloaded, or temporarily switched off — because the broker holds the backlog and the sender never waits.

Part 2 · One reader, or the whole crowd? Queues versus topics

A message always goes to a named place called a destination. There are two kinds of destination, and choosing between them is the single most important decision in messaging. The kind decides who gets the message.

2.1 A queue: exactly one reader

A queue delivers each message to exactly one consumer. If ten workers are all listening to the same queue, each message is still handed to only one of them. The others never see it. This style has a formal name: Point-to-Point — from one producer to one consumer.

If several workers listen, they share the load: the broker spreads messages across them, one each. That is how you process ten thousand orders quickly — add more workers to the same queue.

🍳
Analogy A queue is the order-ticket rail in a restaurant kitchen. Orders clip onto the rail in a line. Whichever cook is free grabs the next ticket — and each ticket is cooked exactly once. Two cooks never make the same order. Add more cooks and the rail clears faster.

2.2 A topic: everyone who is listening

A topic gives every subscriber its own copy of each message. Send once; everyone tuned in receives it. This style is called Publish/Subscribe (often “pub/sub”): one publisher, many subscribers.

📻
Analogy A topic is a radio station. The DJ plays the song once, and every radio tuned to that frequency hears it at the same time. The station does not care how many are listening — and if your radio is switched off, you simply miss that song.
In plain words

A queue is for work: “somebody — any one of you — do this job once.” A topic is for news: “everybody who cares, here is what just happened.”

2.3 The important difference: what if the reader is offline?

This is where queues and topics part ways most sharply.

  • Queue: if no consumer is available, the message simply waits in the queue until one shows up. Nothing is lost.
  • Topic: if you were not subscribed and online when the message was published, you miss it — just like a radio broadcast — unless you set up a durable subscription, which asks the broker to hold messages for your named subscriber even while it is switched off.
🎧
Analogy A durable subscription turns the live radio broadcast into a podcast subscription: the episodes you missed are kept for you, waiting the next time you open the app.

Here is the full comparison. Keep it for reference — the rows you most need are the first and the third:

FeaturePoint-to-Point — QueuePublish/Subscribe — Topic
Delivery Model One-to-One: Each message is received and processed by exactly one consumer One-to-Many: Every active subscriber gets its own independent copy
Real-World Analogy A physical ticket queue at a bank counter (one customer per teller) A radio broadcast (every receiver tuned in hears the song)
Offline Consumer Message waits safely inside the queue until a consumer boots up Messages are missed by default, unless the consumer uses a Durable Subscription
Typical Use Case Order processing, financial fund transfers, background invoice printing Live stock ticker feeds, breaking news broadcasts, system alert notifications

2.4 How to choose, every time

❓
One question decides it
  • Should exactly one worker do this job? → use a Queue (orders, payments, invoice printing).
  • Should everyone who is interested hear about this event? → use a Topic (price updates, news feeds, system alerts).
⚠️
The trap: using a topic for work that must happen once Put “charge the customer's card” on a topic and every subscriber charges the card — the customer is billed three times. Work that must happen exactly once belongs on a queue. Use a topic only for notifications, where many listeners are the point.

  1. One. A queue delivers each message to exactly one consumer; the broker shares the load across the five, one message each.
  2. Queue: the messages waited safely until the consumer returned. Topic: they were missed — unless it had a durable subscription, which holds them for a named subscriber.

Part 3 · The setup the server does for you, and the easy modern way to send

3.1 You never build the plumbing — the server does

To send a message, your code needs two things:

  • a way to open a connection to the broker, called a ConnectionFactory;
  • the destination itself — the specific Queue or Topic to send to.

You do not create either one. An administrator sets them up ahead of time inside the server and registers each under a name. Objects prepared this way have a name of their own: Administered Objects — literally, “objects an administrator looks after.” Your code just asks for them by name.

Asking “by name” uses the server's naming directory, JNDI — think of it as the server's phone book. The ConnectionFactory is listed under a name like java:/ConnectionFactory, and a queue under something like java:/jms/queue/OrderQueue. (JNDI first appeared in the Session 1 diagram, and gets its own treatment in Session 3.)

🏢
Analogy Administered objects are the fixtures in a serviced office. Before you moved in, the building manager ran a phone line to your desk (the ConnectionFactory — your line to the outside) and bolted a labelled mailbox to the wall (the Destination — where your mail goes). You never lay cable or build mailboxes. You just use the ones already labelled with your name.
In plain words

A ConnectionFactory is your pre-installed line to the broker; a Destination is a pre-made queue or topic. Both are set up by the server in advance, and you fetch them by name instead of building them.

3.2 The old way of sending, and the new way

Messaging has been in Java a long time, and the way you write it changed dramatically.

In the first version — the Classic API (JMS 1.1) — sending a single message was a chore. You had to create a Connection, then open a Session from it, then make a MessageProducer, send, and then carefully close every one of those objects in a finally block, wrapped in nested try/catch. Forget one close() and you leaked a resource.

The modern Simplified API (JMS 2.0+, Jakarta Messaging) folds all of that into a single object: JMSContext. One object replaces the old Connection and Session, it closes itself automatically, and when the container injects it, even the closing is handled for you.

🚗
Analogy The classic API is a manual car: clutch, gears, and you must work them in the right order or stall. JMSContext is an automatic: one pedal, and the car coordinates the gearbox for you. Same journey, far less to get wrong.
In plain words

Old JMS made you assemble and tidy up four or five objects by hand. Modern JMS gives you one — JMSContext — that does the assembling and the tidying itself.

3.3 The code: a modern message producer

Now that you know the pieces — a factory, a destination, and a JMSContext — here is a complete producer. It is an ordinary @Stateless bean (from Sessions 1 & 2) that submits an order onto a queue. Read the three numbered comments, then the explanation below.

OrderProducer.java — a modern producer using JMSContext
package com.globalbank.messaging;

import jakarta.annotation.Resource;
import jakarta.ejb.Stateless;
import jakarta.inject.Inject;
import jakarta.jms.JMSConnectionFactory;
import jakarta.jms.JMSContext;
import jakarta.jms.Queue;

@Stateless
public class OrderProducer {

    // ① The container injects a managed JMSContext automatically
    @Inject
    @JMSConnectionFactory("java:/ConnectionFactory")
    private JMSContext jmsContext;

    // ② Inject the pre-configured JNDI Queue administered object
    @Resource(lookup = "java:/jms/queue/OrderQueue")
    private Queue orderQueue;

    public void submitOrder(String orderXml) {
        // ③ Send in one fluent, clean line!
        jmsContext.createProducer()
                  .setProperty("priorityLevel", "HIGH")
                  .send(orderQueue, orderXml);

        System.out.println("Order submitted asynchronously. Producer thread freed immediately.");
    }
}

What each numbered line is doing:

  • ① @Inject @JMSConnectionFactory("java:/ConnectionFactory") asks the container for a ready-to-use JMSContext, already wired to that factory. You do not create it, start it, or close it.
  • ② @Resource(lookup = "java:/jms/queue/OrderQueue") looks the pre-made queue up in JNDI by name and drops it into your field — an administered object, injected.
  • ③ createProducer().setProperty(...).send(...) is one fluent line: each call returns something you can call the next method on, so making a producer, tagging the message, and sending it read as a single sentence.
🔑
The one thing to notice There is no new, no connection.start(), and no close() anywhere. The container injected a managed JMSContext and will close it when the method ends. It is the same deal as beans in Session 1 — you never create the plumbing; you ask for it.

3.4 The other half: the bean that receives the message

A producer with nobody listening is a letter posted into an empty room. The receiving side is called a message-driven bean (MDB), and it is the third kind of enterprise bean — alongside @Stateless and @Stateful from Sessions 1–2 and the @Singleton from Session 4.

In plain words

A message-driven bean is a bean with no client and no interface. Nobody calls its methods. Instead, the container watches a destination, and the moment a message arrives it calls one method on your bean: onMessage. You never write the loop that waits for messages — that is the container's job, and it is the whole reason MDBs exist.

OrderProcessor.java — a message-driven bean
package com.globalbank.messaging;

import jakarta.ejb.ActivationConfigProperty;
import jakarta.ejb.MessageDriven;
import jakarta.jms.JMSException;
import jakarta.jms.Message;
import jakarta.jms.MessageListener;
import jakarta.jms.TextMessage;

// ① @MessageDriven says "I am a listener, not a servant waiting to be called".
@MessageDriven(activationConfig = {

    // ② Which destination to watch. This is the same lookup name the producer sent to.
    @ActivationConfigProperty(propertyName  = "destinationLookup",
                              propertyValue = "java:/jms/queue/OrderQueue"),

    // ③ What kind of destination it is — a Queue (one reader) or a Topic (all readers).
    @ActivationConfigProperty(propertyName  = "destinationType",
                              propertyValue = "jakarta.jms.Queue")
})
public class OrderProcessor implements MessageListener {

    // ④ The one method the container calls, once per message.
    @Override
    public void onMessage(Message message) {
        try {
            if (message instanceof TextMessage text) {
                String orderXml = text.getText();
                System.out.println("Order received and being processed: " + orderXml);
                // ... do the real work here: save the order, email a receipt, ...
            }
        } catch (JMSException e) {
            // Throwing tells the container the message was NOT handled.
            // What happens next is Section 4.2 — acknowledgement.
            throw new RuntimeException("Could not read the order message", e);
        }
    }
}

Four things to notice, because they are what make an MDB unlike any bean you have written so far:

  • ① No interface, and no client. There is no OrderProcessorRemote, and nothing anywhere calls onMessage. The container does. This is why an MDB cannot be reached by JNDI lookup the way the beans in Session 6 could — there is nothing to look up.
  • ② destinationLookup is the same name the producer sent to. That string is the entire connection between the two classes. Nothing imports the other, and neither one knows the other exists. That is the point of messaging: you can rewrite, redeploy or replace either side without touching the other.
  • ③ destinationType decides the delivery rule you met in Part 2. Say jakarta.jms.Queue and exactly one MDB instance gets each message — deploy three instances of this class and the work is shared out between them, which is how you scale. Say jakarta.jms.Topic and every listener gets a copy.
  • ④ onMessage is the only method. No annotations on it, no business interface. The container calls it on a thread it manages, inside a transaction it started (Session 10), and if it throws, the container treats the message as unhandled.
📬
Analogy — the producer posts, the MDB has a mailbox The producer is somebody dropping a letter into a post box. The MDB is not a person you phone — it is a mailbox with a rule attached: “whenever a letter lands in me, do this.” Nobody waits at the box. The postal service (the container) delivers, and the rule runs when it runs. That is what asynchronous means, and it is why the producer's thread was freed immediately back in Section 3.3.
💡
Try it yourself Start WildFly, deploy a project containing both classes above, then send one order from the producer. You will see the producer's line print immediately, and the MDB's line print a moment later — on a different thread, in a different transaction, with nothing in the producer's code waiting for it. If you would rather watch this before building it, Section 4.4 has a full replay.

Part 4 · What a message is made of, and how to get an answer back

4.1 Every message has three parts

A JMS message is not just a blob of text. It has three parts, and knowing them explains almost everything the broker can do.

✉️
Analogy A message is a posted envelope. The printed address and postmark on the outside are the headers — the postal system reads them to route and track it. The sticky labels you add, like “FRAGILE” or “PRIORITY”, are the properties — sorters act on them without opening anything. The letter folded inside is the body — the actual message.

Here is the same three-part structure as the exam states it:

SectionContentsPurpose
1. Headers JMSMessageID, JMSDeliveryMode, JMSTimestamp, JMSReplyTo, JMSCorrelationID Standard routing metadata used by the broker.
2. Properties Custom key-value pairs (e.g., region="EMEA", amount=450.00) Enables consumers to filter messages without deserializing the body using a message selector — a broker-side filter (SQL-92 syntax).
3. Body (Payload) TextMessage, MapMessage, ObjectMessage, BytesMessage, StreamMessage The actual data payload transported across systems.

The point of properties is worth a sentence on its own. Because they sit on the outside of the “envelope,” a consumer can ask the broker for only the messages it cares about — “just the ones where amount > 400” — without opening and parsing every body. That filter string is called a message selector, and it is written in a SQL-like syntax (SQL-92).

In plain words

Headers are the system's routing info, properties are your own labels for filtering, and the body is the real content. Put anything you want to filter on into a property, not buried in the body.

4.2 How the broker knows a message was handled: acknowledgement

When a consumer finishes with a message, it sends an acknowledgement — a quiet “got it, you can delete it now” back to the broker. Until that happens, the broker keeps the message; if the consumer crashes before acknowledging, the broker redelivers it, so work is not silently lost.

📦
Analogy Acknowledgement is signing for a parcel. The courier will not mark it delivered — and will try again — until someone signs. Your signature is the acknowledgement.
In plain words

Acknowledgement is the receiver confirming “done.” It is what makes a queue reliable: a message is only forgotten once someone has actually handled it. The exact acknowledgement modes are listed in the Reference section at the end.

4.3 Getting an answer back: the Request-Reply pattern

Messaging is one-way by nature: send, and move on. But sometimes you really do need the answer — “get me account summary 1001.” How do you get a reply without going back to a blocking, synchronous call?

The trick uses two of the headers from the table above. Here is the whole dance:

  1. Make a private reply mailbox

    The sender creates a temporary queue — a short-lived queue that exists just for this one exchange and disappears afterwards.

  2. Say where to reply

    The sender puts that reply queue into the message's JMSReplyTo header, so the receiver knows exactly where to send its answer.

  3. Keep a reference number

    After sending, the sender reads the message's unique JMSMessageID and keeps it as a correlation id — its reference number for this request.

  4. Listen for the matching answer only

    The sender waits on the reply queue with a selector that says JMSCorrelationID = '…', so it picks up only the reply that belongs to its request — not some other request's answer flying past.

On the other side, the responder copies the request's JMSMessageID into the reply's JMSCorrelationID and sends it to the JMSReplyTo destination. Here is the sender's half in code:

Request-Reply with JMSReplyTo & JMSCorrelationID
// SENDER (Client):
TemporaryQueue replyQueue = jmsContext.createTemporaryQueue();
JMSProducer producer = jmsContext.createProducer();

TextMessage requestMsg = jmsContext.createTextMessage("GET_ACCOUNT_SUMMARY: 1001");
requestMsg.setJMSReplyTo(replyQueue); // Tell receiver where to answer

producer.send(orderQueue, requestMsg);
String correlationId = requestMsg.getJMSMessageID(); // Unique request token

// Wait on the private temporary reply queue for the specific response
JMSConsumer replyConsumer = jmsContext.createConsumer(replyQueue,
    "JMSCorrelationID = '" + correlationId + "'");
String response = replyConsumer.receiveBody(String.class, 5000); // 5s timeout
🎟️
The one thing to notice Two headers do all the work. JMSReplyTo is the self-addressed envelope — it tells the responder where to send the answer. JMSCorrelationID is the cloakroom ticket — the number that lets the sender match the returning answer to the request it belongs to, even with hundreds in flight at once.

Classic API (JMS 1.1)Simplified API (JMS 2.0+)What changed

      
        
ConnectionFactoryConnectionFactoryUnchanged — still the starting point, usually injected.

        
Connection + Session (created separately)JMSContextOne object now does the job of both.

        
MessageProducerJMSProducerCreated from the context; supports fluent method-chaining.

        
MessageConsumerJMSConsumerCreated from the context.

        
Call connection.start() by handAutomaticThe context starts delivery for you.

        
Close each object in a finally blockAutoCloseableUse try-with-resources, or let the container close it.

      
    

  


  

    📦 The five message body types
    
The body is the payload. JMS defines five shapes for it; pick the one that matches your
      data. TextMessage is by far the most common.

    

      
Body typeCarriesUse it for

      
        
TextMessageA single StringPlain text, JSON or XML payloads. The usual choice.

        
MapMessageName/value pairs, like a MapA handful of named fields without defining a class.

        
ObjectMessageA serialized Java objectSending a whole Serializable Java object.

        
BytesMessageA stream of raw bytesBinary data — images, files, custom formats.

        
StreamMessageA sequence of primitive valuesReading values back in the exact order they were written.

      
    

  


  

    🏷️ Standard message headers
    
Headers are routing and tracking fields. The broker sets most of them; a few you set yourself
      (notably JMSReplyTo). These are the ones named in this session:

    

      
HeaderWhat it holds

      
        
JMSMessageIDA unique id the broker assigns to every message — the “reference number” used in request-reply.

        
JMSDeliveryModePERSISTENT (saved to disk, survives a broker restart) or NON_PERSISTENT (faster, kept in memory, can be lost).

        
JMSTimestampThe time the broker accepted the message.

        
JMSReplyToA destination where the receiver should send its reply. You set this.

        
JMSCorrelationIDLinks a reply back to the request it answers — usually a copy of the request's JMSMessageID.

      
    

    
Other standard headers exist too — JMSDestination, JMSPriority,
      JMSExpiration and JMSRedelivered among them — but the five above are the
      ones this session uses.

  


  

    🔎 Message properties & selectors
    
Properties are your own key/value labels on a message, such as
      region = "EMEA" or amount = 450.00. A consumer can tell the broker to
      deliver only the messages whose properties match a filter, called a message
      selector, written in a SQL-92-like syntax:

    

      
Selector exampleMeans “deliver only messages where…”

      
        
amount > 400the amount property is over 400.

        
region = 'EMEA' AND priorityLevel = 'HIGH'both named properties match.

        
JMSCorrelationID = 'ID:123'the correlation id equals that value (as used in request-reply).

      
    

  


  

    ✅ Acknowledgement modes
    
An acknowledgement is the consumer confirming it has handled a message, so the
      broker can stop tracking it. The mode decides when and how that confirmation happens:

    

      
ModeWhat it does

      
        
AUTO_ACKNOWLEDGEThe session acknowledges automatically once the message has been received and handled. The common default.

        
CLIENT_ACKNOWLEDGEYour code decides, by calling message.acknowledge() explicitly.

        
DUPS_OK_ACKNOWLEDGELazy acknowledgement — faster, but a message may occasionally be delivered twice, so the consumer must tolerate duplicates.

        
Transacted sessionAcknowledgement is tied to a transaction: messages are confirmed only when the transaction commits, and redelivered if it rolls back.

      
    

    
If a consumer fails before acknowledging, the broker redelivers the message —
      which is why messaging can promise that work is not silently lost.

  


  


  

  recap
  
One-line summary of everything

  

    
MessagingOne program leaves a message and moves on; another handles it later. The sender never waits.

    
Synchronous vs asynchronousSynchronous = wait right here for the answer. Asynchronous = drop it off and carry on.

    
Broker / MOMThe “post office” in the middle that stores and delivers messages. WildFly bundles Apache ActiveMQ Artemis.

    
Jakarta Messaging (JMS)The standard Java API for talking to a broker; classes live in jakarta.jms.

    
Queue (Point-to-Point)Each message goes to exactly one consumer. For work that must happen once.

    
Topic (Publish/Subscribe)Every subscriber gets its own copy. For news and notifications. Offline readers need a durable subscription.

    
Administered objectsConnectionFactory (your line to the broker) and Destination (the queue/topic), set up by the server and found by JNDI name.

    
JMSContextThe modern Simplified API: one self-closing object replaces the classic Connection + Session.

    
ProducerAn ordinary @Stateless bean that injects a JMSContext and a destination, then sends. Frees its thread immediately.

    
Consumer — the message-driven bean@MessageDriven + destinationLookup, implementing MessageListener. No client, no interface: the container watches the destination and calls onMessage once per message.

    
Message partsHeaders (routing), Properties (your labels, for selectors), Body (the payload).

    
AcknowledgementThe consumer's “got it” that lets the broker forget a message; unacknowledged messages are redelivered.

    
Request-ReplyJMSReplyTo says where to answer; JMSCorrelationID matches the answer to the request.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Using a topic for work that must happen once (e.g. charging a card)Use a queue — exactly one consumer handles each message.

      
Expecting a plain topic to hold messages for an offline subscriberA topic drops messages for absent subscribers. Use a durable subscription, or a queue.

      
Writing classic JMS 1.1 boilerplate — Connection, Session, manual close()Inject a JMSContext and let it (and the container) handle creation and closing.

      
Creating a ConnectionFactory or queue with newThey are administered objects — inject them (@Inject, @Resource) or look them up by JNDI name.

      
Burying filterable data inside the message bodyPut it in a property so a message selector can filter on it without parsing the body.

      
Blocking on a reply by holding a synchronous call openUse Request-Reply: a temporary reply queue plus JMSReplyTo and JMSCorrelationID.

      
Assuming a message is safe the moment it is receivedIt is safe once acknowledged. Until then the broker may redeliver it — design consumers to cope.

      
Trying to give a message-driven bean a business interface or a JNDI nameNobody calls an MDB. It has no client — the container watches the destination and calls onMessage. The only two things that must match are destinationLookup here and the destination the producer sends to.

      
Swallowing an exception inside onMessageLet it propagate. Throwing is how you tell the container the message was not handled, which is what triggers redelivery instead of silent data loss.
