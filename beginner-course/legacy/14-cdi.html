Unit 14 · CDI — injection & scopes

You’ve used @Inject and @Named in nearly every unit without a proper introduction. CDI (Contexts and Dependency Injection) is the wiring layer that decides which object fills an injection point and how long it lives.

↩︎
Recap “Inject” = the container fills a field with a ready object so you don’t call new (Unit 00). CDI is the machinery that does it.
concept

The basics

Any suitable class is a “CDI bean”. Ask for one with @Inject; CDI finds a matching type, creates it (respecting its scope), and hands it over.

public class GreetingService {
    public String greet(String name) { return "Hello, " + name; }
}

@Path("/hello")
public class HelloResource {
    @Inject GreetingService greeting;              // CDI supplies it

    @GET public String hi() { return greeting.greet("world"); }
}

A near-empty src/main/webapp/WEB-INF/beans.xml (or META-INF/beans.xml) switches CDI on for the module.

concept

Scopes — how long an injected bean lives

ScopeOne instance per…Use for
@RequestScopedone HTTP requestForm-backing beans, per-request state
@SessionScopedone browser session (needs Serializable)Logged-in user, cart
@ApplicationScopedthe whole applicationCaches, config, stateless helpers
@Dependent (default)its injection point — lives and dies with its ownerSmall helpers with no state of their own
@ConversationScopeda developer-controlled multi-page conversationWizards spanning several pages
✦
Scope is the whole point Inject a @SessionScoped cart into a @RequestScoped controller and each request automatically gets this user’s cart. CDI routes every injection to the right instance for the current context.

@Inject vs @EJB

@Inject (CDI)@EJB (EJB)
InjectsAny CDI bean, including EJBsOnly enterprise beans
Understands CDI scopes/qualifiersYesNo
Works in plain (non-EJB) classesYesLimited
Today’s advicePrefer it almost everywhereLegacy; still fine for remote EJB lookups

Modern style: annotate session beans as usual (@Stateless …) but inject them with @Inject.

concept

Qualifiers — when one type isn’t enough

Two implementations of the same interface? Tell CDI which one with a custom qualifier annotation:

@Qualifier @Retention(RUNTIME) @Target({FIELD, PARAMETER, TYPE})
public @interface Sms {}

public interface Notifier { void send(String to, String msg); }

@Sms   public class SmsNotifier   implements Notifier { ... }
@Email public class EmailNotifier implements Notifier { ... }

public class AlertService {
    @Inject @Sms Notifier notifier;         // unambiguous now
}
concept

Producers — inject things you don’t own

Need to inject a value or a third-party object that has no annotations? A @Produces method turns any return value into something injectable:

@ApplicationScoped
public class Config {
    @Produces @MaxTransfer
    public double maxTransfer() { return 50_000.0; }
}

public class TransferBean {
    @Inject @MaxTransfer double limit;       // gets 50000.0
}
concept

CDI events (decoupled notifications)

// fire
@Inject Event<AccountFunded> funded;
funded.fire(new AccountFunded(accountId, amount));

// observe — anywhere, no registration
public void onFunded(@Observes AccountFunded e) {
    sms.send(e.customer(), "Your account was credited.");
}

The firer doesn’t know who’s listening. Same Observer pattern the original Session 4 notes used for NotificationBean.
