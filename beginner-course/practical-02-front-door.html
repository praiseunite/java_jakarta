Practical 2 · The Front Door

Practical 1 built a bank that only a URL could reach. This one gives it a page a person can use — and then adds the four things that only start to matter once something outside your application is talking to it: a program on your laptop that calls the beans directly, a queue that does work while nobody is waiting, a form that checks itself before the bank ever sees it, and an audit log that survives a rollback. That last one is the single most surprising thing in the course, and by the end of Part 4 you will have watched it happen.

✓
Four promises before we start
  1. Nothing from Practical 1 is thrown away. Same entities, same AccountService, same database, same three seeded accounts. This project is the last one plus more files.
  2. There is still nothing to install. No database, no message broker. WildFly ships both an in-memory database and Artemis, its message broker, and this project is configured to use them.
  3. The queue creates itself. Messaging normally begins with an administrator running a command to make a queue. You will not run one — the queue is declared in the Java code, and the container builds it at deploy time.
  4. You will see a rule break, and then understand why it exists. You will watch an audit line outlive the transaction that wrote it, and then switch the rule off and watch it vanish.

concept

Part 1 · What you are building

Practical 1's bank answered plain text at a URL. That works for testing and it is hopeless for a customer. A real application needs a page: boxes to type in, a button to press, and an answer that appears without anybody editing an address bar.

This practical adds that page — and every other part of Jakarta EE that only becomes relevant once something outside your application is involved. Three different outsiders, in fact:

The outsiderHow it reaches the bankPart
A person with a browserA Facelets page, backed by a CDI beanParts 3–4
Another program on your machineA @Remote interface over the networkPart 6
Nothing at all — the work waitsA message queue and a message-driven beanPart 5
In plain words

A Facelet is an ordinary HTML page with holes in it. Where a value goes, you write #{something} instead of typing the value, and the server fills the holes in before sending the page. That is the whole idea. It is not a new language to learn — it is HTML plus placeholders.

In plain words

A backing bean is the Java object behind a page. The page asks it questions (#{bank.accounts} calls getAccounts()) and tells it what happened (#{bank.submit} calls submit()). You never write the connection between the two — you give the bean a name with @Named and use that name in the page.

In plain words

A message-driven bean is the only bean in this entire course that nobody calls. Every other bean waits to be asked. This one is told: the container watches a queue, and when something arrives it wakes the bean up on a thread of its own. There is no request, no user and no browser involved.

In plain words

A remote interface is a promise published on the network. Mark an interface @Remote and any Java program that can reach the server may call its methods as if the object were local. It cannot be local, of course — every argument is copied, posted, and rebuilt on the far side — but the code that calls it does not have to know that.

🚪
The analogy: a bank branch gets a lobby

Practical 1 was a bank with no lobby. You could get money moved, but only by shouting the exact right instructions through a letterbox — which is roughly what ?action=transfer&id=1001&to=1002&amount=100.00 is.

This practical builds the lobby. A counter with a form on it (the Facelets page), a clerk who reads the form and decides what it means (the backing bean), a clerk at the door who refuses forms that are filled in wrongly before they reach the counter (bean validation), a back office where paperwork waits to be processed when somebody is free (the queue and the message-driven bean), and a driver who can phone the branch from outside the building and speak to the same clerks (the remote client).

The clerks are the same people as before. AccountService has not changed its job — it has just acquired four new ways to be reached.

What changed in Practical 1's files

Three files, five small changes. It is worth knowing exactly what moved, because "the same project plus more" is only true if you can see the joins:

FileChangeWhy
AccountService implements AccountServiceRemote The methods were already the right shape. Adding the interface is what publishes them to the outside world.
AccountService.findAll() wraps its result in new ArrayList<>(…) A remote call has to serialise the list. A JPA provider's List is not guaranteed to be serialisable; a plain ArrayList is.
AccountService new method transferOrRefuse(…) A refusal that is thrown poisons the transaction. A message-driven bean needs one that is returned. Part 5 is entirely about this.
AccountServlet new ?action=raw case So the same rows can be read a second way, with hand-written SQL, side by side with JPA.
persistence.xml <class>…AuditEntry</class> JPA has to be told the new table exists.

  2. The page will show #{bank.accounts}. Where in the Java code is the method that answers that?

Show answers

  2. In AccountsBean.getAccounts(). The name bank comes from @Named("bank") on the class, and accounts is the property behind getAccounts(). The page never names the class.
  3. Because the list now has to survive being turned into bytes, sent, and rebuilt. JPA's List happens to be an ArrayList with Hibernate; the point is that nothing guarantees it, and the copy costs one small object.
  4. The queue. Work sitting on a queue has nobody waiting for it — it is processed whenever the container gets round to it, which may be after the user has closed the browser.

Part 3 · A page a person can use


  
The whole front door is two files: accounts.xhtml, which is HTML with holes in it, and
    AccountsBean.java, which fills them. Read them together — neither makes sense alone.


  
In plain words
    
@ViewScoped decides how long the bean lives. A scope is a lifetime:
      the container creates the object when the page opens and throws it away when you leave. Compare the
      two you have now met:

    
    
      
  • @SessionScoped (Session 5) — lives until the browser closes. Two tabs share
        one object, and yesterday's half-typed form is still in memory.
    • 
      
  • @ViewScoped (this bean) — lives until you leave this page. Each tab gets
        its own, and the memory is released when you navigate away.
    • 
    

    
For a form like this one, the data belongs to the page rather than to the person, so view scope is
      the honest choice.

In plain words
    
Declarative means you state the rule instead of running it.
      Writing if (amount == null || amount.signum() <= 0) throw … is imperative — you are
      performing the check. Writing @DecimalMin("0.01") on the field is declarative — you are
      describing what a valid value looks like, and letting something else do the checking.

    
Bean Validation is declarative, and that is why the same rule is enforced by the web page, by the
      EJB container, and by JPA before an INSERT — without you repeating it once.

  


  
⚠️
    
The trap in the cross-field rule
      
Four of those five rules sit on a single field. The fifth — "money cannot be sent from an account
        to itself" — mentions two fields, and no annotation can express that. So it is written as
        a method returning boolean, named like a property, marked @AssertTrue.

      
Here is the trap. A brand-new form has both fields at zero, so
        fromAccount == toAccount is true — and the rule would fail, greeting every visitor
        with "you cannot transfer from an account to itself" before they had typed anything. Open
        TransferRequest.isAccountsDiffer() and read the first line of the condition. Guarding
        against the untouched form is part of writing the rule, not a way of cheating it.

Part 4 · The line that should not exist


  
Part 3 left you with a puzzle. A transfer was refused, and the transaction that attempted it was
    rolled back. Yet the record of the refusal is sitting in the database.


  
Roll that back in your head, because it is genuinely strange. A transaction is supposed to be
    all-or-nothing. Everything that happened inside it should have been undone. The audit line was written
    inside it. So the audit line should be gone.


  
Open ejb/AuditService.java and look at the annotation on record():


  
@TransactionAttribute(TransactionAttributeType.REQUIRES_NEW)
public void record(String action, String outcome, String detail) {
    em.persist(new AuditEntry(action, outcome, detail));
}


  
🔑
    
What REQUIRES_NEW means
      
It is the container being told:

      

        "Suspend whatever transaction the caller is in. Start a brand new one for me. Commit mine when
        I finish, and then resume theirs."

      
So the audit line is committed on its own, before the transfer it describes has
        succeeded or failed. When the transfer later rolls back, the audit line is in a different
        transaction that has already committed, and nothing can reach it.

    

  


  
Compare the alternatives, because the difference between them is exactly what Session 10 is about:


  

    
AttributeWhat happensRight for an audit log?

    
      

        REQUIRED (the default)
        Joins the caller's transaction
        No. A rollback erases the audit line along with the transfer — including the refusals,
          which are the most valuable lines in the log
      

      

        REQUIRES_NEW
        Suspends the caller's, runs in its own, commits independently
        Yes. This is the textbook example of the attribute
      

      

        MANDATORY
        Refuses to run unless the caller already has a transaction
        No — but useful for "this must never run outside a transaction" rules
      

    
  


  
📝
    
The analogy: the incident book
      
Think of a workshop with an incident book bolted to the wall, and a rule that
        says: whoever tries a risky job must write it in the book first, then do the job.

      
If the job succeeds, the entry says so. If the job goes wrong and everything is undone, the
        job is undone — but the book entry is not, because writing in the book was its own
        separate act, finished before the job started.

      
That is exactly the relationship between AuditService and
        AccountService. One writes the record in its own transaction; the other does the work
        in its own. Neither can undo the other.

      
And the entry that matters most is the one describing the job that failed — which is
        precisely the entry a normal transaction would throw away.

    3. 

  


  
🚨
    
Why a thrown refusal breaks the queue
      
Open AccountService.transferOrRefuse() and read its comment. Here is the problem it
        exists to solve.

      
An MDB method runs inside a container-managed transaction, and the message acknowledgement is
        part of that transaction. That gives you a guarantee you want: if
        onMessage throws, the transaction rolls back and the message comes back.
        A crash never loses a transfer.

      
Now the mirror image. AccountService.transfer() throws
        InsufficientFundsException, and that exception is marked
        @ApplicationException(rollback = true). The instant it leaves a bean method, the
        container marks the current transaction rollback-only — and no catch block anywhere can
        undo that. So a message-driven bean that catches the refusal still sees its transaction
        roll back, which means the message is delivered again. And again. A refusal that can never succeed
        loops until the broker gives up.

      
transferOrRefuse() refuses by returning a sentence instead of throwing. A
        returned value is a success, so the transaction commits and the message is acknowledged.

      
Choosing which failures to throw and which to return is the whole skill of writing a
        message-driven bean. It is also a lesson that only makes sense once you have watched the
        alternative loop.

    

  


  
The two names of one queue

  
There is one detail in TransferQueueSender worth stopping on, because mixing these two
    names up is the most common messaging mistake there is:


  

    
NameWhat it isWhere you use it

    
      

        java:jboss/exported/jms/queue/TransferQueue
        The JNDI name — how code finds the queue. The exported part means "visible
          to clients outside the server"
        In the @JMSDestinationDefinition, which asks the container to create it
      

      

        java:/jms/queue/TransferQueue
        The same queue under its shorter internal name. WildFly publishes both
        In the @Resource(lookup = …) and in the MDB's
          destinationLookup
      

      

        TransferQueue
        The physical name — what the queue is called inside the broker
        In destinationName, and when you go looking in Artemis
      

    
  


  
Session 7 taught that a queue must exist before you can look it up — and that is still true. What is
    new here is that the application can now state the requirement itself instead of relying on
    somebody having run a CLI command first. @JMSDestinationDefinition is that statement, and
    the container honours it at deploy time, before anything is injected.

          is what the queue is called inside the broker. Having one name for both would be convenient
          right up until you needed to point two JNDI names at the same physical queue.

In plain words
    
JNDI is a phone book for objects. You do not create the thing you want and you do
      not hold a reference to it — you ask a directory for it by name and get back something you can use.
      Session 6 introduced it; here is what the name actually looks like:

    
ejb:/globalbank-web/AccountService!com.globalbank.ejb.AccountServiceRemote
     └── module ──┘ └── bean ──┘ └──────── interface ────────┘

    
Read it as a sentence: an enterprise bean, in the module called globalbank-web, the
      bean class AccountService, seen through this interface. The ! matters
      — a bean can have several interfaces, and the lookup has to say which one you want.

  


  
⚠️
    
Do not "fix" the javax imports
      
Open RemoteClient.java and you will see
        import javax.naming.InitialContext;. This is correct, and it is not a leftover from
        before the rename.

      
Jakarta EE 9 renamed the Enterprise Edition specifications from javax to
        jakarta. JNDI and JDBC belong to Java SE, not to Jakarta EE, and kept their names. So
        javax.naming.* and javax.sql.DataSource are right, and an IDE that
        "helpfully" offers to rewrite them is wrong.

  1. Why does the client need the interface but not the bean class?

Part 7 · Break it on purpose, and learn why the rules exist


  
Every rule you met in this practical has an obvious-looking shortcut that breaks it. This part takes
    the two best ones and breaks them, so you can see the failure instead of taking it on trust.


  
    

    
  1. 
      
    Break the audit log
    
      
    In ejb/AuditService.java, change the annotation on record() from
        REQUIRES_NEW to REQUIRED — the default. Rebuild, redeploy, and make a
        transfer the bank will refuse.
    
      
    You should see the refusal reported on the page, and
        the audit log unchanged. The line recording what happened is gone, because it
        joined the transfer's transaction and rolled back with it.
    
      
    Now make a transfer that succeeds. That one is logged.
    
      
    ⚠️
        
    That combination is the dangerous one. An audit log that shows successes
          and silently omits refusals looks complete. You would never notice the missing lines
          unless you went looking for a specific one — which is exactly what an investigation does.
    
      
    
      
    Put it back to REQUIRES_NEW before you continue.
    
    
    2. 

    
  2. 
      
    Break the queue
    
      
    In messaging/TransferMDB.java, change the call from
        service.transferOrRefuse(from, to, amount) to
        service.transfer(from, to, amount). Rebuild, redeploy, and queue a transfer you know
        will be refused.
    
      
    You should see the same audit line appear over and over in the server log, and
        WildFly reporting redelivery attempts in the console. The message is being delivered, refused,
        rolled back, and delivered again — because a thrown
        @ApplicationException(rollback = true) dooms the transaction, and catching it in
        onMessage cannot undo that.
    
      
    This is what a poison message looks like in production: one bad message that
        occupies a worker forever. WildFly will retry a fixed number of times and then park it on a dead
        letter queue.
    
      
    Put it back to transferOrRefuse.
    
    
    3. 

    
  3. 
      
    See what JPA was doing for you
    
      
    Open these two side by side in two browser tabs:
    
      
    http://localhost:8080/globalbank-web/account?action=all
http://localhost:8080/globalbank-web/account?action=raw
    
      
    You should see the same rows twice. The second one is RawAccountDao,
        which opens a pooled DataSource, writes
        SELECT id, holder, balance, version FROM accounts by hand, and maps the result itself
        with rs.getInt and rs.getString.
    
      
    Put the two side by side. Everything JPA saves you is the difference between them — and the one
        string it had been hiding from you all along,
        java:jboss/datasources/ExampleDS, is now visible in two places at once.
    
      
    Then open RawAccountDao and find the try ( block. Look at what happens
        when you close() a connection you got from a pool: you are not closing it, you are
        giving it back. Leaking one is a slow-motion outage — the pool empties and the
        application stops answering.
    
    
    4. 

  


  
➡️
    
Restore everything before Practical 3
      Both files should be back as they were: REQUIRES_NEW on
      AuditService.record(), and transferOrRefuse in
      TransferMDB.onMessage(). Rebuild and redeploy once more, and confirm a refused queued
      transfer produces exactly one audit line. Practical 3 starts from this state — do not leave a
      deliberate bug in place.

  


  
Checkpoint 7 · the quiz comes next
    
    
      
  1. With REQUIRED on record(), why were successful transfers still logged?
    2. 
      
  2. Why does catching the exception inside onMessage fail to stop the redelivery?
    3.

  1. Because a successful transfer's transaction committed, and the audit write was part

    2.

          closed — which is the entire reason a pool is fast.

web/TransferRequest.java — the form and its rules, with no checking
      code anywhere.

    
public class TransferRequest implements Serializable {

    @Min(value = 1000, message = "Account numbers have at least 4 digits")
    @Max(value = 9999, message = "Account numbers have at most 4 digits")
    private int fromAccount;

    @NotNull(message = "Enter an amount")
    @DecimalMin(value = "0.01", message = "The smallest transfer is 0.01")
    @Digits(integer = 10, fraction = 2, message = "Money has at most 2 decimal places")
    private BigDecimal amount = new BigDecimal("10.00");

    @NotBlank(message = "Every transfer needs a reference")
    @Size(max = 40, message = "Keep the reference under 40 characters")
    private String reference = "web transfer";

    /** Two fields at once — no single-field annotation can express this. */
    @AssertTrue(message = "Money cannot be sent from an account to itself")
    public boolean isAccountsDiffer() {
        // The guard matters: an untouched form has both fields at zero, and
        // without it every visitor would be told off before typing anything.
        return fromAccount == 0 || toAccount == 0 || fromAccount != toAccount;
    }
}

    
Nothing here checks anything. That is the point of declarative validation: you state what a valid
      request looks like, and the web page, the EJB container and JPA all enforce it for you — from this
      one description.


    
ejb/AuditService.java — the transaction that has to survive.

    
@Stateless
public class AuditService {

    @PersistenceContext
    private EntityManager em;

    @TransactionAttribute(TransactionAttributeType.REQUIRES_NEW)
    public void record(String action, String outcome, String detail) {
        em.persist(new AuditEntry(action, outcome, detail));
    }

    public List<AuditEntry> recent() {
        return em.createQuery("SELECT a FROM AuditEntry a ORDER BY a.id DESC", AuditEntry.class)
                 .setMaxResults(25)
                 .getResultList();
    }
}

    
One annotation, and an audit line that a rolled-back transfer cannot erase. Note also that
      recent() is deliberately capped — an audit log grows forever, and a page that tried to
      show all of it would fall over.


    
messaging/TransferMDB.java — the bean nobody calls.

    
@MessageDriven(activationConfig = {
        @ActivationConfigProperty(propertyName = "destinationLookup",
                                  propertyValue = "java:/jms/queue/TransferQueue"),
        @ActivationConfigProperty(propertyName = "destinationType",
                                  propertyValue = "jakarta.jms.Queue")
})
public class TransferMDB implements MessageListener {

    @EJB private AccountService service;
    @EJB private AuditService audit;

    @Override
    public void onMessage(Message message) {
        String body = message.getBody(String.class);        // "from:to:amount"
        String[] parts = body.split(":");
        // …
        String receipt = service.transferOrRefuse(from, to, amount);
        audit.record("QUEUED-TRANSFER", receipt.startsWith("REFUSED") ? "REFUSED" : "OK", receipt);
    }
}

    
Two things to notice. onMessage cannot declare a checked exception — the
      MessageListener interface does not allow it — so failures must be handled here or
      turned into runtime ones. And the refusal is returned, not thrown, so the transaction
      commits and the message is acknowledged.


    
dao/RawAccountDao.java — the SQL JPA was writing for you.

    
@Stateless
public class RawAccountDao {

    @Resource(lookup = "java:jboss/datasources/ExampleDS")
    private DataSource dataSource;

    public List<String> allAccountsByHand() throws SQLException {

        String sql = "SELECT id, holder, balance, version FROM accounts ORDER BY id";
        List<String> lines = new ArrayList<>();

        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql);
             ResultSet rs = ps.executeQuery()) {

            while (rs.next()) {
                lines.add("Account " + rs.getInt("id")
                        + " | " + rs.getString("holder")
                        + " | balance " + rs.getBigDecimal("balance").toPlainString()
                        + " | @Version " + rs.getInt("version"));
            }
        }
        return lines;
    }
}

    
Compare this with AccountService.findAll(), which is four lines and returns
      Account objects. Everything in this method is what JPA removes from your code — and the
      ? placeholder with setInt is the part you must never give up, because
      concatenating user input into SQL is how injection happens.

One-Line Summary

  

    
The same bank, reached four new ways. @Named + @ViewScoped gives a page a Java
      object and a lifetime. @Remote publishes methods to programs outside the server.
      @JMSDestinationDefinition creates a queue in code and
      @MessageDriven lets a bean nobody calls pick work up off it.
      Bean Validation states a rule once and every layer enforces it. And
      REQUIRES_NEW writes one thing in its own transaction so that a rollback elsewhere
      cannot erase it — which is the only reason a bank can keep a record of what it
      refused to do.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      

        Throwing a refusal out of a message-driven bean, or catching one and expecting the transaction to survive
        Return the refusal as a value. Once @ApplicationException(rollback = true) leaves a bean method, the transaction is doomed and no catch can save it.
      

      

        Using the default transaction attribute for an audit log
        Use REQUIRES_NEW. With REQUIRED the log rolls back with the thing it was describing, and you lose the refusals — the entries that matter most.
      

      

        Returning a JPA provider's List from a remote method
        Copy it: new ArrayList<>(…). Serialisation is not guaranteed otherwise, and this fails only in production.
      

      

        Confusing the queue's JNDI name with its physical destinationName
        They are different things on purpose. JNDI is for Java code; destinationName is what the broker calls it.
      

      

        Renaming javax.naming to jakarta.naming because "everything moved"
        JNDI and JDBC are Java SE and kept their names. Only the Jakarta EE specifications were renamed.
      

      

        Putting the cross-field rule on one field
        It cannot go there. Use a boolean method with @AssertTrue — and guard the untouched form, or every new visitor gets an error before typing.
      

      

        Letting a getter return something different from what the setter stored
        Keep them boring. JSF reads and writes through them, and the page breaks in a way that produces no exception and no clue.
      

      

        Adding @SessionScoped to a page bean out of habit
        Use @ViewScoped when the data belongs to the page. Session scope means two tabs share one half-filled form, and memory is held long after the user has gone.
