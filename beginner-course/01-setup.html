The three words on the sign
  • JDK (Java Development Kit) — the toolkit that compiles and runs Java.
  • IDE (Integrated Development Environment) — one program that lets you write, run and debug code in the same window, instead of juggling separate tools.
  • Application server — a large program that stays running all day and runs your application inside it. Ours is WildFly.

Why the JDK has to come first

The JDK is the toolkit that turns the Java you type into something the computer can run. Without it, nothing else on this page can do anything at all. IntelliJ needs it. WildFly needs it.

Temurin is the free, no-login build of the JDK, made by the Eclipse Foundation. Use it instead of the Oracle download, which asks you to create an account and attaches licence strings to it.

Version 17 is an LTS release — “Long-Term Support” — which simply means it is a version everyone agrees to keep patched and stable for years. That is why this course pins it rather than chasing the newest number.

In plain words

A JDK is the toolkit that both writes Java and runs it. Everything else you install sits on top of it.

“LTS” just means “the steady version that stays supported for years”, as opposed to a brand-new version that changes often.

🔌
Analogy The JDK is the plug socket on the wall. You cannot plug in the lamp (IntelliJ) or the fridge (WildFly) until the socket exists. Put the socket in first, and everything else has power.

Two invisible settings: JAVA_HOME and PATH

These two words cause more first-day confusion than anything else, so here they are before you meet them in a warning message.

  • An environment variable is a named setting stored by your operating system and remembered by every program that runs. You set it once; the computer keeps it.
  • JAVA_HOME is an environment variable that holds the folder where the JDK is installed. It is the computer’s note of “where Java lives”.
  • PATH is a list of folders the computer searches, in order, when you type a command in a terminal. If the folder holding java is not on that list, the terminal answers “not recognised”.
In plain words

JAVA_HOME answers “where is the JDK?”. PATH answers “where should I look when you type a command?”.

Setting both is what lets you type java -version in any terminal and get an answer instead of an error.

🧰
Analogy Picture a cook at a workbench who only ever reaches for the tools laid out on the bench. A tool still sitting in a drawer might as well not exist. PATH is that bench: if Java’s folder is not laid out on it, the computer behaves as if Java were never installed.

Step 1 — Install the JDK

Three actions. Do them in order, then run the checkpoint at the bottom.

  1. Download the installer

    Go to adoptium.net → “Latest LTS Release” → pick 17 for your operating system. On Windows, choose the .msi installer.

  2. Run the installer

    Run it and accept the default folder. On Windows, tick “Set JAVA_HOME variable” and “Add to PATH” if they are offered — that saves you the manual fix later.

  3. Open a fresh terminal and check it

    Close any terminal you already had open first — an old window will not know about the new settings. Then open a new one and type:

    java -version

    Practise the same commands in the panel below. It is safe: it simulates a command line on your screen and touches nothing on your computer.

Type java -version then echo %JAVA_HOME% (Windows) or echo $JAVA_HOME (Mac/Linux). You want a line starting openjdk version "17.

💡
The one thing to notice You are looking for a line that starts openjdk version "17. If the output shows a different number — 8, 11, 21 — the wrong JDK is being found first, and later builds will fail in confusing ways. Fix it now, while it is one clear problem.
🩹
If java is “not recognised” The PATH was not set. Windows: search “environment variables” → add a system variable JAVA_HOME pointing at the JDK folder, then add %JAVA_HOME%\bin to Path. Close and reopen the terminal. Nothing is broken — the computer simply has not been told where to look.
🔑
Analogy JAVA_HOME is the address label on a parcel. PATH is the list of streets the delivery driver is allowed to check. Give the driver the street, and the parcel arrives.

Step 2 — Install IntelliJ IDEA

Your IDE — the one window where you will write, run and debug code for the rest of the course.

🛠️
Analogy An IDE is a chef’s workbench with every tool within arm’s reach: the chopping board (writing code), the stove (running it) and the tasting spoon (debugging) all in one place, instead of walking between three different rooms.

  1. Download Community Edition

    Get it from jetbrains.com/idea/download → the Community Edition (free) is enough for this course.

  2. Install with the defaults

    Install with the defaults. On first launch, skip the plugin marketplace prompts.

  3. Create your first project

    File → New → Project → Maven Archetype (or “Jakarta EE”) creates a project whose pom.xml is already wired up. An archetype is a ready-made project template — a starter skeleton you fill in.

💡
The one thing to notice You were never asked to install Maven. That is the point — it is bundled inside IntelliJ. When a project is created this way, the pom.xml is already set up, and IntelliJ can build the project with no extra downloads.

Step 3 — Install WildFly and connect it to IntelliJ

WildFly is the application server: the large program that stays running and runs your beans inside it. Then you tell IntelliJ how to start it, so one click runs everything.

🍳
Analogy WildFly is a kitchen that is already built, staffed and connected to gas and water. You do not build an oven each time you want to cook — you walk into the kitchen and hand it a recipe. Your application is the recipe.

  1. Download and unzip WildFly

    Download wildfly-30.x.x.Final.zip from wildfly.org/downloads. Unzip it somewhere stable, e.g. C:\wildfly.

    In plain words

    That folder is your WildFly home. Later units write paths like C:\wildfly\standalone\deployments\ — if you unzipped yours somewhere else, substitute your own folder. The commands never change; only the path does.

  2. Create a new run configuration

    In IntelliJ: the Run configuration dropdown (top right) → Edit Configurations… → + → JBoss / WildFly Server → Local.

  3. Point it at your WildFly folder

    Set Application server → Configure… → point it at your unzipped WildFly folder. Leave HTTP port 8080, management port 9990.

  4. Add what should be deployed

    On the Deployment tab, click + and add your project’s war (or war exploded) artifact.

  5. Start the server

    Apply → OK, then press the green Run (▶) button.

💡
The one thing to notice Two ports, two jobs. 8080 is where your application is served — that is the number you type in a browser. 9990 is the management console, where you administer the server. Leave both at their defaults for now; changing them is what causes “address already in use” later.

WildFly is up when the console prints a line like WildFly Full 30.0.1.Final started in 3512ms. Then open http://localhost:8080 for the welcome page and http://localhost:9990 for the admin console.

💡
The one thing to notice “started in …ms” is your green light. Nothing else will work until that line appears — if a browser page fails, read the console first, because the answer is almost always on that line.

Common setup mistakes

Everyone hits at least one of these. Find your symptom, read what it means, apply the fix. This is normal developer work, not a sign that you broke something.

❌ What you seeWhat it meansWhat to do
java -version not recognisedPATH / JAVA_HOME not setSet JAVA_HOME, add %JAVA_HOME%\bin to PATH, reopen terminal
WildFly won’t start — “address already in use”Port 8080 taken by another appClose the other program, or start WildFly with -Djboss.socket.binding.port-offset=100
“No Java virtual machine found”JDK broken or wrong architectureReinstall the 64-bit Temurin JDK, restart the machine
Red squiggles under @StatelessJakarta EE API not on the project’s pathAdd jakarta.jakartaee-api (scope provided) to pom.xml, reload Maven
Deploy fails silentlyStale buildRight-click project → Rebuild, then re-run
Checkpoint · after troubleshooting

One last check before the quiz.

  1. Which of the five symptoms points at a missing Maven dependency rather than a broken install?
  2. Which symptom is usually not the JDK’s fault at all?
Show answers
  1. Red squiggles under @Stateless — the API is missing from the project’s path, so add jakarta.jakartaee-api and reload Maven.
  2. “address already in use” — that is another program holding port 8080, not a Java problem. Reinstall nothing; close the other app or shift WildFly’s ports.
