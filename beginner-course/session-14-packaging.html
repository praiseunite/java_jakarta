Part 1 · The four ways to box up your code

1.1 You cannot hand the server a pile of loose files

When you compile a Java project you get a scattering of .class files, some web pages, maybe a configuration file or two. A server will not accept that heap. It wants one tidy package, built to a shape it recognises.

That package is called an archive. Jakarta EE defines four kinds, and the file extension on the end tells the server which kind it is looking at.

In plain words

An archive is just a ZIP file with two special things: a fixed layout inside (certain folders in certain places) and a known extension (.jar, .war, .rar, .ear).

The server opens the ZIP, recognises the layout, and knows exactly what to do with what it finds.

📦
Analogy — four ways to post a parcel Think of mailing things. A small jiffy bag carries loose parts to another workshop. A ready-to-display shop-front stand is sent to the showroom. A travel-plug adapter lets your device talk to a foreign socket. And a whole removal van carries all of those boxes to one address in a single delivery. Four containers, four jobs — picked by what is inside and where it is going.

1.2 The four, one line each

Here is the quick version. The full, exact contents table is in the Reference at the end — you do not need it to follow along.

PackageIn the parcel analogyOne-line job
.jar
Java Archive		 the jiffy bag of parts Compiled classes, EJB session beans and JPA entities — reusable business logic with no web pages.
.war
Web Application Archive		 the shop-front stand The web tier: servlets, JSF Facelets (.xhtml), static assets and REST endpoints. This is what the Session 1 lab built (hello-ejb.war).
.rar
Resource Adapter Archive		 the travel-plug adapter A JCA connector that lets the server talk to an outside system (SAP, IBM CICS, a mainframe). Session 8 territory.
.ear
Enterprise Application Archive		 the removal van A big box holding several of the above — WARs, EJB JARs, RARs and shared libraries — delivered as one unit.
💡
The one thing to notice All four are the same technology — a ZIP file. What differs is the layout inside and the extension, and the extension is the server's instruction for how to treat the contents: unpack a .war into a web address, load a .jar as a library of beans, and so on.
⚠️
You cannot fake it by renaming Renaming hello.jar to hello.war does not turn it into a web app. The server looks inside for the required layout — a WAR must contain a WEB-INF/ folder. Wrong layout, wrong result, no matter what the extension says.

Part 2 · The big box (EAR) and its packing list (application.xml)

2.1 Why bundle several packages into one

A real application often has more than one part: a web module that draws the pages, a business module (an EJB JAR) that holds the rules, and some shared libraries both parts use. You could deploy each separately — but then they can drift out of step, and nothing guarantees they travel together.

An EAR (Enterprise Application Archive) solves that. It wraps all those modules in one box so they deploy together, version together, and share libraries.

🧳
Analogy — a suitcase with a packing list An EAR is a suitcase. Inside are smaller bags: a WAR (your clothes) and an EJB JAR (your shoes), plus one shared toiletry bag everything can reach (the lib/ folder). Taped to the lid is a packing list that tells the airport handler what each bag is and where it goes. That packing list is application.xml.

2.2 What an EAR looks like inside

Now that you know the idea, here is the actual shape of one. Read the labels on the right.

Physical structure of GlobalBank.ear
GlobalBank.ear
├── META-INF/
│   ├── application.xml        <!-- the packing list (deployment descriptor) -->
│   └── MANIFEST.MF
├── lib/                       <!-- shared libraries, reachable by every module -->
│   ├── commons-lang3.jar
│   └── postgresql-driver.jar
├── GlobalBank-EJB.jar         <!-- business-logic module -->
│   ├── com/globalbank/ejb/AccountBean.class
│   └── META-INF/beans.xml
└── GlobalBank-Web.war         <!-- presentation (web) module -->
    ├── login.xhtml
    ├── index.xhtml
    └── WEB-INF/
        ├── web.xml
        └── beans.xml
💡
The one thing to notice A WAR and a JAR are sitting inside the EAR, whole and unchanged. The EAR did not melt them together — it just carries them. The shared lib/ folder is the one new idea: it holds libraries that both modules can use, stored once instead of copied into each.

2.3 The packing list: application.xml

A deployment descriptor is a configuration file that tells the server how to treat a package. The EAR's descriptor is application.xml, and it lives in META-INF/. It declares three things.

It declares…Which means…
each web module and its context root"this WAR answers at the URL path /globalbank"
each EJB module"this JAR holds business beans — start it as one"
the shared library directory"libraries in lib/ are available to every module"

Here is the file those three declarations produce:

META-INF/application.xml — the master descriptor
<?xml version="1.0" encoding="UTF-8"?>
<application xmlns="https://jakarta.ee/xml/ns/jakartaee" version="10">
    <application-name>GlobalBankApp</application-name>

    <!-- 1. Web module, with the URL path it answers on -->
    <module>
        <web>
            <web-uri>GlobalBank-Web.war</web-uri>
            <context-root>/globalbank</context-root>
        </web>
    </module>

    <!-- 2. EJB business module -->
    <module>
        <ejb>GlobalBank-EJB.jar</ejb>
    </module>

    <!-- 3. Shared library directory -->
    <library-directory>lib</library-directory>
</application>
In plain words

Read it top to bottom and it says: "My name is GlobalBankApp. I contain a web module — serve it at /globalbank. I contain an EJB module — start its beans. And any JAR in my lib/ folder is shared by both."

That is all a descriptor is: a plain file answering the server's questions in advance.

💡
The one thing to notice <context-root>/globalbank</context-root> is the single most useful line. It sets the web address the application answers on, so pages live under http://localhost:8080/globalbank/… — regardless of what the WAR file happens to be called.
⚠️
Do not copy the same library into every module It is tempting to drop postgresql-driver.jar into both the WAR and the EJB JAR. Don't. Put it once in the EAR's lib/ folder (named by library-directory). Duplicated libraries waste space and can trigger confusing "class loaded twice" errors.

Part 3 · Travel light — the "skinny WAR"

3.1 Why you no longer stuff everything into the box

In the old days every application was an EAR, and teams bundled every library their code touched inside it — including the Jakarta EE API itself. The packages grew huge. Two modern changes fixed that:

  • Since EJB 3.1 (Java EE 6), enterprise beans can live directly inside a WAR. A single application no longer needs an EAR at all — the beans go in WEB-INF/classes alongside the servlets.
  • You stop bundling what the server already has. The Jakarta EE API comes with the server. Shipping your own copy inside the WAR is pointless — and, as you will see, dangerous.

A WAR built this way — your code only, nothing the server already provides — is called a skinny WAR.

🏨
Analogy — packing for a hotel You are flying to a hotel. You do not pack towels, a hairdryer or soap — the hotel supplies them. You pack only your own clothes. A skinny WAR packs the same way: your classes go in, but the Jakarta EE "towels" are left out because the server (the hotel) supplies them.

3.2 How you say "the server will supply this"

You tell Maven that a dependency is needed to compile but must not be packaged, by giving it the scope provided. "Scope" is simply when a library is needed.

pom.xml — the Jakarta API, marked "provided"
<dependency>
  <groupId>jakarta.platform</groupId>
  <artifactId>jakarta.jakartaee-api</artifactId>
  <version>10.0.0</version>
  <scope>provided</scope>      <!-- compile against it, but the server supplies it at runtime -->
</dependency>
In plain words

<scope>provided</scope> means: "I need this library to compile my code, but do not put a copy in my package — the application server already has it and will provide it when I run."

💡
The one thing to notice provided is the whole trick. It keeps the Jakarta API on your compile classpath — the list of places the compiler looks for classes — so your code builds and the IDE is happy, while leaving it out of the finished .war. That single word is the difference between a skinny WAR and a bloated one.

3.3 So do I still need an EAR?

Usually, no. Here is the honest decision.

ModelWhat you buildChoose it when…
All-in-one WAR
(modern cloud / microservices)		 A single .war holding EJBs, JSF and REST together in WEB-INF/classes Modern cloud deployments, Docker containers and microservices. Simpler Maven build. Start here.
Multi-module EAR
(traditional enterprise)		 An .ear holding separate .war and .jar modules Several separate web front ends (say a Customer Portal WAR + an Admin Portal WAR) must share the exact same EJB business JAR.
⚠️
The classic trap: the "fat" WAR If you forget provided and bundle the Jakarta API inside your WAR, you now have two copies of the same classes at runtime: yours and the server's. The result is ugly, intermittent failures — ClassCastException, LinkageError, or "loaded by a different classloader" — because the same class name exists twice. The fix is always the same: mark server-supplied APIs provided and keep the WAR skinny.

3.4 When you do need one: the multi-module Maven project

Section 3.3 said “choose a multi-module EAR when several front ends must share one EJB JAR.” This is what that actually looks like, because it is the one packaging shape a beginner cannot guess.

A multi-module project is one folder holding several small projects. Each is a normal Maven project with its own pom.xml. One extra file at the top ties them together. That is the whole idea.

The folder layout — three modules under one parent
globalbank/                       <- the parent folder. Run Maven HERE.
├── pom.xml                       <- the parent pom. packaging = pom
│
├── globalbank-ejb/               <- module 1: the business logic
│   ├── pom.xml                   <- packaging = ejb
│   └── src/main/java/...             AccountService.java, ...
│
├── globalbank-web/               <- module 2: the web front end
│   ├── pom.xml                   <- packaging = war
│   ├── src/main/java/...             AccountsBean.java, ...
│   └── src/main/webapp/...           accounts.xhtml, ...
│
└── globalbank-ear/               <- module 3: the box that holds the other two
    ├── pom.xml                   <- packaging = ear
    └── src/main/application/META-INF/application.xml

The parent pom builds nothing itself. Its one job is to name its children:

globalbank/pom.xml — the parent (aggregator)
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.globalbank</groupId>
  <artifactId>globalbank-parent</artifactId>
  <version>1.0.0</version>

  <!-- "pom" means: this project produces no jar, war or ear of its own.
       It exists only to hold the modules below. -->
  <packaging>pom</packaging>

  <modules>
    <module>globalbank-ejb</module>
    <module>globalbank-web</module>
    <module>globalbank-ear</module>
  </modules>
</project>

Now each child points back at the parent, and a child that needs another child names it as an ordinary dependency. The web module needs the EJB module, so it says so:

globalbank-web/pom.xml — a child module that depends on its sibling
<parent>
  <groupId>com.globalbank</groupId>
  <artifactId>globalbank-parent</artifactId>
  <version>1.0.0</version>
</parent>

<artifactId>globalbank-web</artifactId>
<packaging>war</packaging>

<dependencies>
  <dependency>
    <groupId>com.globalbank</groupId>
    <artifactId>globalbank-ejb</artifactId>
    <version>1.0.0</version>
    <type>ejb</type>      <!-- note the type: this artefact is an EJB jar -->
  </dependency>
</dependencies>

Finally the EAR module assembles the other two into one .ear, and the maven-ear-plugin decides where each piece lands inside it:

globalbank-ear/pom.xml — the assembly step
<artifactId>globalbank-ear</artifactId>
<packaging>ear</packaging>

<dependencies>
  <dependency><groupId>com.globalbank</groupId><artifactId>globalbank-ejb</artifactId><version>1.0.0</version><type>ejb</type></dependency>
  <dependency><groupId>com.globalbank</groupId><artifactId>globalbank-web</artifactId><version>1.0.0</version><type>war</type></dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <artifactId>maven-ear-plugin</artifactId>
      <version>3.3.0</version>
      <configuration>
        <version>10</version>                        <!-- Jakarta EE 10 application.xml -->

        <!-- Shared jars inside the EAR go to a folder called lib/.
             This is the <library-directory> you meet in application.xml. -->
        <defaultLibBundleDir>lib</defaultLibBundleDir>

        <modules>
          <ejbModule>
            <groupId>com.globalbank</groupId>
            <artifactId>globalbank-ejb</artifactId>
          </ejbModule>

          <webModule>
            <groupId>com.globalbank</groupId>
            <artifactId>globalbank-web</artifactId>
            <!-- The URL folder this war answers on: /globalbank -->
            <contextRoot>/globalbank</contextRoot>
          </webModule>
        </modules>
      </configuration>
    </plugin>
  </plugins>
</build>
💡
You only ever build from the top Run mvn clean package once, in the parent folder. Maven reads the <modules> list, works out the order from the dependencies, and builds the EJB jar before the war that needs it, and both before the ear that needs them. You never have to build the modules by hand or remember the sequence — that is the main thing a multi-module project buys you.
⚠️
The two things that go wrong first

Building in the wrong folder. If you run mvn clean package inside globalbank-web/ you get a war and no ear, and Maven may complain it cannot find globalbank-ejb — because it is only in the local repository if something has installed it. Build from the parent.

Forgetting the <type>. Maven assumes jar unless you say otherwise. An EJB module is <type>ejb</type> and a web module is <type>war</type>. Leave it out and the build fails with a message about a missing .jar that was never going to exist.

Part 4 · Handing it to the server — deploying on WildFly

Deploying means giving your finished archive to a running server so it starts serving it. WildFly offers three ways to do that.

WayHowBest for
1. Management CLI A command-line tool: jboss-cli.sh --connect, then deploy … Production and scripts — repeatable and precise.
2. Admin web console A browser at http://localhost:9990/console, under Deployments → Add Clicking through it once to see what is deployed.
3. File-system scanner Copy the archive into $WILDFLY_HOME/standalone/deployments/ Learning and fast local testing — no tool, no menus.

About $WILDFLY_HOME: it is the folder you unzipped WildFly into — C:\wildfly if you followed Session 1. Substitute your own path wherever it appears.

The one-line CLI form used in production looks like this:

$WILDFLY_HOME/bin/jboss-cli.sh --connect --command="deploy /build/GlobalBank.ear"

The folder WildFly watches

Way 3 is the easiest to understand, so start there. WildFly keeps an eye on one special folder:

$WILDFLY_HOME/standalone/deployments/

Anything you drop into that folder, WildFly tries to deploy — automatically, with no further command. A background part of the server called the deployment scanner is the thing doing the watching.

🚦
Analogy — a parcel-locker status light The deployments/ folder is like a parcel locker with a status light. You place your parcel and press "deliver" (that is the .dodeploy marker). The light turns amber — "preparing" (.isdeploying). Then it goes green, "delivered" (.deployed) — or red, "failed — see the note" (.failed). Take the parcel back and it shows "returned" (.undeployed). The marker files are that status light.

Rehearse the commands safely

Before touching a real server, practise in the simulated terminal below. It runs nothing and touches nothing on your computer. Type help first, then rehearse the real deploy flow: mvn clean package, then copy target\hello-ejb.war c:\wildfly\standalone\deployments\, then dir c:\wildfly\standalone\deployments to see the markers appear. To try the grown-up command line instead, use deploy target/hello-ejb.war, and undeploy hello-ejb.war to take it back down again.

Now do it for real

Follow these steps against a running WildFly. (Need to install it first? See Set up your workshop.) We will deploy the same hello-ejb.war you met in Session 1.

  1. Build the archive

    In the project folder, build the WAR:

    mvn clean package

    Wait for BUILD SUCCESS. You now have a real, deployable file at target/hello-ejb.war.

  2. Drop it into the watched folder

    Copy the WAR into WildFly's deployments/ folder. That is the whole "deploy" — no menus, no configuration:

    copy target\hello-ejb.war  c:\wildfly\standalone\deployments\      REM  Windows
cp   target/hello-ejb.war  ~/wildfly/standalone/deployments/       #    macOS / Linux

    The deployment scanner notices the new file within a second or two and starts deploying it.

  3. Check the status light

    Look at what appeared next to your archive:

    dir c:\wildfly\standalone\deployments

    A second file has shown up — hello-ejb.war.deployed. That green-light marker is the server telling you the application is live and serving requests. If you saw hello-ejb.war.failed instead, open that file: it holds the stack trace explaining exactly what went wrong.

  4. Deploy the production way instead (optional)

    In production nobody copies files by hand. They use the management CLI. Connect to it, then deploy:

    deploy target/hello-ejb.war

    The console confirms Deployed "hello-ejb.war" and registers the web context /hello-ejb. The Admin console at http://localhost:9990/console would do the same job through a browser.

  5. Take it back down

    When you are done, undeploy it:

    undeploy hello-ejb.war

    The application stops, and WildFly marks it hello-ejb.war.undeployed. (With the file-system method, simply deleting the WAR from deployments/ undeploys it too.)

    🧬 Classloading isolation — where to look when libraries clash
    
Not covered in the Parts above, but listed in the objectives, and the first thing you reach for
      when a "fat WAR" clash (Part 3) bites. The ideas in plain words:

    
    
      
  • Classloading isolation. Each deployment gets its own classloader, so one
        application's libraries do not leak into another's. Two apps can safely use different versions of
        the same library.
    • 
      
  • Parent-first vs. child-first delegation. When a class is needed, which
        classloader is asked first? Parent-first (WildFly's default) asks the server's modules
        first; child-first asks your deployment's own copy first. The wrong order is what causes
        the "loaded by a different classloader" errors.
    • 
      
  • jboss-deployment-structure.xml. A WildFly-specific descriptor
        (placed in META-INF/ or WEB-INF/) where you fine-tune this: add a
        dependency on a server module, exclude one, or flip the delegation order for a troublesome
        library.
    •

Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Renaming a .jar to .war to "make it a web app"Build the right archive — the server checks the inside layout (WEB-INF), not just the extension.

      
Bundling the Jakarta EE API inside your WARMark it <scope>provided</scope> — the server supplies its own copy at runtime.

      
Copying the same shared JAR into every module of an EARPut it once in the EAR's lib/ folder (named by library-directory).

      
Building an EAR for a single, simple applicationSince EJB 3.1 one skinny WAR holds EJBs + web — keep it simple.

      
Hand-editing or deleting the .deployed markerTreat markers as the server's controls — deleting .deployed undeploys the app.

      
Ignoring a .failed markerOpen it — it holds the stack trace telling you exactly why deployment aborted.
