concept

Part 1 · From your code to one deployable file

By now you have written Java classes, web pages and configuration files. A server will not accept that pile of loose files. It wants one tidy package, built to a shape it recognises. Packaging is the act of turning your build output into that one file.

In plain words

An archive is just a ZIP file with two special things: a fixed layout inside (certain folders in certain places) and a known extension (.jar, .war, .ear).

The server opens the ZIP, recognises the layout from the extension, and knows exactly what to do with what it finds. Renaming hello.jar to hello.war does not fool it — the server looks inside for the required layout, not just at the name.

1.1 Three boxes, three jobs

You already met these in Session 14. Here they are again, because the assembly pipeline below builds all three:

ArchiveWhat goes insideWhat it becomes
.jar
Java Archive		 Compiled classes, EJB session beans and JPA entities — business logic, no web pages. A reusable library or the business-logic module of an application.
.war
Web Application Archive		 Servlets, JSF Facelets (.xhtml), static assets, REST endpoints, and a WEB-INF/ folder. A web address — the page a user actually visits.
.ear
Enterprise Application Archive		 One or more WARs, EJB JARs, and a shared lib/ folder, plus META-INF/application.xml. One delivery containing a whole multi-module application.
🧳
Analogy — posting a parcel A JAR is a jiffy bag of parts. A WAR is a ready-to-display shop-front stand. An EAR is a removal van carrying several boxes — including the shared lib/ toiletry bag everything can reach — to one address in a single delivery.

1.2 The four stages of the assembly pipeline

A real enterprise application is not built in one step. It is assembled in four, and each stage produces an artifact the next stage consumes. Follow the table left to right:

StageActionArtifact GeneratedVerification Step
1. Business Build Compile EJB and CDI service components with beans.xml GlobalBank-EJB.jar Inspect classes for @RolesAllowed and @Stateless.
2. Web Build Compile JSF Facelets XHTML, controllers, and security definitions GlobalBank-Web.war Verify web.xml and login.xhtml exist in package.
3. Enterprise Packaging Assemble WAR + JAR + shared DB drivers in lib/ GlobalBank.ear Verify META-INF/application.xml declares both modules.
4. Production Deployment Deploy to WildFly via CLI or .dodeploy scanner Server Runtime Check for .deployed marker and verify web context root.
In plain words

Read the four stages as a sentence: compile the business beans into a JAR; compile the web pages into a WAR; put the WAR, the JAR and their shared libraries into one EAR; hand the EAR to the server.

Stages 1 to 3 happen on your machine at build time. Stage 4 is the only one that needs a running server — and it is the whole of Part 2.

Context root is the URL prefix your application lives under. Deploy GlobalBank.ear and its web module answers at localhost:8080/globalbank/… — that first path segment is the context root. Two running apps cannot share one, which is exactly what Fault 2 below demonstrates.

⚠️
The classic trap: the “fat” WAR If you bundle the Jakarta EE API inside your WAR instead of marking it <scope>provided</scope>, you ship two copies of the same classes — yours and the server's. The result is ugly, intermittent failures such as ClassCastException or “loaded by a different classloader”. A WAR built with your code only, and server-supplied APIs left out, is called a skinny WAR — and since EJB 3.1 you can even put the beans straight inside it.

2.2 The exact commands

This is the whole production flow, written out. Read it once before you run the numbered lab below — every line is a step you are about to take for real. The example deploys the enterprise archive GlobalBank.ear from Part 1:

Terminal Commands — Production CLI Deployment
# 1. Start WildFly Application Server in standalone mode
# ($WILDFLY_HOME = the folder you unzipped WildFly into, e.g. C:\wildfly)
$WILDFLY_HOME/bin/standalone.sh

# 2. Launch the JBoss Management CLI
$WILDFLY_HOME/bin/jboss-cli.sh --connect

# 3. Deploy the enterprise application archive
deploy target/GlobalBank.ear

# 4. Verify deployment status
deployment-info --name=GlobalBank.ear

# Output should show:
# NAME              RUNTIME-NAME      PERSISTENT RUNTIME-STATUS
# GlobalBank.ear    GlobalBank.ear    true       OK
In plain words

--connect opens a live conversation with the running server. Once you are connected, deploy sends an archive and deployment-info asks the server to report on it. The last line — OK — is the server saying the application is live.

2.3 Now do it for real

Same four moves, but against the project you can actually build. Keep the server window open for the whole lab.

  1. Start WildFly

    Open a terminal in WildFly's bin folder and run:

    standalone.bat          REM  Windows
./standalone.sh         #    macOS / Linux

    Leave this window open. Wait until the console prints a line ending like:

    WildFly Full 30.0.1.Final started in 3512ms

    You should see that started in …ms line. Nothing else in this lab will work until you do. If it never appears, jump to the troubleshooting table in 2.5.

  2. Build the archive

    Open a second terminal and move into the lab project — the folder that contains pom.xml:

    cd beginner-course/lab/session-01-hello-ejb
mvn clean package

    You should see BUILD SUCCESS. You now have a real, deployable file at target/hello-ejb.war. Type dir target (Windows) or ls target (macOS/Linux) and confirm the .war is there.

  3. Connect the Management CLI

    From WildFly's bin folder, launch the CLI and connect to the running server:

    jboss-cli.bat --connect      REM  Windows
./jboss-cli.sh --connect     #    macOS / Linux

    You should see the prompt change to something like [standalone@localhost:9990 /]. That means you are talking to the server. Nothing has been deployed yet — you are just at the controls.

  4. Deploy through the CLI

    At the CLI prompt, deploy the WAR you just built (use the full path to your project's target folder):

    deploy target/hello-ejb.war

    Watch the server window (the first terminal) as well. You should see two things:

    Deployed "hello-ejb.war"
Deployment status: hello-ejb.war.deployed created.

    That second line is the status light going green — see 2.4.

  5. Verify the deployment

    Still at the CLI prompt, ask the server to report on the archive:

    deployment-info --name=hello-ejb.war

    You should see a row whose RUNTIME-STATUS column reads OK:

    NAME            RUNTIME-NAME    PERSISTENT RUNTIME-STATUS
hello-ejb.war   hello-ejb.war   true       OK

    That OK is your proof the deploy succeeded. If you see FAILED instead, the reason is in the .failed file (2.4) — do not guess.

  6. Use it in the browser

    Open your browser at:

    http://localhost:8080/hello-ejb/greet?name=Ada

    You should see exactly:

    Hello, Ada! (said by a container-managed bean)

    That string came out of a bean that you packaged and deployed through the CLI. Now leave the name off entirely:

    http://localhost:8080/hello-ejb/greet

    → Hello, stranger! (said by a container-managed bean). That is the bean's if (name == null…) rule doing the work — exactly the same bean from Session 1, reached the production way.

  7. Watch the whole enterprise deploy play out

2.4 Read the status light: the marker files

  
WildFly reports every deployment's state with small files next to your archive in the
    deployments/ folder. These marker files are how you and the server
    talk to each other, and reading them is a core exam skill. There are five:


  

    
Marker fileWhat it means

    
      
myapp.ear.dodeployYou created this file to request a deployment. It is the “start” button.

      
myapp.ear.isdeployingThe server is currently unpacking and parsing the archive. Amber light.

      
myapp.ear.deployedDeployment succeeded — the application is live and serving requests. Green light.

      
myapp.ear.failedDeployment failed — this file contains the stack trace explaining why. Red light.

      
myapp.ear.undeployedThe application was successfully stopped and removed.

    
  


  
💡
    
The markers are the server's controls, not scratch files
      Do not hand-edit or casually delete a marker. Deleting hello-ejb.war.deployed tells
      WildFly to undeploy the application. Treat the markers as buttons, not
      litter.

  


  
2.5 Troubleshooting: the four things that go wrong

  
When it goes wrong, find your symptom in this table before doing anything else. This is normal
    developer work, not failure.


  

    
What you seeWhat it meansWhat to do

    
      

        The started in …ms line never appears
        WildFly did not finish starting
        Run it in a terminal you can see and read the first error line. Most often a port is already taken.
      

      

        Address already in use / port 8080 busy
        Something else owns the HTTP port
        Close that program, or start WildFly with -Djboss.socket.binding.port-offset=100 and use port 8180 instead.
      

      

        Connection refused
        The CLI cannot reach the server
        The server is not running, or you skipped --connect. Start WildFly (step 1), wait for started in …ms, then connect again.
      

      

        hello-ejb.war.failed appears
        Deployment aborted
        Open the .failed file — it holds the stack trace. Read the deepest Caused by: line — the last one in the chain. That is the root cause; the ones above it are just consequences.
      

      

        DuplicateResourceException — context root already registered
        An older copy of the same app is still holding the URL path
        Run undeploy hello-ejb.war (or remove the old archive from deployments/), then deploy again.
      

      

        404 Not Found in the browser, but deployment says OK
        Wrong URL, or the deployment has not finished
        Confirm the path is exactly /hello-ejb/greet?name=Ada, and wait for the
          .deployed marker before reloading.

Part 3 · Lock it down — and the three errors you will hit


  
Packaging gets your code onto the server. Security decides who is allowed to do
    what once it is there. Session 13's big idea was that this lives in your code, as CDI
    annotations, not in a server-specific configuration file. That portability is exactly why the same
    EAR deploys to WildFly, Payara or Open Liberty unchanged.


  
3.1 Portable, code-first security in one class

  
Two annotations on one class declare both the login door and the user records. There is no XML and
    no server file:


  
ApplicationSecurityConfig.java — the whole portable security setup

  
package com.globalbank.security;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.security.enterprise.authentication.mechanism.http.CustomFormAuthenticationMechanismDefinition;
import jakarta.security.enterprise.authentication.mechanism.http.LoginToContinue;
import jakarta.security.enterprise.identitystore.DatabaseIdentityStoreDefinition;
import jakarta.security.enterprise.identitystore.Pbkdf2PasswordHash;

@ApplicationScoped
@CustomFormAuthenticationMechanismDefinition(     // 1. the door: our own login page
    loginToContinue = @LoginToContinue(
        loginPage = "/login.xhtml",
        errorPage = "/login-error.xhtml"
    )
)
@DatabaseIdentityStoreDefinition(                 // 2. the records: users and roles in PostgreSQL
    dataSourceLookup = "java:/jdbc/GlobalBankDB",
    callerQuery = "SELECT password_hash FROM bank_users WHERE username = ?",
    groupsQuery = "SELECT role_name FROM user_roles WHERE username = ?",
    hashAlgorithm = Pbkdf2PasswordHash.class      // never compare plain-text passwords
)
public class ApplicationSecurityConfig {
    // Declarative configuration only — no method bodies at all.
}


  
Each line does one clear job. dataSourceLookup says where the
    database is (a JNDI name, never a password in your source). callerQuery fetches
    this user's stored password. groupsQuery fetches this user's
    roles. hashAlgorithm is the rule for turning a typed password into something
    comparable, so the database stores fingerprints, not keys.


  
💡
    
The one thing to notice
      That class is fully portable. Because @DatabaseIdentityStoreDefinition is part of the
      Jakarta Security specification, the setup travels with your code and needs
      zero server XML edits — which is exactly what makes it superior to the old
      server-specific security realms.

  


  
3.2 The three faults, side by side

  
These are the three you will meet in real work. Read the symptom, then the root cause, then the
    fix.


  
1️⃣
    
Fault 1: ClassNotFoundException on Shared Libraries in EAR
      
Symptom: An EJB or Web module crashes at startup unable to find a utility class located in the EAR.

      
Root Cause: The shared JAR was put in the wrong place, so it was never added to the sub-modules' classpath.

      
Fix: In an EAR, shared libraries must reside inside the directory specified by <library-directory>lib</library-directory> in application.xml. Placing JARs directly in the root of the EAR will not add them to sub-module classpaths.

    

  


  
2️⃣
    
Fault 2: WildFly reports .failed with DuplicateResourceException
      
Symptom: Deployment scanner generates GlobalBank.ear.failed stating context root /globalbank is already registered.

      
Root Cause: An older version of the WAR, or an undeployed test archive, is still holding the URL context path.

      
Fix: Execute undeploy GlobalBank.ear in the CLI or remove old archives from standalone/deployments/, then deploy again.

    

  


  
3️⃣
    
Fault 3: HTTP 403 Forbidden on a Valid Logged-In User
      
Symptom: The user logs in successfully, but clicking a protected button yields HTTP 403 Access Denied.

      
Root Cause: The role names returned to the container do not match the role names your annotation demands.

      
Fix: Check the role names returned by groupsQuery in @DatabaseIdentityStoreDefinition. Role names are case-sensitive: if your database returns "teller" and your annotation expects @RolesAllowed("TELLER"), the container will deny access.

    

  


  
3.3 Prove Fault 3 on a real server

  
The security check happens before your business code runs — so you can watch it fire
    without touching a database. Follow these two steps.


  
    
    
  1. 
      
    Log in, then call a method your role does not allow
    
      
    Deploy the application, log in as a user whose role is teller (lower-case), and
        call a method annotated @RolesAllowed("TELLER").
    
      
    You should see an EJBAccessException in the server console, and
        HTTP 403 Forbidden in the browser. Critically, you should see no SQL
        and no work done — the container refused the call before the method body ran.
    
    
    2. 
    
  2. 
      
    Confirm which roles the user actually holds
    
      
    Before blaming your code, check the identity store. If you are using a database identity store,
        run the groupsQuery against the database directly and read the exact strings it
        returns:
    
      
    SELECT role_name FROM user_roles WHERE username = 'alex_m';
    
      
    You should see the role exactly as stored. If it prints teller
        but your annotation says TELLER, you have found the bug — the fix is to make the
        two spellings match, in one place or the other. Change one, redeploy, and the 403 becomes a
        200.
    
    
    3. 
  


  
💡
    
The lesson that sticks
      All three faults are the container protecting your system: it refuses to start a broken
      module, refuses a clashing context root, and refuses a caller without the exact role. None of them
      is random. Each one leaves you a precise clue — the .failed file names the missing
      class, the DuplicateResourceException names the busy context root, and a 403 means
      one thing only: compare the role strings character by character.

    🗂️ application.xml — the EAR's packing list
    
A deployment descriptor is a configuration file telling the server how to treat
      a package. The EAR's descriptor is application.xml, and it lives in
      META-INF/. It declares three things:

    

      
ElementWhat it declares

      
        
<application-name>A logical name for the whole application (used in JNDI names).

        
<module><web>A web module. Holds <web-uri> (the WAR file) and <context-root> (its URL path).

        
<web-uri>The name of the WAR file inside the EAR.

        
<context-root>The URL path the web module answers on, e.g. /globalbank.

        
<module><ejb>An EJB module — names the EJB JAR file to start.

        
<library-directory>The folder (usually lib) whose JARs are shared by every module.

      
    

    
Read it top to bottom and it says: “My name is GlobalBankApp. I contain a web module — serve
      it at /globalbank. I contain an EJB module — start its beans. And any JAR in my
      lib/ folder is shared by both.”

  


  

    🔐 @DatabaseIdentityStoreDefinition — the key attributes
    
The whole portable security setup, in one class (see Part 3.1). Every attribute does one job:

    

      
AttributeWhat it does

      
        
dataSourceLookupThe JNDI name of the database the store queries — never a URL or password in your source.

        
callerQuerySQL returning the stored password for a username. The ? is filled in with the typed username.

        
groupsQuerySQL returning the roles belonging to a username. Case matters.

        
hashAlgorithmThe rule for converting a typed password into a comparable hash (Pbkdf2PasswordHash). Plain-text comparison is never allowed.

      
    

    
SecurityContext, injected with @Inject, is the other half: it lets your
      own code ask getCallerPrincipal() (“who is calling?”) and
      isCallerInRole("ADMIN") (“may they?”).

  


  

    🧬 Classloading isolation — where to look when libraries clash
    
This is the first thing you reach for when the “fat WAR” clash from Part 1 bites. The ideas in
      plain words:

    
    
      
  • Classloading isolation. Each deployment gets its own classloader, so one
        application's libraries do not leak into another's.
    • 
      
  • Parent-first vs. child-first delegation. When a class is needed, which
        classloader is asked first? Parent-first (WildFly's default) asks the server's modules
        first; child-first asks your deployment's own copy first. The wrong order is what causes
        the “loaded by a different classloader” errors.
    • 
      
  • jboss-deployment-structure.xml. A WildFly-specific descriptor
        (in META-INF/ or WEB-INF/) where you fine-tune this: add a dependency
        on a server module, exclude one, or flip the delegation order for a troublesome library.

        Put them in the lib/ folder named by <library-directory> in application.xml. Root-level JARs are not shared.
      

      

        Deploying a new version before undeploying the old one
        Run undeploy first (or remove the old archive) — otherwise you get DuplicateResourceException on the context root.
      

      

        Guessing why a deployment failed
        Open the .failed marker file. It holds the exact stack trace — read the deepest Caused by: line, the last one in the chain. That is the root cause.
      

      

        Blaming your code for a 403
        The code is often correct. Compare the exact role strings from groupsQuery with the @RolesAllowed value — they are case-sensitive.
      

      

        Bundling the Jakarta EE API inside your WAR
        Mark it <scope>provided</scope> — the server supplies its own copy at runtime. Keep the WAR skinny.
      

      

        Deleting or editing a marker file to “clean up”
        Treat markers as the server's controls. Deleting .deployed undeploys the application.
