Unit 11 · Messaging with JMS

Sometimes you don’t want to wait. Jakarta Messaging (JMS) lets one part of a system drop a message and move on; another part picks it up later. The middleman that stores and routes messages is a message broker.

↩︎
Recap An MDB (Unit 04) is a bean that consumes messages. This unit is the messaging system it plugs into — and how to send messages yourself.

Synchronous vs asynchronous

Synchronous call (RMI / REST)Asynchronous message (JMS)
CallerBlocks until the answer comes backSends, continues immediately
Both sides online?Must be, at the same timeNo — the broker holds the message until the consumer is up
Target downImmediate errorMessage waits in the broker (guaranteed delivery)
Traffic spikeOverwhelms the targetQueue absorbs it, drained at a steady rate

Two delivery styles

Point-to-Point — QueuePublish/Subscribe — Topic
DeliveryEach message goes to exactly one consumerEvery subscriber gets its own copy

concept

The pieces

  • Broker / provider — the messaging server (WildFly’s embedded Artemis, Apache ActiveMQ, RabbitMQ…).
  • ConnectionFactory — an administered object (configured on the server, looked up via JNDI) that knows how to connect to the broker.
  • Destination — the Queue or Topic, also an administered object.
  • Producer sends; Consumer receives (by polling with receive(), or via a MessageListener callback like an MDB).
concept

Classic API vs simplified API

Classic (JMS 1.1) — lots of ceremony
Connection connection = factory.createConnection();
connection.start();
Session session = connection.createSession(false, Session.AUTO_ACKNOWLEDGE);
Queue queue = (Queue) ctx.lookup("java:/jms/queue/OrderQueue");
MessageProducer producer = session.createProducer(queue);
producer.send(session.createTextMessage("Order #1001"));
session.close();
connection.close();
Simplified (JMS 2.0+ / Jakarta Messaging) — one resource
try (JMSContext ctx = factory.createContext(JMSContext.AUTO_ACKNOWLEDGE)) {
    ctx.createProducer().send(queue, "Order #1001");
}   // JMSContext is AutoCloseable — connection + session managed for you

JMSContext bundles the old Connection + Session into one auto-closing object. Prefer it.

⚠️
Note on javax.jms vs jakarta.jms The original Session 7 lab uses import javax.jms.* — correct for ActiveMQ 5.18, whose client still uses the old package. On a Jakarta EE 10 server (WildFly + Artemis) the import is jakarta.jms.*. Match the package to the library you actually put on the classpath.

concept

Request–reply over one-way queues

Messaging is one-way, so how does a sender match a reply to its request? Two headers: JMSReplyTo (which queue to answer on) and JMSCorrelationID (a unique tag the reply must echo back).

try itreplay — request/reply
// client sends 2 requests with reply-to + correlation IDs, then waits for matches
send("CHECK_BALANCE ACC-9871", replyTo=REPLY_Q, corrId="CORR-1")
send("RESET_PIN USR-5542",     replyTo=REPLY_Q, corrId="CORR-2")
Replies can arrive in any order; the client matches them by correlation ID.
