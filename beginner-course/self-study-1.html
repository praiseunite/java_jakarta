In plain words

Three shelves. The top shelf draws the screen with Facelets (Session 5). The middle shelf holds your beans — the classes that do the actual thinking (Sessions 1 to 4 and 6). The bottom shelf is everything outside your application: a message queue that carries work away to be done later (Session 7), and a database reached through a managed connection pool (Sessions 3 and 8).

The whole point of an enterprise application is that the middle shelf — the container — does the hard, boring, dangerous work for you: transactions, security, threading and pooling. You write the business rule; the container keeps it safe.

1.1 Enterprise bean types and their lifecycles (Sessions 1 & 2)

There are three bean types, and picking the wrong one is the most common design mistake in this course. The question to ask is always: who owns the state, and for how long?

Feature@Stateless@Stateful@Singleton
Primary use case Business services, calculations, dispatchers Shopping carts, multi-step wizards, conversational state Caching, application counters, global locks
Client association Unbound; any client gets any pooled instance Dedicated one-to-one binding per client session Exactly one instance shared across all clients
Instance pooling Yes (WildFly default: 20 to 64 instances) No (an instance is created per client) No (a single instance, loaded eagerly or lazily)
Passivation Never (no conversational state to preserve) Yes (@PrePassivate / @PostActivate to disk) Never
Lifecycle callbacks @PostConstruct, @PreDestroy @PostConstruct, @PrePassivate, @PostActivate, @PreDestroy, @Remove @PostConstruct, @PreDestroy
Thread safety Container ensures one thread per instance Container ensures one thread per instance Container-managed concurrency (@Lock(READ/WRITE))
In plain words

Pooling means the container keeps a shelf of ready-made instances and lends one out per call, then takes it back. That is why @Stateless is fast and why you must never keep a customer's data in its fields.

Passivation is the container putting a @Stateful bean to sleep on disk when it has not been used for a while, and waking it up later (activation) with its state intact. A stateless bean has no state, so there is nothing to put to sleep.

Concurrency is two threads touching the same object at once. For @Singleton the container guards the single shared instance: many readers may enter at once under @Lock(READ), but a writer takes an exclusive @Lock(WRITE).

🍽️
Analogy — a restaurant A @Stateless bean is the counter staff: any one of them can serve you, and none of them remembers you afterwards. A @Stateful bean is the waiter assigned to your table: they remember your order across the whole meal, and leave when you do. A @Singleton bean is the one wall clock everyone in the building reads — there is only one, it is shared, and reading it is safe for many people at once while setting it must be done by one person.
⚠️
Gotcha alert: never store client-specific state in a @Stateless bean The container returns instances to the pool and hands them to other callers. A field that held customer A's data on one call can be handed, unchanged, to customer B on the next. That is cross-tenant data leakage, and it is a serious bug, not a style point. Keep every value the method needs as a parameter or a local variable.

1.2 JNDI portable naming architecture (Session 3)

JNDI (the Java Naming and Directory Interface) is the phone book of the application server. Everything the container manages — beans, data sources, queues — is looked up by name rather than created by you. Jakarta EE fixes four portable namespaces so the same lookup works on WildFly, GlassFish or WebLogic without change:

The four portable JNDI namespaces
java:global[/<app-name>]/<module-name>/<bean-name>[!<fully-qualified-interface-name>]
java:app/<module-name>/<bean-name>[!<fully-qualified-interface-name>]
java:module/<bean-name>[!<fully-qualified-interface-name>]
java:comp/env/<resource-ref-name>

The difference between them is how far the name reaches. Think of it as four sizes of address:

  • java:global — reachable by every application running on the whole server instance, and by remote standalone Java SE clients too. The widest address there is.
  • java:app — reachable only inside the modules that share the same .ear enterprise archive.
  • java:module — reachable only inside the same .war or .jar archive. Your own back yard.
  • java:comp — private to the one calling component instance (java:comp/env is where a component's own references live). The smallest address.
💡
Why the brackets The square brackets mark the optional parts. A bean with a named class can use the short form java:module/CalculatorBean; a bean that implements an interface uses the ! form — java:module/CalculatorBean!com.aptech.Calculator — to say exactly which interface you want. If only one interface exists, the short form is enough.

1.3 Container-Managed Transaction (CMT) propagation (Session 4)

A transaction is a group of changes that must all happen or none happen. In Container-Managed Transactions (CMT) you never write begin() or commit() — the container opens, commits and rolls back for you, following the propagation attribute you put on the method. Propagation answers one question: if the caller already has a transaction, what should I do?

AttributeClient has an active transactionClient has no transactionBest used for
REQUIRED (default)Joins the existing transactionStarts a new transactionGeneral database operations (updates, inserts)
REQUIRES_NEWSuspends the client's transaction; starts a new independent oneStarts a new transactionAudit logging and notifications that must persist even if the parent rolls back
MANDATORYJoins the existing transactionThrows TransactionRequiredExceptionInternal helper methods that must never run without a transaction
SUPPORTSJoins the existing transactionExecutes non-transactionallyRead-only search methods
NOT_SUPPORTEDSuspends the client's transaction; runs non-transactionallyExecutes non-transactionallyLong-running operations and network calls
NEVERThrows RemoteExceptionExecutes non-transactionallyStrictly non-transactional operations
🔁
Key rule for rollback By default the container only rolls back for unchecked exceptions (RuntimeException and Error). A checked application exception — one that extends Exception — commits by default. If you want a checked exception to undo the work, you must mark it @ApplicationException(rollback = true), or call ctx.setRollbackOnly() before it is thrown.
In plain words

Suspends here means “pauses and puts aside for a moment”. Under REQUIRES_NEW the caller's transaction is not cancelled — it is frozen while the new one runs, then resumed afterwards.

Unchecked means the compiler does not force you to catch it — usually a bug or a system failure. Checked means the compiler makes you declare it — usually a business outcome you expected, such as “not enough funds”. The container treats the two differently: unexpected trouble rolls everything back, expected outcomes are allowed to commit.

1.4 The Facelets and JSF request-processing lifecycle (Session 5)

When a browser submits a JSF form, the request is not handled in one move. It walks through six phases in a fixed order. Knowing the order tells you exactly where a validation error stops the request.

  1. Restore View. Rebuild the component tree from session state (or create a fresh one for a first visit).
  2. Apply Request Values. Decode the submitted HTTP form parameters into the components.
  3. Process Validations. Run the validators (required="true", custom validators, Bean Validation). If any fail, JSF jumps directly to Phase 6.
  4. Update Model Values. Convert and copy the validated values into your backing bean properties.
  5. Invoke Application. Execute the business action methods (for example #{orderBean.submit()}).
  6. Render Response. Generate the resulting HTML markup and send it back to the browser.
💡
The one fact worth memorising Validation lives in Phase 3, and a failure skips Phases 4 and 5 entirely and lands on Phase 6. That is the whole reason a badly filled-in form is cheap: your business method in Phase 5 never runs, and no database call is made.

1.5 Local versus remote clients (Session 6)

A bean can be reached two ways. A @Local call stays inside the same Java Virtual Machine and simply passes a pointer in memory — fast and free. A @Remote call travels over the network to another JVM, so every parameter and return value must be turned into bytes and back again. That act of turning an object into bytes is called serialization (and back again, deserialization).

Attribute@Local interface@Remote interface
Client locationSame JVM / same application serverDifferent JVM / standalone Java SE client
Parameter passingPass-by-reference (a memory address pointer, fast)Pass-by-value (serialized into bytes over TCP)
Serialization requirementNot requiredMandatory (implements Serializable)
Network overheadZero (a direct in-memory call)Socket I/O, plus marshalling and unmarshalling overhead
Exception handlingApplication exceptions are thrown directlyCan throw java.rmi.RemoteException or EJB remote exceptions
📞
Analogy — handing over a document A @Local call is passing a note across the desk: you hand over the actual piece of paper, and any change the other person makes is on that same paper. A @Remote call is faxing the note to another building: you send a copy. Whatever they scribble on their copy never appears on yours — and if the note is not something a fax can carry (a non-serializable object), the whole thing fails.

1.6 Jakarta Messaging (JMS 3.0) and Jakarta Connectors (JCA) (Sessions 7 & 8)

Session 7 is about letting work travel asynchronously — meaning the sender does not wait for the receiver. Session 8 is about reaching systems outside Jakarta EE entirely.

  • Point-to-Point (Queue). Exactly one consumer processes each message. Suitable for payment dispatch, order fulfilment and ticket processing — work that must be done once, not broadcast.
  • Publish/Subscribe (Topic). Every active subscriber receives a copy of each published message. Suitable for price broadcasts, notifications and cache invalidation.
  • Message-Driven Beans (@MessageDriven). Asynchronous, transaction-aware listeners managed by the container. They implement MessageListener and, unlike session beans, expose no client interface — you cannot call them, you can only send them a message.
  • Jakarta Connectors Architecture (JCA). A standardised adapter framework that bridges Jakarta EE to external Enterprise Information Systems (EIS) — databases, mainframes and ERPs. It implements three critical system contracts:
    1. Connection Management Contract — pooling.
    2. Transaction Management Contract — two-phase commit (XA).
    3. Work Management Contract — thread scheduling.
In plain words

Asynchronous is the difference between a phone call and a text message. A phone call (synchronous) makes you wait until the other person answers. A text (asynchronous) lets you carry on immediately; the message is delivered when the other side is ready.

Two-phase commit is how two databases agree. Phase one asks both “can you commit?”; only if both say yes does phase two tell them both to do it. Either both write or neither does — the same all-or-nothing promise, stretched across systems.

EIS is just the industry's umbrella term for the big systems a company already runs, which your Jakarta EE application has to talk to.

1.7 The high-frequency exam questions

These three are asked again and again. Cover the answer and try first.

❓
Q1: Why can a client not invoke a method on a @Stateful bean concurrently from two threads?

Because the EJB specification prohibits concurrent access to stateful session beans. If a second thread invokes a method while an invocation is already in progress, the container throws a ConcurrentAccessException. If shared concurrent state is really needed, use a @Singleton bean with @Lock(LockType.READ) and @Lock(LockType.WRITE) instead.

❓
Q2: What happens if a method annotated @TransactionAttribute(TransactionAttributeType.REQUIRES_NEW) throws a RuntimeException?

The newly spawned independent transaction rolls back. The suspended parent transaction then resumes. Unless the parent method catches the exception, the uncaught exception propagates upward and causes the parent transaction to roll back as well — so a “separate” transaction does not protect the caller if the caller ignores the failure.

❓
Q3: What is the purpose of <ui:insert> and <ui:define> in Facelets?

In a master template, <ui:insert name="regionName"> declares a dynamic placeholder where child pages can inject content. A child page uses <ui:composition template="..."> together with <ui:define name="regionName"> to supply page-specific markup for that region. The template keeps the frame; the child fills the holes.

3.1 Lab Project 1 — Enterprise multi-tier banking core

Concepts tested: @Stateful, @Stateless, @Singleton, @Lock, JNDI injection, CMT rollback.

The scenario. A commercial bank needs a core transactional backend with three distinct enterprise services:

  1. CurrencyRateCache (@Singleton) — holds real-time exchange rates (USD/EUR/GBP). It needs high-concurrency read access and an exclusive write lock for updates.
  2. CustomerSessionBean (@Stateful) — holds the logged-in customer's active session, a cart of pending transfers, and a verification token.
  3. TransferServiceBean (@Stateless) — performs atomic debit and credit operations under Container-Managed Transactions. It must roll back both accounts if either the debit or the credit fails.
In plain words

This one project uses all three bean types on purpose, so you can feel the difference. The rate cache is shared by everyone (singleton). The customer session belongs to one person (stateful). The transfer service is a pooled worker anyone can call (stateless).

Atomic means “all or nothing”: the pair of account updates is one indivisible unit. A @Lock(LockType.READ) lets many readers in at once; a @Lock(LockType.WRITE) locks the door so only one writer may change the map.

@Startup
@ConcurrencyManagement(ConcurrencyManagementType.CONTAINER)
public class CurrencyRateCache {

    private Map<String, BigDecimal> exchangeRates;

    @PostConstruct
    public void init() {
        exchangeRates = new HashMap<>();
        exchangeRates.put("USD_TO_EUR", new BigDecimal("0.92"));
        exchangeRates.put("USD_TO_GBP", new BigDecimal("0.78"));
        exchangeRates.put("USD_TO_NGN", new BigDecimal("1450.00"));
        System.out.println("[CurrencyRateCache] Initialized currency rates in memory.");
    }

    @Lock(LockType.READ)
    public BigDecimal getRate(String currencyPair) {
        return exchangeRates.getOrDefault(currencyPair, BigDecimal.ONE);
    }

    @Lock(LockType.WRITE)
    public void updateRate(String currencyPair, BigDecimal newRate) {
        exchangeRates.put(currencyPair, newRate);
        System.out.println("[CurrencyRateCache] Rate updated: " + currencyPair + " = " + newRate);
    }
}

Step 2 — the stateful customer session

src/main/java/com/aptech/bank/session/CustomerSessionBean.java
package com.aptech.bank.session;

import jakarta.annotation.PostConstruct;
import jakarta.ejb.Stateful;
import jakarta.ejb.Remove;
import java.io.Serializable;
import java.util.ArrayList;
import java.util.List;

@Stateful
public class CustomerSessionBean implements Serializable {

    private String customerId;
    private List<String> pendingTransferIds;

    @PostConstruct
    public void init() {
        this.pendingTransferIds = new ArrayList<>();
    }

    public void login(String customerId) {
        this.customerId = customerId;
        System.out.println("[CustomerSession] Customer logged in: " + customerId);
    }

    public void queueTransfer(String transferId) {
        pendingTransferIds.add(transferId);
    }

    public List<String> getPendingTransfers() {
        return new ArrayList<>(pendingTransferIds);
    }

    @Remove
    public void logout() {
        System.out.println("[CustomerSession] Logging out customer: " + customerId);
        pendingTransferIds.clear();
    }
}
💡
Why @Remove matters A @Stateful bean lives until someone ends it. The @Remove annotation tells the container “this method finishes the conversation — destroy the instance afterwards”. Without it the bean would linger in memory after the customer has gone.

Step 3 — the stateless transactional transfer service

src/main/java/com/aptech/bank/service/TransferServiceBean.java
package com.aptech.bank.service;

import jakarta.annotation.Resource;
import jakarta.ejb.SessionContext;
import jakarta.ejb.Stateless;
import jakarta.ejb.TransactionAttribute;
import jakarta.ejb.TransactionAttributeType;
import java.math.BigDecimal;

@Stateless
public class TransferServiceBean {

    @Resource
    private SessionContext sessionContext;

    @TransactionAttribute(TransactionAttributeType.REQUIRED)
    public void executeTransfer(String fromAccount, String toAccount, BigDecimal amount) {
        System.out.println("[TransferService] Initiating transfer of " + amount + " from " + fromAccount + " to " + toAccount);

        // Step 1: Debit source account
        debitAccount(fromAccount, amount);

        // Simulated validation check for demonstration
        if (amount.compareTo(new BigDecimal("10000.00")) > 0) {
            System.err.println("[TransferService] Transaction exceeds limit! Forcing rollback.");
            throw new IllegalArgumentException("Single transfer cannot exceed $10,000.00");
        }

        // Step 2: Credit target account
        creditAccount(toAccount, amount);

        System.out.println("[TransferService] Transfer completed successfully.");
    }

    private void debitAccount(String accountId, BigDecimal amount) {
        System.out.println(" -> Debited " + amount + " from " + accountId);
    }

    private void creditAccount(String accountId, BigDecimal amount) {
        System.out.println(" -> Credited " + amount + " to " + accountId);
    }
}
In plain words

The debit prints before the limit check. That ordering is deliberate: if the amount is over $10,000, the debit has already “happened” when the IllegalArgumentException (an unchecked exception) is thrown. Because the method is REQUIRED, the container rolls the whole thing back — and the debit never really stands.

SessionContext is your handle on the container. In a fuller version you would call sessionContext.setRollbackOnly() to ask for a rollback yourself.

Step 4 — build, deploy and verify

  1. Start WildFly and build

    Start the server in one terminal, then build in a second terminal from the folder holding pom.xml:

    standalone.bat          REM  Windows
./standalone.sh         #    macOS / Linux
    mvn clean package

    You should see BUILD SUCCESS and a new target/aptech-bank.war.

  2. Deploy by copying the file

    WildFly watches its deployments folder. Copy the war in and the server deploys it for you:

cp   target/aptech-bank.war  ~/wildfly/standalone/deployments/       #    macOS / Linux

    You should see in the server window:

    [CurrencyRateCache] Initialized currency rates in memory.

    The first line is the @Startup singleton running. If it is missing, the singleton never started — check the annotation and redeploy.

  3. Drive the beans and watch the log

    Call each service from a small servlet or a test client — login a customer, queue a transfer, then execute a normal transfer and an over-limit one.

    You should see, for the good transfer, the debit and the credit; and for the over-limit one, the debit printed followed by Transaction exceeds limit! Forcing rollback. The absence of Transfer completed successfully. on the second call is your proof the transaction was rolled back.

Checkpoint 3a · Lab 1

Answer before moving to Lab 2.

  1. Why is the currency cache a @Singleton rather than a @Stateless bean?
  2. Which annotation on the transfer method starts the transaction, and which attribute type does it use?
  3. The over-limit transfer prints the debit line but does not print the success line. What does that tell you?
Show answers

Step 2 — the composite component

src/main/webapp/resources/components/balanceWidget.xhtml
<!DOCTYPE html>

      xmlns:cc="jakarta.faces.composite"
      xmlns:h="jakarta.faces.html">

In plain words

A composite component is a reusable widget you build once and drop in anywhere. The <cc:interface> block declares its knobs — the attributes callers must set — and the <cc:implementation> block is its body. Inside the body, cc.attrs reads whatever the caller passed in. Because the file lives in resources/components/, you can use it as <components:balanceWidget … />.

3.3 Lab Project 3 — Asynchronous JMS auditing with a JCA data source

Concepts tested: JMS 3.0 Queue, Message-Driven Bean (@MessageDriven), JDBC data source via JCA.

The scenario. Every important action in the bank should be written to an audit trail — but the customer should never wait for that writing. So the action is turned into a message and posted to a queue, and a separate listener stores it later.

Step 1 — the JMS audit producer

src/main/java/com/aptech/audit/AuditMessageProducer.java
package com.aptech.audit;

import jakarta.annotation.Resource;
import jakarta.ejb.Stateless;
import jakarta.inject.Inject;
import jakarta.jms.JMSContext;
import jakarta.jms.Queue;

@Stateless
public class AuditMessageProducer {

    @Resource(lookup = "java:/jms/queue/AuditQueue")
    private Queue auditQueue;

    @Inject
    private JMSContext jmsContext;

    public void sendAuditLog(String action, String user, String ipAddress) {
        String payload = String.format("ACTION=%s;USER=%s;IP=%s;TIMESTAMP=%d", action, user, ipAddress, System.currentTimeMillis());
        jmsContext.createProducer().send(auditQueue, payload);
        System.out.println("[AuditProducer] Sent audit message: " + payload);
    }
}
In plain words

JMSContext, injected with @Inject, is your connection to the messaging system. createProducer().send(queue, payload) drops the message onto the queue and returns immediately — the producer does not sit and wait for anyone to pick it up. That is the asynchronous part.

Step 2 — the message-driven bean that stores the log

src/main/java/com/aptech/audit/AuditLogConsumerMDB.java
package com.aptech.audit;

import jakarta.annotation.Resource;
import jakarta.ejb.ActivationConfigProperty;
import jakarta.ejb.MessageDriven;
import jakarta.jms.JMSException;
import jakarta.jms.Message;
import jakarta.jms.MessageListener;
import jakarta.jms.TextMessage;
import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;

@MessageDriven(activationConfig = {
    @ActivationConfigProperty(propertyName = "destinationLookup", propertyValue = "java:/jms/queue/AuditQueue"),
    @ActivationConfigProperty(propertyName = "destinationType", propertyValue = "jakarta.jms.Queue"),
    @ActivationConfigProperty(propertyName = "acknowledgeMode", propertyValue = "Auto-acknowledge")
})
public class AuditLogConsumerMDB implements MessageListener {

    @Resource(lookup = "java:jboss/datasources/ExampleDS")
    private DataSource dataSource;

    @Override
    public void onMessage(Message message) {
        if (message instanceof TextMessage) {
            try {
                String payload = ((TextMessage) message).getText();
                System.out.println("[AuditMDB] Received async log: " + payload);
                persistToDatabase(payload);
            } catch (JMSException e) {
                System.err.println("[AuditMDB] JMS error: " + e.getMessage());
            }
        }
    }

    private void persistToDatabase(String logEntry) {
        String sql = "INSERT INTO audit_logs (log_entry, created_at) VALUES (?, CURRENT_TIMESTAMP)";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, logEntry);
            ps.executeUpdate();
            System.out.println("[AuditMDB] Successfully stored log in database using JCA pool.");
        } catch (SQLException e) {
            System.err.println("[AuditMDB] SQL error persisting log: " + e.getMessage());
        }
    }
}
💡
Reading the three activation properties destinationLookup says which queue to listen to — it must match the producer's lookup exactly. destinationType says what kind of destination it is (a queue, not a topic). acknowledgeMode set to Auto-acknowledge says tell the messaging system the message is done as soon as it is handled. There is no client interface here — nobody calls an MDB; the container calls it when a message arrives.

One-line summary

  

    
Bean types@Stateless is pooled and stateless; @Stateful is one-per-client; @Singleton is one shared instance guarded by @Lock.

    
JNDI reachjava:global > java:app > java:module > java:comp.

    
CMT propagationREQUIRED joins or starts; REQUIRES_NEW suspends and starts fresh; MANDATORY demands one already.

    
Rollback ruleUnchecked exceptions roll back; checked application exceptions commit unless flagged rollback = true.

    
JSF lifecycleSix phases; validation is Phase 3, and a failure jumps to Phase 6.

    
Local vs remoteLocal is pass-by-reference in one JVM; remote is pass-by-value and needs Serializable.

    
MessagingQueue delivers to exactly one consumer; Topic delivers to every active subscriber.

    
JCA contractsConnection Management (pooling), Transaction Management (two-phase commit), Work Management (thread scheduling).

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      

        Storing client-specific data in a @Stateless bean's fields
        Keep it in parameters or local variables. The pooled instance is shared between callers, so fields leak data.
      

      

        Making a login counter or cache a @Stateful bean
        Use @Singleton. State that must be shared belongs in the one shared instance, guarded by @Lock.
      

      

        Expecting a checked exception to roll back the transaction
        Checked application exceptions commit by default. Add @ApplicationException(rollback = true) or call ctx.setRollbackOnly().
      

      

        Passing a non-serializable object to a @Remote method
        Every object that crosses the network must implements Serializable, because remote calls pass values by copy.
      

      

        Retyping a JNDI name by hand
        Copy it exactly from the Admin Console or the CLI (ls java:). A typo produces a “not bound” error that is hard to spot.
      

      

        Sending to a Queue or Topic that was never created
        Create the destination first and give the producer and the MDB the identical lookup name.
      

      

        Expecting a Topic to reach a subscriber that was not active at send time
        Deploy (start) every subscriber before publishing. A Topic reaches only subscribers that are listening when the message is sent.
      

      

        Forgetting @Remove on the logout method of a @Stateful bean
        Annotate the end-of-conversation method with @Remove, or the container keeps the instance alive in memory.
      

      

        Leaving database connections to be cleaned up by hand
        Use try-with-resources — try (Connection c = …) { … } — so the connection is returned to the JCA pool automatically.
