Part 1 · How a transaction travels from one bean to the next

First, a 30-second recall from Session 4

A transaction is a group of changes treated as all-or-nothing: either every change sticks (commit) or none of them do (roll back). That is the "A" of ACID.

Session 4 also showed you two ways to run one. Container-Managed Transactions (CMT) — the container starts and ends the transaction for you, driven by a label. Bean-Managed Transactions (BMT) — you do it yourself in code (that is Part 2 here). And it introduced the six transaction attributes you put on a method: REQUIRED, REQUIRES_NEW, MANDATORY, SUPPORTS, NOT_SUPPORTED and NEVER. If any of that feels hazy, take five minutes with Session 4 — Working with EJB and come back.

1.1 Real work rarely fits in one method

In a real system a single business action spreads across several beans. A checkout bean calls an inventory bean, which calls a billing bean, which writes to an audit-log bean.

So here is the question this whole Part answers:

❓
When bean A calls bean B, is B inside A's transaction, or in one of its own? That single decision is called transaction propagation. It is not something you code — you declare it, with the transaction attribute on bean B's method. The six attributes are simply six different answers to that one question.
In plain words

"Propagation" just means whether the transaction carries over when one bean calls another. The attribute on the method being called decides it.

1.2 The picture that makes it click

📞
Analogy — one phone call, or a fresh one Think of a transaction as a phone call that is already in progress. Bean A is on the call. When A asks bean B to help, B has a choice declared by its attribute:
  • Join the call that is already happening — now A and B are on the same line. If the call drops, it drops for both of them.
  • Step out and make a separate call — B dials its own number, finishes its own conversation, hangs up, and only then does A carry on. A dropping its call later cannot undo B's.
Everything in the table below is a variation on "join the existing call" versus "make your own."

1.3 The six attributes, when the caller is already in a transaction

Say bean A is already running inside a transaction — call it T1. Here is what each attribute on bean B's method does:

Bean B's method is marked…What happens to the transaction
REQUIRED
(the default)		 B runs inside the same transaction T1. One shared line. If B fails, A rolls back too — and the other way round.
REQUIRES_NEW The container suspends T1 (puts it on hold), starts a fresh transaction T2 for B, commits T2 when B finishes, then resumes T1. B's result survives even if A rolls back afterwards.
MANDATORY B joins T1. (But if A had no transaction, B would throw TransactionRequiredException — see 1.4.)
SUPPORTS B joins the same transaction T1, just like REQUIRED — but it never starts one of its own. (If A had no transaction, B would simply run without one.)
NOT_SUPPORTED The container suspends T1, runs B with no transaction at all, then resumes T1 when B returns.
NEVER 🚨 Because a transaction is active, the container throws EJBException immediately and B never runs.
🚪
Analogy — why REQUIRES_NEW exists Picture an audit log that must record "a transfer was attempted" even if the transfer itself later fails and is undone. If the log wrote inside the main transaction, a rollback would erase the log entry too. So the log bean steps out and makes its own call (REQUIRES_NEW): it commits separately, and the main rollback cannot touch it.

1.4 The two that can refuse to run

Two of the attributes do not just redirect the transaction — they can stop the call cold. This surprises people, so it gets its own box.

⚠️
These throw instead of running
  • MANDATORY says "there must already be a transaction." Call it with none and you get TransactionRequiredException.
  • NEVER says the opposite — "there must not be one." Call it while a transaction is active and you get EJBException.
Both failures happen before your business code runs a single line.
🎫
Analogy MANDATORY is a club that only admits people who arrive with a group booking — turn up alone and you are turned away. NEVER is the quiet reading room next door — turn up with a noisy group and you are turned away. Each refuses the exact case the other requires.

1.5 Across machines, too

The caller and the callee do not have to live in the same server. When beans sit on different machines (a distributed call), the transaction can still span both — and a special protocol called two-phase commit keeps the two sides agreeing. You do not need its mechanics today; it is written up in the Reference at the end.

Part 2 · Taking the wheel yourself — UserTransaction (BMT)

Until now the container has started and ended every transaction for you. That is CMT, and it covers about 95% of all code. Part 2 is the other 5%: the times you need to start, commit and roll back the transaction yourself, in code. That is a Bean-Managed Transaction (BMT).

🚗
Analogy — automatic vs manual gearbox CMT is an automatic car: you press the pedal and the gearbox changes gear for you. BMT is a manual (stick-shift) car: you work the clutch and choose each gear yourself. More control, more to get wrong — and only worth it when the automatic cannot do what you need.

2.1 When would you ever want the manual gearbox?

The classic case is a big batch job. Imagine importing 100,000 rows. If all of them sit in one transaction and row 99,000 fails, you lose everything and start over. Instead you commit every 500 rows, so a failure late on only loses the current chunk.

💾
Analogy — saving a long document chapter by chapter You would not type a 300-page book and save only at the very end. You save after each chapter, so a crash loses one chapter, not the book. Committing every 500 rows is exactly that: frequent save points, so a late failure cannot wipe the lot.

2.2 Turning BMT on, and getting the controls

Two steps turn a bean into a manual-gearbox bean:

  • Put @TransactionManagement(TransactionManagementType.BEAN) on the class. That tells the container "hands off — I will manage the transaction myself."
  • Ask the container for a UserTransaction — the object with the begin/commit/rollback controls — with @Resource (or a JNDI lookup of java:comp/UserTransaction).
In plain words

UserTransaction is the gearstick. It only exists for you to hold in a BMT bean. A CMT bean never touches it — the container is holding the stick there.

Here is everything you can say to that gearstick, and what each move can throw if used wrongly:

Method on UserTransactionWhat it doesCan throw
utx.begin()Starts a new transaction on the current threadNotSupportedException (if one is already running)
utx.commit()Makes every change in the transaction permanentRollbackException, HeuristicMixedException
utx.rollback()Aborts and reverses every changeIllegalStateException, SecurityException
utx.setTransactionTimeout(sec)Sets how many seconds before the transaction auto-abortsSystemException
utx.getStatus()Reports the current state (for example STATUS_ACTIVE)SystemException
✍️
Analogy — begin / commit / rollback is signing a contract begin() takes out a blank contract and starts filling it in. commit() is signing it — now it is binding and permanent. rollback() is tearing it up — as if it had never been written. Nothing you wrote on the draft counts until you sign.
🚦
One at a time You cannot begin() a transaction while one is already running on the thread — that is the NotSupportedException in the table. Finish (commit or roll back) the current one before starting the next. In a batch loop that means: begin, do the chunk, commit, then begin the next chunk.

2.3 The shape of every BMT method

Before the code, here is the pattern in five plain moves. The numbers match the ①–⑤ markers in the code below.

  1. Declare bean-managed transactions

    Put @TransactionManagement(TransactionManagementType.BEAN) on the class so the container stops managing transactions for you. (Marker ①.)

  2. Get the gearstick

    Inject UserTransaction with @Resource, or look it up at java:comp/UserTransaction. (Marker ②.)

  3. Open the boundary

    Call utx.begin() to start the transaction, optionally with utx.setTransactionTimeout(...) to cap how long it may run. (Markers ③.)

  4. Do the work, then commit

    Make your changes, then call utx.commit() to lock the chunk in permanently. (Marker ④.)

  5. If anything throws, roll back

    In a catch, call utx.rollback() to undo only this chunk — earlier committed chunks are already safe. (Marker ⑤.)

Now the real code — the batch importer that commits every 500 rows:

BatchImportService.java — a Bean-Managed Transaction
package com.globalbank.batch;

import jakarta.annotation.Resource;
import jakarta.ejb.Stateless;
import jakarta.ejb.TransactionManagement;
import jakarta.ejb.TransactionManagementType;
import jakarta.transaction.UserTransaction;
import java.util.List;

@Stateless
@TransactionManagement(TransactionManagementType.BEAN) // ① Declare BMT
public class BatchImportService {

    // ② Inject the JTA UserTransaction coordinator (or lookup via java:comp/UserTransaction)
    @Resource
    private UserTransaction utx;

    public void processBatchRecords(List<String> records) {
        int batchSize = 500;

        for (int i = 0; i < records.size(); i += batchSize) {
            try {
                // ③ Explicitly open transaction boundary
                utx.begin();
                utx.setTransactionTimeout(60); // 60 seconds limit

                List<String> sublist = records.subList(i, Math.min(i + batchSize, records.size()));
                for (String record : sublist) {
                    insertRecord(record);
                }

                // ④ Commit this chunk of 500 rows
                utx.commit();
                System.out.println("Committed batch: " + i + " to " + (i + sublist.size()));

            } catch (Exception e) {
                try {
                    // ⑤ Abort only this failed chunk; earlier committed chunks remain safe!
                    utx.rollback();
                    System.err.println("Batch starting at " + i + " failed and rolled back.");
                } catch (Exception rollbackEx) {
                    rollbackEx.printStackTrace();
                }
            }
        }
    }

    private void insertRecord(String rec) { /* JDBC persistence logic */ }
}
💡
The one thing to notice Each trip round the loop is its own transaction: a begin(), a commit(), and a rollback() only for the chunk that failed. That is why chunk 2 blowing up cannot undo chunk 1 — chunk 1 was already signed and sealed. CMT could not do this, because CMT gives the whole method one single transaction.

Part 3 · Who decides: commit or roll back when something goes wrong


  
Back in container-managed transactions (CMT), when an exception flies out of a bean method, the
    container has to make a decision: commit the work so far, or throw it all away? The
    answer depends entirely on what kind of exception it is. Get this wrong and you will corrupt
    data while being certain your code is correct — so read it slowly.


  
3.1 Two kinds of exception, two opposite reactions

  
    
    
  • A system exception means "something broke that was never supposed to break." These
      are the unchecked ones — RuntimeException, NullPointerException,
      EJBException. The container reads this as a genuine failure.
    • 
    
  • An application exception means "a normal business outcome the code was expected to
      signal." By default these are the checked ones — things like
      InsufficientFundsException or AccountFrozenException.
    • 
  


  
In plain words
    
"Unchecked" means the exception extends RuntimeException, so Java does not force you to
      declare or catch it. "Checked" means it extends Exception, so the compiler makes you
      handle it. The container uses that same split to guess your intent: unchecked = a crash, checked =
      an expected business "no."

  


  
🍽️
    
Analogy — the dropped tray vs the cancelled dish
      A system exception is a waiter tripping and smashing the plate — an
      accident. The kitchen bins that order and throws the ruined plate away. A
      application exception is a customer calmly saying "actually, cancel the
      dessert" — a normal, expected request. The restaurant just carries on; nobody throws anything
      out.

  


  
That analogy maps exactly onto what the container does:

  
    
    
  • System exception → automatic rollback, and the container discards the
      bean instance from the pool, because its fields may now hold half-finished, corrupt state.
      (The smashed plate is thrown away.)
    • 
    
  • Application exception → the transaction COMMITS by default, and the bean instance
      is kept in the pool. (The waiter is fine; carry on.)
    • 
  


  
3.2 The trap that catches absolutely everyone


  
⚠️
    
A checked exception does NOT roll back by default
      Throw a plain checked InsufficientFundsException after you have already debited an
      account, and expect the debit to be undone? It will not be. The container treats a
      checked application exception as a normal business signal and commits the work done
      so far. The debit stays. This surprises everyone the first time — and silently corrupts balances in
      production.

  


  
3.3 Forcing an application exception to roll back

  
Sometimes a business "no" really does mean "undo everything" — a fraud check, say. You tell the
    container that by stamping the exception class with @ApplicationException(rollback = true).


  
FraudException.java — an application exception that forces rollback

  
package com.globalbank.exceptions;

import jakarta.ejb.ApplicationException;

@ApplicationException(rollback = true)   // when thrown, the container WILL roll back
public class FraudException extends Exception {

    public FraudException(String message) {
        super(message);
    }
}


  
💡
    
The one thing to notice
      The rule lives on the exception class, not on the method that throws it. Write
      rollback = true once and every method that throws a FraudException rolls
      back. (rollback = false does the opposite — it marks an unchecked exception as a normal
      business one that should commit.)

  


  
3.4 Rolling back from inside a catch

  
What if you catch the problem yourself, handle it, and return normally — but you still want
    the transaction thrown away? You cannot rely on an exception travelling out, because you swallowed it.
    So you tell the container directly: setRollbackOnly().


  
TransferService.java — forcing a rollback without throwing

  
package com.globalbank.services;

import jakarta.annotation.Resource;
import jakarta.ejb.SessionContext;
import jakarta.ejb.Stateless;

@Stateless
public class TransferService {

    @Resource
    private SessionContext ejbContext;      // the bean's link back to the container

    public void transfer(Account from, Account to, double amount) {
        try {
            debit(from, amount);
            credit(to, amount);
        } catch (BusinessRuleViolation e) {
            ejbContext.setRollbackOnly();   // doom the transaction: it WILL roll back on exit
            // ... log the problem and return normally
        }
    }
}


  
🚫
    
Analogy — stamping a cheque VOID
      setRollbackOnly() is like stamping a cheque VOID halfway through
      writing it. You can keep filling in the rest of the boxes, hand it over, do everything else
      normally — but it will never, ever be cashed. The container checks for that stamp when the method
      exits and rolls back no matter what.

  


  
💡
    
The one thing to notice
      setRollbackOnly() only marks the transaction — the actual rollback happens when
      the method returns. There is no way to un-mark it. Once stamped, the transaction is doomed, so only
      call it when you truly mean to abort.

Part 4 · Keeping a stateful bean's cache in step — SessionSynchronization


  
Recall the stateful bean from Session 1 & 2: it is dedicated to one client and
    remembers its fields across several calls. Those remembered fields are, in effect, a
    cache — a copy held in memory of data that really lives in the database. And a cache
    has a problem: when a transaction commits or rolls back, the copy in memory and the copy in the
    database can drift apart.

  
To fix that, a stateful bean can implement the SessionSynchronization
    interface. In exchange, the container calls it back at three key moments in every
    transaction, so the bean can keep its cache honest.


  
In plain words
    
SessionSynchronization is a way for a stateful bean to say "tell me when the
      transaction starts, when it is about to commit, and when it is finished" — so the bean can
      load its data at the start, save it just before the end, and tidy up afterwards.

  


  
4.1 The three callbacks

  

    
CallbackWhen the container calls itWhat you typically do there

    
      

        afterBegin()
        Just after the transaction starts.
        Load (or lock) the data from the database into the bean's cache in memory.
      

      

        beforeCompletion()
        Right before the transaction manager issues the COMMIT.
        Flush the changed ("dirty") cached fields down to the database.
      

      

        afterCompletion(boolean committed)
        Just after the transaction commits (true) or rolls back (false).
        If committed is true, update display state. If false,
          throw the modified cache away and reload from the database.
      

    
  


  
🧾
    
Analogy — a shopkeeper's till across one shift
      afterBegin() is counting the cash float into the drawer at the
      start of the shift — bringing the figures out of the safe and onto the counter.
      beforeCompletion() is writing the day's totals into the ledger
      just before cashing up — getting the final numbers down on paper.
      afterCompletion(true) is head office accepting the figures: lock the
      safe and go home. afterCompletion(false) is head office bouncing them:
      tear up the sheet and recount from the bank's own record (reload from the database).

  


  
4.2 What it looks like in code

  
A stateful bean implements the interface and overrides the three methods:


  
ShoppingBasketBean.java — a stateful bean that syncs its cache

  
package com.globalbank.web;

import jakarta.ejb.Stateful;
import jakarta.ejb.SessionSynchronization;

@Stateful
public class ShoppingBasketBean implements SessionSynchronization {

    private Basket cache;        // data held in memory for this one client

    @Override
    public void afterBegin() {
        // transaction just started: load the data into the cache
        cache = loadFromDatabase();
    }

    @Override
    public void beforeCompletion() {
        // about to commit: push the cached changes down to the database
        flushToDatabase(cache);
    }

    @Override
    public void afterCompletion(boolean committed) {
        if (!committed) {
            // rolled back: the cache is now wrong, so discard it and reload next time
            cache = null;
        }
    }

    private Basket loadFromDatabase() { /* read current state */ return new Basket(); }
    private void flushToDatabase(Basket b) { /* write changes */ }
}


  
💡
    
The one thing to notice
      You never call these three methods — the container calls them, in order,
      around your business methods. Your job is only to say what should happen at each moment. The single
      most important line is afterCompletion(false) throwing the cache away: that is what
      stops a rolled-back change from lingering in memory and poisoning the next call.

    🔄 SessionSynchronization — the exact callback order
    
For a single transaction on a stateful bean that implements the interface, the container calls the
      methods in this fixed order:

    
  transaction starts
        │
        ▼
  afterBegin()                 ← load / lock cached data
        │
        ▼
  (your business methods run)  ← the client calls add(), update(), etc.
        │
        ▼
  beforeCompletion()           ← flush dirty cache to the database
        │
        ▼
  COMMIT  (or ROLLBACK)        ← the transaction manager acts
        │
        ▼
  afterCompletion(committed)   ← true = committed, false = rolled back

    
If the transaction rolls back, beforeCompletion() may still have run, but
      afterCompletion(false) is your signal to discard whatever the cache now holds.

  


  

    🌐 Distributed transactions — Two-Phase Commit (2PC) and XA
    
A single business transaction sometimes has to touch more than one resource at
      once — for example a relational database and a JMS message broker. Both must commit, or
      neither must. The server's transaction coordinator guarantees that with a protocol
      called two-phase commit (2PC), over resources that speak the XA
      standard:

    
    
      
  1. Phase 1 — prepare. The coordinator asks every resource "are you ready and able
        to commit?" Each one does all the work short of making it permanent and answers yes or no.
    2. 
      
  2. Phase 2 — commit (or roll back). If every resource said yes, the
        coordinator tells them all to commit. If even one said no, it tells them all to roll back.
    3. 
    

    
💍
      
Analogy
        A wedding officiant. First they ask each person separately, "do you take this commitment?"
        (prepare). Only when both have said "I do" does the officiant pronounce them married
        (commit). A single "no" from either side, and nothing is binding.

    

    
You rarely write 2PC code yourself — the application server's coordinator (in WildFly, the
      Narayana transaction manager) runs it for you across XA-capable resources.

One-line summary of everything

  

    
PropagationWhether a transaction carries over when one bean calls another. Decided by the attribute on the method being called.

    
The six attributesREQUIRED (join or start), REQUIRES_NEW (always its own), MANDATORY (must have one), SUPPORTS (go with the flow), NOT_SUPPORTED (run with none), NEVER (refuse if one exists).

    
BMTDrive the transaction by hand: @TransactionManagement(BEAN) plus UserTransaction's begin(), commit(), rollback().

    
System exceptionsUnchecked. Automatic rollback, and the container discards the bean instance.

    
Application exceptionsChecked by default, and they commit by default. Use @ApplicationException(rollback=true) to force a rollback.

    
setRollbackOnly()Marks a container-managed transaction so it is guaranteed to roll back when the method exits.

    
SessionSynchronizationThree container callbacks for a stateful bean: afterBegin() (load), beforeCompletion() (flush), afterCompletion(boolean) (tidy up or reload).

    
2PC / XAThe server coordinator's prepare-then-commit protocol that keeps several resources (database, message broker) all-or-nothing together.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Expecting a checked application exception to roll back the transactionBy default it commits. Annotate the class @ApplicationException(rollback=true), or call setRollbackOnly().

      
Reaching for REQUIRES_NEW everywhereUse REQUIRED (the default) unless the work must commit independently — audit logs are the classic reason.

      
Injecting UserTransaction but forgetting @TransactionManagement(BEAN)UserTransaction only works in a BMT bean. A CMT bean must not call begin()/commit().

      
Calling utx.begin() while a transaction is already activeThat throws NotSupportedException. Commit or roll back the current one first.

      
Catching an exception in a CMT method and expecting a rollback anywayIf you swallow it, the transaction will commit. Call ejbContext.setRollbackOnly() to actually abort.

      
Leaving a rolled-back change sitting in a stateful bean's cacheDiscard and reload it in afterCompletion(false), so the next call starts from clean data.
