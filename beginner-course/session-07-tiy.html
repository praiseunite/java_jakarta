Try It Yourself · Facelets, Local & Remote Clients

In Sessions 5 and 6 you left the backend behind and learned how other programs talk to your beans. Session 5 gave you Facelets — the server-rendered web pages that make up the presentation tier. Session 6 gave you the two ways a caller can reach a bean: as a Local Client (same machine, in memory) or a Remote Client (a separate program, over the network).

This page turns both into one lab. You will build a currency converter, drive it from a browser form, then call the very same bean from a standalone Java program — and see for yourself why one call is instant and the other travels down a wire.

consolidation

Part 1 · The map: who calls the bean, and how

Before you type anything, hold this picture in your head. There is one bean — the thing that knows how to convert money. Two very different callers want to use it:

  • A web page, served by the same application. That is a Local Client.
  • A partner bank's desktop program, running on a different machine. That is a Remote Client.

Same bean, same method, two totally different journeys. That is the whole of Session 6 in one table:

Client TypeComponentHow It Accesses EJBCommunication Boundary
Web Tier (Local) JSF Facelets + CDI Backing Bean Injected via @EJB or @Inject into backing bean Same JVM (in-memory, nanoseconds, pass-by-reference)
Distributed (Remote) Standalone Java Desktop / External Server Looked up via InitialContext.lookup("ejb:...") Network Boundary (serialized over HTTP-Remoting / RMI, milliseconds)
In plain words

A local call is you shouting across the room to a colleague. A remote call is posting them a letter, having them write the answer, and posting it back.

Both get the job done. But one is nearly free, and the other has to write your request down first — that writing-down is called serialization, and it is where most remote-client bugs live.

🏦
Analogy A teller at the next window is a local client: you hand them a form and they read it directly. A partner bank in another city is a remote client: you must fax the form, and anything you fax has to be on paper — you cannot fax a person. If your argument is not serializable, it cannot be faxed.
❓
The one rule that decides everything
  • Same machine, same application → @EJB injection, a Local Client. Fast, simple, no serialization.
  • Different machine, or a separate program → JNDI lookup(), a Remote Client. Every argument and return value must implement java.io.Serializable.
Checkpoint 1 · before you move on

Answer out loud, in your own words. Then open the answers.

  1. Which client type uses @EJB injection, and which uses InitialContext.lookup()?
  2. Why does a local call take nanoseconds while a remote call takes milliseconds?
  3. You are writing a desktop tool that a partner bank will install on their own machines. Local or remote?
Show answers
  1. The Local Client (web tier) uses @EJB/@Inject; the Remote Client (standalone program) uses InitialContext.lookup().
  2. A local call passes a reference to the object already in memory — the caller and the bean share the same JVM heap, so it is just a pointer. A remote call has to serialize the arguments into bytes, send them over the network, and deserialize the reply — real work with real travel time.
  3. Remote. Different machines means a network boundary, so you need a remote interface and everything passed across must be Serializable.

  3. Write the two interfaces — the whole point of the lab

    This is the design decision the session is really about. One bean, two doorways in. Put both files in src/main/java/com/globalbank/ejb/. Each is a complete file — the package line and the annotation import are not optional, because the bean and the backing bean both refer to them by their fully-qualified name, com.globalbank.ejb.CurrencyLocal and com.globalbank.ejb.CurrencyRemote.

    src/main/java/com/globalbank/ejb/CurrencyLocal.java
    package com.globalbank.ejb;

import jakarta.ejb.Local;

// Local view for the JSF Web Tier
@Local
public interface CurrencyLocal {
    double convert(double amount, String from, String to);
}
    src/main/java/com/globalbank/ejb/CurrencyRemote.java
    package com.globalbank.ejb;

import jakarta.ejb.Remote;

// Remote view for Partner Banks & Desktop Terminals
@Remote
public interface CurrencyRemote {
    double convert(double amount, String from, String to);
}

    Why two? A single interface cannot be both. Local and remote have incompatible rules: local passes an object reference, remote must copy the object as bytes. So you declare two separate interfaces and let one class implement both.

    You should see: two tiny files, each with a package line, one import and one method. That is all an interface needs to be here.

  4. Write the bean that implements both

    2. CurrencyConverterBean.java — Stateless Bean implementing both views
    package com.globalbank.ejb;

import jakarta.ejb.Stateless;

@Stateless
public class CurrencyConverterBean implements CurrencyLocal, CurrencyRemote {

    @Override
    public double convert(double amount, String from, String to) {
        // Simplified exchange rate calculation
        if ("USD".equalsIgnoreCase(from) && "EUR".equalsIgnoreCase(to)) return amount * 0.92;
        if ("EUR".equalsIgnoreCase(from) && "USD".equalsIgnoreCase(to)) return amount * 1.09;
        return amount; // default 1:1
    }
}

    Notice there is no new, no threads, no database. The business rule and one annotation. The implements CurrencyLocal, CurrencyRemote clause is what makes the same method reachable both ways.

  5. Write the CDI backing bean the web page will talk to

    A Facelets page cannot call a bean directly. It binds to a backing bean — an ordinary CDI bean that holds the form fields and calls the EJB. Put it in src/main/java/com/globalbank/web/.

    3. ConverterBackingBean.java — CDI Backing Bean for JSF
    package com.globalbank.web;

import jakarta.ejb.EJB;
import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Named;
import com.globalbank.ejb.CurrencyLocal;

@Named("currencyBean")
@RequestScoped
public class ConverterBackingBean {

    @EJB
    private CurrencyLocal currencyService; // Injected as a local client

    private double amount = 100.0;
    private String from = "USD";
    private String to = "EUR";
    private double result;

    public void calculate() {
        this.result = currencyService.convert(amount, from, to);
    }

    // Getters and setters for amount, from, to, result...
}
    In plain words

    @Named("currencyBean") gives this bean a name the page can use in expressions: #{currencyBean.amount}.

    @RequestScoped means the container makes a fresh one for every request — so the form starts clean each time, and nothing leaks between users.

    @EJB on the field is the Local Client call in action: the container fills in a ready bean, and currencyService.convert(...) is a direct in-memory call.

    Note: the comment at the bottom is not decoration — JSF needs the getters and setters to read and write those fields. Generate them in your IDE (or write them out). Without them the form binds to nothing.

  6. Write the Facelets page

    Put converter.xhtml in src/main/webapp/. This is the file the browser actually opens.

    4. converter.xhtml — Facelets Form
    <!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html">
<h:head><title>Currency Exchange</title></h:head>
<h:body>
    <h:form>
        <h:outputLabel value="Amount: "/>
        <h:inputText value="#{currencyBean.amount}"/>

        <h:commandButton value="Convert" action="#{currencyBean.calculate}"/>
    </h:form>

    <h:panelGroup rendered="#{currencyBean.result gt 0}">
        <p>Converted Value: <strong>#{currencyBean.result}</strong></p>
    </h:panelGroup>
</h:body>
</html>

    Three things carry all the meaning:

    • h:inputText value="#{currencyBean.amount}" — the text box is bound to the bean's amount field. Type 250 and the field becomes 250.
    • h:commandButton action="#{currencyBean.calculate}" — the button's action is a method call, not a link. That is the local call into the bean.
    • h:panelGroup rendered="#{currencyBean.result gt 0}" — gt means “greater than”. The result paragraph is simply not rendered until there is a result to show.

  7. Add an <h:messages /> tag now, not later

    Beginners skip this and then spend an hour wondering why the button “does nothing”. A validation failure makes JSF silently skip your action method and jump straight to rendering — with no error on your page unless you ask for it. Put this line inside the form, just before the button:

    converter.xhtml — add inside <h:form>
    <h:messages />

    You should see: nothing new when everything is fine — h:messages renders only when there are messages to show. It is your smoke alarm, silent until there is smoke.

    Watch the first terminal (the server). Within a second or two:

    Deployed "currency-converter.war"

    You should see: that Deployed line. Then, in the same server window, look for the lines WildFly printed while registering your bean. It logs several JNDI names, and they do not all start the same way:

    java:global/currency-converter/CurrencyConverterBean!com.globalbank.ejb.CurrencyRemote
java:app/currency-converter/CurrencyConverterBean!com.globalbank.ejb.CurrencyRemote
java:module/CurrencyConverterBean!com.globalbank.ejb.CurrencyRemote
ejb:/currency-converter/CurrencyConverterBean!com.globalbank.ejb.CurrencyRemote

    Copy the ejb: line — the last one. The step-10 code calls ctx.lookup() with that ejb:-prefixed form, not with the java:global/… form the log prints most prominently. Copy java:global/… out of habit and the lookup fails with NameNotFoundException. Under the different prefix the two strings carry the same three parts — app name, bean name, fully-qualified @Remote interface — which is why the code can hard-code ejb:/currency-converter/CurrencyConverterBean!com.globalbank.ejb.CurrencyRemote.

    Now write the Remote Client
    
      
    Everything so far lived inside the war. A remote client does not — it is an ordinary Java program sitting
        outside the application, on its own JVM. That means it needs its own small project, and its own build file,
        because the WildFly client libraries (the ones that make InitialContext.lookup() able to
        speak HTTP-Remoting to the server) are not on a plain JDK's classpath.
    
      
    Make a second folder beside currency-converter — not inside it — called
        currency-client, and give it this pom.xml:
    
      
    currency-client/pom.xml
    
      
    <project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
                             http://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>com.globalbank</groupId>
  <artifactId>currency-client</artifactId>
  <version>1.0</version>
  <packaging>jar</packaging>

  <properties>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <exec.mainClass>com.globalbank.client.RemoteClient</exec.mainClass>
  </properties>

  <dependencies>
    <!-- Gives us the @Remote annotation used by the interface we copy in below -->
    <dependency>
      <groupId>jakarta.platform</groupId>
      <artifactId>jakarta.jakartaee-api</artifactId>
      <version>10.0.0</version>
      <scope>provided</scope>
    </dependency>

    <!-- The WildFly client stack: JNDI naming, EJB client, HTTP-Remoting -->
    <dependency>
      <groupId>org.wildfly</groupId>
      <artifactId>wildfly-client-all</artifactId>
      <version>30.0.1.Final</version>
    </dependency>
  </dependencies>

  <build>
    <plugins>
      <plugin>
        <groupId>org.codehaus.mojo</groupId>
        <artifactId>exec-maven-plugin</artifactId>
        <version>3.1.1</version>
        <configuration>
          <mainClass>com.globalbank.client.RemoteClient</mainClass>
          <!-- include the @Remote interface's compile-time API in the run classpath -->
          <classpathScope>compile</classpathScope>
        </configuration>
      </plugin>
    </plugins>
  </build>
</project>
    
      
    Now the client needs the interface contract. The bean implementation stays on the server,
        but the remote interface is the shared agreement both sides must know. Copy the file you wrote in step 3 into
        the client project, at the same package path:
    
      
    currency-client/src/main/java/com/globalbank/ejb/CurrencyRemote.java
    
      
    That is a straight copy of your CurrencyRemote.java from the server project — same
        package, same import, same method. Do not copy
        CurrencyConverterBean.java; the client must never see the implementation.
    
      
    Finally, the client class itself. Create it at
        currency-client/src/main/java/com/globalbank/client/RemoteClient.java:
    
      
    RemoteClient.java — standalone Java SE client
    
      
    package com.globalbank.client;

import javax.naming.Context;
import javax.naming.InitialContext;
import java.util.Properties;
import com.globalbank.ejb.CurrencyRemote;

public class RemoteClient {

    public static void main(String[] args) throws Exception {

        // Tell the client how to reach WildFly over HTTP-Remoting.
        Properties props = new Properties();
        props.put(Context.INITIAL_CONTEXT_FACTORY,
                  "org.wildfly.naming.client.WildFlyInitialContextFactory");
        props.put(Context.PROVIDER_URL, "http-remoting://localhost:8080");

        Context ctx = new InitialContext(props);

        // This is the exact name WildFly printed in its deploy log (step 8).
        CurrencyRemote service = (CurrencyRemote) ctx.lookup(
            "ejb:/currency-converter/CurrencyConverterBean!" +
            "com.globalbank.ejb.CurrencyRemote");

        double result = service.convert(250.0, "USD", "EUR");
        System.out.println("250.00 USD = " + result + " EUR");

        ctx.close();
    }
}
    
      
    Read the lines in order and you can see the difference from the local case. There is no @EJB
        here — nothing to inject, because this program is not part of the application. Instead it builds an
        InitialContext pointed at http-remoting://localhost:8080, then asks the server
        by name for the bean.
    
      
    ⚠️
        
    The name must match exactly
          WildFly builds the JNDI name for you out of the app name, the bean name and the fully-qualified interface
          name: ejb:/<app>/<Bean>!<package.Interface>. A typo anywhere — a capital letter,
          a missing !, the wrong interface — produces NameNotFoundException. Copy it from the
          server log. Never type it from memory.
    
      
    
      
    Note the cast. ctx.lookup() returns a plain Object, so you cast it
        to CurrencyRemote. The client never sees the bean class itself — it only needs the remote
        interface. That is why the interface had to be @Remote.

    jboss-ejb-client.properties

  troubleshooting
  
Part 3 · When it breaks — the three faults beginners hit


  
These are not mistakes you made. They are the three places this integration always goes wrong, and
    knowing them in advance is most of the skill. Each one gives you the symptom first — so you can recognise it on
    your own screen — then the cause and the fix.


  
1️⃣
    
Trap 1: java.io.NotSerializableException on Remote Calls
      
Symptom: Remote client call fails with WriteObjectException: NotSerializableException: com.model.Customer.

      
Cause: to cross a network, every argument and every return value is
        written into a byte stream. Java can only do that for objects that have agreed to it.

      
Fix: When passing custom objects to @Remote methods, every object and every nested member field must implement java.io.Serializable.

      
In our lab: double and String already are,
        which is exactly why this lab runs clean. The moment you add a Money or Customer
        class to a remote method, this is waiting for you.

    

  


  
2️⃣
    
Trap 2: Submitting a form without the action method firing
      
Symptom: Clicking the submit button reloads the page, but the backing bean action method is never executed — no output, no error.

      
Cause: Check Phase 3 (Process Validation). If an input fails validation or conversion, JSF short-circuits straight to Phase 6 and never reaches Invoke Application — so your button's action never runs.

      
Fix: Add an <h:messages /> tag to your view to display the hidden validation error — the one you added in step 7 of Part 2! It turns a silent nothing into a visible message.

      
Why it feels so bad: nothing crashed, so nothing appears in the server
        log either. Without h:messages the failure is genuinely invisible. This is the single most
        common reason a beginner thinks “JSF is broken”.

    

  


  
3️⃣
    
Trap 3: Annotating one interface with both @Local and @Remote
      
Symptom: WildFly deployment fails with an EJB specification violation exception.

      
Cause: local means “hand over the reference”; remote means “serialize a copy”. One interface cannot promise both.

      
Fix: A single Java interface cannot be both local and remote. Declare two separate interfaces (e.g., OrderServiceLocal and OrderServiceRemote) and let the bean implement both — exactly as CurrencyLocal and CurrencyRemote do in step 3.

        One interface carries both annotations
        Split it into two interfaces and have the bean implements both
      

      

        javax.naming.NameNotFoundException on the remote lookup
        The JNDI string does not match what WildFly registered
        Copy the exact ejb:/…!… line from the deploy log; check the capital letters and the !
      

      

        ClassNotFoundException: org.wildfly.naming.client.WildFlyInitialContextFactory
        The standalone client has no WildFly client libraries on its classpath
        Add wildfly-client-all (or the ejb/naming client jars) to the remote project's classpath
      

      

        Connection refused when the remote client runs
        WildFly is not running, or the port in the properties file is wrong
        Start the server (step 1), and confirm http-remoting://localhost:8080 matches your setup
      

      

        Browser shows 404 Not Found for converter.xhtml
        The war has not finished deploying, or the path is wrong
        Wait for Deployed "currency-converter.war" and check the URL spelling

    🔄 The JSF lifecycle, phase by phase
    
Every button click walks these six phases in order. Knowing the names tells you where a bug is hiding.

    

      
PhaseNameWhat happens

      
        
1Restore ViewThe server rebuilds the page's component tree (or creates it on the first request).

        
2Apply Request ValuesValues submitted by the browser are copied into the components.

        
3Process ValidationEach value is converted and validated. On failure, JSF jumps straight to Phase 6.

        
4Update ModelValid values are written into your backing bean's fields.

        
5Invoke ApplicationYour action method runs — this is where calculate() is called.

        
6Render ResponseThe response HTML is produced and sent back to the browser.

      
    

    
💡
      
The one shortcut worth memorising
        Anything that fails in Phase 3 skips Phases 4 and 5. That single fact explains “my button does nothing” more
        often than every other cause put together.

    🔎 How WildFly builds the JNDI name
    
The name the deploy log prints follows a fixed pattern. Read it left to right:

    
ejb:/currency-converter/CurrencyConverterBean!com.globalbank.ejb.CurrencyRemote
 │        │                  │                    │
 │        │                  │                    └── fully-qualified REMOTE interface name
 │        │                  └─────────────────────── the bean class name
 │        └────────────────────────────────────────── the deployed application (war) name
 └─────────────────────────────────────────────────── the EJB namespace prefix

    
Change the war's build name, rename the bean, or move the interface to a different package and this string
      changes with it. That is exactly why you copy it from the log instead of trusting memory.

  


  

    📦 Serialization rules for remote calls — the checklist
    
    
      
  1. The class implements java.io.Serializable.
    2. 
      
  2. Every field inside it is either a primitive, a known-serializable type (like String), or
        itself serializable.
    3. 
      
  3. Fields that cannot be serialized (an open connection, a file handle) are marked transient, so
        they are skipped rather than breaking the call.
    4. 
      
  4. The class has an serialVersionUID, so client and server agree on the version of the class.
    5. 
    

    
Miss any of these on a remote call and you meet Trap 1. On a local call, none of them matter.

Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Annotating one interface with both @Local and @RemoteDeclare two interfaces — CurrencyLocal and CurrencyRemote — and let the bean implement both.

      
Passing a plain custom object to a @Remote methodMake it (and its fields) implement java.io.Serializable, or mark un-serializable fields transient.

      
Forgetting <h:messages /> on a formAdd it inside the form. Without it, a Phase 3 validation failure is completely silent.

      
Typing the JNDI name from memoryCopy the exact ejb:/…!… string from WildFly's deploy log.

      
Putting the exchange-rate rule in the XHTML or the backing beanKeep it in the EJB. Both the page and the remote client then share one rule and one fix.

      
Forgetting the getters and setters on the backing beanJSF binds to fields through them. Without them the form silently binds to nothing.

      
Expecting ctx.lookup() to return your interface typeIt returns Object. Cast it: (CurrencyRemote) ctx.lookup(...).
