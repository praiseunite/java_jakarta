Session 13 · Jakarta Security, Explained Slowly

Every application you have built so far lets anyone do everything. The moment real money or real customer records are involved, that is not acceptable — some people may look, some may act, and some may do neither. This page shows you how Jakarta EE answers the question “who are you, and what are you allowed to do?” with a handful of annotations instead of pages of server configuration files. You do not need to know any security words yet. Every one of them is explained the moment it appears.

concept

Part 1 · Who are you, and what may you do?

1.1 The problem Jakarta Security was invented to fix

Long before Jakarta EE 8, adding a login to a Java web application meant writing a server-specific configuration file. If you used one application server you edited one kind of XML; if you moved to a different server, you rewrote it. The rules lived in a file the compiler never checked, so a typo was discovered only when a user could not log in.

Jakarta Security changed that. It moved security out of server files and into Java annotations — the @ labels you already know from the rest of this course. Your security setup now travels with your code, compiles with your code, and works the same on every server that supports the standard.

In plain words

Old way: security rules written in a configuration file that only one server understood.

Jakarta Security: security rules written as annotations in your Java, understood by every compliant server. Same code, different server, still works.

1.2 The two words everyone mixes up

Before anything else, separate these two. People use them as if they were the same thing, and almost every beginner mistake in security comes from confusing them:

WordThe question it answersBank example
Authentication “Who are you?” — proving you are who you claim to be. You show your ID at the door and the guard confirms it is really you.
Authorization “What are you allowed to do?” — deciding which actions your identity permits. You are allowed to withdraw from your own account, but not to open the vault.

Authentication always comes first — you cannot decide what someone may do until you know who they are. But passing authentication does not mean you may do everything. That is the whole point of the second word.

🏢
Analogy — a bank building with three people in it Picture a bank. There is a guard at the front desk who checks your ID before you go any further. There is an HR database in the back office holding every employee's record and job title. And every person who gets past the desk carries a keycard on a lanyard, which electronic locks all over the building read to decide whether this door opens for you.

Hold on to those three: the guard, the HR database, and the keycard. They are the three pillars of Jakarta Security, and the rest of this page is just naming them properly.

1.3 The three pillars

Jakarta Security is built from exactly three pieces. Learn them once and the annotations in Parts 2–4 will feel obvious:

PillarInterface / annotationWhat it does
1 · The guard
Authentication mechanism		 HttpAuthenticationMechanism
@FormAuthenticationMechanismDefinition		 Stands at the door. Catches the incoming request, asks for credentials, shows the login page, and turns unauthenticated visitors away.
2 · The HR database
Identity store		 IdentityStore
@DatabaseIdentityStoreDefinition		 Holds the real records. Checks whether the supplied password is correct, and looks up which roles belong to that user.
3 · The keycard
Security context		 jakarta.security.enterprise.SecurityContext The identity of the person currently inside. Your own code can read it to ask “who is this?” and “may they do this?” while the request is being handled.
In plain words

The mechanism collects the password. The identity store checks it and says which roles you hold. The security context is what your code can ask, mid-request, about whoever is logged in.

Three jobs, three pillars. Do not blur them together.

💡
The one thing to notice The word pillar is not decoration — it tells you where a problem lives. “The password is never checked” is a pillar 2 problem. “The login page never appears” is a pillar 1 problem. “My code always sees an anonymous user” is a pillar 3 problem. Naming the pillar cuts your debugging time in half.

Part 2 · Setting up the door and the records — with annotations only

2.1 What “declarative” means

Declarative means you describe what you want and the container does the work. You do not write a servlet filter that intercepts logins; you do not write a while loop that checks passwords. You declare “logins happen with a form, and user records live in that database table”, and Jakarta EE wires it all up for you.

In plain words

Imperative: “here are the fifteen steps to check a password.”

Declarative: “passwords are checked against this table.” You state the intention; the container writes the steps.

2.2 Choosing how people log in

The first pillar — the guard — is chosen with one annotation on a class. There are three common flavours:

AnnotationThe login experienceTypical use
@BasicAuthenticationMechanismDefinition The browser's own pop-up box asking for username and password. Quick internal tools and APIs. Ugly, but zero setup.
@FormAuthenticationMechanismDefinition A standard login page the server generates for you. Simple web apps that do not mind the default look.
@CustomFormAuthenticationMechanismDefinition Your own .xhtml login page, with your own branding and error page. Real applications — this is the one we use below.

2.3 The whole security setup in one class

Here is a complete, portable security configuration. Two annotations on one class declare the door and the records:

ApplicationSecurityConfig.java — complete portable security setup
package com.globalbank.security;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.security.enterprise.authentication.mechanism.http.CustomFormAuthenticationMechanismDefinition;
import jakarta.security.enterprise.authentication.mechanism.http.LoginToContinue;
import jakarta.security.enterprise.identitystore.DatabaseIdentityStoreDefinition;
import jakarta.security.enterprise.identitystore.Pbkdf2PasswordHash;

@ApplicationScoped
// 1. The guard: log in on our own page, show our own error page.
@CustomFormAuthenticationMechanismDefinition(
    loginToContinue = @LoginToContinue(
        loginPage = "/login.xhtml",
        errorPage = "/login-error.xhtml"
    )
)
// 2. The records: look users and roles up in a database, through a JNDI DataSource.
@DatabaseIdentityStoreDefinition(
    dataSourceLookup = "java:jboss/datasources/ExampleDS",
    callerQuery = "SELECT password_hash FROM bank_users WHERE username = ?",
    groupsQuery = "SELECT group_name  FROM bank_users WHERE username = ?",
    hashAlgorithm = Pbkdf2PasswordHash.class   // never compare plain-text passwords
)
public class ApplicationSecurityConfig {
    // Declarative configuration only — no method bodies at all.
}

Read it slowly, because every line is doing one clear job:

  • dataSourceLookup — where the database is. Notice it is the JNDI name you met in Session 3, not a URL and password sitting in your code.
  • callerQuery — the SQL that fetches this user's stored password. The ? is filled in with the typed username.
  • groupsQuery — the SQL that fetches this user's roles.
  • hashAlgorithm — the rule for turning a typed password into something comparable.
🔑
Analogy — why passwords are never stored as words Think of a machine that turns a key into a fingerprint of that key. It only works one way: given the key you can produce the fingerprint, but given the fingerprint you cannot rebuild the key. The HR database stores fingerprints, not keys. When you log in, the system fingerprints what you typed and compares the two fingerprints. A thief who steals the whole database gets a room full of fingerprints and no keys — which is exactly why Pbkdf2PasswordHash is here and not a plain text column.
💡
The one thing to notice There is no XML and no server-specific file anywhere in that class. That portability is the entire reason Jakarta Security exists. If you had to memorise one sentence from this page, it is this one — and it is exactly what the exam asks.

2.4 The half that is easy to miss — who actually asks the container to log in?

Look again at that class. It names a login page, it names the database, and it has no methods at all. That is what declarative configuration means: you describe the outcome and the container does the work. So far, so good.

Now the catch — and it catches nearly everybody. The annotation is @CustomFormAuthenticationMechanismDefinition. The word custom is the whole story: it means “I have chosen to supply the form handling myself.” The container will not build a login form for you, will not read your loginPage, and will not check a single password — unless your own code asks it to.

⚠️
A vault is not locked until somebody turns the handle

That class describes the vault: a door, and a list of who may pass through it. It does not open the door. Something in your application must call securityContext.authenticate(...) and hand the typed user name and password to the container.

And when you forget, nothing tells you. No exception, no warning, not even a log line. The form submits, the page redisplays, and the user is still not signed in. Nothing is broken — nothing was ever asked to happen. This is the failure mode people lose whole afternoons to.

🔑
Analogy — the door and the handle ApplicationSecurityConfig is the door and the guest list, both perfectly built. Without the LoginBean below you have a door nobody can open and a guest standing outside it, wondering why they were not let in.

Here is the handle. It is one ordinary CDI bean, and one line inside it does the real work:

LoginBean.java — the code that actually performs the login
package com.globalbank.security;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import jakarta.security.enterprise.AuthenticationStatus;
import jakarta.security.enterprise.SecurityContext;
import jakarta.security.enterprise.authentication.mechanism.http.AuthenticationParameters;
import jakarta.security.enterprise.credential.Password;
import jakarta.security.enterprise.credential.UsernamePasswordCredential;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.faces.context.FacesContext;

@Named("login")
@RequestScoped                       // NOT @ViewScoped — see the note below
public class LoginBean {

    @Inject
    private SecurityContext securityContext;   // the container's authentication front door

    private String username;                    // what the user typed; JSF fills these in
    private String password;
    private String message;                     // shown on the page after a failed attempt

    public String login() {

        // 1. Get the real servlet request and response behind this JSF request.
        FacesContext faces = FacesContext.getCurrentInstance();
        HttpServletRequest  request  = (HttpServletRequest)  faces.getExternalContext().getRequest();
        HttpServletResponse response = (HttpServletResponse) faces.getExternalContext().getResponse();

        // 2. Wrap what was typed in a Credential.
        var credential = new UsernamePasswordCredential(username, new Password(password));

        // 3. Wrap the credential in AuthenticationParameters, and hand it over.
        AuthenticationParameters params =
                AuthenticationParameters.withParams().credential(credential);

        AuthenticationStatus status = securityContext.authenticate(request, response, params);

        // 4. Act on the answer.
        return switch (status) {
            case SUCCESS        -> "/accounts.xhtml?faces-redirect=true";  // signed in
            case SEND_CONTINUE  -> null;   // the mechanism took over the response
            case SEND_FAILURE   -> {      // wrong password, or no such user
                message = "That user name and password combination was not recognised.";
                yield null;
            }
            case NOT_DONE       -> {      // configuration problem — a developer error
                message = "Sign-in could not be completed. See the server log.";
                yield null;
            }
        };
    }

    public String logout() {
        FacesContext.getCurrentInstance().getExternalContext().invalidateSession();
        return "/login.xhtml?faces-redirect=true";
    }

    public String getUsername()  { return username; }
    public void setUsername(String username) { this.username = username; }
    public String getPassword()  { return password; }
    public void setPassword(String password) { this.password = password; }
    public String getMessage()   { return message; }
}

Five things in there are worth slowing down for:

  • The third argument is not the credential. authenticate() takes an AuthenticationParameters — a small wrapper whose job is to carry the credential together with two switches (“is this a fresh login or a re-authentication?” and “should this be remembered?”). We want the defaults, so we build it with AuthenticationParameters.withParams().credential(credential) and set neither. This is the single most common compile error people hit here.
  • Why it needs the request and the response. It looks odd: a method that checks a password, asking for a servlet response. The reason is that logging in is not only a lookup — the container may need to set a session cookie or write a redirect. Passing the real objects in lets it do all of that. A method that only returned true or false would leave you to redo it by hand, badly.
  • Four answers, not two. SUCCESS and SEND_FAILURE are the obvious pair. SEND_CONTINUE means the mechanism has taken over the response itself and is mid-redirect — you must return null, because navigating a response that is already gone would fail. NOT_DONE means the container declined to even try, which is a configuration mistake and belongs in the server log.
  • One message for both kinds of failure. A wrong password and a user name that does not exist produce the same sentence, on purpose. Telling them apart tells an attacker which user names are real, which is half of what they need.
  • @RequestScoped, not @ViewScoped. This bean holds a password in a field. A view-scoped bean lives until the user navigates away, so the password would sit in memory for as long as the page is open. A request-scoped bean is created for the submit and gone immediately afterwards. Lifetime is a security decision, not just a convenience one.

The page that drives it is ordinary Facelets — two inputs and a button, wired to the bean by name:

login.xhtml — the form (the file loginPage points at)
<!DOCTYPE html>
<html xmlns="http://www.w3.org/1999/xhtml"
      xmlns:h="jakarta.faces.html">
<h:head>
  <title>GlobalBank — sign in</title>
</h:head>
<h:body>
  <h1>GlobalBank</h1>

  <h:form>
    <h:outputText value="#{login.message}" rendered="#{not empty login.message}" />

    <p>User name<br/>
      <h:inputText value="#{login.username}" /></p>

    <p>Password<br/>
      <h:inputSecret value="#{login.password}" /></p>

    <h:commandButton value="Sign in" action="#{login.login}" />
  </h:form>

</h:body>
</html>

#{login.login} is the whole connection: login is the name from @Named("login"), and login after the dot is the method. Press the button, the method runs, and the method is the one that asks the container to authenticate.

💡
If you would rather not write any of this Jakarta Security also offers @FormAuthenticationMechanismDefinition — the same annotation without the word custom. It ships a built-in login form and errors page, and it performs the authentication itself, so no LoginBean is needed at all. It is the right choice when you do not need to brand the page. Use the custom one the moment you do — and then remember that the handle is yours to write.

2.5 Where the hashes in that table come from

The identity store does not compare passwords — it compares fingerprints. So before anybody can log in, the bank_users table must already contain a fingerprint for each user. That raises the obvious question the earlier analogy skips over: who makes the fingerprints?

In a real system a DBA's script might insert them. In a teaching project — and in plenty of real ones — a small bean generates them at startup. This is the same @Singleton @Startup pattern you met in Sessions 1–2, doing a job that has nothing to do with concurrency and everything to do with first run:

UserInitializer.java — creating demo users, with properly hashed passwords
@Singleton
@Startup                                   // run once, when the application deploys
public class UserInitializer {

    @PersistenceContext
    private EntityManager em;

    @Inject
    private Pbkdf2PasswordHash hasher;     // the container provides this

    @PostConstruct
    void seed() {
        // Tell the hasher which options to use, before generating anything.
        hasher.initialize(new java.util.HashMap<>());

        // Only seed an empty table. Without this guard, every redeploy would try
        // to insert the same users again.
        if (em.createQuery("SELECT COUNT(u) FROM BankUser u", Long.class)
              .getSingleResult() > 0) {
            return;
        }

        addUser("ada@globalbank.test",     "secret",  "CUSTOMER");
        addUser("manager@globalbank.test", "manager", "BANK_MANAGER");
    }

    private void addUser(String username, String password, String group) {
        String hash = hasher.generate(password.toCharArray());   // the fingerprint
        em.persist(new BankUser(username, hash, group));
    }
}

Two details matter more than the rest:

  • hasher.generate(...) does the work — never build the string yourself. The stored value is not a bare hash. It is a small bundle that carries the algorithm, the iteration count and the random salt along with the result, in the form PBKDF2WithHmacSHA256:27500:<salt>:<hash>. Hand-assembling that is a way to produce something nothing can verify. Ask the same class that will later check the password to produce it, and the two are guaranteed to agree.
  • Run initialize(...) before generate(...). It is how the hasher learns which options to use. Skip it and the object is not ready.
💡
How to check it worked After deploying, look at the bank_users table with whatever database tool you have — WildFly's admin console at http://localhost:9990/console (Session 3) is one way in, and the Practical 3 project builds a raw view into the application itself. You should see two rows, and the password_hash column should hold long strings starting PBKDF2WithHmacSHA256: — never the words secret or manager. If you can read a password in that column, the hashing is not happening, and that is a bug worth stopping for.

Part 3 · Asking “who is logged in?” from inside your own code

3.1 The principal — a name for the logged-in person

Once someone has logged in, the container keeps a small object representing them. It is called the Principal, and for most applications it is simply their username wrapped in an object.

In plain words

A Principal is the container's way of saying “this is the person making the current request.” If nobody has logged in, there is no principal — you get null, which is how you spot an anonymous visitor.

3.2 Reading the keycard

Your own beans can inject the security context — the keycard from Part 1 — and read it at any moment during the request:

AccountDashboardBean.java — a role-aware CDI bean
package com.globalbank.web;

import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import jakarta.security.enterprise.SecurityContext;
import java.security.Principal;

@Named("dashboard")
@RequestScoped
public class AccountDashboardBean {

    // 1. Inject the portable security context, exactly like any other CDI bean.
    @Inject
    private SecurityContext securityContext;

    public String getCurrentUser() {
        Principal caller = securityContext.getCallerPrincipal();
        return (caller != null) ? caller.getName() : "Anonymous Guest";
    }

    public boolean isManager() {
        // 2. Ask whether the current caller holds a particular role.
        return securityContext.isCallerInRole("BANK_MANAGER");
    }

    public String accessVault() {
        if (!isManager()) {
            throw new SecurityException("Unauthorized: the cash vault is for Managers only.");
        }
        return "vault-opened";
    }
}
💡
The one thing to notice securityContext is fetched with plain @Inject — it is an ordinary CDI bean, not a special server object. And note the two different questions it can answer: getCallerPrincipal() tells you who (authentication), while isCallerInRole(...) tells you whether they may (authorization). Same two words from Part 1, one method each.
⚠️
Careful — an if is not real security The accessVault() method above checks a role by hand and throws if the check fails. That works, and it is genuinely useful when the decision depends on runtime data. But it is fragile: the day someone adds a second way into the vault and forgets the if, the hole is invisible. Whenever the rule is simply “only these roles may call this method”, prefer the declarative annotation in Part 4 and let the container enforce it for you.

Part 4 · Locking a method to certain roles

4.1 Three annotations, one idea

Jakarta Security takes the authorization annotations that used to work only on enterprise beans and makes them work on every CDI-managed bean. There are three, and between them they cover every case:

AnnotationMeaning
@RolesAllowed({"A", "B"})Only callers holding role A or role B may call this method.
@PermitAllAnyone may call it, logged in or not. For genuinely public data.
@DenyAllNobody may call it. Used to switch a method off for good.
🚪
Analogy — a name list taped to each door Walk down a corridor of offices. On each door is a small plaque listing who may enter: “Everyone” (@PermitAll), “Tellers and Managers” (@RolesAllowed), or “No entry” (@DenyAll). You never hire someone to stand at each door — the plaques do the work, and nobody can slip past one by taking a different route down the corridor.

4.2 The annotations in action

WireTransferService.java — a secured CDI bean
package com.globalbank.services;

import jakarta.annotation.security.RolesAllowed;
import jakarta.annotation.security.PermitAll;
import jakarta.annotation.security.DenyAll;
import jakarta.enterprise.context.ApplicationScoped;

@ApplicationScoped
public class WireTransferService {

    @PermitAll
    public double getExchangeRate(String currency) {
        return 1.15;   // Public information — every visitor may read it.
    }

    @RolesAllowed({"TELLER", "BANK_MANAGER"})
    public void executeTransfer(int from, int to, double amount) {
        // Only authenticated tellers and managers may move money.
    }

    @RolesAllowed("BANK_MANAGER")
    public void authorizeForeignOverdraft(int accountId, double amount) {
        // Management-only authority.
    }

    @DenyAll
    public void deprecatedLegacySweep() {
        // Permanently disabled — kept only so old code still compiles.
    }
}

Notice what is absent: there is not a single if statement, not one role check written by hand. The rules live on the method like a label, and the container enforces them on every call.

    • 
      
  • @OpenIdAuthenticationMechanismDefinition — login delegated to an OpenID Connect provider
        (for example a corporate single sign-on).
    • 
    

    
All of them are placed on a single @ApplicationScoped configuration class, exactly as shown in
      Part 2.

AttributeWhat it specifies

MethodReturns

    @RolesAllowed, @PermitAll, @DenyAll — the exact rules
    
    
      
  • @RolesAllowed({"A","B"}) — the caller must hold at least one of the listed roles. Usable on
        a class (applying to all its methods) or on a single method (overriding the class).
    • 
      
  • @PermitAll — no restriction. Use deliberately, never as a default.
    • 
      
  • @DenyAll — no caller passes. Useful for disabling a method without deleting it.
    • 
      
  • A method with no annotation inherits the class-level rule, if there is one. If there is
        none anywhere, the method is unrestricted.
    • 
      
  • Roles are plain strings — they must match exactly the role names your identity store
        returns. "BANK_MANAGER" and "bank_manager" are different roles.
    • 
    

  


  

    Why hashing, and what Pbkdf2PasswordHash actually does
    
A hash turns a password into a fixed-length fingerprint that cannot be reversed. Storing
      hashes means a stolen database yields no usable passwords.

    
A salt is random data mixed in before hashing, so two users with the same password produce
      two different stored values — defeating pre-computed “rainbow table” attacks.

    
PBKDF2 deliberately repeats the hashing many thousands of times, so checking one password
      is cheap for your server but testing billions of guesses is prohibitively slow for an attacker.

    
Pbkdf2PasswordHash handles salt generation, iteration count and comparison for you, so your
      configuration just names the class.

  


  
  recap
  
One-line summary of everything

  

    
Jakarta SecurityPortable, CDI-driven, annotation-based security that replaced proprietary per-server configuration files.

    
Authentication“Who are you?” — proving identity. Always comes first.

    
Authorization“What may you do?” — decided by your roles, and a separate question from who you are.

    
Pillar 1 — mechanismHttpAuthenticationMechanism. Collects credentials and drives the login page — by itself for the built-in flavours, through your own code for the custom one.

    
Pillar 2 — identity store@DatabaseIdentityStoreDefinition. Checks the password and loads the caller's roles.

    
Pillar 3 — security contextSecurityContext, injected with @Inject. Lets your code ask who is calling and what they may do.

    
getCallerPrincipal()The current user, or null if nobody is logged in.

    
isCallerInRole(...)Runtime authorization check inside your own code.

    
@RolesAllowedDeclarative role enforcement on any CDI bean, checked by the container before the method runs.

    
@PermitAll / @DenyAllOpen to everyone / open to nobody.

    
Pbkdf2PasswordHashSalted, one-way password hashing so a stolen database reveals no passwords.

    
SecurityContext.authenticate(...)The call that actually logs somebody in. Required with a custom form mechanism, which does nothing on its own.

Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Confusing authentication with authorizationRemember the order: who you are first, then what you may do. Passing one never implies the other.

      
Storing passwords as plain textAlways declare a hashAlgorithm such as Pbkdf2PasswordHash.class, and store only the hash.

      
Putting the database URL and password directly in your codePoint dataSourceLookup at a JNDI DataSource (Session 3) so the secrets stay on the server.

      
Role names in @RolesAllowed that do not match the storeThey must match exactly, including case. "BANK_MANAGER" ≠ "bank_manager".

      
Hand-writing role checks inside methodsPrefer @RolesAllowed so the container enforces it on every path. Reserve in-method checks for decisions that depend on runtime data.

      
Assuming an unannotated method is protectedWith no annotation and no class-level rule, a method is unrestricted. Annotate deliberately.

      
Reaching for @Inject to get a DataSourceA DataSource is a server resource — use @Resource. Reserve @Inject for CDI beans such as SecurityContext.

      
Testing the happy path onlyAlways test the refused case too — log in as a low-privilege user and confirm the protected method actually returns 403.

      
Declaring a custom form mechanism and expecting the container to log people in@CustomFormAuthenticationMechanismDefinition does nothing on its own — it fails with no error at all. Your code must call securityContext.authenticate(request, response, AuthenticationParameters.withParams().credential(...)). Or use plain @FormAuthenticationMechanismDefinition, which handles it for you.

      
Hand-assembling a PBKDF2WithHmacSHA256:iterations:salt:hash string to seed usersCall hasher.generate(password.toCharArray()) on the same Pbkdf2PasswordHash the container will verify with — and call initialize(...) on it first.
