Session 3 · Resources, JNDI and Connection Pools, Explained Slowly

Your enterprise beans must never hardcode a machine address or a password, and must never open a raw database connection themselves. Instead they ask the server for a resource by name. The name registry is called JNDI, and the resource beans ask for most often is a DataSource backed by a connection pool. You do not need to know any of those words yet — every one is explained the moment it appears.

Part 1 · What a “resource” actually is

1.1 The job your bean cannot do alone

Your bean knows the business rule. That is its whole point.

But a rule on its own is useless. To save an account balance, the bean has to reach a database. To send a receipt, it has to reach a mail server. To tell another system that a transfer happened, it has to reach a message queue.

Every one of those things lives outside your application. Your bean did not create them, does not own them, and must not shut them down. It only needs to use them.

Anything a bean needs from the outside world — but does not create and does not own — is called a resource.

In plain words

A resource is a shared service the server provides for you — a database, a mail server, a message queue. Your bean asks for it and uses it. The server sets it up, keeps it running and hands it out.

🏢
Analogy You rent a desk in a large office block. Your desk is your workspace — the work you do there is yours. But you do not install a printer on your desk, buy a postage machine, or build your own meeting room. The building provides a shared printer room, a shared mailroom and shared meeting rooms, and everyone uses the same ones. Those shared facilities are your resources. Your bean is you at your desk.

1.2 The resources a bean usually asks for

Almost every Jakarta EE application asks for the same short list. Here it is, with the Java type that represents each one, and who typically provides it:

What the bean needsThe Java type that represents itWho provides it
A database connectionjavax.sql.DataSourcePostgreSQL, MySQL, Oracle
A place to send messagesjakarta.jms.Queue / TopicActiveMQ Artemis (built into WildFly)
A way to create message connectionsjakarta.jms.ConnectionFactoryYour JMS messaging provider
A mail sessionjakarta.mail.SessionAn SMTP server
A setting you may want to change laterAn environment entry (<env-entry>)The application descriptor (Part 4)

Do not memorise that table. Notice only the shape of it: on the left is a plain need, in the middle is a Java type, on the right is somebody else's system.

⚠️
The trap this whole session exists to prevent Writing a database address, a username and a password inside your Java code, or calling DriverManager.getConnection(...) yourself. It works on your laptop and breaks everywhere else: the password is now in your source code, and moving from the test database to the real one means editing and recompiling the application. The whole rest of this page is the fix.

Part 2 · JNDI — the server’s address book

2.1 The problem: how do you find a thing you did not create?

So your bean needs a database. Fine. But how does it get one?

Your bean did not create the database connection. It does not know where it lives. It has no reference to it. All it knows is the name somebody promised it: “ask for jdbc/GlobalBankDB and you will get a database.”

Something has to hold a big list of names, each pointing at a live object, so that any piece of code can say “give me the thing called this.” That something is JNDI.

2.2 What JNDI is

JNDI stands for Java Naming and Directory Interface. It is the built-in naming service of Jakarta EE. It keeps a list of names, and next to each name it keeps a real, running object inside the application server.

📞
Analogy A telephone directory. You do not memorise everybody's number, and you certainly do not guess it. You look up a name and the book gives you the number that reaches the right person. Nobody cares which office that person is sitting in today — the name still reaches them. JNDI is that book, and the “numbers” it hands back are live objects.

A JNDI name is a plain string. Here is what the book looks like in a running bank application:

The name (the “phone number”)What it points at (the “person”)
java:global/GlobalBankApp/AccountEJB/AccountBean!com.globalbank.AccountRemoteA live AccountBean EJB you can call
java:/jdbc/GlobalBankDBThe pre-configured PostgreSQL DataSource
java:jboss/exported/jms/TransactionQueueA JMS message queue

Those names look frightening. They are not — Part 2.5 breaks them apart, piece by piece.

2.3 Two layers: what you call, and what the vendor supplies

JNDI is deliberately split into two halves. Knowing which half is which is the reason your code does not change when you change servers.

  • The API — the set of methods your code calls. It is fixed and standard: lookup(), and the Context object you call it on.
  • The SPI — the plumbing underneath, which actually talks to this particular server. It is supplied by the server vendor, not by you.

Look at the picture, then read the takeaway underneath it.

In plain words

You learn one set of method calls. The server does the messy part of actually finding the object. Because the method calls belong to the standard, your code is portable — it does not care which server it is running on.

2.4 The trap this page exists for: javax.naming, never jakarta.naming

You have already met this problem once. In Session 1 you saw that javax.ejb became jakarta.ejb when the technology was renamed. It would be reasonable to assume everything renamed itself. It did not — and JNDI is the most important exception.

The rule is simpler than it looks:

  • The Java EE APIs were donated to the Eclipse Foundation. They renamed: javax.ejb → jakarta.ejb, and so on.
  • The APIs that belong to Java SE — the plain Java platform — stayed where they were. Oracle still owns those, and they kept the name javax.

JNDI (javax.naming) and the database type javax.sql are both Java SE APIs. That is why their names never changed.

PackageRenamed to jakarta.*?What it is for
javax.namingNo — stays javax.namingJNDI: InitialContext, Context, NamingException
javax.sqlNo — stays javax.sqlThe database type: DataSource
javax.ejbYes → jakarta.ejbEnterprise beans: @Stateless, @Remote
javax.jmsYes → jakarta.jmsMessaging: Queue, MessageListener
javax.mailYes → jakarta.mailEmail: Session
javax.annotationYes → jakarta.annotation@Resource, @PostConstruct
javax.servletYes → jakarta.servletServlets: HttpServlet
⚠️
Say it once more, because it is on the exam import javax.naming.InitialContext; is correct.
There is no jakarta.naming package. Writing import jakarta.naming.*; will not compile — the package does not exist.
And you will frequently see the two spellings in the same file: a bean importing jakarta.ejb.Stateless right next to javax.sql.DataSource. That is normal, and now you know why.

2.5 The three standard namespaces

A single flat list of names would be chaos — every application on the server would collide. So JNDI names start with a namespace: a scope that says who is allowed to see this name. Think of them as the difference between your desk extension, your department's extensions, and the whole company's.

There are three you must know:

NamespaceScopeThe name looks likeWho can reach it
java:global Whole server java:global[/appName]/moduleName/beanName[!interface] Anyone — any application, any module, even a separate program on another machine connected to this server.
java:app One application (one EAR) java:app[/moduleName]/beanName[!interface] Any module packaged inside the same EAR.
java:module One module only java:module/beanName[!interface] Only code inside the exact same JAR or WAR.
In plain words

Pick the narrowest namespace that does the job. If only your own module needs the bean, use java:module. If another application running on the same server must call it, only java:global will reach. Widen the scope only when you have to.

Inside a name, the square brackets mean “this part is optional.” The !com.globalbank.AccountRemote on the end names the exact interface you want — a bean can offer more than one, so you can say which.

🔌
Why the interface name is on the end One bean can be reachable in more than one way — for example a remote view and a local view. The interface name after the ! is how the directory knows which door you want to walk through. If the bean offers only one, the name can stop at the class name.

2.6 Looking a name up in code

You now have the idea. Here is the smallest piece of code that uses it. Read the comments on the right-hand side — they are the whole story.

ClientService.java — a JNDI lookup
import javax.naming.Context;          // ← note: javax.naming, NOT jakarta.naming
import javax.naming.InitialContext;
import javax.naming.NamingException;

public class ClientService {
    public void queryAccount() {
        try {
            Context ctx = new InitialContext();     // ① open the address book

            AccountRemote account = (AccountRemote) ctx.lookup(
                "java:global/GlobalBankApp/AccountEJB/AccountBean!com.globalbank.AccountRemote"
            );                                      // ② find the object by name

            double bal = account.getBalance(1001);  // ③ use it like any normal object
            System.out.println("Account balance: $" + bal);

        } catch (NamingException e) {               // ④ the name was wrong, or nothing is bound
            System.err.println("JNDI Lookup failed: " + e.getMessage());
        }
    }
}
🔬
The one thing to notice ctx.lookup(...) returns a plain Object — which is why it needs a cast, (AccountRemote). The directory only stores “some object under a name”; you know what type it really is. And the failure mode is a NamingException, which is Java's way of saying “no such name in the book.”
💡
Developer note — you rarely write this by hand In day-to-day work, WildFly calls bind() and unbind() for you whenever an application is deployed or undeployed. As an application developer you will almost always call lookup() — or, better, skip it entirely and let the container do it with @Resource injection (Part 3.4).

Here is what that deployment looks like from the server's side. When an application goes live, the server quietly binds its beans into the directory — and prints the names it used.

Try help, then deploy target/hello-ejb.war, and read the JNDI names the server reports it has bound.

💡
What you just watched Nobody wrote those JNDI names by hand. The server generated them from the application's name, the module's name, the bean's name and its interface. That is exactly the java:global/app/module/bean!interface pattern from Part 2.5, in real life.

Part 3 · DataSource and connection pooling — borrow a connection, never build one

3.1 Why opening a database connection is expensive

The obvious way to talk to a database is to open a fresh connection every time you need one:

Connection conn = DriverManager.getConnection(url, user, password);

It looks harmless. It is not. Opening a connection is a multi-step negotiation: find the machine, shake hands over the network (TCP), prove who you are, and set up a session. That whole dance costs somewhere between 150 ms and 1,500 ms.

Now imagine a thousand customers open the banking portal at the same moment. A thousand of those negotiations start at once. The database runs out of connections and falls over — not because the queries were hard, but because everyone insisted on building their own road to the database.

In plain words

Making a connection is slow. Doing it a thousand times at once is not just slow — it can take the database down. The fix is to make a small number of connections once, and share them.

3.2 The fix: a pool of ready connections

Connection pooling means keeping a small batch of connections already open and ready — say five to twenty of them. When your code needs one, it borrows one from the batch. When it finishes, the connection goes straight back into the batch for the next person.

The object that manages this batch is called a DataSource. Your code asks the DataSource for a connection; the DataSource takes the details — the URL, the username, the password, the pool size — out of your hands entirely.

🚕
Analogy Buying a car for every single trip is absurd: choosing one, paying for it, insuring it, waiting for delivery — and then throwing it away at your destination. That is a fresh DriverManager.getConnection(). A taxi rank is a pool: cars are already there, engine running. You step into one, ride to your stop, step out — and the taxi goes straight back to the rank for the next passenger. Milliseconds, not minutes.

💡
The counter-intuitive part In a pool, conn.close() does not close the physical database connection. It returns the connection to the pool. Forgetting this is why people think pooling “does not work” — they never give the connection back.

3.3 Who configures the pool? Not you.

This is the part beginners find surprising. You do not create a connection pool in Java code. An administrator configures it once, at the server level, and the server then publishes it under a JNDI name for every application to use.

That is the point: the pool is infrastructure, exactly like the office printer in Part 1. The bean just asks for it.

🔑
Read this before you type the command

No PostgreSQL yet? You can still follow every remaining step on this page. WildFly already ships an in-memory database called ExampleDS, published at java:jboss/datasources/ExampleDS. 3.4 Using the DataSource in a bean: @Resource

Now the payoff. The bean does not open a connection and does not know any passwords. It just declares that it wants the resource named java:/jdbc/GlobalBankDB, and the container performs the JNDI lookup behind the scenes before your code ever runs.

AccountBean.java — a stateless bean using a pooled DataSource
package com.globalbank.ejb;

import jakarta.annotation.Resource;      // ← renamed: was javax.annotation
import jakarta.ejb.Stateless;            // ← renamed: was javax.ejb
import javax.sql.DataSource;             // ← NOT renamed: DataSource is a Java SE type
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

@Stateless
public class AccountBean implements AccountRemote {

    // ① ask the container to inject the configured DataSource, by its JNDI name
    @Resource(lookup = "java:/jdbc/GlobalBankDB")
    private DataSource bankDataSource;

    @Override
    public double getBalance(int accountId) {
        String sql = "SELECT balance FROM accounts WHERE account_id = ?";

        // ② try-with-resources: borrows a connection and gives it back automatically
        try (Connection conn = bankDataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {

            ps.setInt(1, accountId);

            try (ResultSet rs = ps.executeQuery()) {
                if (rs.next()) {
                    return rs.getDouble("balance");
                }
            }
            return 0.0;                     // no such account

        } catch (SQLException e) {
            throw new RuntimeException("Database error retrieving balance", e);
        }
        // ③ NOTE: conn.close() does NOT destroy the physical connection.
        //    It returns the connection straight back to the WildFly pool.
    }
}
🔬
The one thing to notice Compare the imports at the top of the file. jakarta.annotation and jakarta.ejb are the renamed packages, while javax.sql kept its old name — both spellings, in one file, on purpose. And note there is no new anywhere: the container fills in bankDataSource for you.
In plain words

@Resource(lookup = "…") means “container, do the JNDI lookup for me and put the result in this field.” You never see the lookup, the URL, or the password. And because the connection comes from a pool, close() means “I'm done, take it back” — not “shut it down.”

Part 4 · Declaring resources in files — and the textbook demo

4.1 Why write it in a file instead of in Java?

Look back at @Resource(lookup = "java:/jdbc/GlobalBankDB"). The name is hardcoded in the Java source. That is fine when the name never changes — but sometimes it does.

Development, QA and production may each point at a different database, or use a different daily transfer limit. Editing Java code for every environment means recompiling for every environment.

The escape hatch is a deployment descriptor — an XML file, packaged with your application, that declares these things outside your Java code. Change the environment, change the file, leave the Java alone.

In plain words

A deployment descriptor is a settings file for your application. Code goes in .java; the things that change per environment go in the descriptor.

4.2 The three tags you need to know

TagWhat it declaresTypical use
<env-entry> A simple configurable value (a number or a string) Tax rates, daily transfer limits, file paths
<resource-ref> An external resource factory that needs authentication A database DataSource (javax.sql.DataSource)
<resource-env-ref> An external resource that needs no authentication (added in Servlet 2.4) JMS queues, JMS topics, mail sessions

The distinction between the last two: does the resource need a username and password? A database does — that is a <resource-ref>. A queue does not — that is a <resource-env-ref>.

4.3 The same declarations in application.xml

Here is all three tags in one file, for our bank application. Read the three numbered comments.

META-INF/application.xml — resources declared, not coded
<?xml version="1.0" encoding="UTF-8"?>
<application xmlns="https://jakarta.ee/xml/ns/jakartaee" version="10">
    <application-name>GlobalBankApp</application-name>

    <!-- 1. a simple, changeable value -->
    <env-entry>
        <env-entry-name>maxDailyTransfer</env-entry-name>
        <env-entry-type>java.lang.Double</env-entry-type>
        <env-entry-value>25000.00</env-entry-value>
    </env-entry>

    <!-- 2. a reference to a database factory (needs login) -->
    <resource-ref>
        <res-ref-name>jdbc/GlobalBankDB</res-ref-name>
        <res-type>javax.sql.DataSource</res-type>
        <res-auth>Container</res-auth>
    </resource-ref>

    <!-- 3. a reference to a messaging queue (no login needed) -->
    <resource-env-ref>
        <resource-env-ref-name>jms/TransferQueue</resource-env-ref-name>
        <resource-env-ref-type>jakarta.jms.Queue</resource-env-ref-type>
    </resource-env-ref>
</application>
🔬
The one thing to notice The value 25000.00 can be changed in production without touching, or recompiling, a single line of Java. That is the whole reason descriptors exist. Also notice <res-type>javax.sql.DataSource</res-type> — the same non-renamed javax.sql from Part 2.4, this time in XML.

4.4 Textbook demo walkthrough · the JNDI UpperCase converter

Finally, the example from the training manual. It is a complete three-tier application — a browser, a servlet, and a bean — and its entire purpose is to show JNDI resolution between a web client and an EJB.

Do not try to memorise the code. Read it for the three parts: the interface, the bean, and the client that looks it up.

1. UpperCaseRemote.java — the remote business interface
package demo.jndi;

import jakarta.ejb.Remote;

@Remote                                  // "this interface is visible to clients outside the app"
public interface UpperCaseRemote {
    StringBuffer sayHello();
}
2. UpperCase.java — the stateless bean, with a mapped JNDI name
package demo.jndi;

import jakarta.ejb.Stateless;
import jakarta.ejb.LocalBean;

@Stateless(mappedName = "Upper")         // "register me under the name Upper as well"
@LocalBean                               // also give me a no-interface local view
public class UpperCase implements UpperCaseRemote {

    public UpperCase() {}

    @Override
    public StringBuffer sayHello() {
        String input = "hello jndi";
        StringBuffer buffer = new StringBuffer(input);

        for (int i = 0; i < input.length(); i++) {
            char c = input.charAt(i);
            if (Character.isLowerCase(c)) {
                buffer.setCharAt(i, Character.toUpperCase(c));
            } else if (Character.isUpperCase(c)) {
                buffer.setCharAt(i, Character.toLowerCase(c));
            }
        }
        System.out.println("Processed in EJB: " + buffer);
        return buffer;
    }
}
3. UppercaseDemo.java — a servlet acting as the JNDI client
package uppercase.jndi;

import java.io.IOException;
import java.io.PrintWriter;
import javax.naming.InitialContext;        // ← javax.naming again
import javax.naming.NamingException;
import jakarta.servlet.ServletException;  // ← but the servlet API was renamed
import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import demo.jndi.UpperCaseRemote;

@WebServlet("/UppercaseDemo")
public class UppercaseDemo extends HttpServlet {

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {
        resp.setContentType("text/html");
        PrintWriter out = resp.getWriter();

        try {
            // get the address book, then resolve the EJB by its global name
            InitialContext ctx = new InitialContext();
            UpperCaseRemote bean = (UpperCaseRemote) ctx.lookup(
                "java:global/Uppercase/UppercaseBean/UpperCase!demo.jndi.UpperCaseRemote"
            );

            // call the bean, then print the answer to the browser
            StringBuffer result = bean.sayHello();
            out.println("<h2>Result from EJB:</h2> <p>" + result + "</p>");

        } catch (NamingException e) {
            out.println("<h3>Naming error: " + e.getMessage() + "</h3>");
            e.printStackTrace();
        }
    }
}
🔬
The one thing to notice The lookup string is java:global/Uppercase/UppercaseBean/UpperCase!demo.jndi.UpperCaseRemote. Read it against Part 2.5: the java:global prefix, then of the application (Uppercase), the module (UppercaseBean), the bean (UpperCase), and finally the exact interface after the !. Nothing here is magic — it is the pattern you already know.

    📇 Decoding a full JNDI name, piece by piece
    
Every java:global name follows the same shape. Here it is split apart:

    
java:global/GlobalBankApp/AccountEJB/AccountBean!com.globalbank.AccountRemote
│            │             │          │           └─ fully qualified interface name
│            │             │          └───────────── bean implementation class name
│            │             └──────────────────────── the EJB JAR module name
│            └────────────────────────────────────── the deployed EAR package name
└───────────────────────────────────────────────────── the global namespace prefix

    
Read from left to right it is simply: which scope → which application → which module → which
      bean → which interface.

  


  

    🧰 The four Context methods
    
InitialContext is your gateway to the directory. From it you can call four operations —
      though in practice you will only ever call the first one.

    

      
MethodWhat it doesThink of it as…

      
        
ctx.lookup("name")Returns the object bound to that nameLooking up a phone number

        
ctx.bind("name", obj)Registers an object under a name; fails if the name is takenRegistering a new phone number

        
ctx.rebind("name", obj)Overwrites an existing nameUpdating your number in the directory

        
ctx.unbind("name")Removes the nameRemoving an entry from the directory

      
    

    
The server calls bind() and unbind() for you on deployment and undeployment.
      Your code calls lookup() — or, more often, lets @Resource do it.

  


  

    🗺️ The namespaces, with a concrete example of each
    

      
NamespaceGeneric patternA real name

      
        
java:globaljava:global[/appName]/moduleName/beanName[!interface]java:global/GlobalBankApp/AccountEJB/AccountBean!com.globalbank.AccountRemote

        
java:appjava:app[/moduleName]/beanName[!interface]java:app/AccountEJB/AccountBean!com.globalbank.AccountRemote

        
java:modulejava:module/beanName[!interface]java:module/AccountBean!com.globalbank.AccountRemote

      
    

    
Notice that the narrower the namespace, the fewer parts the name needs. A module name cannot be seen
      outside its own module, so it does not need to say which application it belongs to.

  


  

    ⚙️ The DataSource command, and what its pool settings mean
    
The full CLI command from Part 3.3, with each pool setting explained:

    
/subsystem=datasources/data-source=GlobalBankDS:add( \
    jndi-name="java:/jdbc/GlobalBankDB", \
    driver-name="postgresql", \
    connection-url="jdbc:postgresql://localhost:5432/globalbank", \
    user-name="bank_admin", \
    password="SecretPassword123", \
    min-pool-size=5, \
    max-pool-size=25, \
    pool-prefill=true \
)

    

      
SettingWhat it means

      
        
jndi-nameThe name the DataSource is published under. This is the string your beans look up.

        
driver-nameWhich database driver to use — postgresql here.

        
connection-urlThe address of the database itself.

        
user-name / passwordThe credentials the pool authenticates with. Kept here, once — never in your Java code.

        
min-pool-sizeThe smallest number of connections the pool keeps open. Here, 5.

        
max-pool-sizeThe largest number it will ever open. Here, 25.

        
pool-prefilltrue means the minimum connections are opened up front, so the first user does not pay the connection cost.

      
    

    
Choose min and max carefully: too small and requests queue up; too large
      and you exhaust the database, which is the very problem you were avoiding.

  


  

    📄 Deployment descriptor tags, in full
    

      
TagPurposeNeeds a login?

      
        
<env-entry>A simple configurable primitive or string valueNo

        
<resource-ref>An external resource factory requiring authenticationYes

        
<resource-env-ref>An unauthenticated resource reference (introduced in Servlet 2.4)No

      
    

    
The value of an <env-entry> is always written as text, and its
      <env-entry-type> says how to read it — for example
      java.lang.Double, java.lang.Integer, java.lang.String or
      java.lang.Boolean.

  


  

    🔤 Where javax and jakarta finally landed
    

      
PackageOld nameJakarta EE 9+ name

      
        
JNDIjavax.namingjavax.naming — unchanged (Java SE)

        
SQL / DataSourcejavax.sqljavax.sql — unchanged (Java SE)

        
Enterprise Beansjavax.ejbjakarta.ejb

        
Messagingjavax.jmsjakarta.jms

        
Mailjavax.mailjakarta.mail

        
Common annotationsjavax.annotationjakarta.annotation

        
Servletsjavax.servletjakarta.servlet

The rule to carry out of this page: if the API came from Java SE, it kept the name
      javax. If it came from Java EE, it became jakarta.

  


  


  

  recap
  
One-line summary of everything

  

    
ResourceAn external service your bean uses — a database, a queue, a mail server — that it does not create and does not own.

    
JNDIThe server's address book: names on the left, live objects on the right. Uses javax.naming.

    
API vs SPIYou call the API; the vendor supplies the SPI. That is why your lookups survive a change of server.

    
The naming trapjavax.naming and javax.sql kept their names. There is no jakarta.naming.

    
Namespacesjava:global (whole server), java:app (one EAR), java:module (one JAR/WAR).

    
A JNDI namescope → application → module → bean → !interface.

    
Connection poolingKeep a small batch of open connections and share them, instead of paying the handshake per request.

    
DataSourceThe object that manages the pool. You ask it for a connection; close() returns it.

    
@ResourceMakes the container do the JNDI lookup and inject the resource into a field.

    
Deployment descriptorAn XML file that declares resources and settings outside your Java code. <env-entry>, <resource-ref>, <resource-env-ref>.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Importing jakarta.naming.*Use javax.naming.*. JNDI belongs to Java SE and was never renamed.

      
Importing jakarta.sql.DataSourceUse javax.sql.DataSource — same reason.

      
Calling DriverManager.getConnection() in a beanAsk for a pooled DataSource by JNDI name, usually with @Resource.

      
Assuming conn.close() destroys the connectionFrom a pool, close() gives it back. Not closing it is what leaks connections.

      
Using java:global for a bean only your own module needsUse the narrowest namespace that works: java:module, then java:app, then java:global.

      
Putting a database URL and password in your Java sourceConfigure the DataSource on the server once; the bean only knows the JNDI name.

      
Hardcoding a limit that changes per environmentPut it in an <env-entry> in the deployment descriptor.

      
Forgetting the cast after lookup()lookup() returns Object; cast it to the interface you expect.
