Testing & reading errors

Two survival skills that often go untaught: writing an automated test so you know your logic works, and reading a stack trace so a wall of red text becomes one fixable line. You do not need to have written a test, used JUnit, or deliberately read an error before. Every difficult word gets explained the moment it appears.

🎯

Part 1 · Why we test at all

1.1 A test is code that checks code

You already know how to check your work by hand: run the program, click the button, look at the answer. That works — once. It tells you nothing about tomorrow, and nothing about the change you have not made yet.

A test is different. It is a short piece of Java that:

  1. calls one of your methods,
  2. compares what came back with what you expected, and
  3. shouts if the two do not match.

Once written, a test re-checks your code in seconds — and it keeps re-checking it forever, every time you change anything.

In plain words

A test is a robot that pokes your code and checks it still behaves. You write it once; it does the poking for you from then on.

1.2 The bug you would otherwise meet at 2 a.m.

Here is the real argument, and it is an argument about time.

Imagine you change one small method. Nothing looks wrong. You ship it. Two days later the phone rings: a customer cannot pay, and it is 2 a.m.

A test would have caught that same break in two seconds, on your own machine, before anybody shipped anything. That is what it is for: it catches the bug you would otherwise find in production, at the worst possible moment.

🚨
Analogy A smoke alarm. You fit it before there is a fire. You barely notice it while things are fine, and it shouts the instant something starts to smoulder. A test is a smoke alarm for code — completely useless the day you need it if you did not install it beforehand.

1.3 What a test is not

Two things people assume, wrongly:

  • A test is not a proof. It checks the cases you thought of. It cannot promise there are no bugs — only that the bugs you tested for have been caught.
  • A test is not something you add at the end. It is written as you go, and it stays in the project, running every time the project is built.
⚠️
The test that passes no matter what A test with no check in it — it calls your method, then does nothing — will always pass, even when the code is completely broken. It gives you a warm green feeling and zero safety. Every test must end in an assertion: a real comparison that is allowed to fail. You will see one in Part 2.

Part 2 · Your first JUnit 5 test

2.1 What JUnit is

JUnit is a Java library whose only job is to find your test methods, run them, and tell you which passed. JUnit 5 is the current version, and it is the one you will meet in this course.

The test below is a unit test: a test of one class on its own, with nothing real around it. No server, no database, no container.

✦
Why you may write new here In a unit test you deliberately test the plain class, without the container. new CalculatorBean() is correct here: you want the raw logic, not the machinery around it. (Outside tests, you still never new a container-managed bean — that rule is about beans, not about ordinary classes.)

2.2 The class under test, then the test

Read the concept first, then the code. Nothing here is magic — it is four familiar pieces of Java wearing two new annotations. First the plain class being tested, then the test for it.

Here is that class in full, complete and compilable — two small methods, no framework anywhere:

src/main/java/com/globalbank/CalculatorBean.java
package com.globalbank;

public class CalculatorBean {

    public int add(int a, int b) {
        return a + b;
    }

    public int divide(int a, int b) {
        if (b == 0) {
            throw new ArithmeticException("Cannot divide by zero!");
        }
        return a / b;
    }
}

And here is its test. Maven keeps tests in a separate source folder that mirrors the main one — src/test/java/…, in the same package as the class under test. Maven compiles and runs everything under src/test/java when you type mvn test, and never packages a test into the application you ship.

src/test/java/com/globalbank/CalculatorBeanTest.java
package com.globalbank;

import org.junit.jupiter.api.Test;
import static org.junit.jupiter.api.Assertions.*;

class CalculatorBeanTest {

    private final CalculatorBean calc = new CalculatorBean();  // plain unit test: no container

    @Test
    void adds_two_numbers() {
        assertEquals(15, calc.add(10, 5));
    }

    @Test
    void divide_by_zero_throws() {
        ArithmeticException ex = assertThrows(
            ArithmeticException.class, () -> calc.divide(1, 0));
        assertEquals("Cannot divide by zero!", ex.getMessage());
    }
}
💡
The one thing to notice There is no main method and no System.out.println. You never call these methods yourself. JUnit finds every @Test method and runs it for you, then reports which passed and which failed. That is the whole trick.
PieceMeaning
@Test“Run this method as a test.”
assertEquals(expected, actual)Fail the test unless they match.
assertThrows(Type.class, () -> …)Fail unless the lambda on the right throws that exception.
Arrange → Act → AssertThe shape of almost every test: set up, do the thing, check.
In plain words

A lambda is a small function written inline, with no name of its own. The () -> … arrow is read as “whatever is on the left are the inputs → whatever is on the right is the code to run”. The () is empty because this little function takes nothing.

So read () -> calc.divide(1, 0) aloud as: “a small nameless function that takes no inputs and calls calc.divide(1, 0)”. assertThrows runs that little function and fails unless it throws the exception you named.

An assertion is the checking line — the part that is allowed to fail. The two in that test ask two completely different questions: “did it give the right answer?” and “did it fail in the right way?”

In plain words

A @Test method is just a normal Java method with a label on top. JUnit calls it for you. Inside it, every assert… line is one check. If a check fails, the test fails — and the report tells you exactly which one.

assertEquals(15, calc.add(10, 5)) reads as: “I expected 15; the code gave me calc.add(10, 5). If those differ, shout.”

🍲
Analogy A chef tasting the soup before it leaves the kitchen. One spoonful answers a precise question — “is this salty enough?” — and the chef either nods or fixes it. A test is that taste, performed by a robot, on every single batch, without ever getting tired.

2.3 Arrange → Act → Assert

Almost every test you will ever write has the same three-part shape. Naming the parts makes a test easy to read at a glance:

  • Arrange — set up what the test needs (new CalculatorBean()).
  • Act — do the one thing being tested (calc.add(10, 5)).
  • Assert — check the result (assertEquals(15, …)).

2.4 Running your tests

Run every test in the project with one command:

mvn test

Or, inside an IDE such as IntelliJ IDEA (a Java editor that can also run your code), click the small green ▶ triangle in the gutter next to a test method. Both routes do the same thing: JUnit runs each @Test and shows a green tick or a red cross.

Practise the build command in the simulated terminal below — it is safe and touches nothing on your computer.

Try help, then mvn clean package — Maven runs your tests as part of the build, before it packages anything.

⚠️
Testing only the happy path It is easy to test the one input that works — add(10, 5) — and stop. The bugs live in the edges: zero, a negative number, an empty string, a missing value. Notice that our second test checks the failure case, not the success case. Always test what happens when something is wrong.

Part 3 · The test pyramid

Not all tests are the same size. Some check one class in a flash; some boot a server and take seconds. Because you will never have infinite time, the mix matters: you want many of the cheap ones and few of the expensive ones. That shape has a name — the test pyramid.

LevelTestsSpeed / count
UnitOne class in isolation (like above). Mock its collaborators.Milliseconds · many
IntegrationSeveral parts together — a bean + a real database. Tools: Arquillian, Testcontainers.Seconds · fewer
End-to-endThe whole app through its HTTP API or UI.Slow · fewest

Two words in that table need translating:

  • Isolation means the class under test is the only real thing present. Anything it depends on is replaced.
  • A mock is a stand-in object that pretends to be a collaborator — a fake database, say — and hands back whatever you told it to, so the test does not need the real thing. Mock its collaborators means: replace the neighbours with fakes.
In plain words

A unit test checks one class. An integration test checks a few things working together. An end-to-end test drives the whole application exactly as a user would.

Each step is more realistic and much slower — so you write a pyramid: a wide base of fast unit tests, a smaller middle, and a thin point on top.

🏥
Analogy A health check-up pyramid. Everyone gets the quick routine checks — temperature, blood pressure — because they take seconds and catch most problems. Far fewer people need an X-ray. Very few need a full-body scan, and you would never scan every patient every visit: it is slow, costly and unnecessary. Fast, cheap checks first; the big machine only where it earns its place.

So the rule is simple: write mostly unit tests. They are fast enough to run on every save, and when one fails it points at a single class — which means it pinpoints the break.

⚠️
The upside-down pyramid If almost all of your tests are end-to-end, you have built an ice-cream cone: slow to run, painful to keep working, and — worst of all — when one fails you have no idea which of a hundred moving parts broke. Keep the base wide and the point thin.

  2. A stand-in object that pretends to be a collaborator, so the test can run without the real database or server.
  3. Unit tests. They are fast enough to run on every save, and a failure points at one class — so they pinpoint the break.

Part 4 · Reading a stack trace

4.1 What a stack trace is

When your program crashes, the JVM prints a stack trace: the list of method calls it was inside at the moment it blew up. The top line names what went wrong; the lines below are the trail of calls it walked down to get there.

The words look intimidating purely because there are so many of them. Read as a list of clues, they are not.

In plain words

A stack trace is a receipt of the last few method calls before the crash. Every line is “I was here”. Your job is only to find the one line that says “I was here — in your code.”

🍞
Analogy A trail of breadcrumbs through a dark forest. The trail is long, and most of it passes through somebody else's land — libraries, frameworks, the server. You do not inspect every crumb. You walk the trail until it reaches your own garden, because that is the only place you can plant a fix.

4.2 The four-step method

Applied in this order, every time, a trace collapses into one line and one fix:

  1. Read the top line

    The exception type and its message tell you what went wrong — NullPointerException, EJBException, and so on. That is the headline, not the answer.

  2. Scan down to the first frame in your own package

    Frames look like at com.globalbank.ejb.AccountService.open(AccountService.java:47). Anything above it that belongs to a library is the framework's plumbing. The first line that names your package (com.globalbank.…) is where in your code it blew up.

  3. Read every “Caused by:” from the bottom up

    A trace can stack several causes, each wrapping the one below. The deepest one at the bottom is the root cause; the ones above it are wrappers that only reported the trouble.

  4. Open that file at that line number — and fix that

    The line number is in the frame. Go to it. That is where the fix belongs — not in the library frames above it.

Part 5 · Reading the WildFly log


  
WildFly keeps a running diary of everything it does. Most of it scrolls past harmlessly. A
    handful of lines tell you the few things you actually care about — whether the server is up,
    whether your application deployed, and what its bean names are.

  
You are not going to read the whole thing. You are going to scan for a few
    signatures. Here they are.


  

    
Line you’ll look forMeans

    
      
WFLYSRV0025: WildFly … started in …msServer is up.

      
WFLYUT0021: Registered web context: '/myapp'Your web app deployed; base URL is /myapp.

      
java:global/myapp/MyBean!…The JNDI name for a bean — copy it for lookups (see Session 3).

      
WFLYCTL0013: Operation ("deploy") failed / a stack traceDeployment broke — the cause follows.

      
ERROR [org.hibernate…]A JPA/DB problem — often a bad mapping or missing table.

    
  


  
In plain words
    
The log answers two questions. “Is it healthy?” — look for
      started in …ms and Registered web context. “Did it
      break?” — look for the word failed or ERROR, and remember
      the stack trace from Part 4 is attached right below it.

  


  
🚗
    
Analogy
      A car's dashboard. Dozens of dials and lights, but you only ever react to one or two: the fuel
      gauge, and a warning light. The full story is not on the dashboard at all — it is written in the
      garage's diagnostic report. The WildFly log is the same: a few lights on the console, and the
      complete record in standalone/log/server.log.

  


  
The full log is written to standalone/log/server.log, or streamed into the IntelliJ
    Services console while the server runs.


  
💡
    
The one thing to notice
      Before you blame your code, find your own Registered web context
      line. If it is missing, your app never deployed — and no amount of reading a request error will
      help. Confirm the app is live first.

    📋 The full JUnit 5 annotation table
    
Part 2 used exactly one annotation. These are the rest you will meet in a real project:

    

      
AnnotationWhat it does

      
        
@TestMarks a method as a test. JUnit runs it on its own.

        
@BeforeEachRuns before every test method — the usual place to build fresh objects.

        
@AfterEachRuns after every test method — the usual place to clean up.

        
@BeforeAllRuns once before all the tests in the class. The method must be static.

        
@AfterAllRuns once after all the tests. The method must be static.

        
@DisplayName("…")Gives a test a readable name in the report instead of the method name.

        
@DisabledSkips the test — with a reason, ideally.

        
@NestedGroups related tests together in an inner class.

        
@Tag("…")Labels a test so you can run only a subset, by tag.

        
@TimeoutFails the test if it runs longer than a given time.

        
@ExtendWithRegisters an extension — for example a mocking extension such as MockitoExtension.

        
@ParameterizedTestRuns the same test many times with different inputs, supplied by @ValueSource or @CsvSource.

        
@RepeatedTestRuns the same test a fixed number of times.

      
    

  


  

    ✅ The assertion methods you will use most
    
Every test ends in one or more of these. Each one is a check that is allowed to fail.

    

      
AssertionPasses when…

      
        
assertEquals(expected, actual)the two values are equal.

        
assertNotEquals(expected, actual)they are not equal.

        
assertTrue(condition) / assertFalse(condition)the condition is true / false.

        
assertNull(value) / assertNotNull(value)the value is null / not null.

        
assertThrows(Class<T> type, Executable code)the code throws exactly that exception type. It returns the exception, so you can read its message.

        
assertDoesNotThrow(Executable code)the code finishes without throwing.

        
assertSame(a, b) / assertNotSame(a, b)a and b are / are not the very same object (identity, not just equal values).

        
assertArrayEquals(a, b)two arrays have equal contents.

        
assertAll(…)groups several assertions so all of them run, and reports every failure instead of stopping at the first.

        
assertTimeout(Duration, Executable)the code finishes within the time. assertTimeoutPreemptively(…) does the same but aborts the code if it overruns.

        
fail("message")always fails — useful for a branch that should never be reached.
