Session 6 · Local and Remote Clients, Explained Slowly

Something has to call a bean. Whoever calls it is the bean's client. If the caller runs in the same Java process as the bean, it is a local client. If it runs in a completely different program — another server, a desktop app, a script on someone else's machine — it is a remote client. That one difference decides how you get your hands on the bean, how your arguments travel, and how fast the call is. This page teaches it from zero.

Part 1 · Two ways to call a bean

1.1 A bean is a very shy object

Session 1 left you with one hard rule: never write new on a bean. A bean you create yourself gets none of the container's services — no security, no transactions, no pooling.

So a bean is delivered to you ready-made, by the container, and you only ever receive a reference to it. Everything on this page is about that one handover: where the reference comes from, and what it actually points at.

1.2 What counts as a “client”?

Any code that calls a bean's method is that bean's client. Nothing more complicated than that.

Who is callingTypical shape
A servlet handling a web requestA class in the same application
One bean calling another beanA class in the same application
A test you run from your IDEUsually a separate program
A desktop app, a script, or another serverAlways a separate program

The first two rows are local clients. The last two are remote clients. The dividing line is one question, and it is worth memorising.

1.3 The one question that decides everything

❓
Is the caller running inside the same JVM as the bean?
  • Same JVM → a local client. Share memory. Fast.
  • Different JVM (another program, another machine) → a remote client. Nothing is shared. Everything travels over the network.

A JVM is the Java Virtual Machine — the running Java process. Two classes are “in the same JVM” when they are loaded and running inside the same process; they can reach into each other's memory directly.

🗣️
Analogy Two colleagues in the same office. One leans over and hands the other their actual notebook — the colleague reads it, writes in it, and the very same notebook is affected. Now imagine the colleague has moved to another branch. You cannot hand anything over; you write on a copy and post it. That is the whole difference between a local and a remote client.
In plain words

Local means “we are in the same building, so I can just pass you things.”

Remote means “you are in another building, so I must photocopy and post everything.” Posting is slower, and you never get the original back.

1.4 The two doors to a bean

Because the two cases are so different, they use two different doors. This is exactly the promise Session 1 made you — here it is, in one table.

Door 1 — from inside the applicationDoor 2 — from outside it
How you ask@EJB on a fieldA JNDI lookup by name
What you getThe container fills the field before your code runsA stub — a local stand-in for the bean on the other machine
The bean's interface@Local (or no interface at all)Must be an explicit @Remote interface
Taught inPart 2Part 3

Both doors end in the same place — you hold a reference and call methods on it. Only the way it got there differs.

1.5 The six differences, side by side

This is the table the exam draws from. Read the two middle rows twice; they are the ones people get wrong.

FeatureLocal ClientRemote Client
Runtime Environment Must run in the same JVM (e.g., a Servlet in the same EAR/WAR) Runs in a separate JVM, external container, or standalone machine
Parameter Passing Pass-by-Reference (direct pointer in RAM) Pass-by-Value (a serialized binary copy sent over the network)
Execution Latency Nanoseconds (no marshaling at all) Milliseconds (network handshake, serialization, socket I/O)
Interface Requirement @Local interface or No-Interface View Must declare an explicit @Remote interface
Object Argument Rules Any standard Java class All arguments and returns must implement java.io.Serializable
Mutations to Arguments Changes the bean makes affect the caller's own object directly Changes affect only the bean's deserialized copy; the caller sees no change

1.6 Pass-by-reference vs pass-by-value — the heart of it

When you call a method, you hand it arguments. What you are handing over is the whole difference.

  • Pass-by-reference (local). You pass the location of your object in memory. The bean works on your object. If the bean calls list.add("x"), your list now has "x" in it.
  • Pass-by-value (remote). Your object is turned into a stream of bytes, sent across the network, and rebuilt as a brand-new object on the other side. The bean works on its copy. If it adds "x", your original is untouched.

That “turn an object into bytes and rebuild it” step has a name you will meet constantly: serialization. We take it apart properly in Part 3.

📓
Analogy Local — you hand your colleague the actual notebook. Anything they scribble in it, you will see, because it is the same notebook.
📠
Analogy Remote — you photocopy a page and post the copy to the other branch. They may scribble all over the photocopy; your original page at home is exactly as you left it. This is why a remote method can never fill in one of your objects for you.
In plain words

Local passes the real thing. Remote passes a copy.

So if the bean changes the object you handed it, a local caller sees the change and a remote caller does not. If you need a value back from a remote bean, the bean must return it — it cannot reach back and change your variable.

1.7 The price you pay for crossing the network

A local call is, at the scale your program cares about, free. A remote call is not.

Step that has to happenLocal callRemote call
Find the beanAlready in memoryConnect over the network
Turn arguments into bytesNot neededEvery argument, every time
Send themNot neededSocket I/O between machines
Run the methodInstantInstant
Send the answer backNot neededSerialize, send, rebuild
TotalNanosecondsMilliseconds
In plain words

A local call is a whisper across a desk. A remote call is a letter: write it, seal it, post it, wait, read the reply, post the reply back.

One letter is fine. Ten thousand letters a minute is not — and that is exactly what decides the next rule.

1.8 Which one should you use?

⚡
Performance rule of thumb Beans that talk to each other frequently — for example an OrderBean calling a TaxBean thousands of times a minute — should always use Local interfaces. Remote overhead will drag the whole system down. Reserve @Remote strictly for genuinely separate systems and external integrations.
⚠️
The mistake everybody makes once Making everything remote “because it is more flexible.” Every one of those chatty calls now pays the letter-writing cost. If two beans live in the same application and call each other in a loop, they must be local. Use remote only when the caller really is in another program.

Part 2 · Calling a bean from inside the same building

This is the everyday case — 95% of your code. You are inside the application, the container is already looking after the bean, so all you do is ask for it.

2.1 Door 1: @EJB — delivered to your field

You write the field and leave it empty. Before your code ever runs, the container fills it in with a ready-to-use bean. That is the whole mechanism Session 1 promised you.

WhoShoutsServlet.java — a local client
@WebServlet("/shout")
public class WhoShoutsServlet extends HttpServlet {

    @EJB                                   // ← the container fills this in for us
    private ShouterBean shouter;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        resp.getWriter().println(shouter.shout("hello"));
    }
}
💡
The one thing to notice There is no new anywhere. You declared the field; the container delivered the object. You are not even told which instance you got — a bean from the pool, or a brand-new one. The container decides, and you never need to know.
In plain words

@EJB means “container, put a bean in this field for me.” This is called injection — the container injects the object into your field.

It only works when the caller is inside the application, so the container can see both the field and the bean. For a separate program, you need the other door.

2.2 A local bean can be exposed in three ways

Before a local client can call your bean, the bean has to say what its local view looks like. There are three standard ways to do it, and you will meet all three.

WayWhat you writeWhat the client can call
No-Interface View No interface at all — just the bean class All of the bean's public methods, automatically
Explicit @Local on an interface An interface marked @Local; the bean implements it Only the methods listed on that interface
Class-level declaration @Stateless @Local(ServiceLocal.class) on the bean The methods of the named interface
⚠️
A No-Interface View is local-only — always The no-interface view is available exclusively to local clients. A remote client can never use it, because a remote caller needs a named interface to look up by JNDI. The moment the caller is in another JVM, you must write an explicit @Remote interface. That is Part 3.

2.3 Worked example: a prime number generator

Three small files, one job: a web page asks for every prime number up to a limit, and a bean works them out. Read them in order — the story runs interface → bean → client.

1. PrimeCalculatorLocal.java — the local interface
package com.demo.local;

import jakarta.ejb.Local;

@Local
public interface PrimeCalculatorLocal {
    String getPrimesUpTo(int limit);
}
💡
The one thing to notice @Local on the interface is a promise to the container: “this view is only ever called from inside this application.” That promise is what lets the container pass references instead of copies.
2. PrimeCalculatorBean.java — the stateless bean
package com.demo.local;

import jakarta.ejb.Stateless;

@Stateless
public class PrimeCalculatorBean implements PrimeCalculatorLocal {

    @Override
    public String getPrimesUpTo(int limit) {
        StringBuilder sb = new StringBuilder();
        for (int i = 2; i <= limit; i++) {
            int count = 0;
            for (int n = i; n >= 1; n--) {
                if (i % n == 0) count++;
            }
            if (count == 2) sb.append(i).append(" ");
        }
        return sb.toString().trim();
    }
}
💡
The one thing to notice implements PrimeCalculatorLocal. The bean keeps its @Stateless label from Session 1 — the interface does not replace it. Labels say how the container manages the bean; the interface says how a client reaches it. Two different jobs.
3. PrimeClientServlet.java — the co-located web client
package com.demo.local;

import jakarta.ejb.EJB;
import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

@WebServlet("/primes")
public class PrimeClientServlet extends HttpServlet {

    // Co-located inside the same EAR/WAR -> Injected directly with @EJB
    @EJB
    private PrimeCalculatorLocal primeCalculator;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        String primes = primeCalculator.getPrimesUpTo(100);
        resp.setContentType("text/plain");
        resp.getWriter().println("Primes up to 100: " + primes);
    }
}
💡
The one thing to notice The field's type is the interface, PrimeCalculatorLocal, not the bean. The servlet never mentions PrimeCalculatorBean and never constructs it. It asks for “something that can calculate primes”; the container supplies the bean.
In plain words

Three files, three jobs. The interface lists what clients may ask for. The bean does the work. The servlet asks the container for a bean and calls it.

The servlet is a local client because it lives in the same deployment as the bean. It shares the bean's memory, so req and resp and every argument travel by reference — no copying, no network.

2.4 Why nothing had to be serialized here

Look back at the two analogies in Part 1. This example is the notebook, not the photocopy:

  • The servlet and the bean run in the same JVM.
  • So the container can hand the servlet a direct reference to the bean.
  • Arguments can be any Java class — they never have to be turned into bytes.
  • If the bean changed an object the servlet passed in, the servlet would see the change.
  • And the call takes nanoseconds.
🏢
Analogy The servlet and the bean are two desks in the same office. The servlet does not post a request to the bean; it turns around and speaks to it. Nothing leaves the building, so nothing needs packaging.

Part 3 · Calling a bean from another branch — the standalone client

Now the harder, more interesting case. A program that is not inside the application — a desktop tool, a scheduled script, another server — wants to call your bean. It has no container to ask, so it must dial in from outside.

3.1 What the outsider is missing

Think about what @EJB quietly relied on:

  • Both classes lived in the same application.
  • The container could see the field and fill it in.
  • Both shared one JVM.

An outside program has none of these. It cannot be injected, because no container is watching it. So it has to go and fetch the bean by name. The fetching mechanism is called JNDI.

3.2 What is JNDI?

JNDI stands for Java Naming and Directory Interface. Strip the long name away and it is a phone book for objects.

  • Something is registered in the book under a name (a string).
  • A client opens the book with an InitialContext.
  • It asks for a name with ctx.lookup("…").
  • It gets back an object it can call.
📖
Analogy Calling another branch means you cannot shout across the office, so you ring the switchboard. You ask for “the reverse-string department,” and the switchboard puts you through. JNDI is that switchboard: you give it a name, it gives you a working connection to the thing on the other end.
In plain words

@EJB delivers a bean to a field inside the application. JNDI fetches a bean by name from outside it.

Three words cover the whole thing: InitialContext is opening the phone book, lookup(name) is looking up a name, and the object you get back is the connection.

3.3 The thing you get back is a stub

A remote client never holds the real bean — the bean is on another machine. What it holds is a stub: a small local stand-in that looks exactly like the bean's interface.

You call a method on the stub. The stub serializes your arguments, sends them across the network, the real bean runs the method on the server, and the stub brings the serialized answer back.

The machinery underneath is RMI — Remote Method Invocation, Java's own standard for calling a method on an object that lives in another JVM. RMI is what makes the stub possible: it lets code in your program invoke a method on a server object as if the object were local, hiding the serialization and the socket work. WildFly carries those calls over its own transport (HTTP-remoting), but the idea — one JVM invoking a method in another — is plain RMI.

☎️
Analogy A phone handset. You speak into it as if the person were right there, but the handset is not the person. It carries your words across the line and brings theirs back. The stub is the handset.
In plain words

A stub is a pretend bean that lives in your program but performs its work on another machine. To you it is just a bean. Behind the scenes it is a courier.

3.4 The three things a remote client must do

  1. There must be an explicit @Remote interface. No-interface views do not work remotely — the client needs a named interface to look up.
  2. Every argument and return value must be serializable. If it cannot be turned into bytes, it cannot cross the wire.
  3. Connect and look the bean up by name. That means setting the JNDI provider properties, opening an InitialContext, and calling lookup().

3.5 Serialization, properly

Serialization is turning an object into a stream of bytes, so it can be sent and later rebuilt exactly as it was. To allow it, the class simply implements a marker interface:

A serializable class
import java.io.Serializable;

public class Customer implements Serializable {
    private String name;
    private int id;
    // ... getters and setters
}
💡
The one thing to notice Serializable has no methods to implement. It is a marker — a flag that says “I am allowed to be written to bytes and read back.” That is why forgetting it is such an easy mistake, and why it fails only at runtime, when someone actually makes a remote call.
⚠️
Not serializable → it blows up at call time If any argument of a @Remote method does not implement java.io.Serializable, the build succeeds and the server starts happily. The failure appears only when a remote client actually makes the call. This is one of the most common remote-client bugs.

3.6 Worked example: a string reverser

Same story as Part 2, but through the remote door. Compare the three files with the prime-number ones — the difference is the annotation on the interface, and everything downstream of it.

1. StringReverseRemote.java — the remote interface
package com.demo.remote;

import jakarta.ejb.Remote;

@Remote
public interface StringReverseRemote {
    String reverseString(String input);
}
💡
The one thing to notice @Remote instead of @Local — and that one word changes everything about how calls travel. This interface is now the bean's published front door to the outside world.
2. StringReverseBean.java — the remote stateless bean
package com.demo.remote;

import jakarta.ejb.Stateless;

@Stateless
public class StringReverseBean implements StringReverseRemote {

    @Override
    public String reverseString(String input) {
        if (input == null) return null;
        return new StringBuilder(input).reverse().toString();
    }
}
💡
The one thing to notice The bean class looks exactly like a local one. The only clue that it is reachable from another machine is the @Remote interface it implements. There is nothing special to write in the bean body.
3. RemoteClientMain.java — the standalone client
package com.demo.remote.client;

import com.demo.remote.StringReverseRemote;
import javax.naming.Context;
import javax.naming.InitialContext;
import javax.naming.NamingException;
import java.util.Properties;

public class RemoteClientMain {

    public static void main(String[] args) {
        try {
            // Configure WildFly EJB Remoting JNDI provider
            Properties p = new Properties();
            p.put(Context.INITIAL_CONTEXT_FACTORY,
                  "org.wildfly.naming.client.WildFlyInitialContextFactory");
            p.put(Context.PROVIDER_URL, "remote+http://localhost:8080");

            Context ctx = new InitialContext(p);

            // JNDI Lookup syntax for WildFly Remote EJBs:
            // ejb:<appName>/<moduleName>/<distinctName>/<beanName>!<interfaceName>
            // NOTE: replace "RemoteLab" with YOUR module (archive) name — the jar/war you
            // deployed the bean in, without the extension. A wrong name here = NamingException.
            String jndiName = "ejb:/RemoteLab/StringReverseBean!com.demo.remote.StringReverseRemote";
            StringReverseRemote service = (StringReverseRemote) ctx.lookup(jndiName);

            // Call method across network socket
            String original = "Enterprise Jakarta Beans";
            String reversed = service.reverseString(original);

            System.out.println("Original: " + original);
            System.out.println("Reversed from WildFly: " + reversed);

        } catch (NamingException e) {
            System.err.println("Remote JNDI lookup failed: " + e.getMessage());
        }
    }
}
💡
The one thing to notice ctx.lookup(jndiName) returns a plain Object, so you cast it to the interface — (StringReverseRemote). From that line on, the code looks like an ordinary method call. The word ejb: at the start of the name tells the server “this is an enterprise bean, not a database or a message queue.”
In plain words

Four lines do all the work: say where the server is, open the context, look up the name, cast the result.

After the lookup, calling service.reverseString(…) is written exactly like a local call. The difference is invisible in the code and enormous on the wire.

3.7 What actually happens on a remote call

Press Run and watch a single remote call play out, message by message. This is the machinery behind those four lines.

    •

    • 
    
  • Then ! and the fully-qualified name of the @Remote interface you want.

Part 4 · Does a bean have a name? Session identity vs entity identity

  
Last question, and it is the one the manual words as “session object identity (anonymity) vs entity
    identity.” In plain terms: can you point at one particular session bean the way you point at
    one particular row in a database? No. Here is why, and what you do instead.


  
4.1 Two very different ideas of “identity”

  
A session bean is a worker. You ask it to do something; it does it; you do not
    care which instance you spoke to. It is anonymous.

  
An entity is a record. It represents one specific row in a database — one customer,
    one account — and it has a primary key that identifies it forever.


  
🧑🔧
    
Analogy
      A session bean is a temp worker hired for the day. You do not know their name, you do not keep
      their number, and tomorrow you will be given somebody else. An entity is a permanent staff member
      with a staff ID — that number identifies one specific person, and it still will next
      year.

  


  
In plain words
    
A session bean does work and is forgotten. That is why the container can swap instances from a
      pool without you noticing.

    
An entity is data, so it must be findable again later — which is exactly why it needs a
      primary key.

  


  
4.2 The differences, side by side

  

    
AspectSession Bean (Stateless / Stateful)JPA Entity

    
      

        Identity
        Anonymous — no identity at all
        An exposed primary key (@Id)
      

      

        A method for its key
        None exists. Your interface is a plain Java interface with your own business methods — there is nothing to call.
        A plain getter such as getId() returns the key
      

      

        Finder methods
        None — you cannot query or “search” for a session bean
        Extensive finders: em.find(), JPQL queries
      

      

        How a client keeps it
        A stateless bean needs no keeping — look it up again, or keep the reference. A stateful bean's reference is held for the length of one conversation.
        Store the primary key, and look the row up again whenever you need it
      

    
  


  
⚠️
    
If you have read older material, this is where it misleads you
      
Many tutorials — and a great deal of what is still online — describe session beans using a
        getHandle() method, a Handle object, handle.getEJBObject(),
        and a getPrimaryKey() that throws an exception. That was EJB 2.x, and
        it is not how you write a bean today.

      
In modern Enterprise Beans you write a plain Java interface for your business
        methods and mark it @Remote or @Local. It extends nothing and contains
        only the methods you wrote. So there is no getHandle() to call — that snippet
        would not even compile against the bean you built in Part 3.

      
You may still see EJBObject, EJBHome and Handle in the API
        documentation. They are kept there so that very old code still builds. You will not use them.

    

  


  
4.3 So how do you “remember” a session bean?

  
Mostly, you do not — and that is the point rather than a limitation. A stateless
    session bean is interchangeable: the container keeps a pool, and any instance will do. There is nothing
    to remember, because remembering which one you spoke to last time would make no difference. Ask for it
    again and you get a bean, which is all you needed.

  
A stateful session bean is the opposite case, and it comes with its own answer: the
    container keeps that bean alive for one conversation, and your client holds the reference for
    as long as the conversation lasts. When the conversation ends, the bean is removed. There is no token
    you save and redeem later.


  
🧑🔧
    
Analogy — no coat check, and no ticket needed
      A session bean is not a coat you hand in and collect. It is a counter clerk. You do not need a ticket
      to find “your” clerk tomorrow — any clerk at the counter can serve you, because they all do the same
      job. A stateful bean is the one clerk who agrees to work through your whole file with you,
      and when the file is closed, that arrangement ends.
    

  


  
In plain words
    
A session bean cannot be “found again” — it has no name. That is not a gap in the design; for a
      stateless bean, being findable is not useful.

    
When you genuinely need to find something again later — after a restart, or from another machine —
      it has to have an identity. That means it is data, and data belongs in an entity with a primary key.
      You store the key, and you look the row up.

    🔎 The full JNDI name, segment by segment
    
A remote bean is published under a name built from its deployment. The general shape is:

    
ejb:<appName>/<moduleName>/<distinctName>/<beanName>!<interfaceName>

    

      
SegmentWhat it isIn our example

      
        
ejb:The scheme, saying “this is an enterprise bean binding.”ejb:

        
<appName>The deployed application (an EAR) name.empty — left out

        
<moduleName>The archive the bean was deployed in — the .jar or .war, without the extension.RemoteLab

        
<distinctName>An optional name a deployment may set to tell two deployments apart.empty — left out

        
<beanName>The bean class's simple name.StringReverseBean

        
!<interfaceName>The fully-qualified name of the business interface you want.!com.demo.remote.StringReverseRemote

      
    

    
Put back together, that is exactly the string in the worked example:

    
ejb:/RemoteLab/StringReverseBean!com.demo.remote.StringReverseRemote

    
Inside the server you will also see the same binding written with a java:global/ prefix
      — the server's own, internal way of writing the identical name.

    
⚠️
      
The ! matters
        Everything before ! is the bean; everything after it is the interface. Point the
        lookup at the wrong interface name and the lookup fails even though the bean is deployed and
        running. When something “cannot be found,” check the ! half first.

    

  


  

    💻 The complete prime-number example (all files together)
    
Interface, bean, and servlet, in one place for copying. This is the local client from Part 2.

    
PrimeCalculatorLocal.java

    
package com.demo.local;

import jakarta.ejb.Local;

@Local
public interface PrimeCalculatorLocal {
    String getPrimesUpTo(int limit);
}

    
PrimeCalculatorBean.java

    
package com.demo.local;

import jakarta.ejb.Stateless;

@Stateless
public class PrimeCalculatorBean implements PrimeCalculatorLocal {

    @Override
    public String getPrimesUpTo(int limit) {
        StringBuilder sb = new StringBuilder();
        for (int i = 2; i <= limit; i++) {
            int count = 0;
            for (int n = i; n >= 1; n--) {
                if (i % n == 0) count++;
            }
            if (count == 2) sb.append(i).append(" ");
        }
        return sb.toString().trim();
    }
}

    
PrimeClientServlet.java

    
package com.demo.local;

import jakarta.ejb.EJB;
import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

@WebServlet("/primes")
public class PrimeClientServlet extends HttpServlet {

    @EJB
    private PrimeCalculatorLocal primeCalculator;

    @Override
    protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException {
        String primes = primeCalculator.getPrimesUpTo(100);
        resp.setContentType("text/plain");
        resp.getWriter().println("Primes up to 100: " + primes);
    }
}

    
What the bean actually does: for every number i from 2 up to
      limit, it counts how many numbers divide into it evenly. A number with exactly two
      divisors is prime. Those numbers are joined with spaces into one string.

  


  

    📡 The complete remote example (all files together)
    
The remote client from Part 3, in one place. Compare the interface — @Remote instead
      of @Local — with the one above.

    
StringReverseRemote.java

    
package com.demo.remote;

import jakarta.ejb.Remote;

@Remote
public interface StringReverseRemote {
    String reverseString(String input);
}

    
StringReverseBean.java

    
package com.demo.remote;

import jakarta.ejb.Stateless;

@Stateless
public class StringReverseBean implements StringReverseRemote {

    @Override
    public String reverseString(String input) {
        if (input == null) return null;
        return new StringBuilder(input).reverse().toString();
    }
}

    
RemoteClientMain.java

    
package com.demo.remote.client;

import com.demo.remote.StringReverseRemote;
import javax.naming.Context;
import javax.naming.InitialContext;
import javax.naming.NamingException;
import java.util.Properties;

public class RemoteClientMain {

    public static void main(String[] args) {
        try {
            Properties p = new Properties();
            p.put(Context.INITIAL_CONTEXT_FACTORY,
                  "org.wildfly.naming.client.WildFlyInitialContextFactory");
            p.put(Context.PROVIDER_URL, "remote+http://localhost:8080");

            Context ctx = new InitialContext(p);

            // Replace "RemoteLab" with YOUR module (archive) name, without the extension.
            String jndiName = "ejb:/RemoteLab/StringReverseBean!com.demo.remote.StringReverseRemote";
            StringReverseRemote service = (StringReverseRemote) ctx.lookup(jndiName);

            String original = "Enterprise Jakarta Beans";
            String reversed = service.reverseString(original);

            System.out.println("Original: " + original);
            System.out.println("Reversed from WildFly: " + reversed);

        } catch (NamingException e) {
            System.err.println("Remote JNDI lookup failed: " + e.getMessage());
        }
    }
}

    
Note the naming difference: the local example's client field is typed to
      PrimeCalculatorLocal and injected; the remote example's client builds an
      InitialContext and casts the result of a lookup. Same idea — hold a reference to an
      interface — two different doors.

  


  

    🏷️ Every annotation on this page, in one place
    

      
AnnotationGoes onIt means

      
        
@StatelessThe bean class“Container, manage this class. It keeps no memory between calls.” (Session 1.)

        
@LocalAn interface“This view may only be called from inside the application.” Pass-by-reference.

        
@RemoteAn interface“This view is published to the outside world.” Pass-by-value, needs Serializable.

        
@LocalBeanThe bean class“Expose a No-Interface View” — used when a bean has no interface at all. Local clients only.

        
@EJBA field“Container, inject a bean here.” Works only for local clients inside the application.

        
@WebServlet("/primes")A servlet class“Give this class a URL,” so a web request can reach it.

      
    

    
⚠️
      
Local and remote are not a choice you can mix freely
        A bean may expose both a @Local and a @Remote interface at once — the
        same bean, two doors, two client populations. What it cannot do is offer a
        No-Interface View to a remote client. Remote always needs a named interface.

    

  


  

    🔁 What can and cannot cross the network
    
Anything that travels to a remote bean is serialized first. That makes some things easy to send
      and others impossible without extra work.

    

      
Kind of valueCan it cross?Why

      
        
A String, a number, a booleanYesThese classes already implement Serializable.

        
Your own class implements SerializableYesIts fields are written out and rebuilt on the other side.

        
Your own class without SerializableNoFails at call time, not at build time.

        
An open socket, a live connection, a database handleNoThese are tied to a running process; they cannot be copied into bytes.

        
A field marked transientNot carriedtransient means “skip this field when serializing.” It arrives as its default value.

      
    

    
In plain words
      
If it can be written down and read back, it can travel. If it only makes sense while the program
        is running — a live connection, an open stream — it cannot be posted to anyone.

    

  


  

    📖 The names behind the magic: RMI, Remoting, and the port
    
Four terms appear in server logs and textbooks when a remote call happens. None of them change
      what you write; they explain what your client library does underneath.

    

      
TermWhat it is

      
        
RMI (Remote Method Invocation)The core Java standard for calling a method on an object that lives in another JVM. The foundation under everything on this page.

        
SerializationTurning an object into bytes so it can be sent, and rebuilding it on arrival.

        
JBoss Remoting / HTTP-remotingThe mechanism WildFly uses to carry remote EJB calls. Our example connects with remote+http://localhost:8080 — the same port the web server listens on.

        
WildFlyInitialContextFactoryThe class that knows how to reach a WildFly server from a standalone client. You name it in the JNDI properties; the client library does the rest.

      
    

  


  

    🧩 Local vs remote — a decision checklist
    
Before you mark an interface @Remote, walk down this list. If you answer “no” to the
      first two, you almost certainly want @Local.

    
    
      
  1. Is the caller genuinely in a different JVM — another program, another machine?
    2. 
      
  2. Will the bean methods be called occasionally, not in a tight loop?
    3. 
      
  3. Can every argument and return value be made Serializable?
    4. 
      
  4. Is the extra latency (milliseconds per call) acceptable for this workflow?
    5. 
    

    
If you cannot comfortably say yes to all four, keep the interface local and let the two beans talk
      in the same JVM.

  


  


  

  recap
  
One-line summary of everything

  

    
A bean's clientAny code that calls the bean's methods — a servlet, another bean, a test, or a separate program.

    
Local clientCo-located in the same JVM; pass-by-reference in RAM; uses @Local or a No-Interface View.

    
Remote clientDistributed across JVMs; pass-by-value over the network; requires @Remote and Serializable.

    
Door 1 — how to get a bean inside the app@EJB on a field. The container injects it. You never write new.

    
Door 2 — how to get a bean from outsideOpen an InitialContext, then ctx.lookup("ejb:…") to fetch a stub by name.

    
JNDIA phone book for objects: a name in, a usable object out.

    
StubThe local stand-in for a remote bean. You call it; it carries the call across the network.

    
SerializationTurning an object into bytes so it can travel. Requires java.io.Serializable.

    
Latency gapLocal = nanoseconds; remote = milliseconds (marshaling plus a network round trip).

    
Rule of thumbChatty beans must be local. Use @Remote only for genuinely separate systems.

    
Session identityAnonymous — no identity, and no method to ask for one. A stateless bean is simply looked up again when needed.

    
Entity identityReal and stable: an exposed primary key (@Id), findable with em.find() and JPQL.

    
EJBObject / EJBHome / HandleLegacy EJB 2.x. Still in the API so old code builds, but never used in a modern bean — your business interface is a plain Java interface.

  


  concept
  
Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Marking every interface @Remote “to be safe”Default to @Local. Make it remote only when the caller really is in another program.

      
Expecting a remote bean to change the object you passed inIt cannot. Remote calls are pass-by-value. Have the method return the value you need.

      
Passing an object that does not implement SerializableImplement java.io.Serializable on every argument and return type of a @Remote method.

      
Trying to reach a No-Interface View from a remote clientImpossible. Write an explicit @Remote interface and look it up by JNDI.

      
Leaving the !interfaceName off the JNDI nameWrite the full name: ejb:/Module/Bean!fully.qualified.Interface.

      
Copying getHandle() or getPrimaryKey() from an old tutorialThose are EJB 2.x. A modern bean's interface is a plain Java interface with only your own methods — the snippet will not compile. If you need something findable later, store its primary key on an entity.

      
Inventing a field to give a session bean an “id”That is not identity, and a stateless bean may not keep it between calls. Store real data in an entity.

      
Using new on the client side out of habitYou never construct a bean. Get it with @EJB inside the app, or a JNDI lookup outside it.
