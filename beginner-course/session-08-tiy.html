Part 1 · The pipeline, in plain words

1.1 Why a checkout page should not wait

A customer clicks Pay. Behind that one click the system has to charge the card, reserve the stock, generate an invoice and send a confirmation email. If the page does all of that before it answers, the customer stares at a spinner for as long as the slowest step takes — and if any single step is down, the whole click fails, even the parts that would have worked.

So a high-throughput web tier does one small thing instead. It drops a note describing the order onto a queue and answers the customer immediately. A separate, invisible worker picks the note up later and does the slow work. The web tier that writes to the queue is the JMS Producer; the background worker that reads from it is a Message-Driven Bean (MDB); and the database write happens over a pooled JDBC connection.

In plain words

The web page takes the order. Somebody else cooks it.

The customer is told “order received” in a few milliseconds. The kitchen works through the ticket when it can — even if that is ten seconds later, and even if the customer has already closed the tab.

1.2 The four stages, and who does what

That whole idea has four stages. Read the table left to right: each stage hands its work to the next, and never the other way round.

StageComponentTechnology UsedOperational Latency
1. Submit Web Checkout Controller JMSContext.send(orderQueue, orderData) 1–3 ms (Returns immediately to browser)
2. Buffer Artemis Message Broker Point-to-Point Persistent FIFO Queue Buffers traffic spikes safely on disk
3. Consume OrderProcessingMDB @MessageDriven implements MessageListener Pulls message from queue in separate worker thread
4. Persist OrderDAO PreparedStatement via pooled JNDI DataSource Executes SQL inside an isolated transaction
🍳
Analogy Stage 1 is the waiter writing your ticket and pinning it on the rail. Stage 2 is the rail itself — it holds tickets safely even when the kitchen is slammed. Stage 3 is whichever cook is free grabbing the next ticket. Stage 4 is that cook plating the dish. The customer never waits for the cooking; they only wait for the waiter.

  5. 
      
    Write the message-driven bean — the heart of the lab
    
      
    Create src/main/java/com/globalbank/messaging/OrderProcessingMDB.java. This single
        class does stages 3 and 4: it listens on the queue, and on each message it opens a pooled JDBC
        connection and inserts a row.
    
      
    OrderProcessingMDB.java
    
      
    package com.globalbank.messaging;

import jakarta.annotation.Resource;
import jakarta.ejb.ActivationConfigProperty;
import jakarta.ejb.MessageDriven;
import jakarta.jms.JMSException;
import jakarta.jms.Message;
import jakarta.jms.MessageListener;
import jakarta.jms.TextMessage;
import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;

@MessageDriven(activationConfig = {
    @ActivationConfigProperty(propertyName = "destinationLookup",
                              propertyValue = "java:/jms/queue/OrderQueue"),
    @ActivationConfigProperty(propertyName = "destinationType",
                              propertyValue = "jakarta.jms.Queue")
})
public class OrderProcessingMDB implements MessageListener {

    @Resource(lookup = "java:/jdbc/GlobalBankDB")
    private DataSource dataSource;

    @Override
    public void onMessage(Message message) {
        try {
            if (message instanceof TextMessage textMsg) {
                String payload = textMsg.getText();
                System.out.println("MDB received background order: " + payload);

                // Persist order details using parameterized JDBC
                saveOrderRecord(payload);
            }
        } catch (JMSException | SQLException e) {
            System.err.println("Failed to process message: " + e.getMessage());
            // Throwing RuntimeException causes container to retry or move to DLQ
            throw new RuntimeException("Rollback message receipt", e);
        }
    }

    private void saveOrderRecord(String payload) throws SQLException {
        String sql = "INSERT INTO processed_orders (order_payload, processed_at) VALUES (?, NOW())";
        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, payload);
            ps.executeUpdate();
        }
    }
}
    
      
    Read it once, because every line is doing a job you have already met:
    
      
      
        
    • @MessageDriven with destinationLookup ties this class to
          java:/jms/queue/OrderQueue — the exact name you printed in step 1.
          destinationType says the destination is a Queue, not a Topic.
      • 
        
    • @Resource(lookup = "java:/jdbc/GlobalBankDB") injects the
          pooled datasource. You never open a raw connection yourself.
      • 
        
    • onMessage() is called by the container, once per message. Nobody
          in your code ever calls it.
      • 
        
    • try (Connection conn = …) is try-with-resources. It returns the
          connection to the pool even if the insert throws — this is the fix for trap 2 in Part 3.
      • 
        
    • PreparedStatement with a ? placeholder binds the value safely — the
          fix for trap 3. Never build SQL by concatenating strings.
      • 
        
    • Throwing a RuntimeException when something fails tells the container “this did not
          work”; it rolls back and retries, or eventually moves the message to the Dead Letter Queue
          (trap 1).
      •

    Write the producer and the web page that uses it (stage 1)
    
      
    The producer is a small stateless bean. It injects a managed JMSContext and the queue,
        and sends. Create
        src/main/java/com/globalbank/messaging/OrderSender.java:
    
      
    OrderSender.java
    
      
    package com.globalbank.messaging;

import jakarta.annotation.Resource;
import jakarta.ejb.Stateless;
import jakarta.inject.Inject;
import jakarta.jms.JMSConnectionFactory;
import jakarta.jms.JMSContext;
import jakarta.jms.Queue;

@Stateless
public class OrderSender {

    @Inject
    @JMSConnectionFactory("java:/ConnectionFactory")
    private JMSContext jmsContext;          // a managed connection to the broker — do not close it

    @Resource(lookup = "java:/jms/queue/OrderQueue")
    private Queue orderQueue;               // the administered destination, looked up by name

    public void submit(String order) {
        jmsContext.createProducer().send(orderQueue, order);   // stage 1: hand it to the queue and return
    }
}
    
      
    Two lines carry the meaning: @JMSConnectionFactory gives you a ready-made line to the
        broker, and @Resource drops the pre-made queue into the field. You do not create,
        start or close either one — the container does.
    
      
    Now the web page, at
        src/main/java/com/globalbank/web/OrderServlet.java. It answers one URL, hands the value
        to the sender, and prints its reply before any database work has happened:
    
      
    OrderServlet.java
    
      
    package com.globalbank.web;

import com.globalbank.messaging.OrderSender;
import jakarta.ejb.EJB;
import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

@WebServlet("/order")
public class OrderServlet extends HttpServlet {

    @EJB
    private OrderSender sender;             // the container injects a ready-made producer

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws IOException {

        String item = request.getParameter("item");     // the ?item=... part of the URL
        sender.submit("ORDER: " + item);                // drop it on the queue — this returns in ms

        response.setContentType("text/plain");
        response.getWriter().println("Order accepted (returned immediately)");
    }
}
    
      
    Notice what is not here: no database call, no waiting, no SQL. The servlet's whole
        job is to hand the order over and answer. The MDB does everything else — later.

2.3 When it goes wrong — the three you will actually hit

  
Everyone meets these. Find your symptom, apply the fix, carry on. This is normal developer work, not
    failure.


  

    
What you seeWhat it meansWhat to do

    
      

        NameNotFoundException: java:/jms/queue/OrderQueue
        The queue's JNDI name in your code does not match what was registered (a typo, or step 1 was never run)
        In jboss-cli run the read-resource from step 1 and copy the exact entries string into destinationLookup. Redeploy.
      

      

        IJ000453: Unable to get a connection from pool
        The connection pool is exhausted — a connection was not returned
        Make sure every Connection and PreparedStatement is opened inside try (…). Never call close() by hand in a catch.
      

      

        The servlet answers, but no row ever appears
        The transaction rolled back — the cause is not the message
        Find the Caused by: line in the server log (bad column name, missing table, wrong credentials) and fix that. Look for the real cause, not the wrapper.
      

      

        The same log line repeats endlessly, CPU climbing
        A poison message the MDB keeps failing on, being redelivered forever
        This is trap 1 below: cap redelivery and let the broker move it to the Dead Letter Queue.

Part 3 · When it goes wrong — the top three integration traps

  
These three faults account for most of the pain in real asynchronous systems. Learn the symptom, then
    the fix — you will meet every one of them in production.


  
1️⃣
    
Trap 1: The “Poison Message” Infinite Loop & DLQ
      
Symptom: An MDB repeatedly throws an exception on a malformed message, consuming 100% server CPU as the broker endlessly retries delivery.

      
Fix: Configure maximum redelivery attempts (e.g., 3 retries) in WildFly's Artemis subsystem. Once exceeded, the broker automatically diverts the failed message to a Dead Letter Queue (DLQ) for administrative inspection. The exact CLI commands are in the Reference at the end.

    

  


  
2️⃣
    
Trap 2: Database Connection Leaks under High Asynchronous Load
      
Symptom: After processing a burst of 5,000 messages, the application server hangs with IJ000453: Unable to get a connection from pool.

      
Fix: A connection was not deterministically returned to the pool because code used manual conn.close() inside an imperfect try/catch. Always use Java try-with-resources!

    

  


  
3️⃣
    
Trap 3: SQL Injection via Statement String Concatenation
      
Symptom: An attacker injects quotes into message payload strings, tampering with backend tables.

      
Fix: Never use Statement.executeUpdate("... " + val). Always use PreparedStatement with question mark placeholders (?) and typed setters.

    

  


  
🔬
    
Why these three, and not others
      Notice that all three are about the seam between two systems, which is exactly where
      Sessions 7 and 8 live. Trap 1 is the queue and the consumer disagreeing about a message. Trap 2 is
      the bean and the connection pool disagreeing about who owns a connection. Trap 3 is your SQL and
      somebody else's data disagreeing about what a value is. In every case the fix is to let the container
      own what the container is meant to own.

Queue or Topic?
      A Queue is point-to-point: each message is delivered to exactly one
      consumer (1:1). A Topic is publish/subscribe: each message is delivered to
      every subscriber (1:N). The lab used a Queue, which is why
      destinationType was jakarta.jms.Queue — and why two MDB instances split the
      work instead of both doing it.

    🔌 JCA in one page — resource adapters and the .rar
    
Jakarta Connectors (JCA) standardises how an application server plugs into an
      Enterprise Information System (EIS) — a mainframe, an ERP like SAP, a messaging
      system. Without a standard, every server would need its own custom driver for every system; the JCA
      standard collapses that into M+N: each server has one standard socket, and each EIS
      ships one standard adapter.

    
That adapter is packaged as a .rar — a Resource Adapter Archive — and
      deployed into WildFly like any other module. Your JDBC DataSource is the everyday example
      of a JCA outbound connection: the application asks for a connection by name and the adapter hands it
      a pooled one.

    
In plain words
      
A .rar is a universal travel adapter: the vendor builds it once, and it fits the
        standard socket on any certified server. Write once, plug in anywhere.

    

  


  

    🧯 What the container does when onMessage() throws
    
    
      
  1. The current transaction is rolled back — the half-finished insert never happens.
    2. 
      
  2. The message is not acknowledged, so it stays “in flight” and is redelivered.
    3. 
      
  3. This repeats up to max-delivery-attempts times. Set too high, a single poison message
        burns CPU forever (trap 1).
    4. 
      
  4. Once the limit is passed, the broker diverts the message to the Dead Letter Queue,
        leaving the production queue clear for healthy messages.
    5. 
    

    
The operational habit that follows: always monitor the DLQ, and treat every message on it as
      a bug report about your payload handling.

Common mistakes to avoid

  

    
❌ The mistake✅ The fix

    
      
Doing the database write inside the servlet so the user waits for itSend to the queue and return; let the MDB persist in the background.

      
Typing the destinationLookup JNDI name from memoryCopy it from the queue's read-resource entries line.

      
Building SQL with "… WHERE id = " + valueBind the value with PreparedStatement and a ? placeholder.

      
Closing a connection by hand inside catchOpen it in try (…) so it is returned to the pool on every path.

      
Ignoring a repeated “failed to process message” log lineIt is a poison message: cap redelivery and check the DLQ.

      
Assuming the row is written the instant the user's page answersIt is not — that is the point. Verify with the server log and the table, not with the browser.
