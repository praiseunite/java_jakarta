Part 1 · What CDI is, and why you stop writing new

1.1 The small word that causes big problems: new

In ordinary Java, when one object needs another, it builds it:

The old way — one class builds its own helper
public class AccountController {

    // the controller reaches out and builds its own service
    private AccountService service = new AccountServiceImpl();
}

That one line, new AccountServiceImpl(), looks harmless. It is not. It welds your controller to one exact class. From now on your controller can only ever use AccountServiceImpl — not a faster version, not a fake version for testing, not a different one for another customer. To change the helper you must open the controller and edit it.

In plain words

Writing new is like gluing two parts together. They now come as a pair. You cannot pull one out and put a different one in without breaking the glue.

Programmers call that gluing tight coupling: two pieces of code stuck so firmly that you cannot change one without disturbing the other.

1.2 The fix: let something else hand you what you need

Here is the whole idea of CDI, and it is genuinely this simple:

  1. Your object says what it needs — "I need an AccountService" — and stops there.
  2. It does not build it. No new.
  3. Before your code runs, the container finds a suitable object and places it into your object for you.

That act — the container putting the needed object into yours — is called dependency injection. A "dependency" is just a thing your object depends on to do its job. "Injection" means the container pushes it in from the outside.

🎭
Analogy — the props master On a film set, actors do not bring their own swords, cups and letters. A props master works out what each scene needs and places the right item into each actor's hand just before the take. The actor simply acts.
CDI is the props master. It works out what your object needs and hands it over, so your object never has to go shopping for its own parts.

1.3 So what does "CDI" actually stand for?

CDI = Contexts and Dependency Injection. Two words, two jobs:

  • Dependency Injection — the handing-over you just met: the container supplies the objects, you never call new.
  • Contexts — the container also decides how long each object lives and how many copies exist. That part is called a scope, and it is the whole of Part 2.
In plain words

CDI is the wiring backbone of modern Jakarta EE: it creates your objects, plugs them into each other, and controls how long each one stays alive. The container supplies the instance at runtime — you just declare what you want.

1.4 "Program to a type, not to a class"

Because the container does the building, your code can ask for a type (an interface or a general class) and let the container pick the exact implementation. That is what people mean by loose coupling — the opposite of the glue in 1.1.

🔌
Analogy — the wall socket Your phone charger does not care which power station it is wired to. It just needs a plug that fits the socket. You depend on the shape of the socket (the type), not on one particular generator (one concrete class). Anything with a matching plug can be swapped in without rewiring the house.
In CDI the injection point is the socket; any bean of the matching type is a plug that fits.

1.5 The beans.xml file — and what it really does

There is a file you will see in nearly every Jakarta EE project, and you should know both what it is called and what it actually does today. It is called beans.xml, and if you use it, it goes in a fixed place. A "module" here means one packaged piece of your app — a .jar or a .war:

  • In a JAR → put beans.xml in META-INF/
  • In a WAR → put beans.xml in WEB-INF/
📌
The single most important thing on this page

Almost every tutorial you will read says “CDI does not scan your application unless you add beans.xml.” That was true in CDI 1.0. It has not been true since CDI 1.1.

Today, an archive that contains classes carrying bean-defining annotations is an implicit bean archive. The container discovers it with no beans.xml at all. The file becomes genuinely required only when you want to change something: to set a discovery mode (Section 1.6), or to declare alternatives, interceptors or decorators (Session 12).

So if your beans are missing, beans.xml is rarely the culprit. Check the annotation first — a class with no scope annotation is not a bean in annotated mode, file or no file.

Here is the whole file, for when you do need it:

WEB-INF/beans.xml — the file that configures CDI discovery
<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="https://jakarta.ee/xml/ns/jakartaee"
       xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
       xsi:schemaLocation="https://jakarta.ee/xml/ns/jakartaee
                           https://jakarta.ee/xml/ns/jakartaee/beans_4_0.xsd"
       version="4.0"
       bean-discovery-mode="annotated">
</beans>
💡
The one thing to notice The whole file is empty between the tags. The only setting that matters today is bean-discovery-mode="annotated" — it tells CDI which classes in this archive to treat as beans. That is the next section. Everything else you will ever put in this file is one of the four declarations above: alternatives, interceptors, decorators, or the discovery mode.

1.6 Which classes become beans? The discovery mode

The discovery mode is a single word in beans.xml that decides which of your classes CDI manages. There are three choices, but you will use the first one almost always:

  • annotated — the default and the recommended one. Only classes that carry an explicit scope annotation (such as @RequestScoped or @ApplicationScoped) become beans. This keeps startup fast, because the container does not have to inspect every class.
  • all — every class in the archive is treated as a bean. This can slow deployment right down.
  • none — CDI is switched off completely for this archive.
🪪
Analogy — the staff lanyard In annotated mode, the container treats someone as staff only if they are wearing a lanyard — the scope annotation. In all mode, everyone standing in the building counts as staff. In none mode, the staff room is locked and nobody gets in.
⚠️
The trap that catches everyone first Under the default annotated mode, a class with no scope annotation at all is simply not discovered — CDI never manages it, and @Inject for it fails to find anything. If a bean "isn't being injected," the first thing to check is whether it has a scope annotation on it.

Part 2 · How long a bean lives — the five scopes

2.1 What a "scope" is

A scope answers two questions about a bean:

  • How many copies exist? One shared by everyone, one per user, or a fresh one each time?
  • How long does each copy live? One web request, one visit, forever, or until you say stop?

You choose a scope by putting one annotation on the class. CDI then creates and destroys the bean on exactly that schedule, with no lifecycle code from you.

In plain words

A scope is a lifespan sticker you put on a class. The container reads the sticker and knows when to make the object and when to throw it away.

2.2 The five scopes as one picture

There are five scopes. Before the formal detail, here is all five in a single everyday scene.

🎡
Analogy — a day at a theme park Each scope is a different kind of pass:
  • @RequestScoped → a single-ride ticket: torn in half as you board, gone the moment the ride ends.
  • @SessionScoped → a day wristband: one per visitor, worn across every ride all day, cut off only when you leave.
  • @ApplicationScoped → the park itself: there is only one, every visitor shares it, and it lives as long as the gates are open.
  • @ConversationScoped → a booked guided tour: you say when it begins and when it ends, and it spans several stops in between.
  • @Dependent → the free map handed out with another ticket: it has no life of its own; it belongs to whatever it came with.

2.3 @Dependent — the default, and the surprise

@Dependent is a pseudo-scope — "pseudo" because the bean has no independent lifespan. It lives and dies with whatever object it was injected into, and it is never shared. Each injection point gets its own fresh copy.

Use it for small, stateless helpers: loggers, converters, little calculation utilities — things with no memory worth sharing.

⚠️
The default surprises people If you forget to put a scope on a bean, you do not get a shared instance — you get @Dependent, which means a brand-new private copy for every place it is injected. People who expected one shared object are caught out: their "shared" counter never adds up, because everyone secretly has their own.

2.4 @RequestScoped — one web request, then gone

A @RequestScoped bean lives for a single HTTP request-and-response cycle. A request arrives, the container makes the bean, your code uses it, the response goes back, and the bean is destroyed. The next request gets a brand-new one.

Perfect for things that only matter for one click: a form's backing bean, a REST endpoint controller.

⚠️
Do not store lasting state here Anything you put in a @RequestScoped bean vanishes when the response is sent. Put a shopping cart or a logged-in user in one and it is empty again on the very next click. That kind of state belongs in @SessionScoped (next section).

2.5 @SessionScoped — one per visitor, for the whole visit

A @SessionScoped bean lives for one user's browser session: it is created on that user's first request and survives across every page click until the session ends. Each user gets their own private copy — your cart is never mixed up with mine.

Good for a shopping cart, the logged-in user's details, or a theme preference.

📌
One hard rule: it must be Serializable A @SessionScoped bean class must implement java.io.Serializable. "Serializable" means the object can be turned into bytes and back. The server needs this because it may passivate the session (write it to disk to save memory) or replicate it across a cluster of servers. Forget it and deployment fails.

2.6 @ApplicationScoped — exactly one, shared by everyone

An @ApplicationScoped bean is a single shared instance for the entire lifetime of the application. Every user, every request touches the same object. It is created once (lazily, on first use) and lives until the app shuts down.

Ideal for global configuration, an in-memory cache, or a site-wide hit counter.

In plain words

@SessionScoped gives each user their own copy. @ApplicationScoped gives everyone the same one copy. That difference is the whole reason both scopes exist.

2.7 @ConversationScoped — you start it and you stop it

The first four scopes begin and end on the container's schedule. @ConversationScoped is different: you decide when it starts and when it ends, in your own code. It can span several requests — more than a single request, but usually less than a whole session — which makes it the natural fit for a multi-step wizard.

You control it through an injected Conversation object. A conversation starts out transient (short-lived, like a request). Calling begin() promotes it to long-running so it survives the next few requests; end() closes it and frees the memory.

LoanApplicationWizard.java — a multi-step wizard with @ConversationScoped
package com.globalbank.web;

import jakarta.enterprise.context.Conversation;
import jakarta.enterprise.context.ConversationScoped;
import jakarta.inject.Inject;
import jakarta.inject.Named;
import java.io.Serializable;

@Named("loanWizard")          // Gives the bean a name a web page can use
@ConversationScoped // Survives across multi-page wizard
public class LoanApplicationWizard implements Serializable {

    @Inject
    private Conversation conversation;

    private int step = 1;
    private double requestedAmount;

    public void startApplication() {
        if (conversation.isTransient()) {
            conversation.begin(); // Promotes transient conversation to long-running!
        }
    }

    public void submitFinal() {
        // execute loan creation ...
        if (!conversation.isTransient()) {
            conversation.end(); // Destroys conversation and frees memory
        }
    }
}
💡
The one thing to notice You never write new Conversation() — it is injected (there is @Inject again). Your only job is the pair begin() … end(). Everything between those two calls is remembered; everything after end() is forgotten. Note also that this bean implements Serializable, just like a session bean, because it too outlives a single request.

Part 3 · Three places to put @Inject


  
You know the container hands your dependencies in. But where does it put them? CDI gives you
    three injection points. They all end with your object fully equipped; they differ in when and
    how clearly it happens.


  
🧰
    
Analogy — your first day at a new job
      Constructor injection is being handed your laptop, pass and keys at reception
      before you reach your desk — you cannot start without them, and they are yours for good.

      Field injection is finding those things already sitting on your desk, with no clue
      who put them there.

      Initializer injection is being called into a side room just after you arrive to be
      handed one more thing.

  


  
3.1 Field injection — the short one

  
You write @Inject straight onto a field and leave it empty. The container fills it in
    before your code runs.


  
Field injection

  
@Inject
private AccountService service;


  
💡
    
The one thing to notice
      It is the shortest to type — and that is its only real advantage. The field cannot be
      final, and because nothing sets it from outside, it is harder to test with
      plain JUnit: you cannot just construct the object and pass a fake in.

  


  
⚠️
    
Why field injection hurts in tests
      In a unit test you build the object yourself with new. With field injection there is no
      container, so the field stays null and you are forced into a reflection-based mocking
      framework just to poke a value in. Constructor injection (next) sidesteps this entirely.

  


  
3.2 Constructor injection — the best one

  
You put @Inject on the constructor. The container calls it and passes the dependencies
    as arguments when it builds your object.


  
Constructor injection — the recommended pattern

  
private final AccountService service;

@Inject
public Controller(AccountService s) {
    this.service = s;
}


  
💡
    
The one thing to notice
      Because the value arrives as the object is built, the field can be final — set once and
      never changed again (that is what "immutable" means). And testing is trivial: a plain
      new Controller(mockService) works, with no container and no reflection framework. This
      is why experienced developers reach for it first.

  


  
3.3 Initializer method injection — the follow-up

  
You put @Inject on an ordinary method (sometimes called setter-style injection). The
    container calls that method after the constructor has run and passes the
    dependencies in. It is handy when a bean needs several dependencies configured together after it
    exists.


  
Initializer method injection

  
@Inject
public void init(AccountService s) { ... }


  
💡
    
The one thing to notice
      The method runs after the constructor — so by the time init() fires, the
      object already exists. That ordering is the point: use it for multi-dependency setup that has to
      happen once the bean is constructed.

  


  
3.4 Which should you use?

  
Same three facts, side by side:

  

    
Where @Inject goesCan the field be final?Easy to unit-test?Reach for it when…

    
      
FieldNoHarder (needs a mocking framework)a quick throwaway or demo where testing does not matter

      
Constructor (best)YesYes — new Controller(mock)almost always; it is the default good choice

      
Initializer methodNoPossibleyou must configure several dependencies after construction

Part 4 · @Inject, @EJB or @Resource — which one when?


  
Three different annotations all "inject something." Beginners mix them up constantly. The good news:
    each has a clear job, and once you see the job, the choice is obvious.


  
🏢
    
Analogy — three desks in the lobby
      @Inject is the main concierge of the modern building: ask for almost
      anything and they fetch it, and they know the rules about how long each thing is yours to keep
      (your scope).

      @EJB is an older specialist desk that only deals with enterprise
      beans.

      @Resource is the facilities desk that hands out the building's
      fixtures — power, water, phone lines — which here means DataSources, message queues and
      transactions.

  


  
4.1 @Inject — your default

  
From Jakarta CDI. It injects any CDI bean, any EJB, or any object produced by CDI.
    Crucially, it is scope-aware: it understands the five scopes from Part 2, plus
    advanced CDI features (a qualifier picks between several beans of the same type; a
    decorator wraps a bean to add behaviour) you will meet in Session 12. If in doubt, this is
    the one to reach for.


  
4.2 @EJB — the legacy, enterprise-beans-only one

  
From Jakarta Enterprise Beans. It injects only enterprise beans — the
    @Stateless, @Stateful and @Singleton beans from Session 1. It
    is an older EJB-container lookup and is not scope-aware. In modern code
    @Inject can usually do the same job and more.


  
4.3 @Resource — for server-managed resources

  
From Jakarta Common Annotations. It injects things the server owns and registers,
    not things you wrote: a DataSource (a database connection pool), a JMS
    queue, a UserTransaction. It reaches straight into the server's JNDI
    registry — a name-to-object directory — and is not scope-aware either.


  
In plain words
    
Ask yourself what you are injecting:

    
Your own bean, or anything scoped → @Inject. An old-style enterprise bean specifically
      → @EJB (or just @Inject). A piece of server plumbing like a database pool
      or a transaction → @Resource.

  


  
⚠️
    
Two mix-ups to avoid
      Reaching for @EJB to grab a @RequestScoped CDI bean does not work —
      @EJB only sees enterprise beans and ignores CDI scopes; use @Inject.
      And trying to @Inject a raw DataSource or UserTransaction
      straight from the server fails too — those are server resources, so use @Resource.

  recap
  
One-line summary of everything

  

    
CDIThe part of Jakarta EE that creates your objects, wires them together and controls how long each one lives — so you never write new.

    
beans.xmlOptional since CDI 1.1 — bean-defining annotations alone make an archive discoverable. Needed when you set a discovery mode (WEB-INF/ for a WAR, META-INF/ for a JAR), or declare alternatives, interceptors or decorators.

    
@DependentThe default. A fresh private copy per injection, no shared state. Lives and dies with its host.

    
@RequestScopedOne HTTP request, then destroyed. For form beans and REST controllers.

    
@SessionScopedOne per user, for the whole visit. Must be Serializable.

    
@ApplicationScopedExactly one shared copy for the whole app. For config, caches, counters.

    
@ConversationScopedYou start it with begin() and end it with end(). For multi-step wizards.

    
@Inject three waysOn a field (short), a constructor (best — allows final, easy to test) or an initializer method (after the constructor).

    
@Inject vs @EJB vs @Resource@Inject for CDI beans and most things (scope-aware); @EJB for enterprise beans only; @Resource for server resources like DataSources, JMS queues and UserTransaction.

    
The golden ruleNever new a managed object. Declare what you need with @Inject and let the container hand it to you.
