Unit 04 · Entity beans & message-driven beans

Unit 03 covered the three session beans (your logic). Two more bean families round out the picture: entity beans (data that lives in the database) and message-driven beans (background workers triggered by messages).

↩︎
Recap Session beans = business logic. Stateless (pooled, no memory), stateful (one per client, remembers), singleton (one shared, use @Lock).
concept

Part 1 · Entity beans = database rows as objects

An entity bean represents a persistent business object — one whose data is stored in a database table and survives after the program stops. A session bean forgets; an entity is remembered on disk.

🗂️
Analogy A library catalogue card. It has a unique number (the primary key), fields (title, author, year), it stays in the drawer even when nobody’s reading it (persistence), and many people can look up the same card (shared).
📌
“Entity bean” today means “JPA entity” The old EJB 2.x “entity bean” was heavy and is gone. Modern Jakarta EE does persistence with JPA (Jakarta Persistence). An entity is a plain class with @Entity and an @Id. This unit shows the shape; Unit 13 does it for real (the EntityManager, queries, relationships).
Account.java — an entity
import jakarta.persistence.Entity;
import jakarta.persistence.Id;

@Entity                              // "map this class to a database table"
public class Account {

    @Id                              // this field uniquely identifies each row
    private Long accountId;

    private String accountHolder;
    private double balance;

    // getters and setters ...
}

Session bean vs entity A session bean is anonymous work — you can’t ask for “session bean #5”. An entity has an identity (its primary key) and you look it up by that key. Logic vs data.
concept

Part 2 · Message-driven beans = background workers

A message-driven bean (MDB) sits in the background and listens. When a message lands on a queue, the container wakes the MDB and hands it the message. The sender didn’t wait for it — that’s asynchronous processing.

📧
Analogy An email inbox with an auto-responder. You send a mail and carry on with your day. Whenever it arrives, the responder processes it — independently, on its own time.

Why bother? The fund-transfer example

10,000 people click “Transfer money” at once.

  • Synchronous: all 10,000 wait for their transfer to finish before the page responds. The system crawls or falls over.
  • Asynchronous with an MDB: each request is dropped on a queue. The user instantly sees “Transfer submitted”. MDB instances chew through the queue in the background. The site stays fast.
FundTransferProcessor.java — an MDB
import jakarta.ejb.MessageDriven;
import jakarta.jms.Message;
import jakarta.jms.MessageListener;
import jakarta.jms.TextMessage;

@MessageDriven(mappedName = "jms/FundTransferQueue")   // which queue to watch
public class FundTransferProcessor implements MessageListener {

    @Override
    public void onMessage(Message message) {           // container calls this per message
        try {
            TextMessage text = (TextMessage) message;
            String details = text.getText();
            System.out.println("Processing transfer: " + details);
            // parse accounts + amount, update the database, send a confirmation email
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}
